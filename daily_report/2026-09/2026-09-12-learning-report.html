首次观测基线

First-Observation Baseline

第一次看见只是给 ref 拍登记照，第二次比较才谈得上变化。

核心要点

  • 第一次看到某个远端 ref，只得到它此刻的 SHA，只能记录基线，不能算作新增提交。
  • 基线要按 ref 分开保存：指针值 SHA、所属命名空间、观测时间以及这次读取是否成功。
  • 基线不是结论，而是后续 unchanged / changed 判断能够成立的前提。

ref 指针 SHA 比较与变化检测

Ref Pointer SHA Comparison and Change Detection

同一个 ref 的两次 SHA 一对比，才知道指针有没有移动。

首次观测基线

完整讲解

首次观测基线说的是：当你第一次看见某个远端 ref，比如 refs/heads/main 时，你得到的是一个当前值，而不是一个变化事件。基线的作用像给这个 ref 拍一张登记照：记录它此刻的 SHA、来自哪个命名空间、观测时间以及这次读取是否成功。只有等到下一次观测，把新读到的 SHA 与登记照里的历史 SHA 比较，相同才叫 unchanged，不同才叫变化线索。为什么第一次不能直接算新增提交？因为“第一次看见”只说明你的监控系统刚建立联系，不说明远端刚刚发生任何事情；第一次看到 refs/heads/main 指向某个 SHA，很可能这个提交已经存在很久了。如果没有基线，系统连比较对象都没有，只能输出未知或首次发现。基线建立后，变化检测才有参照系，就像你第一次给身高记录数字，不能据此说你今天长高了；第二次测量比第一次高，才说明变化。所以，基线不是结论，而是后续比较的前提。它也应该为每个 ref 分开保存，因为 refs/heads/main 和 refs/heads/private/agent-self-customization 是两个不同指针，不能共用一条历史。

原理逻辑

  1. 首次读取只建立“这个 ref 现在指向什么”的登记信息，本身不包含任何时间上的先后对比。
  2. 变化判断必须有两个时刻的值：历史 SHA 作为参照，当前 SHA 作为被比较对象。
  3. 不同 ref 是不同指针，基线必须逐 ref 保存，否则一个 ref 的变动会污染另一个 ref 的判断。

具体例子

假设监控 refs/heads/main。第一次读取得到 SHA 7c9f，系统只记录：main 的基线是 7c9f。第二天再读取仍是 7c9f，输出 unchanged。第三天读取变成 a1b2，才输出“main ref 指针出现变化线索”。第一次那一步不能输出 changed。

常见误区

  • 把“第一次看到”误报成“新增提交”或“远端发生变化”。
  • 只保存一个全局基线，把不同 ref 的 SHA 混在一起，导致 main 没变而私有分支变了时也无法正确判断。

概念关联

关联概念关系说明
ref 指针 SHA 比较与变化检测基线提供历史值，是 SHA 比较能够成立的前提；没有历史值，就只剩首次发现，无法判断当前值是否变化。
观测证据范围限制只读、低数据面的观测只能先记录 ref 元数据，基线本身就是证据范围限制下的第一层产物。
只读远端 ref 监控不 clone、不 fetch 的监控方式决定了第一次只能登记 ref 指针，而不能立刻读取提交详情。

ref 指针 SHA 比较与变化检测

完整讲解

ref 是 Git 中的引用，可以把它想成命名空间里的指针。refs/heads/main 是一个名字，它指向的值是一个 SHA 字符串。SHA 是这个 ref 在某个时刻的指针值，不是提交内容本身。所谓 ref 指针 SHA 比较与变化检测，就是保存同一个 ref 上一次读到的 SHA，再读取当前 SHA，然后比较两者。如果历史 SHA 和当前 SHA 相同，系统可以输出 unchanged，意思是“这个被监控的 ref 指针在两次观测之间没有变化”。如果不同，系统可以输出 changed，但这仍然只是变化线索，不是完整提交详情，因为这个比较只回答“指针有没有移动”，不回答“移动之后多了什么提交、谁写的、改了哪些文件”。比较还必须绑定到具体的 ref：refs/heads/main 的变化不能代表 refs/heads/private/agent-self-customization 的变化，反过来也一样。当天多个远端仓库通过 refs/heads/... 读取状态，并报告未发现远端 ref 指针变化，正说明这种比较是一种可观察边界：你能看见指针值，但不能自动看见指针背后的全部故事。

原理逻辑

  1. 比较的对象是同一个 ref 在不同时刻的指针值 SHA，而不是两个不同分支或标签的 SHA。
  2. 历史 SHA 与当前 SHA 相同则输出 unchanged，不同则输出 changed，两者都是一次观测与上一次基线之间的差分结论。
  3. 比较只覆盖被监控的那个 ref，其他分支、标签或对象库的变化不在这次比较的范围内。

具体例子

假设系统保存了 refs/heads/main 的历史 SHA 为 3f1a。今天读取当前 SHA 仍是 3f1a，于是输出 unchanged。若今天读取到 8b2c，则输出“main ref 指针出现变化线索”。但报告不能写“新增两个提交并修改了配置注册”，因为当前观测层没有下载提交对象、文件树或 diff。

常见误区

  • 把 changed 当成完整提交报告，直接说“新增了几个提交、修改了哪些文件”。
  • 把 unchanged 当成“仓库完全没有任何变化”，忽略其他分支、标签或对象库仍可能变化。

概念关联

关联概念关系说明
首次观测基线比较依赖基线提供的历史值；没有基线，变化检测只剩首次发现，无法输出 unchanged 或 changed。
观测证据范围限制比较结果必须受证据范围约束，只能报告变化线索，不能越级报告提交数量、作者、文件列表或 diff。
ref 命名空间命名空间决定比较的是哪一个指针，refs/heads/main 与私有分支的 SHA 不能混在一起比较。

观测证据范围限制

完整讲解

观测证据范围限制说的是：一个观测接口能回答的问题有明确上限。当天远端监控只通过 git ls-remote 读取远端 ref，不 clone、不 fetch、不下载提交对象、文件树或工作区内容。因此它掌握的是 ref 元数据这一层证据：某个 ref 的指针值是多少，和上次相比是否变化。这层证据能支持“ref 指针是否变化”的结论，但不能支持“新增了多少提交、提交信息是什么、作者是谁、改了哪些文件、diff 内容是什么”的结论。即使看到 changed，也只能说发现版本变化线索，下一步如果要了解详情，需要另一次成本更高的读取或下载。反过来，看到 unchanged 也只能说被监控的 ref 没变，不能说整个仓库绝对没有任何变化。这个限制不是缺陷，而是接口契约。只读监控和最小权限访问让数据面很小、风险很低，代价就是结论强度有限。当天 tiny-sea-war 的未提交变更也体现了同类边界：当前工作区存在变更，但 Git 不能证明它发生在目标日期前一天，所以只能作为待确认变化线索，不能写成已完成的提交事实。

原理逻辑

  1. 接口契约决定证据上限：git ls-remote 只读取 ref 元数据，不下载提交对象、文件树或工作区内容。
  2. 证据层级决定结论强度：ref 指针变化只能支持“版本变化线索”，不能支持提交数量、作者、文件列表或 diff。
  3. 只读与最小权限把数据面和风险压到最小，代价是必须为未知与待确认单独留出表达位置。

具体例子

假设监控报告 refs/heads/main changed。严谨写法是：“被监控的 main ref 指针出现变化线索，尚未获取提交详情。”不能写成：“新增 3 个提交，修复了 scene_presentation_test.gd。”如果报告是 unchanged，严谨写法是：“被监控的 ref 指针未发现变化。”不能写成：“仓库完全没有任何变化。”

常见误区

  • 把 ref 变化线索当成完整提交事实，直接写“远端新增了若干提交并修改了测试运行器”。
  • 把 unchanged 当成“仓库没有任何变化”，或者把未提交变更的存在当成它一定发生在目标日期前一天。

概念关联

关联概念关系说明
ref 指针 SHA 比较与变化检测证据范围限制要求 SHA 比较只报告变化线索，不越级报告提交数量、作者、文件列表或 diff。
首次观测基线基线只记录 ref 元数据，正是证据范围限制下能拿到的最小可用信息。
证据缺失不等于事件不存在未提交变更只能作为待确认变化线索，说明结论强度必须匹配证据等级，缺失应留在未判定。
