多 ref 命名空间聚合观测

完整讲解

ref 可以理解成贴在某个对象 ID 上的名字标签。远端仓库里不只有一个 main，还有 refs/heads/* 分支、refs/tags/* 标签、refs/remotes/* 远端跟踪引用、远端 HEAD 等命名空间。只盯 refs/heads/main，就像只检查一个主门是否开过，而忽略侧门、公告栏和临时通知。多 ref 聚合观测的关键是：每个 ref 都有自己的基线和生命周期。第一次看到的 ref 只能作为基线，不能立刻算作新增事件；已存在的 ref 如果读取失败，不能写成未变化；一个 ref 没变，也不能抵消另一个 ref 已变。整体结论可能是部分未变、部分已变、部分未判定。

原理逻辑

  1. ref 是“名字 → 对象 ID”的入口标签，每个命名空间都有自己的入口集合，观测必须遍历整组入口，而不是只读一个入口。
  2. 基线是聚合判断的前提：只有先记录某个 ref 此前的对象 ID，才能区分首次发现、正常更新、删除和读取失败这几种情况。
  3. 各 ref 的结论相互独立，必须先按 ref 聚合再给出整体判断，任何单个 ref 的结果都不能覆盖其他 ref 的结果。

具体例子

想象一个港口有多个信号旗：主航道旗、仓库区旗、危险品旗、天气旗。你只盯着主航道旗，看到它没动就宣布整个港口今天没有新消息；可实际上仓库区已经换了作业批次，或者天气旗升起了大风预警。多 ref 观测就是同时读取这些旗杆，而不是把港口状态压缩成一根旗杆。换到仓库也一样：假设今天 refs/heads/main 与昨天相同，但新增了 refs/tags/v1.2，并且 refs/heads/dev 移动到了新提交。只观察 main 会得出没有变化；多 ref 聚合则能看到标签发布与非默认分支更新两个信号。

常见误区

  • 认为 main 不变就等于整个远端没有发布。
  • 认为标签只是附属信息，可以不看；或者把多个 ref 的 SHA 简单列出来，却不给每个 ref 建立历史基线，看起来收集了很多数据，仍会漏掉标签发布、非默认分支更新或远端 HEAD 切换。

概念关联

关联概念关系说明
引用作为可达闭包入口每个 ref 都是一个潜在入口，聚合观测先比较入口名称和对象 ID，但不能因此知道闭包里的具体提交内容。
观测结果的三值状态机多个 ref 可能部分读取成功、部分读取失败，整体报告必须保留未判定，不能简单写成无变化。
索引/暂存区作为第三层状态边界远端多 ref 关注发布入口，本地三层状态关注工作区改动，两者是不同观测面，不应混在一起。

索引/暂存区作为第三层状态边界

完整讲解

Git 的本地状态不是只有已提交和工作树两种。中间还有索引，也叫暂存区。HEAD 指向当前分支最新提交，代表正式历史中的快照；索引记录下一次提交准备包含的快照；工作树是磁盘上正在编辑的文件。git status 会做两组比较：HEAD 与索引比较，得到已暂存的变化；索引与工作树比较，得到未暂存的变化。这样同一个文件可以同时有已暂存和未暂存两部分改动。git checkout 或切换分支前检查未提交修改，是为了避免更新 HEAD 时覆盖索引或工作树中的未提交状态。索引因此是提交对象图与工作树之间的安全边界。

原理逻辑

  1. 三层结构把“正式历史”“下一次提交的内容”“当前磁盘内容”分别保存，使同一个文件的 staged 与 unstaged 改动可以并存且互不覆盖。
  2. status 的清晰分类来自两组比较的组合：HEAD 与索引、索引与工作树；差集的方向决定了改动属于哪一类。
  3. 索引是更新 HEAD 之前的保护层：checkout 必须判断新的 HEAD 是否会覆盖索引或工作树中的未提交状态，因此可能拒绝切换。

具体例子

把写书想成 Git：已经出版的版本是 HEAD 提交快照，桌上正在改的稿子是工作树，而你已经挑了部分段落放进“待出版文件夹”的版本是索引。你可以在桌上继续改，同时待出版文件夹里保留另一份更早的挑选结果；出版社只看待出版文件夹，不会直接拿桌上的散页去印刷。换成命令：你修改 a.txt 后执行 git add a.txt，此时 HEAD 与索引不同，status 显示已暂存；随后你又修改 a.txt 但不 add，此时索引与工作树也不同，status 会同时显示已暂存和未暂存。若此时切换分支可能影响这些状态，checkout 会先检查并可能拒绝。

常见误区

  • 认为 Git 只比较提交和工作树，暂存区只是多余的中转站；实际上 status 的清晰分类来自 HEAD、索引、工作树三者比较。
  • 以为 checkout 只改文件内容，忽略它还要保护索引和工作树里未提交的状态。

概念关联

关联概念关系说明
提交对象的快照语义与父链重建索引比较的基准是 HEAD 指向的提交快照；没有快照语义，就无法说明已暂存差异从何而来。
观测结果的三值状态机如果索引或工作树因为权限、锁、外部过滤器缺失而读不到，status 的结论应进入未判定，而不是宣布干净。
多 ref 命名空间聚合观测远端多 ref 和本地三层状态是不同观测面，一个是发布入口，一个是工作区状态，自动化报告应分开记录。

观测结果的三值状态机

完整讲解

自动化观测如果只有有变化和无变化两个值，就会把读取失败误写成无变化。更合理的模型至少有三种结论：已确认、已确认不存在、未判定。已确认表示读取成功并得到明确值；已确认不存在表示读取成功且明确知道对象或状态不存在；未判定表示读取失败、超时、权限不足、外部过滤器缺失、锁冲突、格式门槛等阻止了判断。已确认内部还可以继续区分与历史基线相同或不同。但关键是未判定不能降级成未变化或不存在。网络失败读不到 ref，不等于 ref 不存在；git-lfs 缺失导致工作区读取失败，不等于工作区干净。三值状态机让报告保留这种边界，并提示稍后重试或换一种读取方式。

原理逻辑

  1. 二值模型只有“有变化/无变化”，会把读取失败压缩成无变化，等于把未知当成安全。
  2. 三值把“读取动作是否成功”和“对象是否存在”分开判断：先确认读取结果是否可信，再判断内容是否与基线相同。
  3. 未判定需要携带原因字段，才能在条件恢复后重试，或在多个原因同时出现时决定保留哪些信息、是否升级为人工排查。

具体例子

医院化验会给出阳性、阴性、样本污染无法判定。如果机器故障时报告写成阴性，就会把未知当成安全。仓库观测也一样：网络超时读不到标签，不能写成没有标签；外部过滤器缺失读不到工作树，不能写成没有改动。再看一个具体场景：自动化脚本执行 git ls-remote 检查 refs/tags/v1，但网络超时。正确输出不是标签不存在，也不是标签未变化，而是未判定、原因为网络超时。等网络恢复后重新读取，才能确认标签存在、不存在或 SHA 是否变化。

常见误区

  • 认为没有读到就等于不存在，或者读取失败可以归入未变化。
  • 把未判定当成失败并直接放弃；未判定更像待办事项，它要求保留问题、记录原因，并在条件恢复后重新读取。

索引/暂存区作为第三层状态边界索引或工作树读取失败时，状态报告不能宣布干净，而应把该层标为未判定。
