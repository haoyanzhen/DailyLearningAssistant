Status-Evidence Binding Rules

没读到不是没变化，第一次记录不是新增，状态词必须有证据门槛。

核心要点

监控状态词与证据条件的绑定规则

完整讲解

监控状态词与证据条件的绑定规则，核心是把结论词当成有门槛的标签。在 Git 远端监控里，unchanged 不是今天看起来没动静，而是需要当前读取成功、存在历史基线、当前 SHA 与历史 SHA 相同三个条件同时成立。changed 也需要明确证据，例如远端 ref 指针从旧 SHA 变为新 SHA；如果只有弱线索，还没有提交对象或 ref 更新证据，就应写成 changed_clue 或 pending_commit_detail。unknown 或 read_failed 用于读取失败、网络失败、凭据失败等场景，不能因为没读到就写成 unchanged。baseline_created 用于第一次成功记录某个 ref 的 SHA，它表示建立了参照点，不表示仓库发生了变化。这个规则的价值在于降低误报，让每个结论都能回答：你为什么这么说？你看到了哪些字段？缺了什么证据？

原理逻辑

  1. 状态词不是随意标签，而是由证据条件触发的结论。
  2. unchanged、changed、unknown、baseline_created 各自对应不同证据门槛。
  3. 绑定证据条件后，监控报告可以从自然语言总结变成可检查判断。

具体例子

假设远端 main 的历史基线 SHA 是 abc123。今天只读 git ls-remote 成功读到 origin/main 当前 SHA 也是 abc123，则可以输出 remote_ref_change_status=unchanged。如果今天读取失败，则输出 unknown 或 read_failed，而不是 unchanged。如果今天是第一次记录 origin/main=abc123，则输出 baseline_created。如果今天读到 origin/main 变成 def456，但还没有获取 commit 详情，则可以先输出 changed_clue 或 pending_commit_detail，等证据升级后再写 changed。

常见误区

  • 把状态词当成情绪化总结：没看到变化就写 unchanged，看到一点线索就写 changed，第一次记录就写新增。
  • 把读取失败当成未变化，或把本地引用指向与远端当前 SHA 相同直接写成推送成功。

概念关联

关联概念关系说明
多源证据字段正交化只有 local_ref_points_to、remote_ref_current_sha、remote_ref_baseline_sha 等字段分开后，状态词才有明确输入。
契约失败类型的状态空间设计check_not_run、check_failed、needs_review、manual_review_passed 同样必须绑定证据条件，避免把未运行写成失败。
把无变化写成有证据支撑的状态今日主题作为三张知识卡之外的统摄概念，用来说明这些概念如何共同指向同一条学习主线。

继续深入问题

  2. 当历史基线缺失但当前读取成功时，是否永远只能输出 baseline_created，还是可以在人工确认后升级为 unchanged 或 changed？
  3. 当多个 ref 都 unchanged 时，仓库级状态应该如何聚合，才能避免把指针未变误写成没有任何工程进展？

多源证据字段正交化

完整讲解

多源证据字段正交化，核心是让每个字段只负责一类证据。正交可以理解为坐标轴：x 轴只表示横向位置，y 轴只表示纵向位置，如果把 x 和 y 混在一个数字里，后续计算就会乱。Git 监控里也有多个证据来源：本地 main 指向哪个 SHA，远端 origin/main 当前指向哪个 SHA，远端 origin/main 历史基线是哪个 SHA，是否已经确认窗口内 commit，工作区是否有未提交草稿。它们看起来都和变化有关，但含义完全不同。如果把这些证据塞进同一个 summary 字段，比如写 main 有变化或 main 已完成，下游就很难判断：是本地改了？是远端变了？还是只是工作区有草稿？字段正交化后，系统可以分别记录 local_ref_points_to、remote_ref_current_sha、remote_ref_baseline_sha、workspace_clues、push_evidence，使结论更稳。

原理逻辑

  1. 每个字段只承载一类证据来源，避免多个事实互相覆盖。
  2. 字段分开后，状态词可以由明确字段计算，而不是由自然语言总结猜测。
  3. 正交字段为机器可读报告提供稳定 schema，也便于发现字段缺失或冲突。

具体例子

某个仓库的本地 main 指向 abc123，远端 origin/main 当前也指向 abc123，历史基线也是 abc123，但工作区还有未提交修改，且没有推送日志。正交字段可以写成：local_ref_points_to=abc123、remote_ref_current_sha=abc123、remote_ref_baseline_sha=abc123、remote_ref_change_status=unchanged、workspace_clues=dirty、push_evidence=none。这样下游能准确理解：远端 ref 没有变化，本地有草稿，不能宣称推送成功。

常见误区

  • 用一个大而全的 status 字段表达所有事实，例如把本地指向、远端变化、工作区草稿、人工确认都写进同一个结论。
  • 把多个引用指向同一 SHA 理解成推送成功，忽略推送日志、接收端 ref 更新证据或明确过程记录。

概念关联

关联概念关系说明
监控状态词与证据条件的绑定规则状态词需要由明确字段计算，而不是由自然语言总结猜测。
契约失败类型的状态空间设计检查运行状态、文件缺失、字段格式错误和人工复核状态应分别表达，不能混在一个失败原因字段中。

契约失败类型的状态空间设计

完整讲解

契约失败类型的状态空间设计，核心是把检查没通过拆成多种可定位的原因。很多系统最初只用 pass 和 fail，但 fail 太粗：可能是检查脚本根本没运行，可能是文件缺失，可能是目录存在但为空，可能是文件存在但字段格式错误，也可能是规则本身需要人工判断。状态空间设计就是定义一组有限、互斥、可追溯的状态词，让下游知道问题发生在哪一层。以资产契约检查为例，missing_file 表示契约要求某个文件但文件不存在；invalid_field 表示文件存在，但内容字段不符合约定；empty_directory 表示目录存在但没有必要内容；check_not_run 表示检查没有执行；check_failed 表示检查执行了但整体失败；needs_review 表示自动检查不能确定，需要人工判断；manual_review_passed 表示人工已经复核通过，可能包含例外说明。这些状态不应互相替代，每个状态都应能回答：你依据什么证据得出这个状态？

原理逻辑

  1. 状态空间要有限、互斥、可追溯，让失败原因可以定位。
  2. 自动检查、文件解析、目录扫描和人工复核应分层记录，不能压成一个 fail。
  3. needs_review 是等待人工判断的中间状态，本身不代表资产合规或不合规。

具体例子

假设角色资产契约要求每个角色包包含 concept.png、combat.json 和 review.md。检查发现 concept.png 存在，combat.json 存在但缺少 skill 字段，review.md 不存在。此时不应只写 check_failed，而应分别记录：concept.png=passed、combat.json=invalid_field、review.md=missing_file。如果检查脚本根本没有运行，则整体状态应写 check_not_run；如果人工确认某个例外可接受，则可在对应项上记录 manual_review_passed 并保留例外说明。

常见误区

  • 把所有失败都写成 check_failed，导致下游无法区分检查没运行、文件缺失、字段格式错误和需要人工复核。
  • 把 needs_review 当成通过或失败，忽略它只是自动检查停止、等待人工判断的状态。

概念关联

关联概念关系说明
多源证据字段正交化检查运行状态、文件存在状态、字段格式状态和人工复核状态应分别表达，避免一个字段同时承载多种失败原因。
监控状态词与证据条件的绑定规则check_not_run、check_failed、needs_review、manual_review_passed 都必须有明确证据条件，不能把未运行写成失败。
