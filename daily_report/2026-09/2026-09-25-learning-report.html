窗口边界提交的时间证据优先级

完整讲解

判断一件作品是否属于今天完成时，系统里可能有提交时间、分支更新时间、文件修改时间和检查窗口边界。它们看起来都在描述同一件事，但证据等级不同。提交时间通常绑定到一个可验证的 commit 对象，因此更适合决定目标日期归属；分支更新时间只能说明某个 ref 指针在某个时刻被看到，不能单独证明窗口内产生了新提交；文件修改时间只是工作区现场痕迹，可能早于、晚于提交，也可能从未提交。今天是无变更复习日，没有窗口内提交，因此不讨论实际提交归属，只复习规则。若多个时间证据冲突，应先问三个问题：是否有可验证 commit 对象；该 commit 的提交时间是否落在检查窗口内；其他时间证据能否只作为线索记录。若提交时间不可靠或存在 rebase、amend、时钟偏差等情况，可以保留为待确认线索，而不是直接下结论。例如，检查窗口为 2026-09-25T00:00:00+08:00 到 2026-09-26T00:00:00+08:00，提交 A 的提交时间是 2026-09-24T23:58:00+08:00，分支 origin/main 在 2026-09-25T00:02:00+08:00 被观察到更新，某文件修改时间是 2026-09-24T23:50:00+08:00；报告应写 25 日窗口外提交线索，不作为 25 日完成事实。

原理逻辑

  1. 可验证 commit 对象是目标日期归属的强证据，因为它能绑定到具体提交记录。
  2. 分支更新是观察性证据，只能说明指针在某时刻被看到，不能替代提交对象证明。
  3. 文件修改时间是工作区线索，受编辑、暂存、提交和时钟偏差影响，只能辅助定位。

具体例子

检查窗口为 2026-09-25T00:00:00+08:00 到 2026-09-26T00:00:00+08:00。提交 A 的提交时间是 2026-09-24T23:58:00+08:00，分支 origin/main 在 2026-09-25T00:02:00+08:00 被观察到更新，某文件修改时间是 2026-09-24T23:50:00+08:00。按提交时间，A 不属于 25 日窗口；按分支更新，它只是 25 日看到指针变化；按文件修改，它只是工作区线索。报告应写 25 日窗口外提交线索，不作为 25 日完成事实。

常见误区

  • 看到文件修改时间或分支更新时间落在目标日期内，就认为当天完成了提交。
  • 把窗口外提交线索、窗口外分支更新或工作区痕迹直接写成目标日期完成事实。

阶段完成语义的部分完成表达

完整讲解

一个阶段往往不是完成或未完成两个状态。以角色资产交付为例，一个阶段可能同时包含文档更新、资产包提交、工具提交和审查结果。文档可能已经写 phase two art completion，资产包可能已经提交，工具可能已经统一，但某个角色包审查未通过。这时如果只写完成，会掩盖审查未通过；如果只写失败，又会抹掉已经完成的文档、资产和工具工作。部分完成表达就是把阶段拆成多个子状态，让每个子状态都有明确证据，再用一个更精确的阶段状态概括整体。今天没有阶段完成新增证据，因此不写成今天实际完成某个阶段，只复习如何表达部分完成。设计时可以避免单一布尔字段，改用结构化状态，例如 phase_status=partially_completed，substates.docs=done，substates.assets=done，substates.tools=done，substates.review=failed。这样既能让日报给出高层结论，也能让人快速定位哪个子项阻塞了阶段完成。例如，某阶段目标是完成第二批角色美术，文档已更新为 phase two art completion，角色 A 资产包已提交，角色 B 资产包已提交，工具提交已完成，但角色 B 审查未通过；此时应写 phase partially_completed，并保留 docs=done、assets=done、tools=done、review=failed、blocking_role=B。

原理逻辑

  1. 阶段完成由多个证据子状态共同支持，单一文档措辞不足以决定整体状态。
  2. 部分完成需要把已完成项和阻塞项分别记录，避免高层状态吞掉低层原因。
  3. 结构化子状态可以让报告同时支持高层摘要和具体定位。

具体例子

某阶段目标是完成第二批角色美术。当前证据显示：文档已更新为 phase two art completion，角色 A 资产包已提交，角色 B 资产包已提交，工具提交已完成，但角色 B 审查未通过。此时不应写 phase completed，而应写 phase partially_completed，并保留 substates：docs=done，assets=done，tools=done，review=failed，blocking_role=B。

常见误区

  • 把文档里的完成措辞当作阶段完成事实。
  • 把某一项审查未通过直接等同于整个阶段失败。

批量角色失败的层级化原因保留

完整讲解

批量检查或批量交付中，系统经常要处理多个角色、多个产物或多个步骤。如果只输出一个仓库级结论，例如 failed，使用者只知道有问题，却不知道是哪个角色、哪一步、因为什么原因失败。层级化原因保留就是让报告同时存在两层：上层给出可快速阅读的摘要，下层保留每个角色或步骤的具体原因。上层状态可以由下层状态聚合而来，但聚合不能把下层原因丢掉。今天没有批量管线运行证据，因此不写成今天实际发生批量失败，只复习如何设计层级化表达。一个可用思路是：batch_status=partial_failure，repository_status=failed，roles 数组中每个角色保留 status、failure_code、evidence_level 和 evidence_id。例如角色 A 成功，角色 B missing_file，角色 C review_failed。这样高层能知道整体部分失败，低层能知道 B 缺文件、C 审查未通过。若失败原因来自依赖版本不一致或超时位置，也应保留在角色级或步骤级原因中，而不是合并成一个笼统的 failed。例如，一次批量检查包含三个角色，角色 A 检查通过，角色 B 缺少 review 文件，角色 C 审查未通过；仓库级状态可聚合为 partial_failure，但报告必须保留 A.status=success、B.status=failed、B.failure_code=missing_review、C.status=failed、C.failure_code=review_failed。

原理逻辑

  1. 高层状态负责快速判断整体结果，低层原因负责定位具体阻塞。
  2. 聚合状态可以压缩表达，但失败原因必须保留可追溯的证据字段。
  3. 角色级或步骤级原因能避免把局部失败误写成仓库级失败。

具体例子

一次批量检查包含三个角色。角色 A 检查通过；角色 B 缺少 review 文件，失败原因是 missing_review；角色 C 审查未通过，失败原因是 review_failed。仓库级状态可聚合为 partial_failure，但报告必须保留 roles 数组：A.status=success，B.status=failed，B.failure_code=missing_review，C.status=failed，C.failure_code=review_failed。这样既能回答整体是否成功，也能回答具体哪里失败。

常见误区

  • 认为只要仓库级状态是 failed，就可以不再记录角色级原因。
  • 把多个角色失败合并成一个总原因，丢失每个角色的证据 ID 和定位信息。
