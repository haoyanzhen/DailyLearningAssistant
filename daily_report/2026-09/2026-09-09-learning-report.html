同一个可达闭包的两个方向：fsck 的要求存在集合与 gc 的可清理集合共享同一判定边界

Shared Reachable Closure Between fsck and gc

一张树根地图：fsck 问树根之内哪些必须活着，gc 问树根之外哪些可以清理。

核心要点

  • 完整性检查从当前引用闭包出发，而不是从磁盘上的所有字节出发。
  • fsck 与 gc 使用同一个可达闭包，一个要求闭包内对象可解析，一个只清理闭包外的对象。
  • 分支重新指向一个悬空对象时，该对象及其祖先会瞬间翻转到闭包内侧，变成必须存在的对象。

精读文章 · 数学 / 计算机科学

同一个可达闭包的两个方向：fsck 的要求存在集合与 gc 的可清理集合共享同一判定边界

完整讲解

我们可以把 Git 对象库想象成一棵巨大的树。分支、标签等引用是树根，提交、树对象、 blob 是树上的节点，父子关系就是枝干的连接。fsck 做体检时，并不是要求园子里每一片叶子都必须健康，而是从树根出发，沿着所有能走到的路径，记录下“这棵树此刻应该包含哪些节点”。凡是这条路径上应该出现却找不到的节点，才是真正的 missing。gc 做清理时，用的也是同一张路径图，但它站在相反方向：凡是树根走不到的地方，才可能被当作枯枝扫掉。所以“必须存在”和“可以清理”不是两套独立标准，而是同一个可达闭包的一体两面。

原理逻辑

  1. Git 引用（分支、标签）是可达闭包的根，对象图由提交、树、blob 之间的边构成。
  2. fsck 从当前引用出发递归遍历对象图，记录闭包内所有应存在的对象并验证可解析。
  3. gc 从同一组引用出发，反向寻找闭包外的对象作为可回收候选。
  4. 闭包内外的归属会因引用更新而翻转，例如被重新分支指向的悬空对象立即回到闭包内。

具体例子

假设你有一个提交 A，它曾经被 main 指向，后来 main 移动到 B，A 变成悬空对象。此时 fsck 不会要求 A 必须存在，因为 A 不在当前可达闭包内；gc 也不会立刻删除 A，因为保留窗口还在。接着你创建一个新分支 fix 并指向 A。这一刻，A 重新进入可达闭包，fsck 立刻把 A 视为必须存在；而 A 的父提交 P 也因为 A 的引用而被同一递归遍历覆盖，同样进入必须存在集合。如果 P 恰好已在更早的 gc 中被清理，fsck 会在 P 处报告 missing。

常见误区

  • 误以为 fsck 会检查磁盘上所有对象，或 gc 会删除所有“当前不可达”对象。实际上 fsck 的缺失判定只从当前引用闭包出发，闭包外的文件不会被视为缺失，也不会被当作正式对象检查。
  • 误以为对象一旦不可达就会在下一次 gc 被清理。实际上 gc 还要叠加 reflog、保留窗口等条件，不会一不可达就立刻清理。

概念关联

关联概念关系说明
可达闭包fsck 与 gc 共用同一个闭包判定：闭包内的对象必须存在并可解析，闭包外的对象才可能被回收。
保留窗口对象可以通过引用更新瞬间进入闭包，但其从闭包外到被真正删除仍受保留窗口的时间约束。

精读文章 · 软件工程 / 计算机科学

不可达对象的时间缓冲：gc 保留窗口让“悬空状态”成为可恢复的临时状态

完整讲解

当我们移动或删除一个引用时，旧对象会离开当前可达闭包，但这不等于它立刻变成垃圾。Git 的设计者是知道用户会犯错的：你可能会误删分支，也可能会用 reset 把分支移到一个不该去的地方。为了让这类操作可以撤销，Git 不会在引用更新后的下一秒就清理所有不可达对象。它通过 reflog 记录引用最近指向过哪里，并给 gc 设置一个默认保留窗口，比如两周。在这段时间里，那个“悬空”的提交仍然安静地躺在对象库中，你可以随时找到它并重新用分支指向它。保留窗口结束后，它才真正进入可清理范围。

原理逻辑

  1. 引用空间的变更会让旧对象离开当前可达闭包，但 reflog 会记录其历史位置，保留找回线索。
  2. gc 的默认保留窗口（常为两周）保护了刚离开闭包的对象，不立即当作过期垃圾。
  3. 在保留期内对象可以由 reflog 找回并重新挂到分支上；过期且不再可达才是可清理状态。
  4. 因此，‘不可达’在时间维度上分成仍可恢复和真正可清理两个阶段。

具体例子

你执行 git branch -D experiment 删除了一个包含重要提交 X 的分支。X 立即成为不可达对象，但你不用担心，因为 git reflog 仍会记录 experiment 曾经指向 X。你可以用 git reflog 找到 X 的哈希，然后执行 git branch experiment <hash>，X 便重新回到可达闭包。如果两周内你没有恢复它，之后某次 gc 运行才可能把 X 清理掉。

常见误区

  • 误以为一条引用不再指向某个提交，该提交就马上成为垃圾，下次 gc 就会清掉。
  • 实际上 gc 默认不会清理刚不可达的对象，因为 reflog 仍保留引用；对象真正可清理的时刻是 reflog 条目过期且引用闭包仍不包含它之后。

概念关联

关联概念关系说明
可达闭包闭包外对象不会瞬间消失，保留窗口让它成为可恢复的临时状态，这是从“存在性”到“可回收”的时间过渡。
旧 pack 延迟退出一个处理引用生命周期中的保留期，另一个处理文件读取者生命周期的延迟删除，两者互补地保护并发读者。

精读文章 · 计算机科学 / 软件工程

显式索引是对象库的发布边界：为什么 fsck 不靠扫描 pack 目录来发现对象

完整讲解

Git 对象库里的 pack 文件，并不是一放到目录中就自动成为“正式对象”的。一个 pack 文件要能被读者找到，必须先有一个 idx 文件，或者被写进 multi-pack-index。idx 就像图书馆的目录卡片：pack 是书，idx 是目录。书放在书架上但目录里没有它，读者就查不到；如果图书馆管理员盘点时只看书架上的所有纸张而不看目录，就会把印刷厂刚送来的半成品、还没装订完的散页也当成正式藏书来检查，结果报告一堆“伪损坏”。fsck 也是同理：如果它自动扫描 pack 目录里的所有文件，就会把 repack 正在生成的临时 pack、尚未完成发布的中间状态当成正式对象，从而产生错误的 missing 或 corrupt 报告。所以 fsck 只处理已经通过 idx 或 midx 显式登记的对象。

原理逻辑

  1. 对象查找通过索引入口完成：先找 idx/multi-pack-index，再由对象 ID 定位到具体 pack 和偏移。
  2. pack 文件写完磁盘是一种状态，被索引注册是另一种状态；只有后者才完成‘发布’。
  3. fsck 基于当前显式索引建立对象视图，避免把并发生成中的临时 pack 当作正式对象。
  4. 索引的原子替换决定了新读者看到包集合的精确时机，也就是发布边界。

具体例子

假设一个 repack 进程正在合并多个旧 pack。它先写一个新 pack 文件，此时还没有为新 pack 生成 idx。另一边的 fsck 如果直接扫描目录，会看到一个“没有目录的包”，可能报告异常。但按照显式索引规则，fsck 只检查当前索引里登记的 pack。新 pack 尚未登记，fsck 对它视而不见；旧 pack 仍被旧索引登记，fsck 继续检查它们。等到新 pack 的 idx 完成并替换旧索引后，旧 pack 才从索引视图退出。这个过程里，fsck 的视图始终是“已发布对象”的视图。

常见误区

  • 误以为只要 pack 文件出现在对象目录中，Git 就会自动发现并检查它。
  • 事实上 pack 必须通过 idx 或 multi-pack-index 建立注册关系；没有登记的文件只是磁盘中间产物，不应进入 fsck 的完整性视图。

概念关联

关联概念关系说明
可达闭包想要遍历对象图，必须先通过索引把对象 ID 解析到文件中的位置；没有索引入口的 pack 无法进入 fsck 或 gc 的正常遍历集合。
并发 repack显式索引刻画了已发布与未完成发布之间的边界，是并发读者在 repack 过程中安全切换包集合视图的保证。
