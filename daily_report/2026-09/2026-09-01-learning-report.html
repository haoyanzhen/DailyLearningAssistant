精读文章 · 计算机科学 / 软件工程

quarantine 对象迁移失败后的残留清理与推送幂等恢复

完整讲解

推送代码时，Git 的接收端不会立刻把新对象放进主对象库，而是先放到一个隔离目录（quarantine），有点像快递站的“待检区”。只有钩子检查通过后，这些对象才会被“迁移”进正式库。如果迁移过程被强制中断，隔离目录里会留下一些对象。这些残留会不会让仓库变脏？不会。因为所有正式的对象查找都只认主对象库，隔离区不在查找范围内。残留目录只是一堆暂时没人管的文件，对用户完全不可见，也不影响任何读取。下一次维护（比如 gc）会顺手清掉它们。更重要的是，迁移操作本身是幂等的：它只关心“目标对象是否已经在主对象库可达”，而不要求“源文件必须被删除”。所以哪怕重复执行迁移，也不会造成破坏。这就是“目标可达即成功”的恢复逻辑。

原理逻辑

  1. receive-pack 先把对象放进隔离目录，隔离目录不属于正式对象查找路径。
  2. 正式对象查找只认主对象库，因此隔离区残留不可见。
  3. 迁移的完成标准是目标对象在主对象库可达，而不要求源文件删除。
  4. 因此即使迁移中断，重复执行迁移也是安全的。

具体例子

你执行 git push，receive-pack 先把所有新对象写入 objects 旁边的一个 quarantine 目录，然后运行 pre-receive 钩子。钩子通过后，receive-pack 开始把对象迁移到主对象库。如果迁移到一半进程被 kill -9，隔离目录里还有几个对象没搬走。下一次 push 不会看到它们，git gc 也会把它们当作垃圾清理掉。假如你重新执行一次迁移，只要主对象库里已经有了那些对象，迁移就认为已经完成，不会报错。

常见误区

  • 误以为迁移失败后，残留对象会污染主对象库，或者需要手动把残留对象重新复制进去。
  • 实际上残留目录完全不参与对象查找，主对象库的视图始终干净；迁移重复执行也不依赖清理，而是以目标对象是否可达为准。

概念关联

关联概念关系说明
pack 与 idx 的发布顺序都体现了“中间态不参与正式视图”的原则。
post-receive 补偿幂等性类似，都以目标状态为最终判定，不依赖重复执行的次数。

精读文章 · 计算机科学 / 软件工程

pack 与 idx 的发布顺序：索引缺失窗口中的对象查找一致性

完整讲解

Git 的对象库里，pack 文件只是数据的容器，真正用来定位对象的是配套的索引文件 idx。也就是说，客户端和服务端在找一个对象时，不会直接解压扫描每个 pack，而是先查 idx，从 idx 里得到偏移量再去读 pack。这就带来一个重要的发布顺序问题：Git 写 pack 时，会先写临时 pack，再写临时 idx，最后再把它们发布成正式文件名。如果崩溃恰好发生在正式 pack 已经出现、正式 idx 还没出现的瞬间，情况会怎样？因为我们查找对象时只从 idx 入口走，那个没有 idx 的 pack 就像“不存在”一样，不会被任何查找看到。所以外部观察者要么看到旧状态（idx 还不存在），要么看到新状态（idx 已出现后 pack 可查），永远不会看到“有 pack 但查不到对象”的中间半状态。这就是通过约定让系统保持一致的经典例子：不是保证两个文件同时出现，而是让“不可见”来兜底。

原理逻辑

  1. Git 查找对象时先查 idx，得到偏移量再读 pack，不会直接扫描 pack。
  2. 发布时先写 pack 临时文件，再写 idx 临时文件，最后分别改名为正式名。
  3. 若崩溃发生在 pack 已改名而 idx 尚未改名的窗口，该 pack 因缺少 idx 而不参与对象查找。
  4. 因此系统对外呈现的状态要么是旧状态，要么是新状态，不存在中间半状态。

具体例子

在 git repack 过程中，Git 会生成 tmp_pack_XXXX 和 tmp_idx_XXXX，然后分别重命名为 pack-<hash>.pack 和 pack-<hash>.idx。假设 repack 程序在重命名 pack 后、重命名 idx 前崩溃。此时 pack-<hash>.pack 文件已经存在，但 pack-<hash>.idx 不存在。任何 git log、git fsck 等命令都不会引用这个 pack，因为对象查找只遍历有效的 idx 文件。这个“孤儿 pack”只会被后续维护流程当作未引用文件清理。

常见误区

  • 误以为只要 pack 文件存在，Git 就会扫描它来寻找对象。
  • 实际上常规对象查找依赖 idx（或 multi-pack-index），没有 idx 的 pack 不会参与对象定位。

概念关联

关联概念关系说明
quarantine 对象迁移失败都体现了中间态不参与正式视图的确定性原则。
虚拟合并基构造同样需要确定性视图，避免外部看到偶然状态。

精读文章 · 数学 / 计算机科学

虚拟合并基构造中的冲突传播与处理

完整讲解

当两个分支合并时，Git 需要找到它们的“共同祖先”作为基准。如果历史出现了 criss-cross 结构，也就是两个分支互相交错地引入过不同修改，可能不止一个共同祖先都“同样接近”。这时 Git 不会随便挑一个，而是把这些候选祖先合并成一个虚拟合并基。关键来了：这个合成过程本身也是一次合并，既然是合并，就可能产生冲突。Git 在构造虚拟合并基时，会不会把冲突悄悄忽略掉？不会。recursive 或 ort 策略会把合成过程中的冲突也保留下来，让这些冲突成为虚拟合并基的一部分，接着再参与最终的三路合并。这样，历史上两个分支之间已经存在的分歧就不会被掩盖，最终合并结果也不会因为“这次碰巧选了哪个祖先”而随机变化。换句话说，Git 选择了一种保守策略：让所有历史分歧都显式地浮出水面，而不是假装它们不存在。

原理逻辑

  1. 当多个共同祖先同等接近时，Git 不任意挑选，而是构建虚拟合并基。
  2. 构建虚拟合并基本身是一次合并，因此可能产生冲突。
  3. 这些冲突不会被自动解决，而是保留在虚拟合并基中。
  4. 虚拟合并基随后作为最终三路合并的基准，冲突因此传播到最终合并结果。

具体例子

假设有两个分支 A 和 B，它们都基于共同祖先 X 修改了同一个文件的不同位置，导致它们之间本身就有合并冲突。现在有一个分支 C 是从 B 分出来的，你想要合并 A 和 C。为了找到合并基准，Git 需要先构造 A 和 B 或相关的虚拟合并基。A 和 B 的合并冲突会带到虚拟合并基的构建中。最终合并 A 和 C 时，这个虚拟合并基中记录的冲突会被再次考虑，使得最终合并也会报告相关冲突，而不是静默选择某一方的修改。

常见误区

  • 误以为 Git 会“智能地”挑选一个共同祖先来避免冲突。
  • 误以为构造虚拟合并基时自动解决冲突；实际上冲突会以冲突标记保留并影响最终合并。

概念关联

关联概念关系说明
pack 与 idx 的发布顺序虚拟合并基的确定性构造与 pack/idx 的确定性发布一样，都是为了避免外部看到偶然状态。
quarantine 幂等恢复冲突传播与幂等恢复一样，都体现了不掩盖中间分歧的保守策略。

概念之间的关联

三个概念都围绕 Git 在复杂中间态下保持确定性的设计：quarantine 让残留不污染正式视图，pack/idx 顺序避免半状态，虚拟合并基冲突传播避免掩盖历史分歧。它们共同说明：Git 宁可显式保留中间痕迹，也不让外部看到无法解释的随机状态。
