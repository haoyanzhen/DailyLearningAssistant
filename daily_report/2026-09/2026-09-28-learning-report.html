远端 ref 状态词与证据条件绑定

完整讲解

可以把远端 ref 想象成一个会改写的门牌号，例如 refs/heads/main。门牌号本身不是内容，它指向某个 SHA。监控系统今天读到一个当前 SHA，再和上次记录的历史 SHA 比较，就能得到三种结果：如果读取成功、有历史 SHA、且两者相同，就是 unchanged；如果读取成功、有历史 SHA、但两者不同，就是 changed；如果没有历史 SHA，只能记录当前 SHA 作为基线，就是 first_seen。当天材料里，cannbot-skills 和 public-library 的 unchanged 表示指针未变，chunkcat 和 padv3 的 changed 表示指针变化，gatherpakvcache 和 slicev2 的 first_seen 表示首次建立基线。这个概念的关键不是记住三个词，而是理解每个词背后都有证据条件。

原理逻辑

  1. 远端 ref 是指向 SHA 的可改写指针，状态判断依赖历史 SHA 与当前 SHA 的可比性。
  2. 只有读取成功且存在可比基线，才能进入 unchanged 或 changed；没有历史基线时只能记录 first_seen。
  3. 状态词描述的是指针观测结果，不承载提交内容、作者、文件列表或工程完成度。

具体例子

某仓库 refs/heads/main 的历史 SHA 是 abc123。今天读取成功，当前 SHA 仍是 abc123，则状态为 unchanged；如果当前 SHA 是 def456，则状态为 changed，但只知道指针从 abc123 变到 def456；如果昨天没有历史记录，今天第一次读到 def456，则状态为 first_seen，只记录 def456 作为基线。

常见误区

  • 把 changed 当成已经提交某个功能。
  • 把 unchanged 当成没有任何工作。
  • 把 first_seen 当成新增提交。

概念关联

关联概念关系说明
Git SHA 作为版本指针标识历史 SHA 和当前 SHA 必须可比较，才能判断 unchanged 或 changed。
基于历史状态快照的变更检测需要保存上次 SHA，没有历史快照就无法区分 first_seen 和 changed。
远端 ref 指针变化与提交详情之间的证据边界限制 changed 的表述强度，防止把指针变化写成提交内容。
Agent 或 LLM 输出可靠性与证据约束自动总结只能使用状态词对应的证据范围，不能越界补全。

继续深入问题

  1. 当读取成功但历史基线缺失时，为什么 first_seen 不能写成 changed？
  2. unchanged、changed、first_seen 分别应该映射到哪些自动化动作，例如跳过、升级读取或保留基线？
  3. 多个 ref 同时存在不同状态时，如何聚合到仓库级结论而不把指针未变扩大成无工程进展？

远端 ref 指针变化与提交详情之间的证据边界

完整讲解

ref 指针变化像看到书架上的标签从 A 换到 B。标签变化说明这个位置指向了新的版本标识，但标签本身不会告诉你书架里新增了几本书、谁放的、书名是什么、内容改了什么。git ls-remote 只读取远端 ref 元数据，不 clone、不 fetch、不下载提交对象、文件树或工作区内容，因此它能确认的是指针是否移动，而不是提交对象里的细节。当天 chunkcat 和 padv3 的 refs/heads/main 出现 changed，材料明确说明这只能表述为远端版本变化线索或 ref 指针变化线索，具体提交数量、作者、文件列表和 diff 均待确认。这个概念的核心是区分位置变化和事件细节。

原理逻辑

  1. ref 指针变化只说明位置指向新的 SHA，不说明提交对象内部细节。
  2. git ls-remote 的只读元数据访问决定了证据上限，不会下载提交对象或文件树。
  3. 弱线索必须与已确认提交事实分开，避免把指针变化写成完成事实。

具体例子

远端 main 从 abc123 变为 def456。可以写 main ref 指针发生变化，属于待确认版本变化线索；不能写新增 3 个提交、修改了 level_objectives.json、完成玩家反馈优化，因为这些信息需要提交对象、日志、文件列表或 diff 支持。

常见误区

  • 看到 main 指针 changed 就写提交了玩家反馈、修改了 battle_session.gd、修复了某个问题。
  • 把多个远端 ref 同时 changed 合并成一次完整功能交付。

概念关联

关联概念关系说明
git ls-remote 只读元数据访问只读 ref 指针时不会下载提交对象或文件树，因此决定证据上限。
最小权限访问与只读监控系统故意不扩大读取范围，从而把结论限制在指针层面。
检查窗口与本地 Git commit 作为变更事实源只有窗口内已确认 commit 才能支持提交主题和文件路径。
LLM 拒绝补全或不推断缺失证据缺少提交对象时，自动总结应停止生成具体提交详情。

继续深入问题

  1. 在什么证据条件下，changed 可以从指针变化线索升级为已确认提交详情？
  2. 如何设计字段同时保留 ref 已变化、提交对象未获取、本地 commit 未确认三种状态而不互相覆盖？
  3. 当多个远端 ref 同时 changed 时，如何避免把多个指针变化合并成一次完整功能交付？

路径级证据归纳的边界

完整讲解

本地 commit 是比远端 ref 更强的证据，因为它可以提供提交主题、文件路径、新增或修改类型和行数统计。当天 tiny-sea-war 在 2026-09-27 检查窗口内有 3 个已确认 commit，因此可以归纳出玩家反馈与战斗推进、关卡目标与舰船获取数据、美术资源路径约定与资产目录解析、文档工作单与测试同步等主题。但是，材料没有展开 diff，所以这些归纳仍然停留在路径级和主题级。看到 asset_catalog.gd、asset_path_lookup_test.gd、assets/README.md，可以确认美术资源路径约定和资产目录解析是当天线索；看到 level_objectives.json、ship_acquisition.json，可以确认数据驱动配置线索；但不能进一步说某个函数如何解析路径、某个状态机如何迁移、某个算法如何计算舰船获取概率。这个概念提醒我们，即使证据来自已确认 commit，没有 diff 时也不能把文件名和主题扩写成实现细节。

原理逻辑

  1. 本地 commit 比远端 ref 更强，但仍受证据展开程度限制。
  2. 文件路径和提交主题只能支持路径级、主题级归纳。
  3. 接口、算法、性能、运行时行为需要 diff、测试或运行证据支持。

具体例子

tiny-sea-war 的提交 feat: improve player feedback and battle progression 涉及 player_command_feedback.gd、battle_session.gd、level_objectives.json 等文件。可以归纳为涉及玩家反馈、战斗推进和关卡目标数据；不能归纳为战斗推进算法被重写、玩家反馈延迟被降低、某个 UI 状态机被实现，除非展开 diff 或运行测试证据支持。

常见误区

  • 看到 battle_session.gd 或 player_command_feedback.gd 就推断具体战斗状态机、玩家反馈算法或性能优化。
  • 把总新增删除行数当成精确文件级变化，或把路径级线索写成已确认实现事实。

概念关联

关联概念关系说明
检查窗口与本地 Git commit 作为变更事实源文件路径和提交主题来自窗口内已确认 commit，提供路径级归纳的事实基础。
变更统计的概览口径与去重边界总行数只能作为概览，因为统计按提交相加且未跨提交重复文件去重。
LLM 拒绝补全或不推断缺失证据缺少 diff 时，自动总结应停止推断接口、算法、性能和运行时行为。
文档、工作单与代码变更同步AGENTS.md、docs、workorder 与代码文件同批变化时，只能确认同步变化的路径级线索。

概念之间的关联

三个概念形成一条证据链：状态词绑定证据条件，保证监控结论不被随意放大；ref 指针变化与提交详情边界，保证弱线索不被写成完成事实；路径级证据归纳边界，保证本地 commit 也被限制在可支持范围内。共同点是：证据能到哪一层，结论就只能写到哪一层。
