角色资产包作为交付单元

完整讲解

角色资产包作为交付单元，意思是游戏项目交付角色时，不是把一张立绘或一张战斗图单独交给程序，而是把一个角色需要的整套材料按固定目录组织成一个可检查的包。当天材料中 tiny-sea-war 的角色资产提交按 assets/characters/<character>/ 这样的角色目录批量交付，目录里出现 battle/、concept/、meta/、processed/、ui/、vfx/、qa/ 等结构。这个结构很重要，因为它让生成脚本知道产物应该放在哪里，让后处理脚本知道从哪里读取源图，让契约检查知道哪些目录和文件必须存在，让审查脚本知道审查记录在哪里。换句话说，目录不是随意整理，而是系统之间的接口：一个角色包是否完整，不靠人眼逐张看，而是靠目录形状和文件清单判断。对学习者来说，可以把它理解成角色的完整行李包：头像、服装、动作、特效、质检报告都要装进同一个档案袋，后续工具才能按清单取出所需内容。

原理逻辑

  1. 角色目录把零散素材组织成稳定产物形状，使工具能按路径约定读取。
  2. 目录结构承担接口职责，连接生成、后处理、契约检查和审查流程。
  3. 交付判断从单文件存在升级为目录清单、配置和审查记录共同满足。

具体例子

以 tiny-sea-war 的某个角色目录为例，assets/characters/<character>/ 下可能包含 concept/、battle/、processed/、ui/、vfx/、meta/ 和 qa/ 等材料；cb6449c2 这类资产提交按角色目录批量交付，意味着交付单元是整个角色包，而不是包里的单张 png。

常见误区

  • 看到几张图片文件存在，就认为角色已经交付完成。
  • 把目录结构当成整理习惯，忽略它是脚本、审查工具和交付流程之间的接口边界。

概念关联

关联概念关系说明
文件/目录作为产物接口边界模板化目录让脚本、审查工具和交付流程能按同一形状读取资产。
资产交付契约和审查机制契约检查需要依据角色目录中的文件与审查记录判断交付是否合规。
Git commit 作为已确认变更事实源当天 assets 提交把多个角色目录纳入已确认的窗口内变更。

本地引用名称与远端 ref 变化的证据边界

完整讲解

本地引用名称与远端 ref 变化的证据边界，讲的是 Git 里名字指向某个 SHA 和远端 ref 在窗口内发生变化不是同一层证据。当天 tiny-sea-war 的 c23c5318 对应 HEAD -> main、origin/main、origin/HEAD，这说明本地仓库里的 main、远端引用名称 origin/main 和 origin/HEAD 都指向这个提交。但这里基于当日材料可确认的是：该信息只能说明窗口内提交与本地 main 及远端引用名称的指向关系，不能单独证明远端 ref 在窗口内发生新增或变化。原因是，本地可能早已记录 origin/main 指向某个 SHA，也可能本地引用只是缓存的远端状态；要判断远端 ref 是否变化，通常需要远端 ref 的历史 SHA 与当前 SHA 比较，或者推送、接收端 ref 更新等过程证据。只读 git ls-remote 能读取远端 ref 当前 SHA，但它不下载提交对象、文件树或工作区内容，因此它给出的也是元数据证据，而不是提交详情证据。这个边界对自动化监控很重要：如果把本地引用名称误当成远端变化证据，就会把本地知道远端曾经指向哪里误写成远端刚刚发布了新提交。

原理逻辑

  1. ref 是名称到 SHA 的指针，指针当前位置不等于指针在窗口内移动。
  2. 本地对远端 ref 的记录可能来自缓存，不能替代远端历史比较。
  3. 只读远端监控只能读取当前元数据，提交数量、提交信息、作者和文件 diff 需要更高层证据。

具体例子

tiny-sea-war 中 c23c5318 对应 HEAD -> main、origin/main、origin/HEAD。这个例子可以确认：本地 main 和远端引用名称指向同一提交；但不能仅凭这一行信息确认远端 main 在 2026-09-22 窗口内从旧 SHA 变成 c23c5318。若远端监控同时记录历史 SHA 与当前 SHA，且两者不同，才能把远端 ref 状态写成变化线索。

常见误区

  • 看到 origin/main 或 origin/HEAD 指向某个提交，就认为远端 main 刚刚更新、推送成功或远端 ref 在窗口内变化。
  • 把 git ls-remote 读到的当前 SHA 当成提交内容证据，认为它能证明新增提交数量、提交信息、作者或文件 diff。

概念关联

关联概念关系说明
Git 远端引用与 SHA 指针ref 是名称到 SHA 的指针，而引用名称指向关系不等于指针在窗口内移动。
只读远端监控的元数据读取边界git ls-remote 只能读取远端 ref 当前 SHA，不能单独证明推送过程。
Git commit 作为已确认变更事实源本地可达 commit 可以确认窗口内变更，但远端 ref 变化仍需远端观测证据。

文档状态与资产交付同步

完整讲解

文档状态与资产交付同步，讲的是项目阶段完成不能只靠一句做完了，而要让文档状态、资产产物和工具能力在证据上对齐。当天 tiny-sea-war 在窗口内确认了三类提交：c23c5318 的 docs: record phase two art completion 修改了 docs/00_project_status.md、docs/34_implementation_map.md、docs/46_character_art_asset_pipeline.md 等文档；cb6449c2 的 assets: complete phase two character packages 按角色目录交付资产包；9b2ecfae 的 tools: unify character art delivery pipeline 统一角色美术交付管线。这里基于当日材料可确认的是：文档被修改、资产包被提交、工具管线被统一，并且它们围绕同一阶段完成状态出现。文档在这里不是附属说明，而是状态接口：它告诉后来者第二阶段美术是否完成、实施映射如何更新、资产管线如何落地。资产包提供阶段产物，工具统一提供可复现的处理能力，文档记录阶段状态，三者共同构成阶段完成证据。需要注意边界：当天材料不能仅凭文件列表确认每个脚本的具体运行结果，也不能确认每个资产文件的最终质量结论；AGENTS.md 的具体规则内容也属于待确认线索，不能写成已确认的 Agent 规则。

原理逻辑

  1. 文档状态承担阶段边界说明，让后来者知道阶段是否完成和映射如何更新。
  2. 资产提交提供阶段产物，工具提交提供可复现处理能力，三者共同支撑完成判断。
  3. 阶段完成需要多类证据同步，避免把状态声明、文件存在或工具能力单独当成完成事实。

具体例子

tiny-sea-war 的第二阶段美术完成可以这样理解：docs 提交记录 phase two art completion，assets 提交交付 phase two character packages，tools 提交统一 character art delivery pipeline。三者共同说明：不是只有文档说完成，也不是只有文件存在，而是状态、产物和工具能力在同一窗口内同步。

常见误区

  • 文档里写了 phase two art completion，就认为所有资产质量已经通过。
  • 资产文件提交后阶段就自动完成，忽略工具管线统一和文档状态同步仍可能缺失。

概念关联

关联概念关系说明
角色资产包作为交付单元文档记录阶段完成状态，资产包提交提供阶段产物，两者共同构成阶段完成证据。
资产交付契约和审查机制文档中的完成状态需要与契约检查、来源审查和交付审查记录保持一致。
Git commit 作为已确认变更事实源docs、assets、tools 三类提交都在同一窗口内被确认，才能作为阶段完成证据。
