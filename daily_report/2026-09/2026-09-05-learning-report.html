仓库格式的版本门槛：为什么对象格式要在读取对象之前被宣布

Repository format version gate

读仓库先看格式声明，不认识别硬闯——拒绝发生在对象读取前。

核心要点

  • Git 不通过对象 ID 长度（40/64）猜测 SHA-1 或 SHA-256，必须在仓库格式入口声明对象 ID 算法。
  • 若打开仓库的程序不认识格式声明，应立刻拒绝打开仓库，而不是进入内部等待哈希失配报错。
  • 格式门槛把误读规则的错误挡在读对象之前。

原子重命名与已打开文件描述符：删除旧 pack 不等于切断旧读者

Atomic rename and open file descriptors

路径像书架位置，inode 才是书；删掉旧路径还能翻开手里的旧书。

核心要点

  • 文件系统区分路径名与文件内容（inode）；打开文件拿到的是通向内容的通道，不是路径名字。
  • Git 使用“写临时文件 + 原子 rename”发布新 pack，使路径切换只能呈现完整旧文件或完整新文件。
  • 已打开旧 pack 的进程持有旧 inode 的文件描述符，即使旧 pack 路径被删除，仍能继续读完旧包。
  • 原子替换的并发安全依赖底层文件系统语义，跨平台或网络文件系统可能不保证“删除后仍可读”。

Per-ref status aggregation under unordered delivery

核心要点

  • git push 可一次推送多个 ref，但协议不保证每个 ref 的状态行到达顺序与更新命令发送顺序一致。
  • 客户端不能采用“按到达顺序、最后一条说了算”的简单策略。
  • 正确做法是收集全部状态行后，以 ref 为归类键合并，再判定全部成功、部分成功或全部失败。
  • 同一 ref 出现多行状态时，不能简单以后到覆盖前到，需按协议报告语义合并。

仓库格式的版本门槛：为什么对象格式要在读取对象之前被宣布

完整讲解

要读懂一本书，先要知道这本书用什么语言。如果一本书用中文印刷，你非按英文去读，每个词都可能解释错，而且错误不会只出现在某个复杂句里，而是从第一个字就错了。Git 也面临同样的选择：仓库里的对象 ID 是用 SHA-1 算出来的还是用 SHA-256 算出来的？这个问题不能靠数一数十六进制字符串的长度来猜。40 位十六进制通常是 SHA-1 的产物，64 位通常是 SHA-256 的产物，但 Git 并不会做这种“看起来像”的猜测。它要求仓库在正式读取对象之前，先在仓库格式的入口处明确声明对象 ID 使用哪一种算法。如果打开仓库的程序不认识这个声明，正确的做法是立刻拒绝打开仓库，而不是继续走进去，等到对象解压完、算完哈希才发现对不上。可以这样理解门槛的作用：假设你要进一座大型资料库，每份资料都有一个编号。管理员事先规定编号用“A 套规则”生成；如果你不知道这套规则，就算资料库大门开着，你也不能进去乱翻。Git 的仓库格式版本和扩展声明就是门口的门卫。它告诉访问者：这是 SHA-1 对象库，请按 SHA-1 规则计算；这是 SHA-256 对象库，请按 SHA-256 规则计算。如果你携带的程序只会 SHA-1，而现在仓库声明的是 SHA-256，你必须在入口处停下，而不是闯入内部靠报错去猜。

原理逻辑

  1. 对象 ID 的计算规则不能事后观察结果推断，必须在读取对象前由仓库格式层声明。
  2. 一旦程序不认识声明中的对象格式扩展，打开仓库的入口就必须拒绝，否则后续按错误规则读取会制造混乱。
  3. Git 因此把“是否认得出格式”放在对象读取之前，而不是等到哈希失配才报告。

具体例子

想象你收到两本外观完全相同的密码本，一本使用凯撒密码，一本使用维吉尼亚密码。如果你不先看封面上的说明，而是直接翻到内页去解码，得到的结果有可能是乱码，也可能碰巧看起来像一段有意义的文字，于是你以为自己读懂了，实际上用的完全是一套错误的规则。Git 遇到不认识的仓库格式声明时，选择的是“先看说明，看不懂就拒绝”，而不是“先试试，看结果像不像”。

常见误区

  • 可以用对象 ID 的长度来判断仓库采用 SHA-1 还是 SHA-256。实际上 Git 把哈希算法当作仓库格式层的声明，对象 ID 只是该算法作用在内容上得到的结果，不能靠观察 ID 长度反向推断。
  • 如果格式不对，最多只是哈希验证失败而已。实际上若按错误规则读取，可能在早期对象遍历时就产生难以定位的混乱，因此拒绝动作要提前到读取对象之前。

概念关联

关联概念关系说明
pack/idx 源/派生关系只有先确认对象 ID 算法，才能计算 pack 中每个对象的内容哈希，也才能用该哈希重建 idx。
原子重命名与已打开文件描述符格式门槛防止“规则被误读”；原子替换防止“规则切换过程中读到半旧半新的数据”。
状态行顺序不保证时的按 ref 聚合同属“先定边界，再处理结果”：格式门槛在本地拒绝误读，状态行聚合在远端避免误判。

继续深入问题

  2. 如果仓库格式声明中出现了未来版本的扩展，旧版 Git 应该如何处理才能避免破坏仓库？
  3. 当把 SHA-1 仓库完整迁移到 SHA-256 时，格式声明要在哪一步切换，才能保证正被旧格式读取的进程不会被中途影响？

原子重命名与已打开文件描述符：删除旧 pack 不等于切断旧读者

完整讲解

在文件系统里，一个文件有两个不同的东西需要区分：一是文件的名字（路径），二是文件本身的内容（在 Unix 中底层代表内容的对象叫 inode）。当你打开一个文件时，你拿到的更像是“通向文件内容的通道”，而不是仅仅记下它的名字。即使随后有人把这个文件从目录里删掉或改名，只要这个通道还开着，你依然能继续读取文件内容。Git 的仓库维护正是利用了这个机制。假设有一个旧 pack 文件要被淘汰，Git 不会一边停掉所有正在读仓库的程序，一边慢慢替换。它会先把新 pack 写到一个临时文件，然后用一次原子 rename 操作把它放到最终路径。所谓原子，就是当新路径出现时，它要么指向完整的旧文件，要么指向完整的新文件，绝不会出现半个文件。新来看这个路径的进程会得到完整选择；而早已打开旧 pack 的进程，由于持有旧 inode 的文件描述符，即使旧路径后来被删除，也能继续安全地使用旧包里的对象。于是“旧 pack 已删除”和“某个进程仍在使用旧 pack 数据”完全可以同时成立。这个语义是不是在所有系统上都成立？并不一定。跨平台的文件锁差异会影响这种语义：有些系统不让你删除一个正在被打开的文件，有些网络文件系统也不保证已经打开的文件在删除后仍可读。Git 的并发安全设计依赖于底层文件系统的这些行为，所以在某些平台上，删除旧 pack 的时机和方式需要额外考虑。

原理逻辑

  1. 路径名与 inode 分离：rename 替换的是目录项名称，不是已打开文件的内容。
  2. 原子 rename 保证新读者只会看到完整旧文件或完整新文件，不会看到半旧半新。
  3. 已打开文件描述符保护旧读者，即使文件被 unlink 也可继续读取，直到所有打开者关闭。
  4. Git 利用这种语义在 gc 运行时并发替换 pack，但跨平台文件锁差异会增加约束。

具体例子

你去图书馆借书，管理员把一本书放到你手上，你拿着书开始读。这时候另一位管理员把书架上的那本书取走，换成了新版。你手里的旧书会因为书架上没有它而消失吗？当然不会。你打开的是“那本具体的书”，而不是“书架上的位置”。在文件系统里，路径就像书架位置，inode 就像那本具体的书，文件描述符就是你递给管理员的借书证。你已经打开的文件，即使目录项被删掉，你仍然能继续翻看内容。

常见误区

  • 删除文件之后，所有正在读它的进程会立即出错。实际上在 Unix/Linux 传统语义下，只要进程在删除前已经打开文件，仍可通过文件描述符继续读，删除目录项只是让路径消失。
  • 原子 rename 意味着旧文件立刻不存在。实际上 rename 把旧路径瞬间替换成新路径，不代表已打开的旧文件消失；旧文件只是不再出现在该路径下，可能仍被已打开它的进程引用。

概念关联

关联概念关系说明
仓库格式的版本门槛格式门槛回答“用哪套规则读”，原子替换回答“读的过程中数据会不会被半路调包”。
状态行顺序不保证时的按 ref 聚合本地用原子 rename 得到全局清晰的切换边界；远端没有统一原子替换机制，因此改用不依赖顺序的消息聚合来收敛结果。
pack 与 idx 的源/派生关系重建 idx 依赖 pack 内容稳定，而原子 rename 与已打开文件描述符保证替换过程中内容稳定。

  3. 在文件锁语义不同的平台上，为什么删除旧 pack 的时机需要重新设计？ Git 的代码需要为此做哪些特殊处理？

精读文章 · 软件工程 / 计算机科学

状态行顺序不保证时的按 ref 聚合：部分成功推送怎样变成客户端结论

完整讲解

一次 git push 可以同时推送多个分支或标签，每个分支或标签被称为一个 ref。服务端会为每个 ref 返回一行状态，告诉客户端这次更新是成功（ok）还是失败（ng）。问题是，这些状态行到达客户端的顺序不一定和客户端发送更新命令的顺序相同。协议并没有承诺“先发的 ref 先返回结果”。因此客户端不能采用“按收到顺序处理，最后一条说了算”这种简单策略。那应该怎么办？正确思路是：把推送过程中收到的所有状态行先收集起来，不放行也不马上判决，而是在全部报告到达后，按 ref（或者按原始推送命令）作为归类键，把属于同一个 ref 的状态行合并成一条最终结论。最后再看总体结论：全部 ref 都成功，就是全部成功；只要有一个 ref 失败，而其他成功，就是部分成功；全部失败，就是整体失败。这个判定结果不依赖先收到哪条、后收到哪条。打个比方：老师一次布置了十道题，请十位同学分别批改，然后让课代表汇总。如果同学们交回批改结果的顺序是乱的，课代表不会因为最后收到某道题写着“对”就认为所有题都对，也不会因为先看到某道题写着“错”就急着宣布整张试卷不及格。他会先把交上来的结果按题号归位，再统计有多少题对、多少题错。推送状态行也是如此。

原理逻辑

  1. 协议未对状态行到达顺序作承诺，因此顺序不能作为决策依据。
  2. 客户端应缓存完整状态报告，以 ref 作为归类键，把同一 ref 的状态行合并为一条最终结论。
  3. 最终整体判定为全部成功、部分成功或全部失败，取决于各 ref 的结果集合，不依赖先到后到。

具体例子

你同时向远程仓库推送两个分支：main 和 dev。远程服务器可能因为 main 被保护而不能更新，而 dev 顺利更新。但它返回状态时没有保证顺序：也许先在网络里到达的是 dev ok，然后才是 main ng。如果你的客户端看到第一条 ok 就认为所有推送成功，那就大错特错；如果看到第一条 ng 就中断并报告失败，也会忽略后面可能存在的其他 ref 结果。客户端要像投票统计员一样，先收集所有选票，再按 ref 分类，才能准确说出“dev 成功，main 失败，本次推送部分成功”。

常见误区

  • 状态行到达顺序等于服务端处理顺序，所以可以按到达顺序做最后一条判断。实际上协议没有给出顺序保证，顺序不能作为决策依据。
  • 同一 ref 返回多行时，后到达的行自然覆盖先到达的行。实际上应把同一 ref 的所有状态行收集在一起，再根据协议报告语义确定最终状态，简单覆盖可能被乱序欺骗。

概念关联

关联概念关系说明
原子重命名与已打开文件描述符本地使用原子 rename 得到清晰的全局切换边界；远端没有这种统一替换机制，因此协议选择不保证顺序，客户端通过按 ref 聚合得到可判定性。
仓库格式的版本门槛状态行聚合与格式门槛都体现“先明确边界再处理结果”：格式门槛在读取前定规则，状态行聚合在报告收齐后才下结论。
idx 查找表对象查找按对象 ID 定位，推送结果按 ref 定位；顺序不改变最终定位结果，聚合同 idx 一样是一个查找/归类过程。

  2. 客户端聚合出“部分成功”后，不同 Git 命令应该分别返回什么退出码？
  3. 远端服务端的 update 钩子和 pre-receive 钩子可能造成同一个 ref 的结果被多行状态覆盖，客户端要怎样设计才能正确合并这些行？

概念之间的关联

这三个概念表面上分布在本地仓库和远程协议两个场景，但底层都围绕一个共同问题：Git 如何在不知道全局时间顺序或者不能依赖简单顺序的环境中保持判断可靠。仓库格式版本门槛是在“读任何内容之前”确定解释规则；原子替换是在“路径切换期间”保证新旧数据不混；按 ref 聚合则是在“消息到达顺序不可靠”时，通过集合而不是顺序来得出最终结论。Git 的设计思路不是让所有操作都变成一个大事务，而是把可靠性分散到不同边界上：格式边界负责拒绝对规则的误读，文件系统边界负责给替换操作一个清晰的原子分界，协议边界则让客户端以 ref 为单位消化不确定性。

今日最值得记住的一句话

Git 不把可靠性押在单一事务上，而是将其分散到格式边界、文件系统边界和协议边界上。
