被引用边界与悬空对象：什么对象缺失才值得让完整性检查报错

完整讲解

想象一个巨大的仓库，里面放着很多文件。但并不是仓库里每个文件都对客户有价值，只有写在当前商品目录里的那些才需要保证随时能拿出来。Git 对象库也是类似：分支和标签就是“已发布引用”，它们相当于对外承诺的商品目录；从这些引用能一路走到达的对象，才是仓库必须保证完整的东西。那些曾经被用过但现在没有任何分支或标签指向的对象，叫悬空对象。它们可能是历史操作留下的旧提交、临时写入的中间数据，它们不碍事，完整性检查也不会因为它们不完整而报错。换句话说，“文件在不在盘上”和“文件是否被当前引用需要”是两个完全独立的维度。完整性检查真正关心的是：被已发布引用指向的对象，必须能找到、能读、内容正确。

原理逻辑

  1. Git 以分支、标签等“已发布引用”作为对外承诺，从这些 refs 出发的图遍历定义了“必须完整可达的对象集合”。
  2. 悬空对象不在任何已发布引用的可达范围内，所以完整性检查不会把它们的损坏当作必须报告的仓库错误。
  3. 判断对象缺失是否值得报错，应先判断它是否落在已发布引用可达闭包内，而不是只看该对象文件是否存在。

具体例子

一个仓库只有 main 分支指向提交 C。C 的目录树里引用了文件对象 B。另外，仓库里还有一个旧提交 X，那是几天前 main 还指向它时留下的，但现在没有分支或标签指向 X。如果 B 在对象库里缺失，fsck 会报错，因为 C 经过引用可达性需要 B；如果 X 这个提交对象本身发生损坏，fsck 不会把它当作仓库错误，因为 X 不在任何已发布引用的可达范围内，只是一个悬空对象。同一个文件丢失，会不会被报告，取决于它是否落在引用边界之内。

常见误区

  • 误以为完整性检查应保证仓库里没有多余对象，或每个对象文件都健康。
  • 误以为“对象损坏”一律是问题，但无引用对象即使损坏，只要不在当前可达范围内，通常不会影响操作和报告。

概念关联

关联概念关系说明
引用可达性与可读性的独立维度两者组合出“被引用且可读、被引用却缺失、无引用但可读、无引用且不可读”四种情况；完整性检查只在引用可达边界内判断错误。
git fsck 的 missing 与 corrupt 判定被引用边界先确定对象是否在可达闭包内，随后缺失才被报告为 missing 或 corrupt。

精读文章 · 计算机科学 / 软件工程

引用可达性决定“缺失”分类：git fsck 的 missing 与 corrupt 判定

完整讲解

git fsck 是一把“引用可达性扫描器”。它不会把对象库里所有文件都查一遍，而是从已发布引用出发，沿着提交指向树、树指向子树和文件、提交指向父提交这样的关系向前走，形成一个“必须能到达的对象集合”。在这个集合里，如果一个本应存在的对象找不到，fsck 会叫它 missing，意思是引用链在这里断了，仓库无法兑现它对外承诺的内容。如果对象文件存在，能读取，但读取后算出的内容哈希与对象 ID 对不上，fsck 会叫它 corrupt，意思是东西找到了，但不是它声称的那个。missing 和 corrupt 的修复方式也不同：missing 可能是因为索引没建好、pack 没完整发布，或者对象真的丢失了；corrupt 往往意味着数据物理损坏或内容被改写。所以，错误报告必须把两者分开，否则维护者会走错修复方向。

原理逻辑

  1. 扫描器从已发布引用出发，沿提交→树→blob 等关系形成“必须可达集合”。
  2. 若对象不应缺失却缺失，分类为 missing。
  3. 若对象能读取但内容哈希与对象ID不匹配，分类为 corrupt；两者对应不同修复路径。

具体例子

假设 fsck 从 main 指向的提交 C 开始遍历。C 的树对象 T 中记录了一个文件 blob，哈希编号是 abc123。如果对象库中没有 abc123 这个对象，fsck 会输出类似“missing blob abc123”，它说明 C 引用了这个 blob，但对象库里找不到它。另一个场景：对象库中存在一个文件也叫 abc123，但 git 读取并解压后计算 SHA-1，发现结果是 def456，不是 abc123，fsck 就会报告 corrupt。前者可以用从上游重新获取或恢复 pack 来解决，后者如果没有任何副本，通常无法靠 Git 自行恢复。

常见误区

  • 把 missing 和 corrupt 都笼统称为“对象损坏”，实际上 missing 是“应有却无”，corrupt 是“有但不对”。
  • 以为 fsck 会检查所有对象文件，实际上它只检查从已发布引用可达的对象；不在可达闭包里的对象即使缺失也不报 missing。

概念关联

关联概念关系说明
被引用边界missing 与 corrupt 的判定依赖被引用边界；只有位于已发布引用可达闭包内的对象，其缺失或损坏才会被 fsck 报告。
错误关键词与故障层定位报告后要根据具体关键词区分故障层：sha1 mismatch 指向内容身份冲突，inflate error 指向压缩流问题，从而引导修复方向。

精读文章 · 软件工程 / 计算机科学

并发仓库维护中的旧 pack 回收所有权：谁可以安全删除仍在延迟让位的旧文件

完整讲解

当 Git 执行 repack 或 gc 时，会把多个旧 pack 中的对象重新打包成一个新 pack，然后让旧 pack“延迟让位”。所谓延迟让位，是因为在 Linux 上删除一个文件后，已经打开它的进程还能继续读，所以可以马上删掉文件名；但在 Windows 或某些网络文件系统上，删除一个仍有进程打开的文件会失败，或会立即影响读者。于是一个安全策略是：先让旧 pack 保留一段时间，等所有读者都不再使用它之后，再真正删除。但这个策略在并发维护下会变得复杂：如果有两个维护命令同时运行，各自都会生成新的 pack，也会各自列出“我认为可以删除的旧 pack”。命令甲认为旧包 O 已经可以被清掉，因为它的新包 N 已经包含了所需对象；命令乙却可能还在使用 O 作为当前查找路径的一部分，或者它的新包 M 正在把 O 中的对象当成来源。如果甲直接删掉 O，乙就会读到一半找不到数据。安全回收必须解决“所有权”问题：在多个维护者并存的情况下，要有一个统一的机制（例如锁、读写计数、multi-pack-index 版本切换）来确定“当前有效包集合”到底是什么，以及“旧 pack 从这一刻起不再属于任何可观察的有效状态”。只有这样，执行删除的进程才能证明自己拥有回收权，而不是基于自己刚才看到的瞬间快照。

原理逻辑

  1. repack 或 gc 生成新 pack 后，旧 pack 不能立即删，要按读者生命周期延迟让位。
  2. 并发维护命令可能仍以旧 pack 作为查找来源，某进程对“旧”的判断可能与其他进程冲突。
  3. 安全的回收需要先确定“当前包集合”的唯一有效状态——通过锁、原子索引切换或所有权机制——删除者才能行动。

具体例子

命令 A 执行 `git repack -ad`，它读到了旧 pack O，生成新 pack N，然后把 O 放进自己的“延迟删除候选列表”。与此同时，命令 B 执行 `git multi-pack-index write`，它基于自己启动时的对象库状态构建新的 multi-pack-index，这个新索引里仍然包含 O 中某个对象的位置。A 如果只看到“旧 pack O 已经不在 A 生成的新 pack 集合中”就认为可以删除 O，那么 B 写入的 multi-pack-index 就会指向一个已经被删除的 pack。后续所有查找该对象的读操作都会失败。正确设计是：A 与 B 必须先争夺同一个锁，让“谁先完成包集合切换”变成串行步骤；只有当一个维护操作已经把旧包从所有读者能观察到的当前索引中彻底移除之后，它才真正拥有删除旧包的权利。

常见误区

  • 认为只要过了 gc.pruneExpire 时间窗口，旧 pack 就能安全删除；实际上时间窗口只对短暂读者有效，覆盖不了并发维护进程自己生成新索引的情况。
  • 觉得每个维护命令都可以根据自己看到的“旧 pack 不再被需要”进行删除；其实一个维护者看到的“旧”可能是另一个维护者正在使用的“当前”，必须有共同认可的所有权仲裁。

概念关联

关联概念关系说明
被引用边界旧 pack 是否仍包含被已发布引用可达的对象，决定了它是否仍承载有效数据，不能只因“旧”就被回收。
