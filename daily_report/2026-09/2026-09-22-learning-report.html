Git commit 作为唯一变更事实源

完整讲解

我们可以把 Git 仓库想象成一个不断变化的现场。现场里有很多东西看起来都变了：某个文件被修改了，某个新文件出现在未跟踪目录里，某个 ref 指针从旧 SHA 变成新 SHA。但这些“看起来变了”并不一定都能成为结论依据。Git commit 是 Git 中已经封存的一条历史记录，它通常包含提交时间、作者、提交说明、文件变更等信息，可以被读取、被验证、被归属到某个检查窗口。所谓 Git commit 作为唯一变更事实源，就是系统只把已经进入 commit 的变更当作“已确认事实”，其他东西都只能作为线索。这个口径非常重要，因为它让结论变得可追溯。工作区草稿可能只是半成品，ref 变化可能只是远端指针移动，未跟踪文件可能只是临时实验；而 commit 至少说明有人把一组变更正式写入了历史。对于自动化总结来说，事实源越窄，结论越不容易跑偏。

原理逻辑

  1. Git commit 是已封存的历史记录，包含可读取、可验证、可归属时间的变更信息。
  2. ref 变化、工作区修改和未跟踪文件都属于现场线索，不能直接证明已确认变更。
  3. 把事实源收窄到 commit，可以让报告中的每条结论都追溯到具体提交。

具体例子

假设监控发现 sliceV2 的 refs/heads/main 历史 SHA 与当前 SHA 不同，但当天只读取 ref 元数据，不下载提交对象、文件树或 diff。可靠写法是“远端 main 指针发生变化，提交级内容待确认”，不能写“sliceV2 当天修改了某个文件”或“完成了某功能”。

常见误区

  • 把“看到变化”直接当成“确认变化”，例如看到远端 ref SHA 变了就认为一定新增了某个功能。
  • 把目标日期直接等同于所有相关变化的发生时间，忽略提交窗口、读取失败和待确认状态。

概念关联

关联概念关系说明
Git SHA 对象标识与 ref 比较ref 比较只能判断指针是否移动，commit 事实源提供指针背后可确认的变更内容。
提交事实与工作区线索的证据分层只有排除未提交、未跟踪和工作区状态后，commit 才能成为唯一可确认变更事实源。
LLM 输出可靠性与证据约束事实源越明确，大模型生成总结时越不容易把弱线索说成已完成工作。

文件接口作为系统边界

完整讲解

一个 Agent 系统看起来可能只是一段提示词加一个脚本，但真正稳定运行时需要多个文件共同配合。提示词文件约束 Agent 应该怎么说、不能说什么；脚本决定实际流程如何执行；架构文档和任务文档说明系统为什么这样设计、任务边界在哪里；测试文件验证行为是否符合预期。这里可以把“文件接口”理解成：每个文件都承担一种接口职责，合在一起定义了系统的能力、限制和验证方式。如果只改提示词，不更新脚本或测试，系统可能出现“嘴上说得很严，实际执行没跟上”的漂移。如果只改脚本，不更新文档，后来的人就不知道边界为什么变了。如果只改测试，不更新提示词，测试可能验证了一个没人真正要求的规则。因此，文件接口作为系统边界，强调的是多文件一致性：提示词、脚本、文档、测试要共同表达同一套规则。

原理逻辑

  1. 每个文件承担一种接口职责，共同定义系统能力、限制和验证方式。
  2. 提示词、脚本、文档和测试必须同步表达同一套边界，否则会出现行为漂移。
  3. 文件接口把抽象规则变成可检查、可维护、可回归的系统约束。

具体例子

假设每日总结 Agent 的提示词要求“没有窗口内 commit 就不能写完成项”，脚本也确实只读取窗口内 commit，测试也构造了无 commit 场景并断言输出不能包含完成项。这时文件接口是一致的。如果提示词后来改成“可以补充本地草稿”，但脚本仍然只读取 commit，测试仍然只验证 commit，就会形成边界漂移：模型可能想补充草稿，但系统证据源并不支持。

常见误区

  • 认为文档只是说明，不参与系统行为，或者认为测试只是附属产物。
  • 认为只要核心脚本改了，系统边界就自动更新了，忽略提示词、文档和测试的同步。

概念关联

关联概念关系说明
提示词工程与任务约束设计提示词是文件接口中约束大模型输出语言和证据范围的一部分。
测试作为行为契约与回归验证测试把文件接口中的行为约定变成可执行、可回归的验证对象。
Agent 工作流与任务编排文件接口承载了工作流各阶段的输入、输出和边界说明。

  2. 如何为 Agent 文件接口设计一致性检查，自动发现 prompt 与测试覆盖范围漂移？
  3. 如果新增一个任务阶段，应该同步修改哪些文件才算完成边界扩展？

LLM 输出可靠性与证据约束

完整讲解

大语言模型很擅长把零散信息组织成通顺文本，但这也带来一个风险：它可能会把不确定信息说得很确定。比如只看到 ref 变化，它可能自动补全成“完成了某功能”；只看到工作区草稿，它可能自动补全成“当天推进了某任务”。LLM 输出可靠性不是简单要求模型“更聪明”，而是要给模型设置证据约束：哪些证据可以支持结论，哪些证据只能作为线索，哪些内容必须标注为待确认。只读 git ls-remote 只能证明 ref 指针变化，不能证明提交数量、提交信息、作者、文件列表或 diff；工作区状态不采集，就不能把草稿写成已完成工作。证据约束的意义，就是让大模型的输出像有引用来源的报告，而不是没有边界的自由发挥。

原理逻辑

  1. 大模型会把弱证据包装成通顺事实，因此必须明确证据等级和可推断范围。
  2. 输入证据、脚本过滤、文档边界和测试断言共同构成输出约束。
  3. 每条结论都应能追溯到可确认证据，证据不足时应标注待确认或拒绝补全。

具体例子

假设输入中只有 sliceV2 的 refs/heads/main 历史 SHA 与当前 SHA 不同，但没有提交对象、提交日志、文件树或 diff。可靠输出应写“远端 main 指针发生变化，提交级内容未确认”；不可靠输出会写“sliceV2 当天完成某功能”或“修改了某文件”。如果输入中还有窗口内 commit、文件列表和 diff 摘要，才可以写具体变更，并最好附带 commit 标识作为证据引用。

常见误区

  • 认为只要在提示词里写“不要编造”，大模型输出就可靠了。
  • 认为输出流畅就等于可靠，忽略通顺文本可能只是把弱证据包装得更像事实。

概念关联

关联概念关系说明
Git commit 作为唯一变更事实源commit 事实源为大模型输出提供了可确认的证据上限。
文件接口作为系统边界提示词、脚本、文档和测试共同把证据约束变成可执行系统规则。
证据边界与可确认事实分层大模型必须区分已确认事实、待确认线索和不可推断内容，避免把弱证据升级成强结论。

  2. 当 Agent 自己生成的日报提交进入监控输入时，应如何排除、标记或单独审计？
  3. 如何测试 LLM 在证据不足时是否会拒绝补全，而不是生成看似合理的总结？

概念之间的关联

三个概念分别回答什么可以作为事实、系统边界由什么承载、大模型输出如何不越界。Git commit 作为唯一变更事实源解决事实选择问题；文件接口作为系统边界解决约束承载问题；LLM 输出可靠性与证据约束解决输出可信问题。三者形成递进关系：先限定事实源，再让文件接口把规则变成可执行系统，最后让大模型在边界内生成可靠总结。

今日最值得记住的一句话

弱证据只能支持弱结论，强结论必须依赖可验证的提交事实。
