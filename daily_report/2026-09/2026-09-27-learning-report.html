检查窗口边界的时间归属规则

完整讲解

检查窗口边界的时间归属规则，讨论的是当一个提交时间正好落在检查窗口起点或终点时，系统应该把它算进哪一天。检查窗口可以理解成一个时间区间：起点 start 和终点 end 之间有哪些提交。为了让规则可重复，报告必须显式说明边界采用哪种包含方式，例如 [start, end) 表示起点包含、终点不包含；这样 end 那一秒的提交会归到下一个窗口，而不会在两个相邻日期里同时出现。对高中基础读者来说，这就像课程表里 8:00 正好下课又正好上课：如果不规定 8:00 属于哪一节，就会出现同一节课被算两次的混乱。报告字段要保持一致，例如 window_start、window_end、boundary_inclusion、commit_attribution 和 evidence_level 要一起表达：窗口是什么、边界怎么算、提交归属到哪一天、这个归属有多可靠。如果提交时间被 rebase、amend 或 cherry-pick 改写，或者时间读取失败，系统就不应继续把它当作强时间证据，而应降级为弱线索并保留人工确认入口。

原理逻辑

  1. 时间窗口必须定义边界包含语义，才能避免同一提交在相邻窗口重复或漏计。
  2. 边界归属不是孤立结论，需要与窗口字段、提交归属字段和证据等级字段共同表达。
  3. 时间证据被改写或读取失败时，应降低证据等级并保留人工确认入口，而不是继续输出确定日期。

具体例子

假设检查窗口是 2026-09-27T00:00:00+08:00 到 2026-09-28T00:00:00+08:00，采用 [start, end) 规则。一个提交的 commit time 是 2026-09-28T00:00:00+08:00，那么它不计入 2026-09-27，而应计入 2026-09-28。报告可以记录 window_end_exclusive=true、commit_attribution=next_window；如果这个提交时间后来被 rebase 改写，则 evidence_level 应降为 weak_time_clue，并进入 needs_review，而不是直接写成确定归属。

常见误区

  • 认为边界提交可以灵活处理，导致同一提交在不同报告中被计入不同日期。
  • 默认终点 end 必须包含在窗口内，导致相邻窗口重复统计同一提交。

概念关联

关联概念关系说明
提交时间被改写后的证据降级规则当提交时间被 rebase 或 amend 改写后，边界归属只能作为弱线索而不能直接写成确定日期。
部分完成状态到自动化报告退出码的映射窗口内提交证据会影响阶段子状态是否被确认，窗口归属不确定时阶段状态也应保留待复核标记。
批量失败原因的层级保留与下钻窗口归属错误可能导致仓库级状态错误，进而让批量报告的下钻定位失去可信基础。

部分完成状态到自动化报告退出码的映射

完整讲解

部分完成状态到自动化报告退出码的映射，讨论的是当一个阶段里有些子任务完成、有些子任务阻塞时，自动化系统如何给出机器可读的结果。部分完成不是简单的成功或失败，而是多个子状态组合后的中间状态。例如 open 问题中提到 docs、assets、tools、review 四个子状态可以独立记录；当 docs 和 assets 完成，而 tools 失败或 review 未通过时，阶段状态可以表达为 partially_completed。对自动化系统来说，仅写部分完成还不够，因为它还需要知道下一步该自动重试、等待人工确认，还是直接标记失败。因此可以设计退出码表：0 表示全部成功，10 表示部分完成，20 表示失败，30 表示需要人工确认；这只是讲解示例，不是当天事实。报告还应记录阻塞项、责任角色、证据等级和下一步动作，例如 blocking_items、owner_role、evidence_level、next_action。这样人看报告能理解哪里卡住，脚本看退出码也能选择正确动作。

原理逻辑

  1. 阶段状态需要先拆成可独立记录的子状态，才能表达部分完成而不是二选一。
  2. 退出码必须承载机器动作，例如重试、等待人工确认或标记失败，而不是只表达语义。
  3. 报告字段要同时服务人和脚本，保留阻塞项、责任角色、证据等级和下一步动作。

具体例子

假设一个阶段包含 docs=success、assets=success、tools=failed、review=pending。组合状态是 partially_completed，阻塞项是 tools，责任角色是 tools_owner，证据等级是 confirmed_step_failure。报告可以设置 exit_code=10、retry_policy=retry_tools_step、manual_review_entry=review_tools_failure。这样自动化系统知道不是整体失败，而是 tools 步骤需要重试；人工复核也知道要看 tools 失败证据，而不是重新检查 docs 和 assets。

常见误区

  • 认为部分完成可以用 0 表示成功，导致自动化系统误以为阶段已全部完成。
  • 用一个模糊的 1 表示失败，导致无法区分哪些子状态已完成、哪些阻塞、应该重试哪个步骤。

概念关联

关联概念关系说明
批量失败原因的层级保留与下钻部分完成可能只发生在某个角色或步骤，批量报告必须保留该层级原因而不能只给仓库级失败。
检查窗口边界的时间归属规则窗口内提交证据会影响子状态是否被确认，窗口归属不确定时阶段状态也应保留待复核标记。
Agent 文件接口的一致性漂移检测新增阶段或文件边界扩展会改变子状态集合，如果 prompt、脚本和测试不同步，退出码映射可能无法正确消费。

  3. 当文档声明 completion 但 review 未通过时，报告应如何同时记录声明来源、阻塞证据、责任角色和证据等级，避免把弱线索补全成完成事实？

批量失败原因的层级保留与下钻

完整讲解

批量失败原因的层级保留与下钻，讨论的是当一次批量检查或批量交付中多个仓库、多个角色、多个步骤都出现问题时，报告如何既给出整体摘要，又保留定位细节。可以把批量报告想象成一棵树：仓库级是树干，角色级是树枝，步骤级是树叶。仓库级状态回答这个仓库整体是否失败，角色级状态回答哪个角色失败，步骤级状态回答具体哪一步失败，failure_code 和 evidence_id 则回答失败原因是什么、证据在哪里。聚合展示是为了让人快速看懂整体，但聚合不能把叶子节点证据吞掉。多个角色失败原因相似时，可以合并成一组，例如都标记为 version_drift，但每个角色的 evidence_id、step_id 和定位信息仍要保留，否则后续无法判断是输入计划错误、处理脚本错误，还是依赖锁文件与脚本实际使用版本不一致。对自动化系统来说，下钻能力意味着同一份报告既能给脚本一个仓库级退出码，也能给人工复核一条从仓库到角色再到步骤的证据链。

原理逻辑

  1. 批量失败需要分层表达，仓库级、角色级和步骤级分别回答不同定位问题。
  2. 相似失败可以分组，但分组不能替代证据 ID、步骤 ID 和定位信息。
  3. 下钻结构要让自动化系统和人工复核使用同一份数据，从摘要一路追到具体证据。

具体例子

假设 batch_id=B20260927 中仓库 repoA 的 repository_status=failed。角色 role1 的 step=dependency_check 失败，failure_code=version_drift，evidence_id=EV-101；角色 role2 的 step=asset_review 失败，failure_code=review_not_passed，evidence_id=EV-102；角色 role3 的 step=dependency_check 失败，failure_code=version_drift，evidence_id=EV-103。仓库级摘要可以写 dominant_failure=version_drift、affected_roles=[role1, role3]、other_failures=[review_not_passed]。下钻时仍要保留 EV-101 和 EV-103，而不是把它们合并成一条没有证据 ID 的依赖问题。

常见误区

  • 认为批量失败只要给一个仓库级原因就够了，导致无法定位具体失败位置。
  • 把相似失败合并后丢掉每个角色和步骤的证据 ID，导致无法判断相似失败是否真的来自同一个根因。

概念关联

关联概念关系说明
部分完成状态到自动化报告退出码的映射部分完成状态需要被映射到退出码，同时批量报告要保留造成部分完成的具体角色和步骤原因。
依赖锁文件与脚本版本漂移的管线状态依赖版本漂移可能出现在步骤级，若只记录仓库级失败，就无法判断是输入计划错误还是处理脚本错误。
