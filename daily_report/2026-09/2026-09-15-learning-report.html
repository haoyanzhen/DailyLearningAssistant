数据驱动配置与配置注册

完整讲解

数据驱动配置与配置注册，可以理解成：游戏表现层不把每个视觉细节写死在代码里，而是先从一份“数据说明书”开始。当天材料里，`docs/25_presentation_data_schema.md` 是文档变更线索，用来描述表现数据应该长什么样；`presentation_settings.json` 是实际配置值；`config_registry.gd` 是配置注册入口，把配置接入运行时；`ship_unit_view.gd` 是表现层代码，读取这些配置并影响显示；`scene_presentation_test.gd` 和 `test_runner.gd` 则是测试线索，用来验证表现行为。底层逻辑是：先定义数据结构，再注册可用配置，最后让代码读取。schema 不是运行时逻辑本身，但它像一张表格模板，规定哪些字段存在、字段是什么类型、配置应该怎样组织。配置注册表则像“入口名单”，告诉运行时哪些配置可以被读取。这样改视觉参数时不必改代码，测试也能围绕同一份数据契约展开。当天材料确认了潜艇深度表现视觉、表现设置、配置注册和测试文件之间的线索，但没有给出具体字段名、深度计算公式或物理模型。因此这里应理解为“深度作为一个表现维度被配置和呈现”，不能推断浮力、压强或潜艇动力学。

原理逻辑

  1. 先定义结构：schema 像表格模板，规定哪些字段存在、字段是什么类型、配置怎样组织，它本身不是运行时逻辑，却是后续一切的前提。
  2. 再注册入口：配置注册表像“入口名单”，告诉运行时哪些配置可以被读取，没有注册的配置即使写在文件里也无法真正生效。
  3. 最后消费与验证：表现层代码按 schema 和注册表读取配置影响显示，测试围绕同一份数据契约检查行为，于是改视觉参数不必改代码。

具体例子

可以把 schema 想成餐厅菜单：菜单规定菜名、价格和辣度等级，厨房的登记表决定今天哪些菜可做，顾客点单则给出具体选择。顾客最后吃到什么，不靠服务员背下所有菜，而靠菜单、登记表和点单三者配合。数据驱动配置也是这样，代码不需要背下所有视觉细节，只要按 schema 和注册表读取配置。

常见误区

  • 把“潜艇深度表现视觉”误当成物理建模。当天材料只确认它出现在表现设置、表现数据 schema、配置注册和表现层代码中，没有浮力、压强、介质阻力或动力学方程线索。
  • 以为 schema 定义完就自动生效。实际上还需要配置注册表接入运行时，并由表现层代码和测试消费。
  • 把配置文件当成随便改的文本，忽略了它背后可能存在结构约束和测试保护。

概念关联

关联概念关系说明
配置校验与配置契约配置注册接入运行时之前，配置本身需要符合 schema 并被检查，所以两者是“定义结构”和“确认结构合法”的前后关系。
资产契约与契约检查后处理计划和资产审计同样是把规范变成可检查对象，与配置注册共享“先定义结构再消费”的思路。
有序 LLM provider 故障转移provider 候选链同样需要配置契约才能进入编排器，表现层的配置驱动链与它是同一种配置消费模式。

配置校验与配置契约

完整讲解

配置校验与配置契约，说的是系统不要等到真正使用配置时才碰运气。当天材料里，`config.example.json`、`docs/configuration.md` 和 `scripts/check_config.py` 同时出现变更线索，这提示配置不是一个随便写的文本文件，而是被示例、文档和校验脚本共同约束的结构契约。底层理念是“把运行时错误尽量提前”。如果 provider 顺序、表现设置或其他关键配置不符合约定，系统应该在前置检查阶段就报错，而不是等到某个 provider 失败、某个场景加载时才暴露。配置契约把示例配置、说明文档和校验脚本绑在一起：示例告诉人怎么写，文档解释为什么这样写，校验脚本则用可执行方式检查是否符合约定。这样，后续的 failover 链、表现层或调用方才有一个相对可靠的前提。需要谨慎的是，材料确认了这些配置相关文件发生变更，但没有展开具体校验规则。因此不能编造“校验了哪些字段”或“失败后如何处理”。可以确认的是：配置被当作需要检查的前置条件，而不是单纯注释。

原理逻辑

  1. 错误前置：与其等到 provider 失败或场景加载时才暴露问题，不如在系统启动前用可执行检查把结构错误拦下来。
  2. 三位一体：示例配置告诉人怎么写，说明文档解释为什么这样写，校验脚本用可执行方式检查是否符合约定，三者共同构成契约。
  3. 契约只给前提：校验通过只证明配置满足已定义契约，它为后续 failover 链和表现层提供可靠前提，但不保证所有运行结果都符合预期。

具体例子

这像飞机起飞前的检查单：飞行员并不是不信任飞机，而是把关键条件在起飞前逐项确认——油量、舵面、仪表、天气。配置校验就是软件起飞前的检查单，它不保证飞行一定成功，但能避免很多本可提前发现的错误。再具体一点：如果 provider 选择顺序配置里写了一个系统不认识的名字，或把本该是列表的结构写成了普通字符串，校验脚本应在系统运行前报错；否则系统可能直到主 provider 失败、需要找备用 provider 时，才发现备份入口根本无效。

常见误区

  • 以为有 `config.example.json` 就代表配置一定正确。示例只是给人看的模板，不等于实际配置已经通过校验。
  • 以为校验通过就等于业务绝对正确。校验通常只能证明配置满足已定义的契约，不能证明所有运行结果都符合预期。
  • 忽略文档、示例和校验脚本之间的同步关系。三者一旦不一致，人就会按旧示例写配置，而系统按新脚本拒绝它。

概念关联

关联概念关系说明
有序 LLM provider 故障转移provider 配置需要先被校验，才适合进入 failover 链，否则候选链可能在运行时才发现配置错误。
数据驱动配置与配置注册两者都遵循“先定义结构、再让运行时消费”的顺序，只是一个强调结构注册，一个强调结构检查。
资产契约与契约检查两者都是前置条件式检查，区别只在检查对象：一个是配置，一个是角色资产。

有序 LLM provider 故障转移

完整讲解

有序 LLM provider 故障转移，来自当天 DailyLearningAssistant 的已确认提交主题 `Add ordered LLM provider failover`。这里有三个关键词：LLM provider、ordered、failover。LLM provider 是抽象边界，系统把不同的大语言模型服务提供方当作可替换后端；ordered 表示这些 provider 不是无序集合，而是有顺序或优先级的候选链；failover 表示当前 provider 不能完成调用时，系统按顺序转移到下一个候选。底层逻辑是可靠性设计。如果系统只绑定一个模型服务，它不可用时整个调用就失败；如果把多个 provider 排成候选链，就可以在失败时降级到备用路径。当天材料还显示 `orchestrator/llm.py`、`orchestrator/check_status.py`、`config.example.json`、`docs/configuration.md`、`scripts/check_config.py`、agents 与 scripts 下多个调用方，以及新增的 `tests/test_llm_failover.py`。这些线索说明 failover 不是孤立函数，而是配置契约、状态检查、调用方适配和回归验证共同组成的设计。但必须谨慎：材料没有给出 provider 列表、排序字段、失败分类、重试次数或最终兜底策略。因此只能确认“有序 failover”这个方向和文件范围，不能从主题名推出完整实现。

原理逻辑

  1. 抽象边界：把不同的大语言模型服务统一成可替换的 provider 接口，调用方不直接绑定某一家服务。
  2. 有序候选链：provider 不是无序集合，而是有顺序或优先级的候选链，ordered 意味着存在选择次序。
  3. 失败时转移：只有当前 provider 不能完成调用时，才按顺序转到下一个候选，而不是一开始就无差别并发；所有候选都不可用时仍需表达失败。

具体例子

可以把它想成出门带多把钥匙：主钥匙打不开门，就按备用顺序试第二把、第三把。重点是有顺序、有备用，而不是同时把所有钥匙都插进门里。failover 也是这样：当前 provider 不能完成调用时，才按候选链往下走，而不是一开始就无差别地并发调用所有服务。再具体一点：一个学习助手要生成概念关联报告时，编排器先调用主 provider；主 provider 不能完成调用，就按配置顺序尝试备用 provider，最终把结果交给 `agents/concept_relevance.py` 或 `agents/daily_work_summary.py`，状态检查用来看当前走到哪一步，测试文件验证 failover 行为。

常见误区

  • 把 failover 等同于简单重试。重试通常是对同一个目标再试，failover 则是转向另一个候选 provider。
  • 以为 failover 就是同时问多个模型然后投票。材料只确认有序转移，没有确认并发投票。
  • 以为有 failover 就永远不会失败。如果所有候选都不可用，系统仍然需要表达失败。
  • 把 ordered 理解为所有 provider 完全等价。有序通常意味着优先级或选择顺序，但具体排序依据材料未给出。

概念关联

关联概念关系说明
配置校验与配置契约provider 选择顺序需要配置契约和校验，否则 failover 链可能在运行时才发现配置错误。

概念之间的关联

数据驱动配置与配置注册、配置校验与配置契约共享同一种工程思想：先定义一份可检查的结构，再让代码、配置、测试围绕它协作。表现层通过 schema 和配置注册读取视觉参数，LLM 编排通过配置和校验确定 provider 是否可用，资产管线则通过契约检查判断角色资产是否符合规范。有序 LLM provider 故障转移把这种契约思想推进到运行时可靠性：provider 是抽象边界，ordered 表示候选链有顺序，failover 表示当前提供方不能完成调用时按顺序转移；而配置校验、状态检查和回归测试，分别负责进入前的合法性、运行中的可观察性和行为验证。三者还共同体现了证据分层：提交主题、文件变更、测试新增都是线索，但材料没有给出的细节不能编造。

今日最值得记住的一句话

一个系统要可靠，不能只靠调用点临时判断，而要把“什么数据合法、什么配置可用、失败后往哪里走”提前设计成可检查、可测试的边界。
