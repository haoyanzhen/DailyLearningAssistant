配置文档与代码行为同步

完整讲解

配置文档与代码行为同步，可以理解为菜单和厨房做法要对齐。配置文档告诉使用者某个字段是什么意思、默认值是多少、影响哪些行为；代码行为则是系统真正读取这个字段并执行动作。如果文档写 LLM failover timeout 表示主模型失败后最多等待多久再切换，但代码没有读取这个字段，或者读取了别的字段，那么用户以为系统会遵守 30 秒，实际却可能 10 秒就切换，或者一直等待。当天提交主题是 fix: honor configured LLM failover timeout，并且 docs/configuration.md 和 orchestrator/README.md 发生变化，这说明配置项变化时，文档说明需要同步更新。核心不是写文档本身，而是让配置成为一份可验证的契约：文档说明承诺什么，代码负责执行什么，测试负责检查执行是否符合承诺。

原理逻辑

  1. 文档是配置语义的说明层，负责告诉使用者字段含义、默认值和影响范围。
  2. 代码是配置执行层，负责在调用链中读取字段并触发对应行为。
  3. 测试是配置验证层，负责把文档承诺固定成可重复检查的行为断言。

具体例子

想象一个外卖平台在页面里写配送超时 30 分钟自动赔付，但后端实际只按 10 分钟判断。用户等到 20 分钟投诉时，客服查不到赔付依据。后来页面说明、后端判断逻辑和自动化测试都改成同一个 30 分钟，问题才消失。

常见误区

  • 以为配置项写在文档里就等于系统已经支持。
  • 以为改了代码默认值就不需要改文档，导致纸面配置和实际行为漂移。

概念关联

关联概念关系说明
LLM failover timeout 配置与生效路径timeout 的含义必须先被文档清楚说明，才可能被代码正确执行。
Agent 工作流与任务编排当多个 agent 共享同一份 LLM 配置时，文档需要说明这个配置会影响哪些任务路径。

Agent 工作流与任务编排

完整讲解

Agent 工作流与任务编排，可以想象成一条流水线上的多个工位，以及负责调度的总控台。每个 agent 负责一个具体任务，比如概念相关性分析、日报发送、工作总结、知识解释、学习报告发布等；orchestrator 则负责启动流程、管理生命周期、提供共享的 LLM 调用入口。这些 agent 表面上各自独立，但它们都可能调用 LLM，也可能共享同一份 LLM 配置。当天 DailyLearningAssistant 中 agents/concept_relevance.py、agents/daily_email_send.py、agents/daily_work_summary.py、agents/knowledge_explaination.py、agents/learning_report_publish.py 以及 orchestrator/lifecycle.py、orchestrator/run_daily.py 等文件发生变化，这说明 LLM 调用配置不是某个 agent 的内部细节，而是会影响多个任务路径的编排层配置。理解这个概念的关键是：配置变化的影响范围，取决于它被放在哪一层，以及哪些任务共享这一层。

原理逻辑

  1. Agent 是任务执行单元，负责完成概念相关性、日报发送、工作总结等具体工作。
  2. Orchestrator 是调度与共享层，负责启动流程、管理生命周期，并提供统一 LLM 调用入口。
  3. 共享配置会沿编排层传播，因此一个 timeout、failover 或 provider 设置可能同时影响多个 agent。

具体例子

学校广播站里有多个节目主持人，每个主持人负责不同节目，但都共用一个总音量旋钮。如果总控台把无人应答 20 秒后自动切换备用麦克风的规则改掉了，所有节目都会受到影响，而不是只有某一个节目受影响。

常见误区

  • 以为每个 agent 都是完全独立的，改一个 agent 的脚本就只影响那个任务。
  • 以为 LLM 配置只是某个函数里的参数，和编排层无关。

概念关联

关联概念关系说明
LLM failover timeout 配置与生效路径timeout 配置需要通过编排层传递到各个 agent 的 LLM 调用路径中。
配置文档与代码行为同步agent 工作流越复杂，文档越需要说明某个配置会影响哪些任务、哪些入口和哪些失败路径。

  2. 编排层应该如何记录每次 LLM 调用来自哪个 agent、哪个任务阶段、使用了哪个 provider，以便排障和审计？
  3. 当某个 agent 不需要 failover 或需要更短 timeout 时，配置应该如何表达继承和例外，同时保持文档、代码和测试一致？

LLM failover timeout 配置与生效路径

完整讲解

LLM failover timeout 配置与生效路径，讲的是主模型调用失败或卡住时，系统最多等多久才允许切换到备用模型。failover 是备用切换，timeout 是时间上限。它不是普通的请求超时这么简单，因为它控制的是故障转移的决策边界：在 timeout 内，系统可能继续等待、重试或记录状态；超过 timeout 后，系统才应该按配置进入 failover 流程。当天提交主题是 fix: honor configured LLM failover timeout，关键在 honor，也就是真正按配置判断主模型失败后最多等多久再切换备用模型。文件分布显示 orchestrator/llm.py 发生变化，说明 LLM 编排层被调整；多个 agents/* 和 scripts/* 发生变化，说明知识解释、学习报告等生成流程可能与这条调用链相关；tests/test_llm_failover.py 发生变化，说明 failover 行为需要测试固定；docs/configuration.md 和 orchestrator/README.md 发生变化，说明配置说明和编排说明需要同步。这里基于当日材料可确认的是配置被遵守的方向，不能确认具体超时值、provider 选择策略、失败分类或实际运行效果。

原理逻辑

  1. timeout 是故障转移的时间边界，不是普通请求超时的简单别名。
  2. 在 timeout 内，系统可以继续等待、重试或记录状态；超过 timeout 后，才应进入 failover 流程。
  3. 配置要生效，必须从文档说明进入编排层读取，再传递到多个 agent 的 LLM 调用路径，并由测试固定。

具体例子

想象你打电话找客服，总机规定如果主线路 20 秒没接通，就自动转备用线路。如果总机没有真正看计时器，就会一直等主线路；如果总机看错了计时器，10 秒就转，又可能造成不必要的切换。修复 honor configured failover timeout，就是让总机真正按照配置的 20 秒来判断。

常见误区

  • 以为配置里写了 timeout 就自动生效，但代码可能读取了错误字段或根本没有读取。
  • 把 failover timeout 等同于普通请求 timeout，忽略它真正控制的是何时允许切换到备用模型。
  • 只改文档或只改某个 agent，却没有检查编排层和测试，导致不同任务路径行为不一致。

概念关联

关联概念关系说明
Agent 工作流与任务编排timeout 配置需要通过 orchestrator 传递到多个 agent 的 LLM 调用路径中。
配置文档与代码行为同步timeout 的含义、默认值和影响范围必须在 docs/configuration.md 与 orchestrator/README.md 中说明清楚。
