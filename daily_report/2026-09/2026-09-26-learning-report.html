空目录与缺失文件的状态边界

完整讲解

空目录与缺失文件的状态边界，核心是把目录是否存在、文件是否存在、文件内容是否合规看成三个不同层次的事实。目录像房间，文件像房间里的一张表格，内容合规性像表格里字段是否正确。检查系统如果只输出一个 missing 或 failed，后续处理就会混乱：目录缺失需要创建路径或检查配置；目录存在但为空可能表示产物还没生成、任务还没跑完，或者生成器没有输出；文件存在但内容不合规则需要修字段、修格式或触发人工复核。这里基于当日材料可确认的是，今天没有资产目录检查运行证据，所以这个概念只作为问题延展，不写成今天实际发生了目录检查失败。

原理逻辑

  1. 状态词必须匹配事实层次，目录、文件和内容不能互相替代。
  2. 空目录可能是正常中间态，也可能是产物未生成，需要保留可追溯状态。
  3. 结构化状态能让后续流程选择创建、等待或修复，而不是笼统失败。

具体例子

检查 roles/warrior/ 时，目录不存在输出 missing_directory，目录存在但为空输出 empty_directory，battle.json 缺少必需字段输出 invalid_field。

常见误区

  • 把目录为空直接当成文件缺失。
  • 把文件内容不合规也归到目录缺失里。

概念关联

关联概念关系说明
字段冲突时的保留旧值与待复核策略两者都要求区分不同证据层次，不能用一个状态覆盖另一个状态。
契约例外的记录载体与审计边界两者都属于契约检查中的状态表达，空目录不能被整体契约通过或失败吞掉。

  3. 目录状态字段应如何与人工复核入口连接，让 needs_review 能追溯到具体目录和文件？

多 ref unchanged 的仓库级聚合表述

完整讲解

多 ref unchanged 的仓库级聚合表述，讲的是当多个 Git ref 的历史 SHA 与当前 SHA 相同时，仓库级报告应该怎么写。ref 可以理解为仓库里的指针，比如 main、release/1.0、origin/HEAD。如果几个被监控 ref 都没有移动，只能说明这些指针没有变化，不能说明整个仓库没有任何工程进展，因为可能还有未监控分支、标签、工作区草稿、提交对象或其他仓库没有进入监控范围。这里基于当日材料可确认的是，今天多个远端仓库 ref 状态为 unchanged，但只作为无变更证据，不扩展为工程进展判断。把状态写成 unchanged 而不是 no new commits，是因为 unchanged 绑定的是历史 SHA 与当前 SHA 相同这一证据；no new commits 通常需要窗口内提交证据，可能超出 ref 元数据能证明的范围。

原理逻辑

  1. unchanged 绑定的是可比较 SHA 证据，不是窗口内提交证据。
  2. 聚合结论必须保留被监控对象范围，不能覆盖未监控对象。
  3. 仓库级状态需要区分指针未变、窗口提交无新增和工程无进展。

具体例子

监控 main、release/1.0 和 origin/HEAD，三者历史 SHA 与当前 SHA 相同，可写 monitored_refs_unchanged，不应写 repository_has_no_new_commits。

常见误区

  • 把多个 ref unchanged 直接写成仓库没有新增提交。
  • 把有限 ref 证据扩大成没有任何工程进展。

概念关联

关联概念关系说明
基线缺失时状态升级的证据门槛两者都涉及证据不足时不能升级结论，多 ref unchanged 也不能推出完整工程进展。
本地/远端引用同 SHA 的推送成功误判边界两者都要求聚合结论不超过字段可证明范围，同 SHA 只能证明指针一致，多 ref unchanged 只能证明被监控指针未变。

  2. 如何区分 monitored_refs_unchanged、no_new_commits_in_window 和 no_engineering_progress？
  3. 未监控 ref、读取失败或工作区草稿应如何进入仓库级状态，而不是被 unchanged 覆盖？

证据不足时 LLM 拒绝补全的测试边界

完整讲解

证据不足时 LLM 拒绝补全的测试边界，关注的是 LLM 产物层面的可靠性，而不是模型内部机制。LLM 很擅长生成流畅文本，但如果输入证据不足，它可能会把没看到补成没有发生，把不确定补成确定结论。因此需要设计测试边界：当输入缺少 commit SHA、ref 状态、人工确认记录等关键证据时，合格输出应该说明证据不足，给出 unknown、needs_review 或 missing_evidence，而不是生成完整日报。这里承接之前关于 LLM 输出可靠性与证据约束的讨论，但不重复模型内部机制，只聚焦测试边界。这里基于当日材料可确认的是，今天没有 LLM 生成新日报或新总结的证据，所以这个概念只作为问题延展，不写成今天发生了 LLM 输出事故。证据引用字段的作用是让每条结论都能追溯：evidence_type 说明证据类型，evidence_id 指向具体 commit、ref 或人工确认记录，confidence 表示置信程度，forbidden_inference 用来标记哪些推论被禁止。

原理逻辑

  1. 生成式输出也必须受证据约束，流畅文本不等于工程事实。
  2. 测试边界要验证模型在关键证据缺失时拒绝补全完整结论。
  3. 证据引用字段让结论可追溯，也能识别越界推论。

具体例子

输入只有某个仓库今天好像没变化，没有 remote_ref_baseline_sha 和 remote_ref_current_sha，合格输出应写证据不足，无法判断 unchanged。

常见误区

  • 认为 LLM 生成流畅总结就代表事实成立。
  • 认为最终结论碰巧正确，就可以省略证据引用。

概念关联

关联概念关系说明
自生成日报提交的监控隔离两者都要求特殊来源或证据不足时不补全事实，自生成提交需要隔离，LLM 证据不足时需要拒绝生成完整结论。
基线缺失时状态升级的证据门槛两者都强调低证据状态下的保守表达，基线缺失时不升级状态，LLM 证据不足时不补全结论。
