未完成发布不等于对象库损坏：中间态与真实损坏在完整性检查中的分类

Pack/Idx Incomplete Publish vs Corruption

pack 未配 idx，常是发布没走完；要等校验失败证据出现才能说损坏。

核心要点

  • Git 先发布 pack 正文，再发布 idx 索引，两步之间崩溃会留下 pack 在而 idx 缺失的中间态。
  • 未完成发布是发布流程停在半路，不等于内容损坏；真实损坏是对象无法解析或按已发布引用找不到。
  • 完整性检查应以“被正式引用指向的对象能否可靠解析”为准，而不是机械地要求 pack/idx 成对。
  • 对所有不对称一律报损坏会形成误报，把维护工具的注意力从真正数据丢失引到可修复的半成品上。

Delayed Old Pack Retirement by Reader Lifecycle

精读文章 · 计算机科学 / 软件工程

未完成发布不等于对象库损坏：中间态与真实损坏在完整性检查中的分类

完整讲解

Git 会把对象压缩进 pack 文件保存，pack 是正文，idx 是配套索引，负责告诉读者对象在 pack 里的位置。为了不让读者看到半份文件，Git 采用分步发布：先让 pack 出现在正式名字下，再发布对应的 idx。如果程序在两步之间崩溃，磁盘上就可能留下“正文在、索引还没到”的状态。这种状态看起来不整齐，却不等于内容损坏。真实损坏是对象内容已经无法解析，或者按已发布引用找不到它声称的对象；未完成发布只是发布动作停在半路，通常还能通过补齐索引或清理残留来恢复。因此，完整性检查的第一判断不应是“文件是否成对”，而是“被正式引用指向的对象还能不能可靠解析”。把未完成发布一律报成损坏，会造成误报；误报和漏报一样会误导后续修复动作。

原理逻辑

  1. Git 分两步发布 pack 与 idx：先让 pack 在正式名字下可见，再配 idx。
  2. 两步之间的崩溃产生 pack/idx 不成对，这是发布动作未完成，而非对象数据损坏。
  3. 完整性检查的判据是正式引用能否解析出可靠对象；用 index-pack 可从完整 pack 重建缺失 idx。

具体例子

假设崩溃后对象目录中出现了 pack-abc.pack 却没有 pack-abc.idx。若用 git index-pack pack-abc.pack 能成功扫描整个 pack、校验通过并生成 idx，说明它只是完成了一半的发布，不是损坏；若校验过程中出现解压失败或内容哈希不匹配，那才是真实损坏。

常见误区

  • 看到 pack 文件没有对应 idx，就认为仓库已经损坏。
  • 所有不对称都被报成损坏，会让维护工具忽略真正的数据丢失而聚焦在可修复的半成品上。

概念关联

关联概念关系说明
没有“删除后仍可读”时，旧 pack 如何延迟让位互补关系：未完成发布看新文件集还没补齐的窗口，旧 pack 让位看旧文件集还不能立即消失的窗口，两者共同覆盖一次 pack 替换的前后半场。
仓库格式的版本门槛同构关系：格式声明也是一种发布物，不能把半套新规则提前暴露给仍按旧规则运行的读者。

精读文章 · 计算机科学 / 软件工程

没有“删除后仍可读”时，旧 pack 如何延迟让位：从 unlink 到按读者生命周期删除

完整讲解

Linux/unix 中的 unlink 并不是“把文件从世界上抹掉”。它的准确效果是删掉目录项；如果还有进程已经打开这个文件，文件数据仍由 inode 保留，直到最后一个文件描述符关闭。正因如此，Git 在替换 pack 时可以先让新 pack 生效，再 unlink 旧 pack；已经打开旧 pack 的并发读者不会断粮。但“删除后仍可读”并不是所有平台都提供。Windows 常会阻止删除正在被打开的文件；某些网络文件系统也不保证这个语义。如果平台缺少这种能力，旧 pack 的回收就必须延迟：先发布新包，让新读者使用新包；旧读者继续读旧包；等到所有可能打开旧包的文件描述符关闭后，才能真正回收旧文件。于是，删除不再是调用一次 unlink 的瞬时动作，而是围绕“读者生命周期”安排的过程。

原理逻辑

  1. unlink 只是删除目录项；文件数据是否常驻取决于是否仍有进程持有打开的文件描述符。
  2. 支持删除后仍可读的平台可以即时 unlink 旧 pack；不支持的平台需等待旧读者完全退出。
  3. 因此旧 pack 删除策略要从一次性 unlink，转化为基于读者生命周期的延迟回收队列。

具体例子

一个仓库正在 repack，新的 pack-new.pack 已经可供新连接使用；但一个早先启动的 git archive 进程仍然打开了旧 pack-old.pack。在 Linux 上，gc 可以直接 unlink 旧包，archive 进程继续读旧 inode；在不支持“删除后仍可读”的文件系统上，gc 若立刻 unlink，archive 可能在读取中途找不到数据。正确顺序是等 archive 进程结束后再真正删除旧文件。

常见误区

  • 认为 rm 就等于数据立刻销毁；在 Linux 上 rm 只删名字，已打开文件仍可通过描述符读取。
  • 认为新包一发布，旧包就必须马上删除才算干净；在不支持删除后仍可读的平台，过早 unlink 会导致并发读者失去数据源。

概念关联

关联概念关系说明
未完成发布不等于对象库损坏互补关系：一个处理新文件集还没发布完整的窗口，一个处理旧文件集仍在被读的窗口；两者合成一次替换的完整生命周期。
同一 ref 的 ok/ng 冲突类比关系：处理旧包要追踪真正使用旧文件的读者生命周期，处理推送状态要追踪真正产生状态行的逻辑命令身份；两者都不能被表面名字或到达顺序欺骗。

精读文章 · 软件工程 / 计算机科学

同一 ref 的 ok/ng 冲突：为什么不能用“最后一条”而要绑定逻辑命令

完整讲解

推送时，服务端会为每个 ref 返回状态行，比如 ok 或 ng。由于钩子或批量报告的存在，同一个 ref 有可能出现多行状态：先出现 ng，后来又出现 ok，或者反过来。客户端不能把这些行看成普通时间线，更不能认为“最后到达的才是结论”，因为协议并不保证状态行的到达顺序。更深层的问题是：这些状态行到底是对哪一次更新命令的回答？一个更新动作的身份不能只用 ref 名字代表，还要包含客户端声称的期望旧值和新值；ref 名、期望旧值、新值合在一起，才构成同一次逻辑命令。只有在同一逻辑命令上出现明确的 ok，这个 ref 才能被算作成功；一旦 ok 与 ng 互相冲突，安全策略不是挑一条看起来更好的，而是不宣告成功。这样可以避免把不确定状态误当成可编程的成功结果。

原理逻辑

  1. 协议不保证状态行的到达顺序，因此“最后到达的才是结论”不成立。
  2. 逻辑命令的身份由 ref 名 + 期望旧值 + 新值共同构成，单靠 ref 名不足以定位是哪一次更新。
  3. ok 与 ng 在同一逻辑命令中冲突时，客户端应保守处理：不宣告成功，避免把不确定当作确定。

具体例子

客户端发出一次更新：refs/heads/main 的旧值是 abc123，新值是 def456。随后状态报告中出现 ok refs/heads/main 和 ng refs/heads/main update hook declined 两行。因为两条都可能属于同一个 ref 的同一逻辑命令，客户端不能因为 ok 在那里就不管 ng；它应当把该 ref 视为没有被明确确认成功，而不是当作成功继续执行。

常见误区

  • 认为状态行先来的是旧消息、后来的是新消息，所以最后一条一定最准确。
  • 认为同一个 ref 名字出现多个状态，就都可以当作同一次更新的证据。
  • 认为只要出现过 ok 就可以宣告成功；但当同一逻辑命令也有 ng 时，证据冲突，不应宣告成功。

概念关联

关联概念关系说明
退出码压缩上下游关系：单 ref 的冲突状态先合并为成功或不成功，后续才能把多 ref 的部分成功压缩成进程退出码；单 ref 若含糊，整体退出码也会失真。
没有“删除后仍可读”时，旧 pack 如何延迟让位类比关系：处理旧包时要追踪真正打开文件的读者生命周期，处理推送状态时要追踪真正产生状态行的逻辑命令身份；两者都不能被表面名字或到达顺序欺骗。
