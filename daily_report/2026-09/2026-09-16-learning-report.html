读取失败不等于未变化

完整讲解

我们可以把远端变化检测想成一次对答案：先拿出上次记录的 SHA，再读一次当前 SHA，然后比较。成功读取且两个 SHA 相同，才是 unchanged；成功读取且两个 SHA 不同，才是 changed；如果当前 SHA 根本没读到，就只能标成 failed 或未知。failed 不是第三种“变化”，而是“比较需要的一端缺失了”。为什么不能把 failed 当 unchanged？因为 unchanged 要求你确实看到了当前值和历史值相等，而网络失败、超时、凭据不可用时，你根本没有看到当前值。看不到，只能说不确定，不能说不存在变化。

原理逻辑

  1. 远端变化检测需要两个可比较端点：上次记录的 SHA 与本次读取的当前 SHA。
  2. 只有成功读取当前 SHA，才能与历史 SHA 比较并得出 unchanged 或 changed。
  3. 读取失败意味着比较所需的一端缺失，因此结果只能进入 failed 或未知，而不是第三种“变化”。

具体例子

public-library 通过 ssh_git 成功读取 refs/heads/main，历史 SHA 与当前 SHA 相同，所以可以写 unchanged；而 cannbot-skills 的 ref 读取 failed，当前 SHA 未读取到，就不能写 unchanged，只能写 failed 或未知。

常见误区

  • 把“没读到”当成“没变化”，或把网络失败、超时、凭据问题直接写成 unchanged。
  • 报告会把未知伪装成确定，导致真实更新可能被静默漏掉。

精读文章 · 软件工程 / 计算机科学

首次观测基线与旧基线保留

完整讲解

基线就是你用来比较的参照点。第一次看到某个远端 ref 时，系统只应该记录它的 SHA，把它当作以后比较的起点，而不是宣布“这里刚刚发生了变化”。变化至少需要两个可比观测：上一次的 SHA 和这一次的 SHA。首次观测只有一次，所以不能构成变化事件。另一个关键点是，读取失败时不能把旧基线删掉或覆盖成空值。旧基线是未来成功读取后还能比较的基础；如果失败一次就清空，下次即便读到新值，也不知道它相对于什么发生了变化。保留旧基线，同时把当前状态标成 failed 或未知，才是更安全的设计。

原理逻辑

  1. 基线是用来比较的参照点，没有历史 SHA 就无法判断 unchanged 或 changed。
  2. 变化事件要求至少两个可比观测，首次观测只有一次，因此不能升级为变化。
  3. 失败时保留旧基线，下一次成功读取后仍能知道相对什么发生了变化；清空基线会破坏未来比较能力。

具体例子

某个 ref 的历史 SHA 是 A。今天首次监控看到 A，只记录 A 作为基线；明天读到 A，状态是 unchanged；明天读到 B，状态才是 changed；明天读不到，则状态是 failed，并继续保留 A 作为旧基线。

常见误区

  • 把“第一次看到某个 ref”误报成“新增提交”。
  • 读取失败时用空值覆盖历史 SHA，导致下一次成功读取也失去参照；还有人把基线更新本身当成变化事件。

只读远端监控的访问路径与凭据边界

完整讲解

只读远端监控通常用 git ls-remote 这类命令，只读取 ref 指针，不 clone、不 fetch，也不下载提交对象、文件树或工作区内容。它的好处是副作用小、权限小、观测面清晰。但能不能读到 ref，不只取决于远端仓库本身，还取决于访问路径和凭据边界。http_git 和 ssh_git 是两条不同的路：http_git 可能遇到 network_failed 和 30 秒超时；ssh_git 成功通常依赖本机 SSH key 或 SSH agent。状态文件不应记录密钥，HTTP(S) URL 里的用户名、token、密码也要脱敏。只读最小权限意味着监控只需要读 ref 元数据，不需要写权限，也不需要下载完整历史。这样既降低泄密风险，也避免把访问失败误判成仓库变化。

原理逻辑

  1. 能否读到 ref，不只取决于远端仓库状态，还取决于访问路径与凭据是否可用。
  2. http_git 与 ssh_git 的失败原因不同；ssh_git 成功通常依赖本机 SSH key 或 SSH agent。
  3. 只读最小权限限制证据范围：ls-remote 只能证明 ref 指针状态，不能证明提交详情；凭据脱敏保证排障时不泄露秘密。

具体例子

public-library 通过 ssh_git 读取 refs/heads/main 成功，历史 SHA 与当前 SHA 相同；同一批里的 http_git 仓库 30 秒超时，只能记录 failed 和 network_failed，不能记录 changed 或 unchanged。

常见误区

  • 以为 ssh 成功就等于有写权限；把 token 或密码写进日志。
  • 认为 ls-remote 成功就能看到提交详情；把 http_git 失败直接归因于仓库没有变化或仓库损坏。

概念关联

关联概念关系说明
读取失败不等于未变化访问路径与凭据边界直接决定 failed 是否出现，因此失败不能被解释成没有变化。
首次观测基线与旧基线保留只读最小权限限制证据范围，失败时应保留旧基线并标记未判定，而不是覆盖或宣告变化。
