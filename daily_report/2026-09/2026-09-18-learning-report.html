提交窗口与时间归属

完整讲解

提交窗口与时间归属解决“某个变化能不能算作昨天完成”的问题。检查窗口可以想象成一段监控录像的时间范围：只有在录像里拍到的动作，才能被确认发生在这一段时间内。Git 提交记录带有时间信息，可以作为较可靠的时间锚点；如果一次提交落在检查窗口内，就可以确认“这个窗口内发生了一次提交”。但工作区里的未暂存修改、未跟踪文件，更像桌上正在写的草稿：它只能证明现在草稿在那里，不能证明草稿是昨天下午写的。因此，当天 tiny-sea-war 没有窗口内提交，但存在大量未暂存和未跟踪文件时，只能写成“当前工作区存在待确认变化线索”，不能写成“昨天完成了这些工作”。这个概念的关键不是判断工作有没有价值，而是区分“有可确认提交”和“只有现场痕迹”。

原理逻辑

  1. 提交记录提供时间锚点，可把事件归入检查窗口。
  2. 工作区状态描述当前现场，不自动提供历史时间归属。
  3. 无窗口内提交只能说明证据不足，不能证明没有工作，也不能证明工作完成。

具体例子

tiny-sea-war 在检查窗口内没有提交，但存在未暂存修改和未跟踪文件，只能写“当前工作区存在待确认变化线索”；DailyLearningAssistant 在窗口内有 1 个已确认提交，修改 scripts/send_daily_email.py，可确认窗口内有一次邮件脚本维护提交，但具体 diff 和 timeout 类型仍不可确认。

常见误区

  • 看到文件存在、文件被修改或工作区有变更，就认为这些工作一定发生在检查窗口内。
  • 把“没有提交”理解成“没有工作”。

概念关联

关联概念关系说明
工作区、暂存区与未跟踪文件的状态分类工作区状态只能描述当前现场，不能自动证明时间归属。
远端 ref 指针一致性ref 指向同一 SHA 只能说明指针位置，仍需窗口内提交确认事件发生时间。
状态分类与证据边界为证据边界提供时间维度，帮助区分已确认提交、待确认工作区线索和不可确认内容。

远端 ref 指针一致性

完整讲解

远端 ref 指针一致性讲的是多个 ref 当前是否指向同一个 SHA。ref 是命名指针，比如 main、HEAD、origin/main、origin/HEAD；SHA 是指针指向的提交对象标识。当天 DailyLearningAssistant 中这些指针都指向 3a82746，说明它们当前指向同一个提交。这个事实可以确认，但它只能证明“指针位置一致”，不能证明“刚刚发生推送”“同步过程成功”或“远端刚刚更新”。指针一致是状态事实；推送、同步、发布是过程事实。要确认过程，需要提交窗口、推送日志、远端接收记录等更强证据。

原理逻辑

  1. ref 与 SHA 分离：ref 是名称，SHA 是对象标识。
  2. 比较多个 ref 的当前 SHA 只能得到状态一致性。
  3. 过程发生需要时间、日志、接收记录等额外证据。

具体例子

DailyLearningAssistant 中 main、HEAD、origin/main、origin/HEAD 都指向 3a82746。可确认的是：这些 ref 当前指向同一提交。不可确认的是：是否刚刚执行 push、push 是否成功、远端监控是否检测到变化、仓库其他分支是否变化、以及这次指针一致是否由某次同步导致。

常见误区

  • 本地 main 与 origin/main 指向同一 SHA，就认为已经推送成功或远端一定刚刚更新。
  • 把被监控 ref 一致当成整个仓库内容完全一致。

概念关联

关联概念关系说明
Git 远端引用与 SHA 标识ref 是命名指针，SHA 是指针指向的对象标识。
提交窗口与时间归属指针一致只能说明当前状态，不能替代窗口内提交对事件时间的证明。
状态分类与证据边界必须标为“指针位置一致”，而不是“推送过程已确认”。

超时控制与调用可靠性

完整讲解

超时控制与调用可靠性讲的是给外部调用设置等待上限。脚本调用外部服务时，比如发送邮件、访问网络或调用模型，如果不设 timeout，就可能一直等待，占住资源，让调用方不知道是慢、坏还是已经放弃。timeout 把“无限等待”变成“最多等这么久”，超时后系统可以报错、重试、降级或记录日志。它不是简单配置项，而是可靠性边界：保护调用方不被长期阻塞，限制失败传播，并让资源占用可预测。基于当日材料可确认的是：DailyLearningAssistant 在检查窗口内有提交，提交主题包含 timeout，变更文件是 scripts/send_daily_email.py，因此可以确认“邮件发送脚本存在超时相关维护方向”。不可确认的是：timeout 具体是网络超时、任务超时还是 LLM 模型调用超时，也没有 diff 证明其实现、重试或 failover 行为。

原理逻辑

  1. 外部调用需要等待上限，避免调用方无限阻塞。
  2. 超时是可靠性边界，不是失败原因本身。
  3. 确认 timeout 类型必须依赖 diff、日志、测试或调用链证据。

具体例子

假设 send_daily_email.py 发送每日邮件时调用 SMTP 服务，并设置 10 秒网络超时。10 秒内收到响应则继续；超过 10 秒则记录“发送超时”，脚本可以退出或重试。但当天材料没有 diff，因此不能确认是否真的是 SMTP 网络超时，也不能确认是否存在重试、降级或模型调用。

常见误区

  • 看到提交主题有 timeout，就断定它是 LLM failover timeout。
  • 认为 timeout 越短越好。

概念关联

关联概念关系说明
脚本化邮件发送流程邮件发送脚本可能调用外部服务，timeout 用于限制等待时间。
LLM 调用超时与失败边界当前只能确认提交主题提到 timeout，不能确认它是模型调用超时。
提交窗口与时间归属timeout 线索必须来自检查窗口内已确认提交，才能作为当天可确认方向。
