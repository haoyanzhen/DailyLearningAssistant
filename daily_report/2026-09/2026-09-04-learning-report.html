SHA-256 对象格式与哈希迁移后的对象寻址空间

SHA-256 object format and object address space after hash migration

更大的门牌号空间只是基础，保持一致的门牌规则才是迁移的真正难点。

核心要点

  • Git 用内容摘要作为对象 ID，摘要位数决定整个寻址空间，SHA-1 为 2^160，SHA-256 为 2^256。
  • 对象格式是仓库级属性：使用 SHA-256 时对象 ID、父提交指针与校验和都按 256 位计算，同一对象库不能混用两种算法。
  • SHA-256 只是把碰撞概率下界从 2^80 量级提升到 2^128 量级，并不是绝对不碰撞；哈希迁移也不是简单加长旧 ID，而是要重建统一的新对象库。

Two corruption signals on pack verification: inflate failure vs content hash mismatch

核心要点

精读文章 · 数学 / 计算机科学

SHA-256 对象格式与哈希迁移后的对象寻址空间

完整讲解

Git 用固定长度的哈希为对象分配 ID，这个 ID 不是内容本身，而是把任意长度内容压缩成固定长度摘要。摘要位数决定了门牌号空间：SHA-1 输出 160 位，约提供 2^160 个门牌号；SHA-256 输出 256 位，约提供 2^256 个门牌号。两套空间的碰撞难度不同，SHA-1 的生日界约在 2^80 量级，SHA-256 约在 2^128 量级。仓库必须声明自己使用哪一种对象格式。使用 SHA-256 的仓库，对象 ID、树对象条目、父提交指针以及校验和都按 SHA-256 计算，对象 ID 写成 64 个十六进制字符。选择不是局部属性，而是整仓库格式属性。迁移到 SHA-256 不是给旧仓库逐个把 ID 拉长，而是从一个统一的 256 位门牌号体系重新建立对象库。已初始化为 SHA-1 的仓库不能在同一对象库里部分使用 SHA-256，因为同一份地址簿不能同时采用两套互不兼容的编号规则。

原理逻辑

  1. 对象 ID 是内容摘要，摘要输出长度决定寻址空间大小，SHA-256 让空间从 2^160 扩大为 2^256。
  2. Git 把对象格式当作仓库级属性，任何对象 ID 的生成和解析必须与仓库声明一致。
  3. 哈希迁移需要整体切换对象格式，不能部分混用；大空间只是降低碰撞风险的手段，不是安全证明。

具体例子

用 SHA-1 初始化时，对象 ID 是 40 个十六进制字符；用 git init --object-format=sha256 初始化后，对象 ID 是 64 个十六进制字符。把一个 SHA-1 对象文件硬塞进 SHA-256 仓库，Git 不会把它当成同一地址空间里的合法对象。

常见误区

  • 认为 SHA-256 能绝对保证不同对象永远不会得到同一 ID；实际上它只是把碰撞概率降到极低，现实规模下几乎不可能找到一个碰撞。
  • 把哈希迁移理解成简单地把 SHA-1 对象 ID 加长；实际需要按新对象格式统一计算和解析对象，同一仓库不能混用 SHA-1 与 SHA-256 对象。

概念关联

关联概念关系说明

delta 对象的外部依赖对象 ID 只说明目标内容的身份，不说明内容是以完整快照还是 delta 配方存在；ID 正确与内容可还原并不等价。

精读文章 · 计算机科学 / 软件工程

压缩流解压失败与内容哈希失配：pack 验证路径上的两类损坏信号

完整讲解

pack 对象读出来之前，通常不知道真实内容，它先表现为压缩数据，经过解压和校验。Git 验证路径像一个两关流水线：第一关 zlib 解压，第二关内容哈希比对。压缩数据可能因为磁盘坏道、传输截断或写入出错而损坏，zlib 解压器无法按规则继续读，此时 Git 在解压中途失败，报错指向数据流异常。这类损坏意味着压缩包已经破损到连原始字节都取不回来。另一类损坏发生在解压成功之后：zlib 把字节还原出来，但内容未必属于仓库声称的那个对象。Git 会把解压出的对象内容连同类型和长度按对象格式重新计算哈希，再与预期对象 ID 比较；不一致就说明内容层的字节与号牌不符，字节能被读出，但不是它所自称的对象。这个区别决定维修方向：前者需要找回原始压缩数据或重新获取对象，后者说明数据虽可读但内容错位，必须用正确副本覆盖。

原理逻辑

  1. 每个对象先以压缩流形式存在，读取时第一步必然是 zlib 解码。
  2. 解码失败意味着压缩流已被破坏到无法还原原始字节，属于第一类损坏。
  3. 解码成功只是数据可读，还需要按对象格式重算哈希并与对象 ID 比较，不一致时属于内容层失配。
  4. 两类损坏在验证路径上位置不同，因此排查与修复策略应分别对待。

具体例子

以登记内容为 hello world 的 blob 为例：如果压缩数据损坏，解压器可能在读到第 5 个字节时报数据流错误，到不了哈希比较；如果解压成功却得到 hello world（多一个空格），重新计算得到的哈希就会与预期对象 ID 不匹配。

常见误区

  • 认为 zlib 解压成功对象就验证通过；实际上解压成功只说明压缩流结构完整，还需要内容哈希与对象 ID 匹配。
  • 把所有 Git 错误都归为对象损坏，不区分损坏发生在压缩层还是内容层；实际上两类信号在验证路径上的位置和修复策略都不同。

概念关联

关联概念关系说明
SHA-256 对象格式与哈希迁移后的对象寻址空间对象 ID 来自内容哈希，检测内容哈希失配正是用这个 ID 去验证解压出来的字节；如果哈希算法或对象格式不一致，同一段内容会得到不同 ID，比对就无法正常进行。
delta 对象的外部依赖即使对象通过 zlib 解压和内容哈希校验，也只能说对象自身的字节可信；若它是 delta 形式，还要看依赖的基对象是否完整，这会把问题推向 delta 依赖层。

delta 对象的外部依赖：基对象缺失时数据补全的边界

完整讲解

Git 为节省空间不总是把每个对象存成完整快照。当多个版本差异很小时，一个对象可能被存成 delta 对象：它不直接保存完整内容，而是保存一组指令，告诉 Git 如何从另一个对象——基对象——生成当前对象。指令加上基对象里的原始字节，才能还原真实文件内容。由于打包方式不同，delta 基对象可能和它放在同一个 pack 中，也可能位于 pack 之外。普通自包含 pack 会尽量让包内 delta 的基对象也在包内，包可以独立使用；但 thin pack 是网络传输时的瘦包，为了少传字节允许引用接收方可能已有的外部基对象，接收方必须先补全缺失的基对象，thin pack 才能正常使用。所以判断对象是否能完整还原，不能只看对象自身的字节是否完好，还要看从它开始向上追溯的整条 delta 链。一个对象文件存在只说明它的字节占据可寻址位置；如果需要的基对象已经缺失，它依然处于不可还原状态。Git 给出的信息会指向缺少基对象而非压缩流损坏，因为问题不在当前对象的物理字节，而在逻辑依赖断掉了。

原理逻辑

  1. Git 用 delta 压缩历史版本，把完整快照替换成生成指令加基对象。
  2. 基对象可能在包内也可能在包外，thin pack 会引用接收方未收到的外部对象。
  3. 对象自身字节完好不足以代表可还原，必须检查自当前 delta 对象向上的整条链。
  4. 基对象缺失时的错误指向是逻辑依赖断裂，而不是当前对象压缩流损坏。

具体例子

仓库有两个版本的 note.txt：版本 1 是 100 字节完整内容，版本 2 只改了一句，打包时版本 2 被存成 delta：前半部分从版本 1 复制并插入新字节，后半部分继续从版本 1 复制。版本 2 的对象 ID 已在索引里，但如果保存版本 1 的旧 pack 被删除，Git 再去还原版本 2 时就会因为找不到基对象而失败。这不是版本 2 压缩流坏了，而是版本 1 已经从依赖链中消失。

常见误区

  • 一看到对象文件还在就认为内容一定可用；遇到 delta 对象时，文件只是生成配方，配方所依赖的基对象消失后内容依然拼不回来。
  • 以为普通 pack 的校验和能防范这种缺失；校验和只能检测包内字节是否变化，而基对象可能处于另一个 pack、另一个对象库，甚至是被 repack 删除的过期包中。

概念关联

关联概念关系说明
压缩流解压失败与内容哈希失配概念二判断对象自身字节是否通过解压与内容哈希，而 delta 基对象缺失是自身没问题但依赖链断裂的另一种损坏，不能靠重算当前对象哈希解决。
