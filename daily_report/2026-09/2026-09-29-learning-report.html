战斗帧布局与 HUD 控制区/海洋视口分离

完整讲解

可以把战斗界面想象成一间教室：海洋视口像黑板，用来显示舰船、战场和运动画面；HUD 控制区像讲台旁的操作面板，用来显示船速、弹药、暂停和加速等控制信息。战斗帧布局先规定整个战斗界面由哪些区域组成，再给每个区域划定边界。HUD 控制区与海洋视口分离，就是不让操作面板和战场画面绑死在一起：改按钮位置时不会破坏海洋画面，调整视口大小时也不会让控制区错位。这里基于当日材料可确认的是提交标题、文档路径和测试路径，说明项目正在把战斗界面拆成可约束的区域；不能确认具体像素、渲染算法或性能实现。

原理逻辑

  1. 先定义帧结构，再拆分区域，让界面有稳定边界。
  2. HUD 与海洋视口分离后，表现层职责更清晰，减少互相影响。
  3. 用布局测试约束区域，使界面变化可被验证。

具体例子

假设战斗界面顶部是 HUD 控制区，中央是海洋视口，底部是暂停、加速和回放控制；布局测试可以检查顶部 HUD 不超过指定高度，中央视口不被控制按钮遮挡，窗口缩放时控制区仍留在顶部，海洋视口仍保留足够显示区域。

常见误区

  • 把 UI 分离理解成只是把按钮挪个位置。
  • 只关注视觉排列，忽略职责边界和可测试性。

概念关联

关联概念关系说明
战斗帧布局定义了界面区域，HUD 控制区与海洋视口分离是这种区域拆分的具体表现。
UI 布局测试让战斗帧布局的约束从文档描述变成可执行检查。
Godot/GDScript 分层脚本结构presentation 层适合承载 HUD、视口和战斗帧布局相关脚本。

继续深入问题

  3. 当表现层布局变化时，如何避免把界面改动误写成战斗规则变化？

数据驱动配置与平衡参数

完整讲解

如果舰船耐久、武器射程、战斗公式参数都写死在脚本里，每次调整平衡都要改代码，容易把设计调整和程序逻辑混在一起。数据驱动配置的思路是：把舰船、武器、公式等参数外置到 JSON 数据文件中，例如 data/ships/*.json、data/weapons/*.json、data/formulas/combat_formulas.json，并用构建脚本维护这些数据。代码只负责读取数据并执行规则，这样设计者调整参数时，不必深入修改核心脚本。这里基于当日材料可确认的是数据文件路径、构建脚本路径和提交标题中的 balance 线索；不能确认具体数值、公式内容、变量、约束或平衡结果。combat_formulas.json 与 combat_formula_design.md 只能作为战斗公式数据化的候选线索。

原理逻辑

  1. 参数与逻辑分离，让平衡调整不直接侵入核心代码。
  2. 数据文件需要 schema 约束字段、类型和含义。
  3. 构建脚本和测试共同保证数据可维护、可验证。

具体例子

假设某艘舰船的耐久、装填时间、射程放在 ship.json，某武器的伤害、射速、射程放在 weapon.json；调整平衡时，只改 JSON 中某艘舰船的耐久或某武器的伤害，然后运行构建脚本和测试，不需要修改 battle_session.gd 的核心战斗逻辑。

常见误区

  • 以为数据驱动只是把数字放到文件里。
  • 看到 combat_formulas.json 就认为已经确认了数学公式。

概念关联

关联概念关系说明
数据 schema 契约约束 JSON 字段、类型和含义，让读取稳定。
战斗会话状态协调读取舰船、武器和公式数据时，schema 决定它能稳定依赖哪些字段。
战斗公式数据化combat_formulas.json 指向公式外置，但当天未确认具体公式内容。

  3. 在只有文件路径和提交标题时，如何把数据驱动配置写成可确认概念而不是具体公式事实？

模拟聚合与报告输出

完整讲解

一场战斗运行过程中会产生很多事件：舰船移动、开火、命中、损伤、沉没、战斗结束等。battle_recorder.gd 可以理解为记录员，把运行中的战斗状态记录下来；simulation_aggregator.gd 可以理解为统计员，把零散记录汇总成指标；simulation_report_writer.gd 可以理解为报告员，把统计结果写成可阅读或可机器读取的报告。这条链路把一场战斗从运行过程转化为可分析数据，再转化为可追溯报告。在 Godot/GDScript 分层脚本结构中，infrastructure 层适合承载这类模拟、记录、报告能力，而 application 层的 battle_session.gd 负责协调战斗会话。这里基于当日材料可确认的是这些脚本路径和记录—聚合—报告链路线索；不能确认具体指标名称、采样频率、报告格式、聚合算法或运行时性能。

原理逻辑

  1. 先记录事件，再聚合指标，最后输出报告，形成分析管道。
  2. 聚合需要定义指标、分组方式和汇总规则，不能只打印日志。
  3. 报告可作为验证证据，支撑回归测试、文档状态和项目复盘。

具体例子

假设一场战斗记录包含舰 A 开火、舰 B 被命中、舰 B 沉没等事件；聚合器可以按舰船统计被命中次数，按战斗统计平均存活时间或战斗结束原因；报告写入器把结果写成报告，供回归测试或项目状态文档引用，说明某次行为调整是否被检查。

常见误区

  • 以为模拟聚合只是把日志打印出来。
  • 以为报告输出只是展示结果，忽略其作为验证证据的作用。

概念关联

关联概念关系说明
战斗会话状态协调产生运行状态和记录，模拟聚合与报告输出基于这些记录生成分析结果。
回归测试与验证状态模拟报告可作为证据，说明某类行为是否被检查。
Godot/GDScript 分层脚本结构infrastructure 层适合承载模拟、记录、报告等基础设施能力。
