精读文章 · 计算机科学 / 软件工程

成功读取与 unchanged 的证据条件

完整讲解

在 Git 远端监控里，unchanged 不是一个随口可写的状态，而是一个需要证据支撑的结论。要把某个 ref 写成 unchanged，至少需要三件事同时成立：第一，这次成功读到了当前 ref 指向的 SHA；第二，系统里有历史基线 SHA 可以比较；第三，当前 SHA 和历史 SHA 相同。如果这次网络失败、权限失败或命令失败，系统只是没读到当前 SHA，不能说明远端没有变化，只能写成读取失败或未知。如果第一次看到某个 ref，也没有历史 SHA，只能写成首次建立基线，不能写成新增变化。这里的 unchanged 更准确的含义是：成功读取后，历史 SHA 与当前 SHA 相同。这个概念的核心不是 Git 命令本身，而是证据链：没有完整证据，就不能把未知写成稳定。

原理逻辑

  1. ref 是名称到 SHA 的指针，只读监控先要成功读取当前指针位置。
  2. 历史基线提供比较参照，没有历史 SHA 就没有 unchanged 或 changed 的判定基础。
  3. 证据不完整时，状态应降级为读取失败、未知或首次建立基线，避免把未知误判成稳定。

具体例子

假设监控系统昨天记录 origin/main 的 SHA 是 A。今天通过只读方式成功读取 origin/main，得到当前 SHA 也是 A，那么可以写成 unchanged。如果今天读取失败，报告应写成 read_failed 或 unknown，而不是 unchanged。如果今天成功读取到 B，则可以写成 changed，但 changed 也只是指针变化线索，不自动等于已下载提交详情。

常见误区

  • 把这次没读到或没看到新提交直接当成 unchanged。
  • 把历史 SHA 与当前 SHA 相同理解成检查窗口内一定没有提交、推送或文件内容变化。

概念关联

关联概念关系说明
Git 远端引用与 SHA 指针比较对象是 ref 指向的 SHA，而不是提交对象或文件内容。
基于历史基线的变更检测只有成功读取当前 SHA 后，历史 SHA 与当前 SHA 的比较才有意义。
Git 工作区状态与未提交变更远端 unchanged 不能覆盖本地工作区存在未提交线索的事实。

继续深入问题

  1. 如果一次读取成功但历史基线缺失，报告应该输出 baseline_created 还是 unknown，为什么？
  2. 当历史 SHA 与当前 SHA 相同时，如何设计字段同时表达 unchanged 和 changed 的置信等级？
  3. 如果读取失败后重试成功并读到不同 SHA，应如何标注变化发生的时间窗口和证据等级？

Git worktree 与多工作区状态归属

完整讲解

Git 仓库不一定只对应一个工作区。一个仓库可以有主工作区，也可以用 worktree 创建多个工作区，每个工作区都像同一份档案库的不同办公桌。每个工作区有自己的文件现场，也可能绑定不同的分支 tip。因此，判断哪里发生了变化不能只看仓库名，而要看具体 worktree 路径、分支 tip、未暂存修改、未跟踪文件和检查窗口。当天 tiny-sea-war 的 main worktree 在 b5672c2c7f88 上存在未暂存修改和未跟踪文件，但检查窗口内提交数为 0。这个事实说明：当前工作区有差异，但这些差异不能可靠归属到目标日期，也不能写成已提交完成的工作。这里基于当日材料可确认的是：main worktree 存在待确认变化线索，且 worktree 状态需要与分支 tip 和工作区路径一起理解。

原理逻辑

  1. 仓库名只是容器，真正状态现场在 worktree 路径中。
  2. 分支 tip 决定已提交历史位置，未暂存、未跟踪文件决定当前草稿差异。
  3. 检查窗口决定时间归属，窗口内提交为 0 时，工作区差异不能可靠归属到目标日期。

具体例子

tiny-sea-war 的 main worktree 当前 tip 是 b5672c2c7f88，工作区有未暂存修改和未跟踪目录，但检查窗口内提交数为 0。报告应写 main worktree 存在待确认变更，而不是 2026-09-21 提交了角色资产更新。

常见误区

  • 看到仓库有未提交变更，就认为这个仓库今天完成了这些工作。
  • 把 main worktree 的未提交线索直接归到 main 分支已提交历史。

概念关联

关联概念关系说明
Git 工作区状态与未提交变更worktree 的差异就是未暂存修改、未跟踪文件和分支 tip 的组合。
提交窗口与时间归属只有把变更绑定到具体 worktree 和检查窗口，才能判断是否属于目标日期。
待确认变化线索与证据分层避免把某个工作区的草稿直接写成仓库级已完成事实。

继续深入问题

  1. 如果同一个仓库有两个 worktree 分别绑定不同分支，报告应如何避免把它们的未提交变更混在一起？
  2. 当 main worktree 的分支 tip 未变化但工作区有大量未跟踪文件时，应如何设计字段表达版本未变但现场有草稿？
  3. 人工确认 worktree 线索时，哪些证据可以帮助判断变更发生时间，例如提交记录、文件时间戳、任务日志或人工说明？

资产合同检查与交付审查

完整讲解

资产合同检查是把角色资产应该长什么样、放在哪里、包含哪些文件写成可执行规则；交付审查是进一步问这些检查结果能否支撑交付。它不只关心文件是否存在，还要区分检查未运行、检查脚本失败、目录缺失、文件不合规、人工已复核通过等不同证据等级。这里基于当日材料可确认的是 tiny-sea-war 出现 check_character_asset_contract.py、contract_audit、delivery_review 等路径，提示契约检查和交付边界；但当天没有脚本内容或检查结果，因此不能确认具体规则或已通过交付。底层思想是：交付不是看起来完成，而是有可检查的边界和可追溯的审查记录。资产目录可以作为产物接口，合同检查可以作为自动守门员，交付审查则决定哪些产物可以进入下一步，哪些产物需要人工复核。

原理逻辑

  1. 资产目录是产物接口，合同检查是自动守门员，交付审查决定产物能否进入下一步。
  2. 检查结果必须分层表达，避免把工具存在、检查运行、内容合规和人工复核混为一谈。
  3. 交付判断需要可追溯证据，包括失败原因、QA 报告和人工复核入口。

具体例子

某个角色目录有 concept/ 和 processed/，但缺少 meta/ 或 qa/。合同检查可以输出 missing_directory。交付审查不应直接写角色完成，而应写 contract_failed 或 needs_review，并保留失败原因和人工复核入口。

常见误区

  • 把存在 check_character_asset_contract.py 直接理解成所有角色资产都通过了合同检查。
  • 把目录名存在当成内容合规，把脚本存在当成检查已运行。

概念关联

关联概念关系说明
角色资产目录结构作为产物接口边界目录和文件约定是合同检查的对象。
批量 QA 报告与验证产物归档批量角色资产需要把每个角色的检查状态汇总成可追溯报告。
待确认变化线索与证据分层脚本路径存在不等于检查已运行，检查结果存在不等于资产已交付。

继续深入问题

  1. 当契约检查发现某个文件存在但内容格式错误时，报告应如何区分 missing_file、invalid_field 和 needs_review？
  2. 如果多个角色共用同一份契约，某个角色需要例外，应如何记录例外而不破坏整体审计？
  3. 如何设计交付审查字段，让下游能区分检查未运行、检查失败、资产不合规和人工已复核通过？
