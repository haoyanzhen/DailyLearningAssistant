工作区、暂存区与未跟踪文件的状态分类

Working Tree, Index & Untracked States

提交历史是档案柜，暂存区是讲台上的答题卡，工作区是桌上的草稿纸，未跟踪文件是还没登记的纸片。

核心要点

  • Git 把本地改动分成三个位置：工作区是当前编辑现场，暂存区（索引）是下一次提交的候选清单，未跟踪文件是尚未纳入版本管理的文件或目录。
  • 三个位置对应不同证据强度：已暂存说明改动已进入下一次提交候选清单，未暂存与未跟踪只说明现场留有痕迹，正式提交历史里没有新记录。
  • 只有被放入暂存区并执行提交的改动才会进入提交历史，所以判断结论之前，先要判断改动停在哪个区域。
计算机科学 / 数学 ★★★

基于历史基线的变更检测

History-Baseline Change Detection

SHA 像书架排头的编号：编号没变，只能说明指针没动，不能说明没人翻过书。

核心要点

  • 检测方法是先取上一次成功观测留下的值作为历史基线，再和本次读到的当前值比较；相等记为 unchanged，不等才说明被监控对象可能发生了变化。
  • 两个必要前提：必须先有一次成功读取并留下历史基线，本次读取也必须成功；读取失败时不能写成 unchanged，因为没有成功观测就没有可靠比较。
  • 首次看到某个 ref 只记录基线，不视为新增提交或 changed，否则第一次观测就会被误报成一次变化。

工作区、暂存区与未跟踪文件的状态分类

完整讲解

工作区、暂存区和未跟踪文件，是 Git 用来给本地改动分位置的三类状态。工作区就是你眼前正在编辑的文件现场；暂存区也叫索引，是下一次提交的候选清单；未跟踪文件是 Git 还没有纳入版本管理的文件或目录。当天 tiny-sea-war 的材料明确说：窗口内提交数为 0，但主工作区存在未暂存变更和未跟踪文件或目录，已暂存变更为无。翻译成状态分类就是：正式历史档案里没有新提交；索引里也没有准备提交的改动；但工作现场有改动，而且还有 Git 尚未登记的新文件或目录。这里的核心不是判断改动好坏，而是判断改动停在哪个区域，因为不同区域代表不同证据强度。

原理逻辑

  1. Git 用区域而不是用“有没有变化”来组织本地状态：工作区、暂存区（索引）与未跟踪集合三者互相独立，可以同时存在不同内容。
  2. 状态分类决定了证据强度：已暂存意味着改动已进入下一次提交的候选清单，未暂存与未跟踪只意味着现场留有痕迹，尚未被正式历史收录。
  3. 提交历史只收录被暂存并提交的改动，因此“窗口内提交数为 0”与“工作区有痕迹”在逻辑上并不冲突，也不需要互相解释。

具体例子

tiny-sea-war 窗口内提交数为 0，主工作区存在未暂存变更和未跟踪文件或目录，已暂存变更为无。可确认的结论是：当前工作现场有编辑痕迹和未登记文件，但没有准备好进入下一次提交的暂存内容，也没有目标窗口内的提交记录。

常见误区

  • 把工作区有变化当成已经提交。工作区、未暂存、未跟踪与已暂存是不同状态，只有被暂存并提交的改动才进入提交历史。
  • 把未跟踪文件当成会自动进入下一次提交。未跟踪文件在 Git 还没有任何记录，除非显式加入暂存区，否则不会被提交。
  • 看到窗口内提交数为 0 就以为仓库完全没有变化。提交历史为空窗和当前工作区有痕迹是两回事。

概念关联

关联概念关系说明
基于历史基线的变更检测状态分类关注本地改动停在哪一层；基线比较关注远端 ref 指针是否移动。两者面向不同的证据来源，结论不能互换。
待确认变化线索与人工确认未暂存与未跟踪的改动只能提示方向，属于待确认线索；只有先分清改动位置，才能判断这条线索的证据强度。
提交历史与工作区状态的证据层级提交历史是正式档案，工作区是当前现场，暂存区是两者之间的候选清单，三者不能混写成同一句事实。

基于历史基线的变更检测

完整讲解

基于历史基线的变更检测，是先用上一次成功观测留下的值作为参照，再和这一次读到的值比较。当天远端 ref 监控用 git ls-remote 读取 ref，每个 ref 都有历史 SHA 和当前 SHA。历史 SHA 是上次记录下来的基线，当前 SHA 是这次读到的指针值；两者相等就记为 unchanged，不等才表示这个 ref 指针可能发生了变化。关键前提有两个：第一，必须先有一次成功读取并留下历史基线；第二，这次读取也必须成功。当天多个仓库的 ref 都显示 unchanged，是因为它们已有可比较的 SHA 且读取成功。首次看到一个 ref 只记录基线，不视为新增提交；否则就会把第一次观测误报成变化。

原理逻辑

  1. 比较需要参照物：没有历史基线时只剩一个孤立观测值，无法判断它相对过去是否变化。
  2. 比较需要双方都成功：基线缺失或本次读取失败，比较条件不成立，结果应进入未知或待确认，而不是 unchanged。
  3. SHA 是内容寻址的哈希指针值，相等就表示 ref 指向同一个对象；因此 SHA 相等足以支撑“这个 ref 指针没动”这一层结论。

具体例子

假设昨天记录 refs/heads/main 的历史 SHA 是 A，今天通过 git ls-remote 读到当前 SHA 还是 A，就记 unchanged。若某个 ref 是第一次出现，只把 A 记录成基线，不报告新增提交。2026-09-14 材料中多个远端仓库正是这种成功读取且 ref 未变化的情况。

常见误区

  • 以为 unchanged 等于仓库没有发生任何变化。它只说明被监控 ref 指针与历史基线相同，其他 ref、工作区、文件内容或提交对象是否变化并不在这条结论里。
  • 把首次看到某个 ref 当成 changed。首次观测只能建立基线，不能宣告变化。
  • 在读取失败时仍然写成 unchanged。没有成功观测就没有可靠比较，读取失败应留在未知或待确认状态。

概念关联

关联概念关系说明
ref 元数据证据边界变更检测的结论只覆盖被监控的 ref 指针，不覆盖提交数量、作者、文件列表或 diff 内容。
首次观测基线首次观测基线是变更检测的前置条件；没有历史基线时只能建立参照点，不能宣告变化。
待确认变化线索与人工确认当基线缺失或读取失败时，结论无法升级为 unchanged 或 changed，只能作为待确认状态交给后续处理。

待确认变化线索与人工确认

完整讲解

待确认变化线索与人工确认，说的是自动化系统看到了某种变化痕迹，但证据还不足以把它写成已经确认的事实。当天 tiny-sea-war 的情况是：窗口内提交数为 0，但主工作区存在未暂存变更和未跟踪文件或目录。材料明确要求，这些只是待确认变化线索，不能写成目标日期前一天已经完成的提交事实。原因是工作区里的改动只能证明当前现场有痕迹，不能可靠证明它是什么时候发生的，也不能证明作者、意图或是否完成。材料还列出一些候选路径，例如表现层数据 schema、配置注册、战斗单位视图、测试与回归验证、角色美术批处理与 QA 报告等，但它们都只是候选方向。自动化报告应该把这类线索单独标注，等待人工确认后再升级为结论。

原理逻辑

  1. 证据强度决定表述强度：工作区痕迹只能证明“当前现场有改动”，不足以支撑“某日完成了某次提交”这样的事实陈述。
  2. 时间归属需要额外证据：文件修改时间、编辑器记录、提交时间等都可能帮助确认，但缺一不可时只能停留在待确认状态。
  3. 候选路径只是方向而不是成果：把待确认线索外推成完整开发内容，是自动化报告最典型的越界方式。

具体例子

tiny-sea-war 当天窗口内提交数为 0，主工作区存在未暂存变更和未跟踪文件或目录，已暂存变更为无。材料列出的 config_registry.gd、presentation_settings.json、scene_presentation_test.gd、character_art_batch_report.json 等路径，只能作为待确认变化线索，不能写成 2026-09-13 已完成的提交成果。

常见误区

  • 把待确认线索直接写成已确认的提交事实。工作区有未暂存或未跟踪变化，只能说明现场存在痕迹。
  • 把窗口内提交数为 0 误读成完全没有工作痕迹，忽略了工作区可能仍有未提交改动。
  • 看到候选路径就外推出完整开发内容，把候选方向当成已经完成的开发成果。

概念关联

关联概念关系说明
工作区、暂存区与未跟踪文件的状态分类只有先分清改动停在哪个区域，才能判断这条线索的证据强弱，决定它能否升级为结论。
提交历史与工作区状态的证据层级提交历史是正式档案，工作区是当前现场，两者不能混写，线索也不因位于现场就自动具备档案效力。
ref 元数据证据边界它延续了 ref 元数据证据边界的思想：自动化报告必须说明结论来自哪一层证据，不能把线索外推成事实。
