工作区状态快照作为候选变更证据

完整讲解

在软件开发中，Git 仓库就像一本账本，每一次正式提交（commit）都是一笔带时间戳和签名的确定记录。而工作区状态快照，也就是我们运行 git status 看到的那些“修改过但还没提交”“新加进来还没跟踪”的文件列表，就像写在本子边上的铅笔草稿。它说明了谁可能在修改什么，但既没有说明为什么而改，也没有说明什么时候完成的、改完之后有没有经过测试。因此，它只能当作“候选证据”——告诉我们这里可能有值得关注的变化，却绝不是可以盖章定论的工程事实。今天的整个分析里，tiny-sea-war 项目所有线索都来自这种未提交的快照，所以我们必须在每一步都声明“待确认”，避免把施工中的脚手架错当成已经竣工的大楼。

原理逻辑

  1. Git 提交是有时间戳、作者签名和完整变更记录的事实，而工作区状态是瞬时、易失的草稿
  2. 未提交修改缺乏上下文（为什么改、何时完成），无法作为可靠审计或报告的依据
  3. 在证据层级中，工作区快照位于最底层，必须通过标注“待确认”来区分它与已确认提交的差异

具体例子

想象你是一个侦探，来到一个房间，发现桌子上摊开着一张画了一半的地图，旁边还散落着几支铅笔和橡皮屑。你可以推断这个房间的主人正在修改地图，甚至能猜出他可能在往西方扩展一块陆地。但你不知道他是不是昨晚突发奇想随手改的，还是按照一个深思熟虑的方案在工作，更不知道他会不会明天就全部擦掉重来。这张未完成的草图就是工作区快照，给你线索，却不给你结论。

常见误区

  • 很多人以为只要 git status 显示一堆修改，就说明项目正在往这些方向推进，甚至可以写进进度报告。实际上，未提交的工作区状态只是开发者的“临时实验场”，随时可能被放弃、覆盖或推翻。
  • 若把这种瞬时状态当作决定性的工程证据来决策，就很容易被误导。

概念关联

关联概念关系说明

  2. 如果快照中包含用户并未打算提交的临时文件，如何通过自动化脚本筛选出真正意图改动的文件，从而减少噪音？

git‑lfs 缺失环境下的二进制资产可观测性缺口

完整讲解

Git LFS（大文件存储）是一种把大型二进制文件（比如游戏美术的贴图、模型）替换成轻量级“指针”的扩展工具。正常环境下，git diff 可以穿透这些指针，展示实际图片或资源的变化。但如果环境里没有安装 git-lfs 这个命令，Git 就只会看到指针文件的哈希变化，而无法解码背后的真实内容。这时候，对于二进制美术资产，就像一个能拍出模糊轮廓的廉价监控镜头：你知道文件动过了，但根本看不清它到底从一张什么图变成了另一张什么图，这就是可观测性的缺口。在今天的 tiny-sea-war 仓库里，检查工具直接报出了 `git-lfs: command not found`，导致大量地形贴图、导航纹理等资源的变化无法被读取，让整个项目的美术更新蒙上了一层迷雾。

原理逻辑

  1. Git LFS 用指针文件代替真实大文件，正常环境下通过 smudge/clean 过滤器透明还原内容
  2. 当 git-lfs 命令不可用时，Git 只比较指针字符串，无法展示实际内容的差异
  3. 这种缺口直接导致基于 git diff 的自动化质量检查（如视觉回归、资产审计）失效

具体例子

假设图书馆把所有厚重的大部头书换成了小小的索引卡片（指针），你想知道某本书有没有被读者修改过，就必须有一台特殊的机器能根据卡片找到原书并比较。如果机器坏了或根本没装，你只能看到卡片上的编号变了，却完全不知道书里面到底是被撕了几页、还是被加上了整章新内容。今天 tiny-sea-war 项目就遇到了这种情况——管理员发现很多美术资产的“卡片”编号变了，但因为缺少那台特殊机器，根本没法知道这些资产的内容到底发生了什么变化。

常见误区

  • 一个常见的误解是，只要 git status 正常显示了文件变更，就说明所有信息都可以被完整追踪。实际上，当 git-lfs 缺席时，二进制文件的 diff 几乎完全失效，你可能看到 git status 报告某个大文件被“修改”，但 git diff 输出的只是一行指针哈希变更，根本体现不出图像、模型等资产的实际改动。
  • 这会让人误以为系统监控覆盖到位，实则存在致命的盲区。

概念关联

关联概念关系说明

  2. 如何设计一个 pre-flight 检查脚本，在开发者或 CI 流水线的一开始就探测 git-lfs 是否可用，并在缺失时给出清晰的安装指引和降级策略？
  3. 如果团队迁移到其他版本控制系统（如 Perforce），二进制资产的可观测性机制有何本质不同？会不会依然存在类似的工具链依赖问题？

多比例资产管线中的比例适配与清单传播

完整讲解

游戏在不同屏幕比例的设备上运行时，地图、UI、导航数据等都需要做专门的适配，不然就会出现画面错位、AI 撞墙等问题。这个过程不是简单地缩放图片，而是需要一整套自动化管线：从美术制作的原始资产开始，经过裁剪、重排、遮罩合成等步骤，烘焙出针对特定比例（比如 16:9）的运行时版本，同时生成一份“清单”文件来记录哪些资产对应哪个比例、以及它们之间的依赖关系。当项目决定新增一个比例时，这条管线就需要传播变化：一方面要为新比例生成独立的清单和产物，另一方面，原有的工具脚本、构建规则、甚至 Agent 的技能文件都要跟上，不然它们还会试图使用旧路径或旧格式去访问资产，导致构建失败或自动化流程出错。今天的 tiny-sea-war 工作区快照正好展现了这种传播的初期形态：出现了独立的 16:9 地图清单、专门的地图烘焙脚本，以及一个名为 coastal-map-scale-runtime-integration 的工作订单，预示着项目正在将比例适配从想法推向实施。但因为所有改动都未提交，我们无从判断这是最终选定的“独立清单”策略，还是只是过渡方案。

原理逻辑

  1. 屏幕比例不同导致游戏视觉和逻辑区域变化，需要专门的裁剪、重排和遮罩合成来生成适配的资产
  2. 清单文件是管线各阶段的契约，定义了资产、比例及其依赖关系，下游工具依赖清单查找和加载资源
  3. 新增比例时，必须更新清单、烘焙脚本以及所有消费该清单的工具（如 Agent、自动化测试），否则会出现加载失败或错误

具体例子

想象一家出版社同时印刷纸质书和电子书，这两种格式的排版完全不同，不能把印刷用的版面直接丢到电子屏幕上去。于是他们建立了一条自动化流水线：作者提供原始文稿（源资产），排版软件根据不同格式（比例）的需求，自动调整字体、图片位置、页面边距，生成针对特定终端的版本。每一批生成好的文件，都附带有详细的物料单（清单），上面写着这一版本里有哪些章节、图片编号、以及它们来自作者原稿的哪些部分。如果出版社要增加一种新的电子阅读器格式，就不能只把旧物料单复制一份，而是要更新整条流水线，增加新的排版规则，重新先生成一份新物料单，并通知所有后期校对工具和分发系统，否则新格式的书就会缺页少图。今天项目里的 16:9 地图就像这种新格式，它正在催生一套新的清单和生成脚本，同时也要确保自动化 agent 知道去哪里找它。

常见误区

  • 很多人认为只要把旧比例的资产文件复制一份，改改尺寸就算完成适配了。但实际上，多比例适配根本不是一个文件操作问题，而是一个管线契约传播问题。
  • 如果只复制文件而不生成新的清单并更新加载器的路径配置，系统就根本找不到新资源；反之，如果只生成了新清单却忘了通知 Agent 或自动化测试，它们就会基于过时的信息执行错误操作。
