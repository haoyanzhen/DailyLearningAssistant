文档-实现-测试同步契约

完整讲解

文档-实现-测试同步契约，可以理解为“合同、施工和验收单必须一起更新”。在一个工程里，文档说明规则应该是什么，脚本或代码把规则做出来，测试则自动检查规则是否真的被做对。当天 tiny-sea-war 的多个提交同时修改 docs/、scripts/ 和 scripts/tests/，这不是偶然，而是把一次功能变化拆成三层证据：设计层、实现层和验证层。对高中基础读者来说，可以类比班级值日：公约写清楚谁负责哪块，值日表落实到具体人，检查表每天核对是否完成。如果只改公约不改检查表，后面就不知道规则有没有被执行；如果只改代码不改文档，别人接手时只能靠猜。这里基于当日材料可确认的是，多个提交形成了 docs、scripts、tests 同步变化的文件级事实，而不是具体算法或业务规则细节。

原理逻辑

  1. 文档是声明层，说明规则应该是什么；实现是执行层，把规则做出来；测试是验证层，自动检查规则是否真的被做对。
  2. 多个提交同时修改 docs、scripts 和 tests，形成设计层、实现层和验证层的文件级事实，使功能变化可追溯。
  3. 测试是文档和实现之间的自动检查器：文档说规则应该是什么，测试就验证实现是否真的符合；没有测试，文档和实现可能慢慢脱节。

具体例子

以菜单分类操作指南为例：文档说明主菜单中操作指南应如何分类，main_menu.gd 实现菜单项和跳转逻辑，operation_guide.gd 承载指南内容，菜单 QA 测试验证菜单项是否存在、分类是否正确、点击后是否进入指南。若其中任一环节缺失，后续维护者就无法确认这次变化是否完整。

常见误区

  • 认为测试只是“顺手加的文件”，文档只是“给人看的说明”，真正有用的只有代码。
  • 认为只改代码不改文档或测试也能保持可维护性，实际上会让后续维护者只能靠猜。

概念关联

关联概念关系说明
功能提交伴随测试测试文件是契约中可执行、可复跑的部分，让规则变化能被自动检查。
数据驱动进度与奖励一致性进度数据、schema、流程脚本和测试也需要一起约束同一套规则，避免规则与数据脱节。
Agent 生成总结的证据边界当文档、实现和测试都同步变化时，Agent 可以更谨慎地判断功能变化线索，但仍需绑定证据等级。

继续深入问题

  2. 如何为 docs、scripts 和 tests 设计最小同步字段，使每个规则变化都能追溯到文档段落、实现文件和测试断言？
  3. 当测试只验证界面文本而没验证运行时行为时，如何区分“文档契约已验证”和“运行时行为已验证”？

角色远距战斗资产管线

完整讲解

角色远距战斗资产管线，可以理解成一条“从美术原图到游戏运行时可用资产”的流水线。当天 tiny-sea-war 的提交 80eb1bcf 中出现大量 assets/characters/<角色>/battle、meta、processed、config 文件，以及 asset_catalog.gd、资产接口设计文档和资产管线文档。这说明角色远距战斗资产不是散落的图片，而是有源文件、裁切规格、修订记录、处理后 body/rig 图、交付审查配置和远距战斗配置的链路。对高中基础读者来说，可以类比服装制作：先有设计稿，再按尺码表裁剪，再缝成成衣，再贴吊牌，最后质检员确认吊牌、尺码和实物一致。资产目录与接口就像吊牌和仓库索引，告诉运行时“该拿哪一件、放在哪里、是否合格”。这里基于当日材料可确认的是文件路径、目录分层、资产目录脚本、审查工具目录和文档线索，而不是具体图片效果或物理渲染参数。

原理逻辑

  1. 源文件、裁切规格、修订记录、处理后 body/rig 图、交付审查配置和远距战斗配置共同组成资产链路。
  2. 资产目录与接口提供稳定身份和引用路径，让运行时知道该拿哪一件、放在哪里、是否合格。
  3. 审查工具把人工判断变成 JSON、HTML 等可复核数据，使资产状态可查、可降级、可进入后续发布检查。

具体例子

某角色远距战斗需要一张处理后图：原图进入 assets/characters/<角色>/battle，裁切规格说明需要哪些区域，processed 目录生成运行时可用图，config 指定战斗状态下的引用，asset_catalog.gd 登记路径和接口，tools/art_review/far_view 生成 JSON 与 HTML 审查数据。只有这些环节都齐备，资产才能被稳定引用并进入后续发布检查。

常见误区

  • 认为“把图片放进 assets 目录就算完成资产接入”。
  • 认为只要文件存在就可以进入运行时或发布包，忽略目录索引、接口约束、审查数据和配置。

概念关联

关联概念关系说明
资产目录及资产接口目录索引和接口约束让资产能被运行时稳定引用，而不是靠人工猜路径。
资产审查工具及审查数据审查工具把人工判断变成 JSON、HTML 等可复核数据，让资产状态可以被复核。
Windows 导出预设及包资产清单管线产出的资产最终要进入导出包，并受包资产清单约束。
文档-实现-测试同步契约资产接口文档、目录脚本、审查脚本和测试需要同步维护，避免资产规则与实现脱节。

继续深入问题

  1. 如何设计资产 ID，使其同时包含源路径、生成路径、运行时路径、角色、战斗状态和版本？
  2. 当 source、generated 和 runtime 出现同名文件时，如何用命名空间和 manifest 字段避免误认为同一对象？
  3. 当审查数据缺失或审查未通过时，资产状态应如何降级，避免被误认为可发布？

Agent 生成总结的证据边界

完整讲解

Agent 生成总结的证据边界，意思是自动化助手写报告时，不能自由发挥，只能根据当前拿到的证据说话。当天远端仓库总结明确说明：总结由第 1 步 Agent 基于远端 Git ref 元数据生成，并且 ref-only 证据只能证明 ref 指针是否变化，不能证明新增提交数量、提交信息、作者、文件列表或 diff 内容。这里基于当日材料可确认的是“Agent 输出受 ref-only 证据边界约束”这一规则，而不是 Agent 具体使用了什么提示词或模型。对高中基础读者来说，可以类比学生写评语：如果只看到总分从 80 变成 85，只能说“总分有变化线索”；如果想说“数学进步了”，必须看到数学单科成绩；如果想说“上课更认真了”，还需要课堂观察记录。Agent 也一样：证据等级不同，能说的结论强度也不同。

原理逻辑

  1. 记录层提供 ref、历史 SHA、当前 SHA、指针状态、访问状态等字段，聚合层派生仓库级状态，报告层由 Agent 生成但必须被字段约束。
  2. ref-only 证据只能证明 ref 指针是否变化，不能证明新增提交数量、提交信息、作者、文件列表或 diff 内容。
  3. 后续补充 commit log 或 diff，才能把结论升级为提交级或文件内容级；证据不足时，应显示不可确认字段。

具体例子

某远端仓库监控记录为：ref=refs/heads/main，historical_sha=A，current_sha=B，pointer_status=changed，commit_detail_status=unknown，access_status=success。Agent 可以生成：“该 ref 指针发生变化，形成远端版本变化线索。”但不可生成：“今日新增 5 个提交，修改了 12 个文件，其中包含战斗结算脚本。”若后续补充 commit log，才能把结论升级为提交级；若再补充 diff，才能升级为文件内容级。

常见误区

  • 认为 Agent 很聪明，所以可以把缺失细节自动补全。
  • 认为“让 Agent 尽量写完整”比明确证据边界更重要，实际上补全缺失事实就是幻觉风险。

概念关联

关联概念关系说明
ref-only 证据边界ref 指针变化只是弱证据，不能自动升级为提交、文件或功能结论。
记录-聚合-报告三层最小字段契约Agent 的每句话都应能追溯到记录层字段，而不是依赖临时状态或界面状态。
文档-实现-测试同步契约如果 Agent 要判断功能是否完成，需要文档、实现、测试三类证据共同支持，而不是只看提交标题。
