Repo-Level Wording for Unchanged Refs

只说被监控的 ref 未变，不说整个仓库无进展。

核心要点

  • 仓库级措辞必须保留监控了哪些 ref、检查窗口是什么、证据来自哪一层。

精读文章 · 软件工程 / 计算机科学

多 ref 未变时的仓库级聚合措辞

完整讲解

检查一个仓库时，如果只检查 main 和 release 两个 ref，且检查窗口内历史 SHA 与当前 SHA 相同，能确认的事实是被监控的 ref 指针在该窗口内没有变化。这个事实只能写成 monitored refs unchanged，不能写成 no engineering progress，因为仓库中可能还有未监控 ref、文档、评审、CI、资产生成或其他工程活动。仓库级聚合措辞需要保留监控范围、检查窗口和证据来源，避免把局部观察扩大成整体判断。

原理逻辑

  1. 证据范围决定结论范围：只监控部分 ref，就只能得出部分 ref 的状态。
  2. 窗口边界决定时间归属：窗口外的变化不能进入当天结论。
  3. 状态词必须可追溯：仓库级措辞应能回溯到具体 ref、窗口和访问证据。

具体例子

某仓库监控 main 和 release 两个 ref，窗口为 2026-10-01 00:00 到 2026-10-02 00:00，两个 ref 的历史 SHA 与当前 SHA 相同且访问成功。正确措辞是：在指定窗口内，被监控的 main 和 release ref 指针未变；不能写：该仓库当天没有任何工程进展。

常见误区

  • 把多个 ref unchanged 直接说成仓库没有任何工程进展。
  • 把某个 ref 访问失败混进 unchanged，或把检查窗口外的历史变化纳入当天结论。

概念关联

关联概念关系说明
只读远端监控的访问状态与详情未知字段仓库级措辞必须基于每个 ref 的访问状态和指针状态，访问失败不能被聚合为 unchanged。
机器注册表与人工页面的一致性模型机器状态词和人工页面措辞必须一致，否则会出现机器说 monitored unchanged、页面说无进展的两套事实。
多仓库监控窗口的基线命名空间与首见隔离若基线串用，仓库级聚合会把首次基线误判为新增提交。

  2. 当某个 ref 访问失败而其他 ref 未变时，仓库级状态词应如何表达才能既不夸大也不隐瞒？
  3. 如何设计一个措辞检查规则，在出现 no engineering progress 时要求提供窗口内提交证据或人工确认？

精读文章 · 计算机科学 / 软件工程

只读远端监控的访问状态与详情未知字段

完整讲解

只读远端监控例如 git ls-remote，通常只能读取远端 ref 指针元数据，不会下载提交对象、文件树或 diff。系统能知道某个 ref 当前指向哪个 SHA，也可能知道历史 SHA，但不能直接知道提交内容、提交数量、作者、文件列表或 diff。因此字段设计必须把访问状态、指针状态、提交详情状态分开：访问状态回答有没有读到远端，指针状态回答历史 SHA 和当前 SHA 是否相同，提交详情状态回答是否知道提交内容。访问成功且 SHA 相同可写 pointer_status=unchanged，但 commit_detail_status 仍可能是 unknown；访问成功且 SHA 不同只能写 pointer_status=changed，仍不能写提交详情。

原理逻辑

  1. 证据层级不同：访问成功、指针相同、指针变化、提交详情已知是不同层级的事实。
  2. 字段正交化：access_status、pointer_status、commit_detail_status 各自回答不同问题。
  3. 未知必须显式表达：无法读取或无法判断时应使用 unknown，而不是默认 unchanged。

具体例子

历史 main SHA 为 abc，当前 main SHA 为 abc，访问成功，则 access_status=success、pointer_status=unchanged、commit_detail_status=unknown。若访问失败，则 access_status=failure、pointer_status=unknown、commit_detail_status=unknown。若当前 main SHA 变为 def，则 access_status=success、pointer_status=changed、commit_detail_status=unknown。

常见误区

  • 把访问失败当成未变化。
  • 把 SHA 变化当成提交内容变化，或把提交详情未知补全成具体提交数量、作者、文件列表。

概念关联

关联概念关系说明
多 ref 未变时的仓库级聚合措辞访问状态、指针状态和详情未知字段是仓库级措辞的证据基础。
变更状态机的可测试事件与状态迁移读取成功、读取失败、SHA相同、SHA不同等事件需要被状态机接收并产生明确状态词。
多仓库监控窗口的基线命名空间与首见隔离访问失败会影响基线是否能建立，基线必须按仓库、ref、窗口隔离。

  3. 如何为 access_status、pointer_status 和 commit_detail_status 设计枚举值，使它们互不覆盖且可被自动化检查？

精读文章 · 软件工程 / 计算机科学

变更状态机的可测试事件与状态迁移

完整讲解

状态机是一种用表格描述系统如何变化的方法：当前状态、输入事件、输出状态、输出措辞。first_seen、unchanged、changed、unknown 等状态可以由明确事件驱动，例如首次读取成功、历史 SHA 与当前 SHA 相同、历史 SHA 与当前 SHA 不同、读取失败。状态机的价值是把自然语言判断变成可穷举、可测试的迁移关系。首次读取成功且没有历史基线时，状态应为 first_seen，而不是 changed；读取失败时，状态应为 unknown，而不是 unchanged；历史 SHA 与当前 SHA 相同时，状态才是 unchanged。若多仓库共享同一检查窗口，还需要结合仓库、ref、窗口形成基线命名空间，避免一个仓库的首次基线被误读为另一个仓库的新增提交。状态迁移还应保留记录，使后续能判断当前状态是由哪些事件触发。

原理逻辑

  1. 事件驱动：状态变化必须由读取成功、读取失败、SHA相同、SHA不同等明确事件触发。
  2. 迁移可穷举：每个状态和事件组合都应能映射到明确输出状态和措辞。
  3. 历史可审计：只保存当前状态不够，需要保留迁移记录以判断状态如何形成。

具体例子

仓库 A 的 main 在窗口内首次读取成功，历史基线为空，状态迁移为 first_seen。下一次读取成功，历史 SHA 与当前 SHA 相同，状态迁移为 unchanged。再下一次读取成功，历史 SHA 与当前 SHA 不同，状态迁移为 changed。如果某次读取失败，状态迁移为 unknown，并且不能把 unknown 当作 unchanged。

常见误区

  • 用自然语言总结直接判断状态，例如看到 ref 有 SHA 就写成 changed。
  • 把 first_seen 写成 changed，或把读取失败写成 unchanged；只保存当前状态，不保存迁移历史。

概念关联

关联概念关系说明
多仓库监控窗口的基线命名空间与首见隔离状态迁移必须知道当前状态属于哪个仓库、哪个 ref、哪个检查窗口，否则 first_seen 可能跨仓库串用。
只读远端监控的访问状态与详情未知字段状态机需要把访问成功、访问失败、SHA相同、SHA不同等事件分开，才能输出正确状态词。
注册表历史状态与最新状态分层状态迁移需要保留可追溯记录，否则无法判断当前状态是如何迁移来的。
