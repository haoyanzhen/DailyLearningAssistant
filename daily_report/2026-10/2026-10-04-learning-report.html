文件级证据与内容级证据的分离

完整讲解

想象你在检查一个仓库里的文件变化。文件级证据包括文件是否存在、是否新增、是否修改、是否删除、路径是否变化、ref 指针是否变化。它回答的是“这个对象在文件系统或版本引用层面有没有变”。内容级证据则包括 diff、解析结果、运行时测试、人工审查、音频试听、图像对比等，它回答的是“内容语义或行为有没有变”。这里基于当日材料可确认的是：文件变化不能直接证明内容变化，结论强度不能超过证据等级。对高中生来说，可以把文件级证据理解为“快递单上的重量和尺寸变化”，它只能说明包裹外观或重量变了，不能说明里面商品换了；要看内容，需要打开包裹、称重明细或扫描内容。工程报告如果只拿到文件级证据，就应该写成“某路径文件发生变化”，而不是“功能已更新”或“资产内容已验收”。

原理逻辑

  1. 证据等级决定结论强度：低层证据只能支持低层事实。
  2. 文件存在、路径变化、ref 指针变化属于文件级证据，不自动包含内容语义。
  3. 要升级到内容级结论，需要 diff、解析、审查、试听或运行时测试等更高层证据。

具体例子

监控发现 assets/sound/explosion.ogg 被修改，manifest 记录了路径、更新时间和 hash 变化。可以确认该路径下存在文件级变化；不能确认爆炸声变响、时长变短、音频内容符合设计或运行时播放正常。若要确认内容，需要音频 diff、解析器输出、试听记录或运行时测试。

常见误区

  • 文件变了，就一定代表内容变了、功能变了或行为变好了。
  • 没有 diff 时，根据文件路径或扩展名猜测实现细节，例如看到 .png 变化就说“贴图内容已更新”，看到 .json 变化就说“关卡规则已改变”。

关联概念关系说明
资产命名空间与同名校验文件级证据必须绑定到 source、generated、runtime 等命名空间，否则同名文件变化会被误判为同一资产变化。
Agent 输出证据等级标签Agent 如果只说资产已更新而没有证据等级，就会把文件级变化误写成内容级完成或验收通过。

资产命名空间与同名校验

完整讲解

资产管线里常见 source、generated、runtime 三层。source 是源资产，generated 是生成后的成品资产，runtime 是运行时实际使用的资产。它们可能使用相同文件名，例如 level1.json 或 map.png，但代表不同阶段和不同身份。命名空间就像给文件加上“楼层和窗口”：只说红烧肉不够，要说一楼窗口 A 的红烧肉；只说 level1 不够，要说 source/level1、generated/level1 或 runtime/level1。这里基于当日材料可确认的是：source、generated、runtime 三层资产需要命名和绑定，以避免同名文件覆盖；我们不展开 manifest 与交付契约的整体流程，只讨论身份绑定和同名覆盖风险。稳定身份通常来自资产层、路径前缀、源路径、生成路径、运行时路径以及版本或 hash 等绑定字段。

原理逻辑

  1. 文件名只是局部标识，不是全局唯一身份。
  2. 资产身份需要资产层、路径、版本或 hash 等字段共同绑定。
  3. 同名校验要在生成前、生成后和运行前防止不同层记录互相污染。

具体例子

source/maps/level1.json、generated/maps/level1.json、runtime/maps/level1.json 都叫 level1.json。manifest 不应只记录 name=level1，而应记录 layer=source、layer=generated、layer=runtime，并绑定 source_path、generated_path、runtime_path、version 或 hash。QA 文件 qa/level1_review.json 如果只写 level1，就可能覆盖或误绑到错误层。

常见误区

  • 文件名相同就是同一资产。
  • 只要 runtime 目录里存在同名文件，就认为 source 和 generated 已经一致。
  • 把路径末端名字当作唯一键，忽略资产层、源路径、版本和 hash，导致同名覆盖或版本误判。

概念关联

关联概念关系说明
文件级证据与内容级证据的分离路径级证据必须绑定命名空间，才能知道变化发生在 source、generated 还是 runtime，否则文件变化证据无法定位到具体资产对象。
Agent 输出证据等级标签Agent 输出资产路径、生成记录或审查状态时，需要命名空间和证据等级共同约束，避免把 generated 层的 receipt 写成 runtime 层的 review。

Agent 输出证据等级标签

完整讲解

Agent 或 LLM 输出如果只是一段自然语言，很容易过度补全：把 receipt 写成 review 通过，把 completion 写成验收通过，把 ref-only 写成 commit 详情，把路径线索写成实现结论。证据等级标签的作用，是把输出变成结构化结论，让每个说法都绑定它能依赖的证据。这里基于当日材料可确认的是：AGENTS.md 或 SKILL.md 中的约束需要字段化，receipt 与 review 需要区分，completion 与 review 未通过需要不同措辞；我们不确认具体 Agent 执行过程。可以理解的标签包括 ref-only、commit-only、file-diff、runtime-test、receipt、review 等。它们不是装饰，而是结论强度。ref-only 只说明指针变化，commit-only 可能说明有提交记录，file-diff 说明文件内容差异可检查，runtime-test 说明运行时行为被验证，receipt 说明生成或提交回执存在，review 说明审查结论存在。生成完成、审查存在、验收通过、运行时可用是不同等级，不能互相替代。

原理逻辑

  1. 证据等级标签把自然语言结论变成可检查的结构化字段。
  2. 不同标签对应不同事实边界：指针、提交、文件差异、运行时测试、回执、审查。
  3. 报告措辞必须与标签匹配，弱证据不能写成强结论。

具体例子

Agent 生成关卡资产后输出 asset_path=runtime/maps/level1.json、receipt=generated、review=not_passed、evidence_level=file-diff、claim=completion。正确报告应写：生成回执存在，但评审未通过，不能写成验收完成；当前证据只到文件差异级，不能写成运行时可用。若只有 ref-only，应写：仅指针变化，提交详情未知。

常见误区

  • 把 receipt 当 review 通过，把 completion 当验收通过，把 ref-only 当 commit 详情，把文件路径线索当实现结论。
  • 认为 Agent 措辞越自信，事实就越可靠；实际上措辞强度必须与证据等级匹配，而不是与语气匹配。

概念关联

关联概念关系说明
文件级证据与内容级证据的分离receipt、review、runtime-test 等标签对应不同证据等级，Agent 输出措辞必须匹配，不能把文件级变化写成内容级完成。
资产命名空间与同名校验Agent 输出资产路径、生成记录或审查状态时，需要命名空间和证据等级共同约束，避免把不同层同名文件误认为同一对象。
