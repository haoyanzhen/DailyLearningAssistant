二维整数向量到展示文本的格式化映射

完整讲解

二维整数向量可以想成平面上的一个点，也可以当成一对整数描述的两个量。在 2026-10-13 的 tiny-sea-war 局部材料里，window_options[index] 是一个 Vector2i，它有 x 和 y 两个整数分量，被用来表示窗口配置中的宽和高。展示层要让玩家看懂的却是“宽 × 高”这样的文字，于是代码用 `%d × %d` % [window_options[index].x, window_options[index].y] 把二维整数点投影成一个字符串。这里的关键词是“投影”：数据模型是一层，展示文本是另一层，文本是数据的一个有损视图。投影规则必须明确，例如哪个分量先写、用什么分隔符、要不要空格、是否带单位。测试逐项比较显示文本与数据源按同一规则格式化出的结果，本质上是在检查展示层有没有偏离数据源契约。要注意，这种检查只覆盖展示文本和控件状态，不等于证明窗口运行时真的按这个尺寸打开，也不等于音乐模式等行为已经生效。它是有用的最小契约，但证据强度有限。

原理逻辑

  1. 数据模型层用 Vector2i 的 x 与 y 两个整数分量表示宽和高，是一对没有展示语义的整数。
  2. 展示层必须补上一条明确的投影规则，规定分量顺序、分隔符、空格与单位，例如 `%d × %d`。
  3. 测试按同一规则独立算出期望字符串，再与控件上的展示文本比较，从而把“展示层是否偏离数据源契约”变成可执行检查。
  4. 由于投影是有损的，通过文本比较只能得到展示层或控件状态证据，不能自动升级为运行时尺寸证据。

具体例子

假设 window_options[1] 是 Vector2i(1280, 720)，格式化规则是 `%d × %d`，那么展示文本应当是“1280 × 720”。测试把这个文本和按同一规则算出的期望值比较，而不是去启动窗口测量真实像素。

常见误区

  • 看到界面文字正确，就宣布窗口运行时行为也正确，把展示层证据当成行为证据。
  • 把 x 和 y 当成没有语义的两个数字，随便颠倒顺序，或在不同地方各写一遍格式化代码，使展示文本没有单一规则可比。

控件树遍历与语义选择器过滤

完整讲解

界面测试的第一件事常常不是“断言什么”，而是“找到谁”。在 Godot 这类场景树里，控件以父子节点组成一棵控件树。如果测试直接假设“第 3 个 OptionButton 就是窗口尺寸选择器”，那么界面一重排、加一个按钮或换一个容器，测试就可能找错对象。2026-10-13 的局部材料给出了更稳的思路：先遍历 menu.content 下的后代，用 _descendants_of_type(menu.content, 'OptionButton') 收集所有类型为 OptionButton 的候选，再按语义角色过滤。材料中看到的行为是排除 menu.music_mode_selector，从而定位窗口选择器。这里的“语义选择器”不是 CSS 那种选择器，而是用控件在业务上的角色来命名和区分，例如“音乐模式选择器”“窗口尺寸选择器”，而不是“第几个按钮”。遍历负责扩大候选集，过滤负责缩小到目标。这样界面重构时，只要语义角色没变，测试就不必跟着控件位置改。它是一种把“偶然结构”降级、把“业务身份”升级的工程习惯。

原理逻辑

  1. 控件树由父子节点组成，若用位置或数量定位控件，测试就绑在偶然结构上，一次重排即可失效。
  2. 遍历先把候选集扩大：按类型收集 menu.content 下的全部 OptionButton，不预设哪个是目标。
  3. 过滤再按业务角色缩小：排除 menu.music_mode_selector，剩下的候选才被认定为窗口选择器。
  4. 语义角色比偶然位置稳定，界面重构时只要求角色不变，测试无需跟随控件位置改动。
  5. 定位成功只说明测试找到了对象，它本身不构成断言被运行或行为被验证的证据。

具体例子

菜单里有两个 OptionButton：一个是窗口尺寸选择器，一个是音乐模式选择器。测试先调用 _descendants_of_type(menu.content, 'OptionButton') 得到两个候选，再排除 menu.music_mode_selector，剩下的候选就是窗口选择器，然后才读取它的 item_count 或文本。

常见误区

  • 以为控件数量能当唯一身份，比如页面里只有一个音乐模式选择器，就永远用数量 1 来定位。
  • 认为排除法一定稳定：排除 menu.music_mode_selector 能定位窗口选择器，但若未来新增第三个同类选择器，排除逻辑就需要重新设计。

精读文章 · 软件工程 / 计算机科学

可执行断言的证据分层与运行时结论降级

完整讲解

断言是写进测试里的可执行契约。它可以检查结构，例如某个控件是否存在；可以检查数量，例如 item_count 是否等于 window_options.size()；也可以检查文本格式，例如窗口尺寸是否显示成“1280 × 720”。这些断言很有价值，但它们证明的事情有强有弱。2026-10-13 的材料能看到测试检查控件数量、选择器存在性、item_count 和文本格式，但没有提供测试运行结果，也没有展示运行时状态变化。因此不能把“写了断言”或“改了断言”写成“运行时已经通过”。更成熟的做法是给报告标注证据层级。path_level 通常只能说明路径或对象出现、变化；diff_level 能说明局部代码或断言被修改；runtime_level 才需要实际运行、观察状态变化或执行路径。若当前证据只到 path_level 或 diff_level，报告就应该自动降级措辞，例如说“已配置”“已断言”“待运行验证”，而不是说“已生效”“运行通过”。这不是文字游戏，而是防止弱证据被包装成强结论。

原理逻辑

  1. 断言是可执行契约，它能检查结构、数量与文本格式，但不同断言的证明力强弱不同。
  2. 报告需要显式的证据层级：path_level 说明路径或对象出现与变化，diff_level 说明局部代码或断言被修改，runtime_level 才需要实际运行与状态观察。
  3. 当证据只到 path_level 或 diff_level 时，结论措辞应按规则自动降级为已配置、已断言、待运行验证。
  4. 只有引入分层，才能防止“断言被修改”或“界面文本正确”被包装成运行时行为已通过的强结论。

具体例子

测试断言 menu.music_mode_selector.item_count == 3，这能说明控件当前配置里音乐模式选择器有三项；但它不能单独证明运行时玩家切换音乐模式时，三项都按预期生效。若没有运行结果，报告只能写“已断言 item_count 为 3，运行验证待补”。

常见误区

  • 把测试文件存在、断言被修改、断言逻辑看起来正确，当成运行通过；或把界面文本断言当成运行时行为断言。
  • 报告只写“passed”，却不说明证据停在路径、局部 diff 还是运行时，导致读者无法判断结论强度。

概念关联

关联概念关系说明
控件树遍历与语义选择器过滤只有先稳定定位到正确的控件，数量、存在性和文本断言才不会被偶然位置污染。
二维整数向量到展示文本的格式化映射它验证格式化映射，但必须承认这种验证停在展示文本或控件状态层，不能自动变成窗口尺寸的运行时证据。
