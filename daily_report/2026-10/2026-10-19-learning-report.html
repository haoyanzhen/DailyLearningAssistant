Archival Candidate Isolation and Commitment Downgrade

C14 归档候选片段的隔离与承诺降级

完整讲解

归档候选片段的隔离与承诺降级，说白了就是：有些旧东西可能以后有用，不能直接丢掉，但也不能继续摆在客厅当新主家具。做法是把它搬进一个明确标注的储藏室，贴上说明“这里只是候选片段，不是新核心，也不是运行入口”。这样既保留了可追溯性，又降低了它对当前系统的承诺：别人不能因为看到这个文件，就以为它已经被当前程序调用、已经被维护、已经被验证。这里的“承诺降级”不是贬低材料价值，而是把它的证据身份说清楚：它可以用于参考、考古、未来候选，但不能冒充当前核心实现或可运行入口。可以想象一个学校社团整理旧器材：坏掉但零件还有用的麦克风被放进“也许有用”箱子，箱子上写着“不要直接拿去演出”，谁想用必须先检查、测试、登记。归档候选片段就是那个箱子，保留不等于恢复上岗。

原理逻辑

  1. 保留可追溯性与提升实现等级是两件事：前者靠目录与说明保留，后者要靠内容级、运行级证据。
  2. 隔离目录是一种显式声明边界，它用物理位置告诉读者：这里只是候选片段，不是新核心，也不是运行入口。
  3. 承诺等级属于证据身份信息，它决定读者能拿这份材料支撑什么结论，而不评价材料本身的价值。

具体例子

0cda6e4 删除了大量旧应用文件，包括后端、前端、E2E、迁移、测试与依赖配置，同时新增 archive/maybe_useful/ 隔离候选片段，并由归档 README 明确这些片段不是新核心或运行入口。这个例子说明的是资产治理设计线索，不是今天新增的运行验证。

常见误区

  • 只要归档片段还在仓库里，就说明它仍是当前可用代码。实际上目录隔离恰恰是在降低承诺，而不是提升实现等级。
  • 只要 README 写了“也许有用”，就等于已经验证它能用。文档声明说明的是用途与承诺等级，不是运行验证结果。

概念关联

关联概念关系说明
C16 非严格JSON输出的宽容解析与严格验证边界两者同来自 0cda6e4 归档线索：C14 把旧片段放入隔离目录并降低承诺，C16 说明即使归档片段里有解析函数，也只能作为待确认证据。
C1 证据分离文件列表和归档 README 只能支撑归档治理的设计线索，不能升级为运行验证或当前核心事实。
C13 当前真源与历史附录分离历史附录与归档候选都保留可追溯性，但都不冒充当前真源或新核心运行入口，二者是同一种边界思路的邻近参照。

继续深入问题

  2. 如果要自动检查归档片段没有被当前运行入口引用，可以设计哪些最小检查规则和输出字段？
  3. 当某个归档片段后来被证明有用，把它升级为新核心需要补哪些证据、审查步骤和运行验证？

C16 非严格JSON输出的宽容解析与严格验证边界

完整讲解

大语言模型有时不会老老实实只输出一段 JSON，而会包上 Markdown 代码围栏，或者在前后加说明。宽容解析就像拆快递时允许剪开外层泡沫：它只负责把常见的完整外围 Markdown fence 去掉，拿到里面那段文本。但拆开包装不等于里面货物合格，所以还要有一层严格验证：由调用方检查 JSON Schema，拒绝 NaN 和 Infinity 这类非有限数值。核心边界是“解析层可以有限宽容，验证层必须严格”，不能让“我能把它解出来”冒充“这份数据已经合格可用”。像机场安检先帮你把外套脱下来放进托盘，这叫宽容处理包装；但外套脱了不代表人一定通过安检，真正的身份和违禁品检查还在后面。解析器只负责拆包装，Schema 验证才是安检。

原理逻辑

  1. 模型输出可能带围栏或前后说明，因此解析层需要被允许处理一种明确限定的包装形态。
  2. 拆开包装只得到一段文本，文本是否合格必须由 Schema 与字段语义检查来判断，两者是不同职责。
  3. NaN 与 Infinity 这类非有限数值即使能被解析器读入，也必须在验证层被拒绝，否则“可解出”会被当成“可用”。

具体例子

归档 fragments.py 中的 decode_json_text 只解开完整外围 Markdown fence，JSON Schema 由未来调用方验证，并拒绝 NaN 和 Infinity。这个例子来自 archive/maybe_useful 归档片段局部 diff，待确认，不是新核心，也没有运行验证。

常见误区

  • 只要 JSON 解析成功，就说明模型输出可靠、字段齐全、可以入库。实际上解析成功只说明文本能被拆出结构，Schema 验证、字段语义、身份确认和入库判断仍是不同职责。
  • 宽容解析意味着可以容忍任意前后说明。宽容应被限定为常见完整外围 Markdown fence 的白名单，而不是对所有包装都放行。

概念关联

关联概念关系说明
C17 字段投影解析、验证、字段投影、身份确认和入库分属不同职责，不能用解析成功替代整条处理链的结论。
C1 证据分离能解开 Markdown fence 只说明解析层局部成功，不等于 Schema 验证通过，更不等于运行级事实成立。
封闭输入契约与字段存在性语义宽容解析不能把字段存在性语义混在一起，未提供、显式空值、只读与未知仍需由严格验证层分别判定。

继续深入问题

  1. 如何为宽容解析器设计白名单，只允许解开完整外围 Markdown fence，而不把任意前后说明都当作合法包装？
  2. 当模型输出 NaN 或 Infinity 时，解析层、验证层和调用方各自应如何报告失败原因，才能让问题可复核？
  3. 如何把解析、Schema 验证、字段投影、身份确认和入库写成一条职责清楚、可检查的处理流水线？

C4 确认令牌的职责分离

完整讲解

确认令牌可以理解成一张“我已经知道风险并明确同意”的签字单。服务端生成 token，并把它绑定到操作者、对象、动作、目标修订、影响范围和有效期。它的作用是证明风险确认这件事发生过，但它不是万能通行证：签字单不能代替门禁权限，不能代替版本匹配，不能代替锁，也不能代替状态机检查。换句话说，确认令牌只负责“风险确认”这一项职责，其他执行控制必须各司其职。像医院做有风险的检查：患者签了知情同意书，不等于医院可以跳过身份核对、设备检查、医生资质和手术排期，同意书只证明患者知情同意，不能替代整套医疗安全流程。常见误区是只要请求里带了确认 token，就可以自动重试、跳过并发检查或直接推进业务状态，而 token 只证明风险确认，不能替代 expected_revision、权限、锁或状态检查。

原理逻辑

  1. 有副作用请求同时牵涉多种控制：风险确认、并发匹配、权限、锁与状态检查，各自解决不同失败模式，不能互相顶替。
  2. 确认 token 的意义来自它的绑定字段：一旦操作者、对象、动作、目标修订、影响范围或有效期不匹配，这份确认就不再指向当前这次操作。
  3. 把人工确认边界、凭证有效期和风险 id 写进当前契约，才能让“风险确认”这件事可审计；但契约文本本身只是设计证据。

具体例子

设计契约中出现 Confirmation={confirmation_token:string!, acknowledged_risk_ids:string[]!}。有副作用请求收到 412 后，如果考虑自动重试，不能只看 token 是否存在，还要检查 token 是否仍绑定同一操作者、对象、动作、目标修订、影响范围和有效期，同时仍需 expected_revision 匹配、权限、锁和状态检查。这里只有设计契约文本，未实现、未运行验证。

常见误区

  • 只要请求里带了确认 token，就可以自动重试、跳过并发检查或直接推进业务状态。token 只证明风险确认，不能替代 expected_revision、权限、锁或状态检查。
  • 确认 token 与幂等键可以互替。幂等键防止重复提交产生重复副作用，确认 token 记录风险确认，二者服务同一请求但不承担同一职责。

概念关联

关联概念关系说明
有副作用请求的幂等性键幂等键防止重复副作用，确认 token 记录风险确认，二者都不能替代 expected_revision、权限、锁或状态检查。
C1 证据分离确认 token 出现在设计契约中，只能证明设计上存在风险确认机制，不能证明执行控制已经正确或已经运行验证。
C13 契约显式化人工确认边界、确认凭证有效期和风险 id 需要写进当前契约，历史文档不能冒充当前确认规则。

概念之间的关联

三个概念共同围绕一个判断：局部材料可以支撑“设计上存在某机制”或“归档片段中出现了某逻辑”，但不能自动支撑“已经实现、已经运行、已经验证或已经成为当前核心”。C14 把旧片段放入隔离目录并通过 README 降低承诺；C16 把解析成功与验证通过分开；C4 把风险确认凭证与并发控制、权限、锁和状态检查分开。它们不是同一主题的三节重复课，而是三个不同边界：资产治理中的承诺降级、外部输出处理中的解析与验证分责、安全架构中的确认凭证与执行控制分责。C1 的证据分离是上位边界，C13 的当前真源与历史附录分离可作为 C14 的邻近参照。

今日最值得记住的一句话

解析成功不等于验证通过，存在片段不等于当前可用，带了确认 token 也不等于可以跳过执行控制。
