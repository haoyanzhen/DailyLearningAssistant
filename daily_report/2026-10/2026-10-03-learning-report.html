检查窗口与提交证据边界

Check Window and Commit Evidence Boundary

文件改了不等于当天事实，证据落在窗口内才算。

核心要点

  • 检查窗口给“今天”划定明确时间范围，只有窗口内可确认的 Git commit 或 ref 元数据才能作为当天证据。
  • 未暂存、未提交、未跟踪文件即使本地存在，也不能自动算作当天变化。
  • 远端 ref 是否变化必须结合访问状态和前后值判断，不能只凭标题或 HEAD 引用推断。

检查窗口与提交证据边界

完整讲解

检查窗口可以理解成给“今天”画一条明确的时间线。就像学校规定“今天 0 点到 24 点提交的作业才算今天完成”，Git 监控也会规定一个时间范围，例如 2026-10-02T00:00:00+08:00 到 2026-10-03T00:00:00+08:00。只有落在这个窗口内、并且能作为 Git commit 或 ref 元数据确认的内容，才能作为当天证据。未暂存、未提交、未跟踪的文件虽然可能存在于本地，但没有进入提交历史，因此不能自动算作当天变化。这个概念的关键不是“文件有没有改”，而是“系统有没有足够证据把它归到这一天”。

原理逻辑

  1. 时间窗口是状态判断的输入边界，先决定证据是否属于目标日期，再解释提交或 ref 变化。
  2. Git 证据等级不同：提交历史、ref 元数据、本地未提交文件不能互相替代。
  3. 只读远端访问只能确认读取到的 ref 指针状态，不能补全未读到的提交详情。

具体例子

假设检查窗口是 2026-10-02T00:00:00+08:00 到 2026-10-03T00:00:00+08:00。某个仓库在 2026-10-03T01:00:00+08:00 有一个提交，这个提交不能算作 2026-10-03 当天窗口证据；如果本地还有未提交的修改，即使文件内容已经变化，也不能作为当天 Git 提交证据。

常见误区

  • 看到某个文件存在、某个提交标题提到某个功能，或者看到 HEAD 被 origin/main 引用，就直接认为“远端当天发生了变化”。
  • 把本地未提交修改或窗口外提交误判为当天新增。

概念关联

关联概念关系说明
Git ref 指针变更检测ref 是否变化必须放在明确时间窗口内解释。
只读远端监控只读访问只能提供 ref 元数据，窗口决定这些元数据能否作为当天证据。
资产 manifest资产文件的修改也必须落在窗口内提交中，才能进入当天交付记录。

继续深入问题

  1. 如果提交时间、作者时间和检查窗口使用不同时区，应如何设计归属规则？
  2. 当 rebase 或合并改写提交时间时，检查窗口如何避免把旧工作误判为当天新增？
  3. 未提交文件和未跟踪文件是否应该进入另一类本地草稿证据，而不是直接忽略？

资产 manifest 与交付契约

完整讲解

资产 manifest 可以理解成“资产行李牌”或“道具清单”。游戏项目里有很多素材，比如音乐、音效、地图、角色头像，如果只把 .png、.wav、.ogg 等文件放进目录，系统并不知道它们属于哪个版本、从哪里来、是否经过审查、是否能被运行时使用。manifest 就是机器可读的清单，它把资产文件、用途、来源、生成记录、审查记录和运行时接入绑定在一起。当天材料中，音频资产有 music_manifest.json、sfx_manifest.json、catalog.json，地图资产有 manifest.json、layout_reference.json、input_manifest.json，角色头像有 delivery_review.json、postprocess_manifest.json 和契约检查工具。这些文件共同说明：资产交付不是“文件存在即可”，而是要有可检查的证据链。

原理逻辑

  1. manifest 提供结构绑定，把文件从孤立资源变成可登记、可追溯的交付对象。
  2. provenance、review、acceptance 分别回答来源、审查和验收问题，形成不同证据层。
  3. 运行时接入需要 manager、director 等对象使用资产，才能从“已交付文件”进入“可运行系统”。

具体例子

一个音乐资产目录里有 music.wav、music_manifest.json、source_record.json、acceptance.review.json。music_manifest.json 记录这个音乐文件属于哪个系统、用途是什么；source_record.json 记录来源信息；acceptance.review.json 记录验收结论；运行时还需要 music_manager.gd、sound_manager.gd 等对象接入，音乐才能真正进入游戏流程。

常见误区

  • 把 manifest 当成内容审查本身，认为清单登记就能证明像素、音频或碰撞数据正确。
  • 认为生成完成就等于验收通过，或者验收通过就等于运行时可用。

概念关联

关联概念关系说明
生成资产来源、审查与验收记录manifest 提供清单，provenance 和 acceptance 提供来源与验收证据。
运行时分层清单中的 runtime 资产需要 manager、director 等对象接入才能被游戏使用。
检查窗口只有窗口内提交的 manifest 和资产变化才能作为当天交付证据。

继续深入问题

  1. 当 manifest 中登记了文件但文件缺失时，应该报错、跳过还是降级为待确认？
  2. source、generated、runtime 三层资产如何命名和绑定，才能避免同名文件覆盖？
  3. 二进制资产只确认文件变化时，manifest 能证明哪些事实，不能证明哪些事实？

难度测量与平衡选择

完整讲解

游戏难度如果只靠“我觉得太难”或“我觉得太简单”，就很难稳定修改。难度测量与平衡选择把这个问题变成一条工程链路：先通过模拟实验得到可比较数据，例如 win_rate_20.json 这类胜率结果；再用调参工具汇总多个关卡的数据；然后把选择结果沉淀成 challenge_balance_selection.json 这样的选择记录；最后让关卡、目标、武器等运行时数据通过 config_registry.gd 等入口进行校验。这里的关键不是某个具体公式，而是“测量—比较—选择—校验”的流程。材料没有给出随机种子、置信区间或最终平衡效果，因此只能确认工具链和选择记录存在，不能断言它一定让游戏变得更好玩。

原理逻辑

  1. 模拟实验提供可比较数据，把“难”和“简单”转成可重复观察的胜率指标。
  2. 工具汇总和测试保证选择逻辑可检查，避免单次结果或手工判断直接决定参数。
  3. 选择记录与配置注册表、运行时校验绑定，使平衡结果可审计、可进入运行系统。

具体例子

假设关卡 m1 的模拟结果文件名为 level_m1_win_rate_20.json。tune_challenge_difficulty.py 可以汇总多个关卡的胜率数据，summarize_challenge_tuning.py 生成摘要，test_challenge_tuning.py 检查调参工具本身，challenge_balance_selection.json 记录最终选择。之后关卡 JSON、目标 JSON、武器 JSON 等数据再通过 config_registry.gd 和 validate integrated runtime data 相关提交进入运行时校验。

常见误区

  • 把胜率数字直接当成最终答案，认为胜率越高越好。
  • 认为一次模拟结果就能决定关卡参数，忽略样本、随机性和关卡数据影响。

概念关联

关联概念关系说明
模拟实验胜率模拟提供可比较的数据基础。
配置注册表平衡选择结果必须进入运行时数据校验后才能使用。
多层测试调参工具本身也需要测试，避免汇总或选择逻辑出错。

继续深入问题

  1. 如果两次模拟胜率接近，如何设计选择规则来避免随机波动导致反复改参数？
  2. win_rate_20.json 这类结果文件应如何记录样本数、随机种子和参数版本，以便复现？
  3. 平衡选择记录如何与关卡数据版本绑定，避免旧选择被新数据误用？

概念之间的关联

三个概念共同体现“证据入口—结构绑定—数据决策”的关系。检查窗口决定哪些 Git 提交和 ref 元数据能进入当天事实；资产 manifest 决定素材、生成物和运行时文件如何被清单、来源、审查和验收记录绑定；难度测量决定关卡参数如何从模拟数据变成可校验选择。
