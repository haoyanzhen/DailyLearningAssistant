精读文章 · 软件工程 / 信息架构

C2 现行设计、历史归档与工作单的索引分层

完整讲解

你可以把项目文档想成一座图书馆。现行设计入口像今天仍在使用的借阅目录，历史归档像闭架书库里的旧版本，工作单像管理员记录为什么要清理某本旧书的便签。三者都可能提到同一个对象，但身份完全不同：现行设计回答现在按什么规则做，历史归档回答过去曾经怎么想，工作单回答为什么发生变更、后面还要做什么。索引分层就是让读者一进来就知道自己在看哪一层，而不是把旧版本误当成当前说明书。材料中可确认 README、设计映射、项目状态和 file_map 同步更新，退役设计文件被移入归档目录，并出现归档 README、manifest.json 和清理工作单；但这些只能说明历史材料中有过提交级和内容级的整理动作，manifest 全文与校验输出没有展示，所以不能声称归档治理已经通过运行验证。

原理逻辑

  1. 入口分层保护承诺等级：现行入口代表当前可参考设计，历史归档代表已退役或降级材料，工作单代表追溯原因和后续动作。
  2. 同一个对象可以同时出现在三类入口中，但读者必须能通过目录、声明和字段判断它当前处于什么状态。
  3. 内容级或提交级线索只能支撑“已整理”这类结论，不能自动升级为“校验通过”或“治理运行完成”。

具体例子

仓库里有 docs/current/design.md、docs/archive/2025-old-design.md 和 work_orders/cleanup-001.md。design.md 是当前设计入口，旧设计文件应标明“历史归档，不得作为现行规则”，工作单记录归档原因与后续动作。若 manifest 只列清单但没有校验输出，只能写“已完成归档入口整理，manifest 校验待确认”。

常见误区

  • 只要文件放进 archive 目录，就算治理完成。
  • 有 manifest.json 就说明校验已经通过。
  • 把工作单当成现行设计说明，仿佛计划中的清理动作已经等于完成状态。

概念关联

关联概念关系说明
C1 设计契约与实现状态的证据分离现行入口、历史归档和工作单本身就是不同来源的证据，不能互相冒充，报告措辞必须停在对应证据层级。
C6 Agent 输出的提案态与提交凭证分离C2 区分文档的现行、归档和工作单，C6 区分 Agent 的提案态和提交凭证，二者都在处理状态分层。
C1 证据分层对归档升级的约束归档片段要升级为新核心，必须补齐内容级、实现级甚至运行级证据，不能仅凭“看起来有用”就升级。

继续深入问题

  1. 当一份项目状态既像当前说明又像历史记录时，应依据哪些字段判断它该留在主文件还是归档到附录？
  2. 怎样设计最小校验规则，自动发现当前状态文档混入了历史快照内容？
  3. 当某个归档片段后来被证明有用，把它升级为新核心需要补哪些证据、审查步骤和运行验证？

C6 Agent 输出的提案态与提交凭证分离

完整讲解

Agent 输出很像实习生写好的草稿：它可能很有用，也可能已经引用了正确的资料编号，但草稿不等于已经盖章生效的合同。C6 的核心是：LLM/Agent 产生的是待校验的结果提案，不是提交凭证。Knowledge 服务可以把候选结果准备成隔离产物，但它不能凭自己就把默认版本切过去，也不能改写 Session/Review 的绑定关系。真正把提案变成业务事实的，是经过校验、授权和提交边界之后的 writer 或相应应用模块。材料中可确认的是 6635076 的设计文档线索：Agent 输出是提案，Knowledge 服务可准备隔离产物，但不能独立切换默认版本或改写绑定。这里必须标明证据层级：这是内容级设计材料，未显示已实现，也没有运行验证。因此不能把“设计上应该重新校验”写成“系统已经自动重新校验”。

原理逻辑

  1. 生成只回答候选答案长什么样，没有回答它是否满足当前 Schema、权限、业务状态、版本绑定和审计要求。
  2. 隔离产物只是待校验对象，默认版本切换、Session/Review 绑定改写和业务事实提交需要额外授权与提交边界。
  3. 哪些校验可以复用 Agent 自检、哪些必须由 writer 重新执行，必须逐项确认，不能让生成者自己批准自己的结果。

具体例子

Agent 读了几篇论文，提出“把 KnowledgeVersion 的默认内容换成新摘要”，并生成一个隔离产物。Knowledge 服务可以把这个产物放在临时区域，但默认版本仍是旧版本，Session 和 Review 仍绑定原来的知识版本。只有当 writer 重新检查 Schema、业务状态、授权和版本绑定，并通过提交接口写入后，新摘要才可能成为业务事实。

常见误区

  • 模型已经生成完整结果，所以任务已经完成。
  • Knowledge 服务已经生成隔离产物，所以默认版本已经更新。
  • 所有校验都可以复用 Agent 的自检结果，不需要 writer 重新执行。

概念关联

关联概念关系说明
C8 资料标识命中不等于授权通过Agent 输出即使包含文件 ID、DOI 或缓存命中，也只是提案和线索，不能绕过当前主体、Project、业务状态和资料政策的授权判定。
C1 设计契约与实现状态的证据分离Agent 生成属于提案级，writer 重新校验和提交才可能进入实现级或运行级事实，报告必须按证据层级表达。
C2 现行设计、历史归档与工作单的索引分层C2 区分文档的现行、归档和工作单，C6 区分 Agent 候选结果、隔离产物和提交凭证，二者都在处理状态分层。

继续深入问题

  1. 当 Agent 输出被 Knowledge 服务准备成隔离产物后，哪些校验必须由 writer 重新执行，哪些可以复用？
  2. 如果 Task 成功但业务 Run 仍处于待确认状态，报告应该怎样分层表达，避免读者误解为已完成？
  3. 如何验证 Knowledge 服务不能独立切换默认版本或改写 Session/Review 绑定？

C8 资料标识命中不等于授权通过

完整讲解

知道一本书的书架编号，不等于你有借阅权限。C8 说的是：文件 ID、DOI、缓存命中、全局论文身份，甚至正文长度，都只是定位线索或输入信息，不能直接推出现在可以使用这份资料。授权判定要从当前主体和 Project 权限出发，再检查业务状态、版本或候选范围，接着检查本次执行的资料读取政策，再判断资料本身和来源依赖是否满足政策，最后才进入受控读取、上下文构造或外部调用。材料中可确认的是 7d4bf93 的局部 diff 线索：标识命中不能跳过授权，正文长度不是权限边界。但这是内容级证据，未显示已实现，也没有运行验收，因此不能写成某个 Worker 已经在中途政策变化后完成了重验。

原理逻辑

  1. 标识命中只说明系统知道资料是谁，授权通过才说明当前主体在特定 Project、业务状态和资料政策下可以使用它。
  2. 授权判定应按主体与项目权限、业务状态与候选范围、资料读取政策、资料与来源依赖分层执行，而不是从文件 ID 直接跳到读取。
  3. 执行中途政策变化可能触发边界重验，缓存命中也不能跳过；拒绝路径还要保持无副作用。

具体例子

你住酒店时知道某个房间号，甚至看到门牌上写着房型，但房卡打不开门。前台要检查你是不是当前住客、房间是否已分配、是否在有效时段内、有没有特殊限制，才会给你开门权限。资料系统也一样：DOI 和文件 ID 只是门牌号，不是万能房卡。

常见误区

  • 有文件 ID 就能读，或者 DOI 是公开的所以全文一定能进上下文。
  • 缓存命中就说明当前用户有权限，正文越长越像公开资料。
  • 拒绝时只返回“没权限”却已经产生了读取或上下文副作用。

概念关联

关联概念关系说明
C6 Agent 输出的提案态与提交凭证分离Agent 输出即使包含文件 ID、DOI 或缓存命中，也只是提案和线索，不能据此绕过授权成为提交凭证。
C11 乐观并发与状态语义授权判定需要区分业务 revision、内部执行 epoch 和快照版本，不能把执行序号或缓存标识误当作业务授权依据。
C1 设计契约与实现状态的证据分离授权条件、拒绝后果和证据记录必须标明是设计级、实现级还是运行级，设计文档不能冒充运行验收。
