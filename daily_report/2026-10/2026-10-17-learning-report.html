稳定全序与游标分页

Stable Total Order & Cursor Pagination

排序加唯一键打破平局，翻页记住坐标而不是页码。

核心要点

  • 只有 created_at 一个排序键时，时间相同的记录之间没有确定次序，翻页边界就可能重复或漏项；加上唯一第二排序键 id，created_at DESC,id DESC 让每条记录都有唯一坐标。
  • 游标分页不记页码，而是记住上一页最后一条的坐标，下一页请求从这个坐标之后继续取，meta.next_cursor 保存坐标，meta.has_more 表示是否还有下一页。
  • 本质是两步转换：先把“排序”变成稳定全序，再把“翻页”变成基于坐标的继续读取。
  • 分页参数和响应字段的语义必须清楚，游标才可解释，因此它依赖明确的输入契约。

基于修订号的乐观并发控制

Revision-based Optimistic Concurrency Control

写入前先报出“我基于哪一版改”，版本对得上才允许覆盖。

核心要点

  • 不提前上锁，而是在写入时检查客户端“以为的版本”：客户端发送 expected_revision=7，表示“我是基于第 7 版改的”。

  • 本质是把“当前版本等于我期望的版本”作为写入前提，避免旧版本悄悄覆盖新版本。

稳定全序与游标分页

完整讲解

假设你在看一个按时间倒序排列的列表。如果只按 created_at 排序，两个记录如果时间完全相同，谁在前谁在后可能每次都不一样。翻页时，上一页的最后一条和下一页的第一条就可能重复，或者中间漏掉。解决方法是加一个唯一的第二排序键，例如 id：created_at DESC,id DESC。这样每一条记录都有一个唯一的坐标。游标分页不是记页码，而是记住上一页最后一条的坐标；下一页请求从这个坐标之后继续取。meta.next_cursor 保存这个坐标，meta.has_more 告诉前端还有没有下一页。它的本质是把“排序”变成稳定全序，再把“翻页”变成基于坐标的继续读取。

原理逻辑

  1. 单一时间键不唯一：created_at 可能重复，重复值之间没有确定次序，翻页边界因此不稳定。
  2. 加入唯一键后形成稳定全序：created_at DESC 与 id DESC 组合使每条记录获得唯一坐标，顺序可复现。
  3. 把翻页表达为坐标续读：用 meta.next_cursor 记录上一页最后一条的坐标，用 meta.has_more 表达是否还有下一页，避免页码在数据插入时发生偏移。

具体例子

论文列表第一页按 created_at DESC,id DESC 返回，最后一条是 created_at=10:00:03、id=105。next_cursor 记下这个坐标；第二页取 created_at 小于 10:00:03，或 created_at 等于 10:00:03 且 id 小于 105 的记录。

常见误区

  • 把游标分页当成页码分页，以为页号是可以长期引用的稳定位置。
  • 以为只要有 created_at 就足够稳定；其实时间戳可能重复，插入新数据也会让页码偏移，稳定全序才能让游标有确定位置。

基于修订号的乐观并发控制

完整讲解

多个客户端可能同时修改同一条数据。如果系统只让后到的写入直接覆盖，先写入的人就会丢失。乐观并发控制的思路是：不提前上锁，而是在写入时检查客户端“以为的版本”。每个对象有一个 revision。客户端发送 expected_revision=7，表示“我是基于第 7 版改的”。服务端比较当前 revision：如果还是 7，就接受并生成第 8 版；如果已经是 8，说明别人先改过，就返回 412，让客户端重新读取、合并或提示用户。若客户端根本没带 expected_revision，服务端返回 428，要求补上这个前提。它的本质是把“当前版本等于我期望的版本”作为写入前提，避免旧版本悄悄覆盖新版本。

原理逻辑

  1. 先假设不冲突：不提前加锁，让读写可以并行进行，只在提交写入时做版本检查。
  2. 把版本等式当作写入前提：expected_revision 与服务端当前 revision 相等才允许写入并生成新版本号。
  3. 用明确的协议状态表达结果：版本失配返回 412 让客户端处理冲突，前提缺失返回 428 要求补齐 expected_revision。

具体例子

更新论文元数据时，客户端发送 RevCommand={expected_revision:7,...}。服务端当前 revision=8，于是返回 412 Precondition Failed；如果请求缺少该字段，则返回 428 Precondition Required。

常见误区

  • 以为 expected_revision 是权限或锁；其实它不阻止别人同时读或改，只在提交时发现冲突。
  • 把 412 当成系统错误，其实它是要求客户端处理冲突的正常协议状态。

概念关联

关联概念关系说明
资源槽独占与构建运行状态机两者都在维护写一致性：修订号避免旧写入覆盖新状态，资源槽确保同一项目至多一个构建写入者。
幂等键同属写路径防线，但修订号解决并发覆盖，幂等键解决重复提交，不能互相替代。
确认令牌确认令牌关注风险确认与职责分离，不能代替 expected_revision 的并发检查。

资源槽独占与构建运行状态机

完整讲解

构建一个项目可能很重，系统需要保证同一项目不会同时被两个构建任务写入。资源槽独占就是这个意思：把“构建资格”看成一把唯一的钥匙。ConstructionRun 处于 paused 时仍持有钥匙；取消才释放；继续使用原实例，不新建；重跑会创建新 Run，旧 Run 变成 cancelled，新 Run 接管钥匙，并记录替代原因和关联的新 Run；queued 只是排队，不占钥匙。这个状态机的关键不变量是：同一项目至多只有一个持有构建资格的 Run。它不是简单的“状态标签”，而是用资源槽和状态转移把互斥写资格表达清楚。

原理逻辑

  1. 资格与状态分层：资源槽表达“谁有写资格”，状态机表达“当前处于哪个阶段”，两者不能混为一张状态标签。
  2. 迁移规则固定：paused 仍持槽、取消释放槽、继续沿用原实例、重跑新建实例并由新 Run 接管槽。
  3. 以不变量约束迁移：同一项目至多一个持有构建资格的 Run，重跑时必须保证旧 Run 被标记 cancelled，避免两个 Run 同时持槽。

具体例子

Project P 的 ConstructionRun R1 处于 paused，仍持有独占构建资格。此时重跑：创建 R2，把 R1 标记为 cancelled，R2 接管原槽，记录 replaced_by=R2 和原因；如果 R2 还在 queued，则它不占槽，不能被认为已经构建。

常见误区

  • 把 queued 当成正在构建；其实排队只是等位，不占构建资格。
  • 以为 paused 会释放资源，或以为重跑就是继续旧 Run；其实暂停仍持槽，重跑会创建新 Run 接管钥匙。
  • 把某个 attempt 的局部失败显示成整轮失败，忽略了资格、实例和局部尝试是不同层次。

概念关联

关联概念关系说明
基于修订号的乐观并发控制两者都在维护写一致性：修订号避免旧写入覆盖新状态，资源槽确保同一项目至多一个构建写入者。
稳定全序与游标分页Run、attempt 和事件列表需要稳定排序与游标分页，才能可靠翻页审计。
