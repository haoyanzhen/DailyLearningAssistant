有副作用请求的幂等性键

Idempotency Key for Side-Effectful Requests

幂等键是业务请求的订单号：只防重复下单，不负责权限、版本和业务完成。

核心要点

  • 用唯一编号标识同一件业务请求，服务端据此识别重复提交。
  • 目标是防止重复提交造成重复副作用，而不是保证请求一定成功。
  • 不能替代并发匹配、权限、锁或状态检查。
  • 当天材料只有设计契约中的 Idempotency-Key 约定，没有实现或运行验证。

有副作用请求的幂等性键

完整讲解

有副作用的请求一旦执行就会改变外部世界，例如创建订单、扣款、发邮件或生成业务记录。网络不稳定时，客户端可能没收到响应就重试；若服务端把重试当成全新请求，就可能产生两遍副作用。幂等性键给“同一件业务请求”一个唯一编号，客户端重复提交时携带同一编号，服务端据此识别并避免重复产生副作用。当天材料可确认的是设计契约中约定有副作用业务 POST 使用 Idempotency-Key，但没有实现或运行验证；它处理重复提交，不替代并发匹配、权限、锁或状态检查。

原理逻辑

  1. 有副作用请求会改变外部世界，失败重试与响应丢失会带来重复执行风险。
  2. 客户端为同一业务请求携带稳定幂等键，服务端据键识别重复提交并去重。
  3. 幂等键只覆盖重复提交问题，版本冲突、权限、锁和业务终态仍需其他机制判断。
  4. 契约中出现 Idempotency-Key 只是设计层证据，不能推出实现或运行验证已完成。

具体例子

假设客户端发起“创建订单”的 POST 请求，并携带 Idempotency-Key: order-abc。第一次请求其实已经在服务端创建成功，但响应在网络上丢失；客户端用同一个键重试。服务端若按设计识别出这是同一业务请求，就不应再创建第二张订单。若客户端换了一个新键再提交，则从契约上看它可能被视为另一件业务请求。这里讲的是设计机制，不是当天已验证的运行结果。

常见误区

  • 以为加了幂等性键就万事大吉，把它当成乐观并发控制、权限校验或状态机的替代品。
  • 以为设计里写了幂等键，就说明系统已经实现并验证了重复请求处理。
  • 以为幂等键能证明业务状态已经完成。

概念关联

关联概念关系说明
封闭输入契约与字段存在性语义幂等性键本身也是输入字段，需要明确出现时机、格式与校验语义；字段写进契约不等于实现完成。
业务状态与技术执行投影分离幂等键只能防止重复副作用，不能证明订单、构建或知识发布等业务状态已经完成。

精读文章 · 计算机科学 / 软件工程 / 状态建模

业务状态与技术执行投影分离

完整讲解

系统中常同时存在技术执行层状态与业务层终态。技术执行投影把执行过程投影成可观察任务状态，例如 Task 是否跑完；它不能替代 ConstructionRun、ResearchSession、ResearchResponseAttempt、ReviewRun、内容确认或 KnowledgeVersion 等业务状态。任务成功不必然表示知识发布或内容被人工采纳。当天材料中的设计契约明确指出 Task 是应用执行的技术投影，但证据停留在设计契约文本，未实现、未运行验证。

原理逻辑

  1. 技术执行层回答执行步骤是否发生，业务层回答业务对象是否到达终态。
  2. Task 等投影是可观察的执行状态，不能直接等价于 ReviewRun 通过、人工确认或 KnowledgeVersion 发布。
  3. 重跑、接管与取消属于业务状态迁移，不能只改技术执行投影。
  4. 设计契约中的状态划分是设计层证据，不等于实现或运行验证。

具体例子

假设一个文档生成 Task 显示 success，这只说明生成步骤执行成功。它不自动说明 ReviewRun 已通过、内容已被人工确认，也不自动说明 KnowledgeVersion 已发布。报告里应区分“生成任务成功”“评审通过”“人工确认”“知识版本发布”等不同状态，不能用一个 Task success 概括全部业务结果。

常见误区

  • 把任务 success 直接当成业务完成，例如生成任务成功就宣布知识已发布。
  • 以为该概念能直接解决重跑时旧 Run 和新 Run 的原子性问题；它只划清边界，不单独给出原子性实现。
  • 把执行队列完成当成内容已被人工采纳。

概念关联

关联概念关系说明
有副作用请求的幂等性键请求入口防重复副作用之后，仍需业务状态层判断最终是否完成，不能以执行任务成功替代业务终态。
封闭输入契约与字段存在性语义状态字段必须区分未知、未提供、执行成功和业务完成，不能让字段缺失被解释为完成。

封闭输入契约与字段存在性语义

完整讲解

API 输入字段不只有值，还有存在状态：未提供、显式 null、只读、未知可能在业务上完全不同。当天设计契约可确认的规则包括：未知写字段要拒绝；只读字段不得回传为更新指令；PATCH 省略表示保持原值，null 仅用于明确允许清空的字段；POST 省略使用明列默认值。把这些语义写封闭是为了减少接口歧义，避免把“用户没填”误当成“用户填了空”，把只读字段回传误当成更新命令，或把未知字段静默忽略后产生隐性错误。证据停留在设计契约文本，未实现、未运行验证。

原理逻辑

  1. 字段的存在状态与字段值是两个维度，未提供、显式空值、只读和未知需要不同语义。
  2. 封闭输入契约用拒绝未知写字段、限制只读回传、区分 PATCH 省略与 null、规定 POST 默认值来消除歧义。
  3. 明确字段语义可避免没填、清空、不能填和不知道互相冒充。
  4. 写出契约不等于实现、测试或运行验证已经通过。

具体例子

假设更新用户资料的 PATCH 请求。若传入 nickname 并省略 bio，按契约 bio 应保持原值；若传入 bio: null，且 bio 是明确允许清空的字段，才表示清空；若请求里带只读字段 id 并试图更新，应拒绝；若请求里出现未知字段，按当天设计契约应拒绝。POST 请求若省略某个字段，则使用契约中明列的默认值，而不是让服务端猜。

常见误区

  • 把 null 当成省略，认为不传和传空值是一回事。
  • 认为未知字段静默忽略更兼容，但这会让拼写错误或越权字段悄悄混过去。
  • 看到字段出现就推断身份、去重或入库结果；字段存在性只是输入契约的一部分。

概念关联

关联概念关系说明
有副作用请求的幂等性键幂等键也是输入契约的一部分，必须明确何时出现、如何校验；字段存在不等于幂等机制已经运行验证。
业务状态与技术执行投影分离状态字段也要区分未知、未提供和已完成，不能让字段缺失被解释成业务完成。

  2. 未知写字段应该统一拒绝，还是按版本兼容策略降级处理？两种策略分别会带来什么风险？
  3. 如何为报告字段设计“未采集、无变化、采集失败、未知”四种状态，使它们在聚合时无法互相冒充？

概念之间的关联

三个概念都在处理“不同层级的语义不能互相替代”。幂等性键守请求入口，防重复提交造成重复副作用；封闭输入契约守字段入口，区分未提供、显式空值、只读与未知；业务状态与技术执行投影分离守状态边界，防止 Task 成功冒充业务完成。它们分别守住入口、字段和状态三层边界，且都只能说明设计契约要求，不能自动升级为实现或运行验证结论。

今日最值得记住的一句话

设计上要求这样做，不等于系统已经这样运行；入口防重、字段辨义、状态分层都不能互相替代。
