Git 远端引用与 ref 指针变更检测

完整讲解

你可以把 Git 仓库里的 ref 想象成一块可移动的门牌。main、origin/main 这类名字不是提交本身，而是指向某个提交 SHA 的指针。git ls-remote 做的事情，相当于只问远端仓库：你的门牌现在挂在哪个编号上？它不会打开仓库，把提交对象、文件树或工作区内容都搬下来。因此，如果昨天记录 main 指向 abc123，今天 ls-remote 仍显示 abc123，我们只能确认 main 这个 ref 指针没有变化。若今天显示 def456，我们只能确认 ref 指针出现了变化线索。至于这个新 SHA 背后新增了几个提交、谁提交、改了哪些文件、代码是否可运行，都需要进一步读取提交对象、文件内容或运行测试来确认。这个概念的重点不是 Git 命令本身，而是证据等级：指针是弱证据，提交详情是更强证据，运行时行为是更强证据。

原理逻辑

  1. 仓库中的 ref 是可移动指针，名字指向某个提交 SHA。
  2. 远端 ref 检查只获得指针位置，因此只能形成弱证据。
  3. 提交详情、文件内容和运行行为需要读取对象、diff 或测试，属于更强证据。

具体例子

假设仓库 main 在历史基线中记录为 abc123。第二天使用 git ls-remote 查询，当前 main 仍为 abc123，那么可确认的结论是 main ref unchanged。不能写成今天没有提交，也不能写成没有任何进展；如果要确认提交详情，需要读取提交对象或文件 diff。

常见误区

  • 看到 ref unchanged 就认为仓库没有任何工程进展。
  • 看到 ref changed 就认为一定新增了高质量提交，并能确认提交数量、作者或 diff。

概念关联

关联概念关系说明
历史基线与 unchanged / first_seen 状态边界为历史基线提供最小比较单位，必须先有历史 SHA 和当前 SHA 才能判断 ref 是否变化。
LLM/Agent 输出可靠性与证据约束提醒 ref 指针变化只是弱线索，不能补全提交数量、作者、文件列表或 diff。

历史基线与 unchanged / first_seen 状态边界

完整讲解

变化这个词其实需要比较对象。第一次看到某个 ref 时，我们手里没有历史，只能记录：我第一次看到 main 指向 abc123。这个动作叫 first_seen，意思是建立基线。它不是新增提交，也不是变化，而是给未来的比较提供起点。有了基线后，下一次再观察同一个 ref，如果当前 SHA 仍是 abc123，才能说 unchanged；如果当前 SHA 变成 def456，才能说 changed。这里的关键是状态词必须绑定证据条件：没有历史 SHA，就不能输出 unchanged；只有当前 SHA，也不能输出 changed。对于监控系统来说，first_seen、unchanged、changed 不是三个随意形容词，而是三个有明确触发条件的状态。

原理逻辑

  1. 变化判断必须依赖比较对象，历史基线提供比较起点。
  2. first_seen 只建立基线，不表示新增提交或变化。
  3. 没有历史 SHA 不能输出 unchanged，只有当前 SHA 不能输出 changed。

具体例子

第一天监控 feature/x 指向 111，系统记录 first_seen。第二天 feature/x 仍指向 111，系统可以记录 unchanged。如果第一天没有历史记录，只看到 feature/x 指向 111，系统不能记录 unchanged，只能记录 first_seen 或 unknown。

常见误区

  • 把首次看到 ref 当成新增提交。
  • 把基线记录当成变化事实，或在没有历史 SHA 时输出 unchanged。

概念关联

关联概念关系说明
Git 远端引用与 ref 指针变更检测基线记录的是某个 ref 在某个时间指向的 SHA，依赖 ref 指针检测提供比较对象。
LLM/Agent 输出可靠性与证据约束缺少基线时系统只能输出 first_seen，不能输出 changed 或 unchanged。

精读文章 · 大语言模型 / 软件工程

LLM/Agent 输出可靠性与证据约束

完整讲解

当 Agent 或自动化系统写报告时，最大的风险不是不会写，而是把弱证据写成强事实。比如只看到 ref 指针变化，就写今天新增 3 个提交并修复了导航；只看到生成回执 receipt，就写音效已评审通过；只看到提交标题，就写功能已实现。这些都会把线索补全成完成事实。可靠输出应该像证据链一样分层：ref-only 只能写指针变化；commit 证据才能写提交数量、作者、标题；file diff 才能写文件变化；runtime test 或 QA 才能写行为通过；review、disposition、registry 才能写评审或注册状态。AGENTS.md、SKILL.md 这类文件的作用，就是把这种边界写成协作规则，让 Agent 知道哪些话可以说，哪些话必须等更强证据。

原理逻辑

  1. 自动化输出的主要风险是把弱线索补全成完成事实。
  2. 报告措辞应按证据链分层，不同证据等级对应不同可写结论。
  3. 协作规则文件可以把证据边界固化成可检查的约束。

具体例子

如果 tools/sfx 中已经出现 full_receipt 文件，但没有 review、disposition 或 registry 更新，可靠报告应写：生成回执已返回，但评审状态和注册状态未确认。不能写：音效已完成并注册。

常见误区

  • 认为模型输出流畅、文件存在、命令成功，就等于事实完成。
  • 把生成回执、提交标题或 ref 变化直接写成评审通过、功能实现或提交详情。

概念关联

关联概念关系说明
Git 远端引用与 ref 指针变更检测吸收 ref 变化的边界，因为 ref 变化只能支持指针变化结论，不能支持提交详情结论。
生成资产批量请求、回执与评审状态追踪生成回执存在不等于评审通过，评审通过不等于已注册，状态必须分别记录。
