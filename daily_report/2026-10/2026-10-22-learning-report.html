机器契约与人工文档的静态一致性检查

完整讲解

可以把 API 看成两份菜单：操作文档给人看，OpenAPI 给机器读。25aa469 新增了 contracts/p0.openapi.json、contracts/p0.coverage.json 和 scripts/check_api_contracts.py，脚本会从操作文档表格和 04-01/04-02 的 prose-only 路由里抽取签名，再从 OpenAPI 的 paths 里提取方法和路径，并用 resolve_refs() 处理 $ref。它有意排除行号，避免因为插入几行文字就误报“漂移”；也不启动应用、不联系 provider。因此它像一位对账员，只核对两份菜单的编号是否一致，并不负责试做菜，更不能证明餐厅今天能正常营业。

原理逻辑

  1. 人工文档与机器契约是同一接口承诺的两种表达，静态一致性检查通过抽取签名并比对来发现漂移。
  2. 排除行号、处理 $ref、限定检查对象，是为了让检查聚焦签名一致性，减少编辑性变化带来的误报。
  3. 静态检查属于内容级证据，证据上限是文档与契约签名一致，不能自动推导运行可用性。

具体例子

操作文档表格写 GET /papers/{id}，OpenAPI 写成 GET /paper/{id}；脚本抽取两边签名后发现路径不一致并报告漂移，但不会启动服务或调用论文接口。

常见误区

  • 脚本跑通就说明 API 能正常工作。
  • 文档一致可以替代运行验收。
  • 新增测试文件就等于测试已经执行并产生运行级证据。

概念关联

关联概念关系说明
设计契约与实现状态的证据分离静态检查属于内容级证据，只能证明文档与契约签名一致，不能替代运行级验收。
跨模块不变量验收与故障注入断言静态检查覆盖契约签名漂移，动态验收覆盖并发、故障、副作用和完整链路，两者证据层级不同。
写入所有权与业务事实提交边界契约检查保证接口签名一致，但不决定谁有权把候选结果提交为业务事实。

写入所有权与业务事实提交边界

完整讲解

可以把业务系统想成一家公司：员工可以填报销单，财务可以审核，但只有记账模块有权把这笔钱记为“已报销”。5296ae6 在 05-01_internal_module_contracts.md 里把 writer 定义为“有权组织领域校验并提交业务事实的应用模块”；repository/adapter 只是这个模块的端口实现，不是另一个业务写者。6635076 又补了一层：Agent 输出是待校验的结果提案，不是提交凭证；Knowledge 服务可以准备隔离产物，但不能独立切换默认版本或改写 Session/Review 绑定。换句话说，产生候选、校验候选、提交事实是三件事，不能因为某个模块能写数据库，就让它成为业务写者。

原理逻辑

  1. 业务事实的成立需要领域校验与提交授权，写入所有权把这种职责集中到明确的应用模块。
  2. repository/adapter 只实现持久化端口，不能因为具备写库能力就获得业务写者身份。
  3. Agent 输出与 Knowledge 隔离产物停留在提案层，只有 writer 在授权重验后才能把它们提交为业务事实。

具体例子

Agent 从论文中抽取“某实验结论”作为候选知识，Knowledge 服务把候选内容准备成隔离产物；只有具备写入所有权的应用模块在完成领域校验和当前授权判定后，才把它提交为新的 KnowledgeVersion。

常见误区

  • Agent 已经生成结构化结果，就可以直接入库。
  • repository 能写数据库，所以它也是业务写者。
  • Knowledge 能准备隔离产物，就能切换默认版本或改写 Session/Review 绑定。

概念关联

关联概念关系说明
Agent 输出的提案态与提交凭证分离Agent 输出只能作为待校验提案，不能直接成为提交凭证。
端口-适配器依赖方向与知识服务边界依赖方向限制谁可以组织校验、谁可以提交事实，适配器不能变成另一业务写者。
固定版本事实、作用域政策与当前使用资格分离即使 writer 有权提交，也必须先通过当前资料政策和授权判定，不能绕过使用资格。

精读文章 · 大语言模型 / 数据工程 / 软件工程 / 安全

固定版本事实、作用域政策与当前使用资格分离

完整讲解

可以把知识系统想成图书馆：一本书的 ISBN 和内容版本是固定的，这叫知识事实；但你能不能把书带出去，取决于你当前的借书证和借阅政策，这叫使用资格。7d4bf93 明确区分：KnowledgeVersion 固定知识事实，资料政策表示当前使用资格。政策按 (user_id, project_id) 保存，新作用域默认只允许公开资料，用户可以选择允许本项目私人资料，切换时提示风险，而且双向立即生效。更关键的是，文件 ID、DOI、缓存命中、全局论文身份都不能跳过判定；正文长度也不是权限边界。缓存的预组装上下文和 Worker 持有的政策快照，必须在下一边界重验。也就是说，知道书号不等于有权限，昨天有权限不等于今天还有权限。

原理逻辑

  1. 知识版本负责固定“事实是什么”，资料政策负责表达“当前谁能在哪个作用域使用它”，两者是不同维度。
  2. 政策按 (user_id, project_id) 保存并双向立即生效，使授权从静态标识判断转为当前作用域下的动态判定。
  3. 文件 ID、DOI、缓存命中、全局论文身份和正文长度都不是授权凭证；缓存上下文与 Worker 政策快照必须在边界处重验。

具体例子

用户 A 在项目 P 中默认只能读公开资料；后来选择允许本项目私人资料，政策按 (user_id, project_id) 保存并立即生效。若 Worker 缓存了旧政策快照，它不能因为已经拿到某个文件 ID 就继续读私人正文，而必须在下一个边界重新检查当前政策。

常见误区

  • 拿到文件 ID、DOI 或缓存命中，就等于授权通过。
  • KnowledgeVersion 固定，就代表永久可用。
  • 启动时拿到的权限上限就是当前授权。

概念关联

关联概念关系说明
资料标识命中不等于授权通过固定版本事实不代表当前使用资格，文件 ID、DOI、缓存命中都不能绕过当前政策。
按操作族的授权判定矩阵与无副作用拒绝授权矩阵按操作族规定允许与拒绝条件，C7 说明政策在读取、上下文发送和提交边界如何重验。
