精读文章 · 软件工程 / 数据工程

版本化迁移作为可执行模式的单一真源

完整讲解

可以把数据库表结构想成班级座位的“正式座位表”。如果墙上贴一张旧草稿、系统里又有一份新表、迁移脚本里还有第三份写法，大家就会按不同版本行事。C10 讲的是：真正可执行的表结构只能有一个真源，也就是版本化迁移；旧的手写 SQL 草案应退役，不能与迁移平行维护。截至今天材料可确认的是：ef9136e 删除了旧的 docs/design/07_data_schema.sql 草案；6bdf08c 明确真正可执行的表结构以后仅由版本化迁移维护，不再平行手写第二份 SQL 草案。材料还说明，逻辑记录名是迁移实现中的逻辑映射，并不要求“一记录一张表”。但今天没有建库、没有运行迁移，因此这只能作为提交级加内容级的原则来理解，不能写成数据库已经验证成功。

原理逻辑

  1. 单一可执行入口避免开发、测试和部署面对不同表结构。
  2. 迁移是结构真源，设计文档只解释逻辑记录与物理表的映射，不重新充当第二真源。
  3. 证据需要分层：提交与内容级只能支撑原则，建库、运行迁移和回滚结果才支撑运行级结论。

具体例子

假设业务上有一个“订单”逻辑记录。迁移实现可能把它落在 orders 和 order_items 两张表里，也可能把部分历史信息放到别的表；这不违反单一真源。真正违反的是：迁移里有 orders 表结构，设计目录里又手写一份不同 SQL 草案让人照着建库，使开发、测试和部署面对两套结构。

常见误区

  • 把 SQL 文件换个目录就叫版本化迁移。
  • 设计文档里画了表结构，就以为数据库已经建好。
  • 以为每个逻辑记录都必须对应一张物理表。

精读文章 · 软件工程 / 安全

按操作族的授权判定矩阵与无副作用拒绝

完整讲解

把系统想成一栋有多个窗口的办公楼。你在大厅屏幕上查到一个房间号，甚至看到某个门禁刷卡记录，并不等于你有权进入档案室。C9 讲的是：权限不能只看“我知道这个资料的 ID、DOI，或者缓存里已经有它”，而要看“当前这个人、当前项目、当前业务状态、当前资料政策，是否允许执行这一类操作”。这类操作要按操作族来分组，例如读取资料、把资料送入上下文、调用外部服务、提交业务事实，它们不是同一种权限。C8 的核心“资料标识命中不等于授权通过”可以并入这里：文件 ID、DOI、缓存命中、全局论文身份、正文长度，都不能跳过判定。C9 进一步要求：授权矩阵不仅写什么情况允许，还要写什么情况必须拒绝，以及拒绝时不得发生哪些副作用。截至今天材料可确认的是：abf1fa4 记录了按操作族索引的授权判定矩阵，列出主体与允许条件、必须拒绝及不得发生的副作用、依据与测试；7d4bf93 记录了从当前主体与 Project 权限，经业务状态或候选范围、资料读取政策、来源依赖，再到受控读取或外部调用的判定链。材料还明确，工程接入不等于运行验收；今天没有新的运行验证。

原理逻辑

  1. 操作族把读取资料、送入上下文、调用外部服务、提交业务事实分开判定，不以文件 ID、DOI、缓存命中或正文长度替代授权。
  2. 判定链逐层检查当前主体与 Project 权限、业务状态或候选范围、资料读取政策、来源依赖，再决定受控读取或外部调用。
  3. 拒绝条件与允许条件同样重要：拒绝必须是事务性、无副作用的，不能留下隔离产物、状态变更或敏感调用记录。

具体例子

一个用户在搜索结果里看到某篇论文的文件 ID，并请求把这篇论文发送到外部模型做摘要。系统不能因为文件 ID 命中或缓存命中就直接发送，而要检查当前用户和项目、论文使用政策、来源依赖以及外部调用操作族是否允许。如果判定拒绝，系统不仅不能发送请求，也不得创建带正文的导出文件、上下文快照或外部调用记录中的敏感内容。

常见误区

  • 拿到文件 ID、DOI 或缓存命中，就以为已经获得使用授权。
  • 只区分能不能看资料，却不区分看、复制到上下文、发给外部模型、提交为业务事实等操作族。
  • 只写允许条件，不写拒绝时的副作用禁令，结果返回失败却已创建隔离产物或改动状态。

精读文章 · 软件工程 / 计算机科学

跨模块不变量验收与故障注入断言

完整讲解

不变量可以理解为“无论中间发生什么，都必须始终成立的条件”。例如一个通用系统里，订单不能既显示未付款又已经已发货；一个资料引用不能一边标记为已隔离，一边又被当作正式业务事实使用。跨模块不变量验收，就是不只是测某个按钮能不能点，而是设计用例验证多个模块连在一起时这些条件是否仍然成立。C13 要求用例记录稳定 ID、规范来源或 FR 子条目、前置数据、动作与并发屏障、故障注入点、正向与负向断言、预期不发生的副作用、诊断证据和清理方式。通俗地说：先搭好场景，再故意让某个环节出错，检查该发生的有没有发生，也检查不该发生的有没有被阻止。并发屏障是为了让多个执行者故意在同一时刻冲进危险区；故障注入是为了模拟数据库失败、权限中途变化或外部服务超时。材料明确说，这是核心架构级用例的验收设计，不是已运行测试；今天更没有新增运行结果，所以不能把设计写成测试通过。

原理逻辑

  1. 跨模块不变量验收验证多个模块连在一起时条件仍成立，因为每个模块单独正确不等于组合后不产生双重写者、错误提交或残留副作用。
  2. 用例需记录稳定 ID、规范来源或 FR 子条目、前置数据、动作与并发屏障、故障注入点、正向与负向断言、预期不发生的副作用、诊断证据和清理方式。
  3. 并发屏障制造可控竞争，故障注入模拟数据库失败、权限中途变化或外部服务超时；正向断言检查应发生结果，负向断言检查不该发生的副作用。

具体例子

用一个通用多模块流程说明：提交候选结果前需要检查授权和写入边界。验收设计可设置并发屏障，让两个执行者同时尝试提交；再在写入前注入一次失败，并模拟授权状态中途变化。正向断言是只有获得授权的写入能生成正式业务版本；负向断言是失败或拒绝路径不得改写已有绑定、不得生成发货任务、不得留下未清理的隔离产物。诊断证据要说明失败发生在哪一步，清理步骤要删除测试产生的隔离数据。

常见误区

  • 写了验收用例就以为已经完成运行验证。
  • 只写正向断言，不写不应该发生什么。
  • 把故障注入当成故意制造混乱，而不是用来证明异常路径不会破坏不变量。
  • 只测单个模块，忽略跨模块承诺：每个模块单独看都对，连起来却可能产生双重写者、错误提交或残留副作用。
