核心要点

  • 目标是审计够用，而不是复制所有敏感信息；既要可追溯，也要控制隐私与存储负担。

K2 不可变配置快照的审计最小充分信息

完整讲解

不可变配置快照像给一次重要决定拍了一张“配置照片”。后来系统里的密码、密钥或当前配置改了，但这张照片不能跟着变，否则就说不清当时到底按什么规则做了决定。不可变配置快照要求：当凭据更新不能改写历史业务配置快照时，快照必须留下足以重建“当时使用了什么配置或策略、作用于谁、何时生效、来自哪个修订或执行上下文、内容摘要与完整性标记”的最小信息。它不是保存越多人越隐私的信息越好，而是保存“审计时够用”的最小充分集合。关键不是凭据本身，而是历史快照要可审计、不能被后续凭据更新污染。当前材料只能确认这是历史设计线索和历史问题方向，没有新的 schema、迁移、测试或运行验证。

原理逻辑

  1. 历史业务配置快照具有不可变性：后续密码、密钥或当前配置更新只能改变当前状态，不能反过来改写当时快照的语义。
  2. 审计重建需要一组最小字段：配置或策略内容及非敏感引用、作用域、来源修订或执行上下文、生效时间、内容摘要与完整性标记。
  3. 充分性由审计需求界定：字段太少会不可审计，字段太多会扩大隐私和存储负担，因此追求最小充分集合。

具体例子

某系统根据“审批策略快照”自动处理报销。后来管理员更新 API 密钥和审批策略，历史记录不能只写“使用当前策略”，而应至少能还原：当时作用于哪个项目或用户、策略来源修订是什么、何时生效、由哪个执行上下文触发、内容摘要是什么、完整性标记是否匹配，以及凭据的非敏感引用。这样即使密钥后来更换，历史审批仍可审计。

常见误区

  • 快照里保存当前凭据的引用就够了；这会被后续凭据更新间接改写历史语义。
  • 快照就是复制所有敏感信息；正确方向是保留审计所需最小充分信息，凭据可用非敏感引用。

概念关联

关联概念关系说明

K1 覆盖域证明与结论量化范围K2 与 K1 都要求显式记录来源、范围和时间边界：K1 约束报告结论的覆盖域，K2 约束历史快照的审计充分信息。
K5 多执行实例状态坐标与业务修订的并列表达历史快照可能需要记录执行上下文或来源坐标，但当前材料没有提供快照 schema 或重跑实现。

继续深入问题

  1. 怎样判定一组快照字段已经达到“最小充分”，而不是太少导致不可审计、太多导致隐私和存储负担过重？
  2. 凭据的非敏感引用应该怎样设计，才能既支持追溯又不把敏感凭据写进历史快照？
  3. 如果后续策略或凭据更新，如何用完整性标记和内容摘要证明历史快照没有被污染？

K1 覆盖域证明与结论量化范围

完整讲解

把“未发现变化”想成一句带范围的话。设真正想说的是全局范围 U，但实际只检查了覆盖集合 C。若只在 C 内没有发现变化，结论只能写成“在 C 上未发现变化”；当 C 是 U 的真子集时，不能升级成“U 中无变化”。这就是覆盖域证明与结论量化范围：结论必须说明它覆盖了哪些仓库、哪个时间窗、哪些采集任务成功或失败。空白结果或部分覆盖不能自动写成全局无变化。今天不是重复“无变化、未采集、失败三态”，而是进一步问：即使记录了状态，是否说明了这个状态覆盖到哪里？当前材料没有新的报告 schema、检查器或运行记录，只有历史问题级依据。

原理逻辑

  1. 全局范围 U 与实际覆盖集合 C 应显式区分；局部未发现变化不能推出全局无变化。
  2. 结论强度受覆盖域限制；状态字段必须与仓库集合、时间窗、采集任务成功或失败绑定。
  3. 空白结果至少可能表示确认无变化、未采集、采集失败或部分覆盖，必须用覆盖域字段区分。

具体例子

假设全局范围 U 是 10 个仓库，时间窗是 2026-10-26 全天。实际覆盖集合 C 只包含 3 个仓库：2 个采集成功且未发现变化，1 个采集失败，其余 7 个未采集。报告应写成：“在已成功采集的 2 个仓库、指定时间窗内未发现变化；1 个仓库采集失败；7 个仓库未采集。”不能写成“10 个仓库全局无变化”。

常见误区

  • 结果为空就等于没有变化；空结果也可能表示没有采集、采集失败、只采集了一部分，甚至时间窗没覆盖到。
  • 只要写了一个状态字段就够了；如果状态没有绑定覆盖范围，读者仍会把局部结论当成全局结论。

概念关联

关联概念关系说明
K3 证据充分性谓词覆盖域不完整时，即使有局部证据，也不能计算为全局强结论，K3 的结论强度需要以 K1 的作用域为前提。
K2 不可变配置快照的审计最小充分信息K1 与 K2 都强调来源、范围和时间边界：一个约束报告结论的覆盖域，一个约束历史快照的审计充分信息。
K5 多执行实例状态坐标与业务修订的并列表达多执行实例报告中的“成功、待确认、替代”也要说明覆盖了哪些执行实例和时间范围，不能只看一个实例就下全局结论。

继续深入问题

  1. 怎样用字段或规则自动判断覆盖集合 C 是否等于全局范围 U，从而避免把局部结论升级为全局结论？
  2. 一份负证据报告最少应包含哪些覆盖域字段，才能让读者区分确认无变化、未采集和失败？
  3. 如果只采集了部分仓库或部分时间段，报告措辞应如何按覆盖比例和失败状态自动降级？

K5 多执行实例状态坐标与业务修订的并列表达

完整讲解

重跑时，系统里可能同时存在旧执行实例、新执行实例和同一个业务对象的不同修订。K5 的核心是：不要把这三类东西压成一个状态。报告或模型应保留多维坐标：业务对象及其修订、执行实例标识或 epoch、发生时间、结果、与旧实例的替代关系。这样读者才能看清“哪个业务对象在哪个修订上，被哪个执行实例处理过，旧实例是否被新实例替代，执行结果和业务状态分别是什么”。它要避免两个方向的误读：用执行成功覆盖业务状态，或用业务状态掩盖执行失败。当前材料只提供历史问题级问题方向，没有新的状态机、资源槽或运行验证。

原理逻辑

  1. 同一业务对象可同时关联多个执行实例和多个业务修订，它们属于不同维度，不可折叠为单一状态。
  2. 重跑报告需要业务对象及 revision、实例标识或 epoch、时间、结果、替代关系等坐标并列表达。
  3. 执行层结果与业务层状态必须分开判断，避免用执行成功覆盖业务状态，或用业务状态掩盖执行失败。

具体例子

某论文构建任务重跑。业务对象 paper-123 当前业务修订是 revision 7。旧执行实例 A 的 epoch 是 1，结果失败，已被替代；新执行实例 B 的 epoch 是 2，执行成功，但业务审核仍处于待确认。报告应并列写成：业务对象 paper-123 / revision 7；实例 A / epoch 1 / 失败 / 已被 B 替代；实例 B / epoch 2 / 执行成功 / 业务审核待确认。不能只写一句“构建成功”，也不能只保留最新实例而丢掉替代关系。

常见误区

  • 新执行实例成功，所以业务必然完成；执行成功只是执行层证据，业务可能仍在待确认、待审核或被旧实例替代。
  • 旧实例失败或过期就可以完全省略；审计和重跑排查往往需要知道旧实例如何被替代、替代发生在什么时间、新实例对应哪个业务修订。
