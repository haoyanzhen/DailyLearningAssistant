C13 文档版本契约与历史附录分离

完整讲解

文档版本契约与历史附录分离，核心是让读者一眼分清“现在有效的规则”和“过去发生过什么”。根据当天材料可确认的是，设计文档保持 v1.x，有显式版本修改时递增次版本并更新日期；未版本化文档从 v1.0 开始；源码由 Git 跟踪；PROJECT_STATUS_APPENDIX.md 保存历史细节，当前有效状态以主文件为准。为什么不能混在一起？因为文档一长，历史细节很容易冒充当前规则。读者看到一段旧描述，可能以为它仍然有效；维护者也可能因为历史附录写得多，就忘了主文件才是当前真源。把当前真源、版本历史和历史附录分责，就是让每类信息待在自己的位置，承担自己的语义职责。这个机制并不自动证明文档内容正确，也不等于已经有自动检查器在运行。它提供的仍是文档治理级证据：规则上要求这样分层，提交文件列表或局部 diff 显示有相关文档约定。它能支撑“设计上要求分离”，不能升级为“运行验证已经通过”。

原理逻辑

  1. 当前真源负责表达现在有效的状态，历史附录负责保存来龙去脉，两者语义职责不同。
  2. 版本号与日期更新是文档治理规则，用来标识显式修改，而不是运行验证结果。
  3. 文档治理级证据只能支撑规则存在，不能自动升级为内容正确或行为已确认。

具体例子

可以把项目文档想成一本家庭册子：户口本记录当前住址和成员，老相册保存过去的照片。老照片很有价值，但不能拿它证明现在的住址。历史附录就像相册，当前主文件就像户口本。

常见误区

  • 看到历史附录写得很详细，就把其中的旧状态当成当前有效规则。
  • 以为文档版本号递增或日期更新就自动证明内容已经通过运行验证；其实版本规则只是文档治理证据。
  • 以为主文件与历史附录分离后，文档内容就自动正确；分离只解决职责边界，不证明内容正确。

概念关联

关联概念关系说明
C1 设计契约与实现状态的证据分离当前主文件、历史附录和版本规则都是文档治理证据，写出当前状态并不等于完成运行验证。
C17 字段投影与身份/去重/入库职责分离文档要区分当前真源与历史附录，处理流水线也要区分字段投影、身份确认、去重和入库，两者都强调显式职责边界。
证据分层与职责边界今日主题作为三张知识卡之外的统摄概念，用来说明这些概念如何共同指向同一条学习主线。

C17 字段投影与身份/去重/入库职责分离

完整讲解

字段投影与身份/去重/入库职责分离，说的是外部响应处理可以拆成多个阶段：解析、验证、字段投影、身份确认、去重和持久化。根据当天材料可确认的是，归档片段 semantic_scholar_fields 对单条已解码响应做字段投影，只负责选择字段，不负责请求、去重、身份确认或入库。为什么不能把这些职责混成一个“成功”？因为字段投影只是一个纯转换步骤：它从已经解码的响应中挑出需要的字段。字段出现在投影结果中，只能说明转换函数选择了它，不能说明这条记录的身份已经确认，也不能说明重复记录已经合并，更不能说明数据已经写入存储。每一步都有不同的判断条件和证据强度。这里要特别谨慎：该证据来自 archive/maybe_useful 中的归档片段，只能标为待确认，不是今天的新核心实现，也没有运行验证。因此今天能讲的是职责分离原理：局部转换成功不能升级为完整处理链成功。

原理逻辑

  1. 字段投影是纯转换步骤，只从已解码响应中选择字段，不承担请求、身份确认、去重或入库职责。
  2. 每个处理阶段有不同判断条件与证据强度，一个阶段成功不能代表后续阶段完成。
  3. 归档片段证据只能标为待确认，职责分离原理成立不等于该实现已成为新核心或通过运行验证。

具体例子

快递站里，扫描面单只能读出姓名和电话，不等于已经核实收件人身份，也不等于已经合并重复包裹，更不等于已经放上货架。字段投影就像扫描面单，后面的身份确认、去重和入库还要分别完成。

常见误区

  • 看到投影结果里出现了某个字段，就认为这条记录已经完成身份确认、去重或入库。
  • 把“函数成功返回字段”当成“整条数据处理流水线成功”；其实它只完成了一个阶段。
  • 把归档片段中的局部实现当成今天的新核心实现，并忽略其待确认、无运行验证的边界。

概念关联

关联概念关系说明
C1 设计契约与实现状态的证据分离字段投影成功只说明局部转换完成，不能升级为身份确认、去重完成或入库成功这类整体事实。
C13 文档版本契约与历史附录分离文档需要区分当前真源与历史附录，处理流水线也需要区分字段投影、身份确认、去重和入库，两者都要求职责边界显式化。

  3. 当某个归档片段后来被证明有用，把它升级为新核心需要补哪些审查步骤和运行验证？

C1 设计契约与实现状态的证据分离

完整讲解

设计契约与实现状态的证据分离，是把“计划做什么”“已经改了什么”“实际运行验证了什么”分成不同证据层级。根据当天材料可确认的是，AGENTS.md 要求区分计划工作、已执行工作和已验证结果；625a7a4 明确所有设计完成不等于代码实现；PROJECT_STATUS.md 写明 P0 API 与应用编排为“已同步（设计；实现待开始）”。它的底层逻辑是：结论强度不能越过证据层级。设计文档、API 契约、领域规则属于设计级证据；局部 diff 属于实现片段级证据；构建、测试、部署、运行结果才是运行级证据。看到设计完成，最多能说“设计上已同步”；看到局部 diff，最多能说“某处代码片段有改动”；只有拿到运行验证，才有资格说“行为已确认”。这不是咬文嚼字，而是防止把局部材料升级成整体事实。任务成功也不等于业务完成，技术执行成功也不等于业务终态完成。当天材料没有实现或运行验证，因此今天只能讲证据分层原则，不能宣称这些设计已经实现或通过验证。

原理逻辑

  1. 证据分层把计划工作、已执行工作和已验证结果分开，不同层级只能支撑不同强度的结论。
  2. 设计级证据说明计划或契约，局部 diff 说明片段改动，运行级证据才说明行为已被验证。
  3. 结论强度不能越过证据来源；任务成功也不自动等于业务完成或运行验证完成。

具体例子

盖房子时有设计图、施工照片和验收报告。设计图画完不能说房子已验收，施工照片只能证明某面墙砌了，验收报告才证明能住。证据不同，能说的话也不同。

常见误区

  • 把“设计完成”写成“代码完成”，把“局部 diff 出现”写成“功能已实现”，把“任务成功”写成“业务已完成”。
  • 认为弱证据反复出现就能自动合并成强结论；其实反复出现仍要保留来源层级和未验证边界。
  • 把“已同步（设计；实现待开始）”误读为“P0 API 已完成”，忽略实现与运行验证尚未提供。
