工作区状态排除边界

完整讲解

可以把 Git 仓库想象成一个正式档案柜，工作区则是你桌上的草稿本。草稿本上写了什么、改了哪里、有没有新增文件，都只说明你正在准备材料，不代表这些材料已经正式归档。这里基于当日材料可确认的边界是：未暂存、已暂存但未提交、未跟踪文件和 worktree 工作区状态不采集，不作为变化或概念依据。也就是说，判断当天是否有工程变化，主要看检查窗口内是否有提交证据；如果窗口内提交数为 0，即使工作区看起来有很多改动，也不能直接写成当天完成了某项开发。这个边界不是否定草稿的价值，而是把草稿和已提交证据分开，避免把准备中的内容误判为已经完成的内容。

原理逻辑

  1. 工作区状态表达的是准备中的材料，不等同于已经提交归档的正式证据。
  2. 检查窗口内提交数是判断当天工程变化的主要证据门槛。
  3. 未暂存、已暂存、未跟踪文件和 worktree 状态只能作为待观察状态，不进入当日提交变化结论。

具体例子

某本地仓库检查窗口内提交数为 0，但工作区里有一个未跟踪文件 report.md，还有一个未暂存修改。当天总结只能写窗口内无提交，工作区状态不采集，不能写当天完成了 report.md 的开发或修复。

常见误区

  • 看到工作区里有新增或修改文件，就认为当天一定发生了工程变化。
  • 把未跟踪文件当成已提交资产，或者把某个 worktree 里的临时状态当成整个仓库的变化。

概念关联

关联概念关系说明
检查窗口与提交证据边界检查窗口只把窗口内提交视为当天变化，而工作区草稿不在窗口内提交证据范围内。
无变化措辞的证据门槛窗口内提交数为 0 时才能写当日无变更，工作区有草稿不能推翻该结论。
自生成提交排除两者都在回答哪些 Git 相关状态可以进入工程变化证据，哪些只能作为待观察状态。

自生成提交排除

完整讲解

Git 历史里出现一个提交，只说明仓库里多了一条提交记录，并不自动说明这条记录来自人工工程进展。有些提交是系统自动产生的，例如自动发布日报、自动备份、自动脚本生成。这里基于当日材料可确认的是，DailyLearningAssistant 已忽略自身自动发布日报产生的 1 个提交，因此该提交不作为当日工程变化依据。这里的关键不是删除历史，而是做证据分类：提交存在是事实，但它是否属于工程变化证据，要看来源、意图和排除规则。若不排除自生成提交，系统每天自动运行一次，就可能被误读为每天有人推进了功能。

原理逻辑

  1. 提交存在是事实，但它是否属于工程变化证据，要看来源、意图和排除规则。
  2. 自动发布日报、自动备份、自动脚本生成等系统行为应从工程变化证据中单独分类。
  3. 排除自生成提交后，才能更准确判断当天是否存在人工或工程进展。

具体例子

DailyLearningAssistant 当天有 1 个自动发布日报提交。如果把它算入工程变化，可能误写成有人改进了学习助手；按当天材料，该提交被忽略后，不作为当日工程变化依据。

常见误区

  • 只要 Git 历史里有提交，就说明当天有人做了工程进展。
  • 认为排除自生成提交就是删除历史；实际上，排除只是把它从工程变化证据中分类出去，仍可作为系统事件保留。

概念关联

关联概念关系说明
检查窗口与提交证据边界即使提交落在检查窗口内，如果来源是自动发布日报，也可能被排除在工程变化证据之外。
无变化措辞的证据门槛排除自生成提交后才能更准确地判断当天是否存在人工或工程进展。
Agent 输出证据约束Agent 总结需要区分系统自动事件和人工工程变化，避免把自动提交补全成工程进展。

ref-only 证据下的结论强度限制与待确认线索标注

完整讲解

远端 ref 指针变化是 Git 监控中最常见的弱证据之一。当天多个远端仓库可确认的是 ref 状态从历史 SHA 变为当前 SHA，例如 refs/heads/main 的历史 SHA 与当前 SHA 不同，因此状态为 changed。但这个事实只说明某个引用现在指向了另一个 SHA，不直接包含中间新增了多少提交、提交信息是什么、作者是谁、文件列表是什么、diff 是什么或功能意图是什么。这里基于当日材料可确认的是：ref 级证据不能升级为提交级、文件级或功能级证据。Agent 生成总结时，应当把内容分成三类：可确认事实，例如 ref 指针变化；待确认线索，例如具体提交内容和文件变更；不可推断内容，例如没有 diff 时不能确认文件新增、删除、修改或功能实现。这样的输出才可靠。

原理逻辑

  1. ref 指针变化只能通过历史 SHA 与当前 SHA 的比较来确认，属于远端版本变化线索。
  2. 提交、文件和功能结论需要更高等级证据支撑，例如 commit log、提交对象、文件树或 diff。
  3. 当提交详情状态未知时，报告应强制显示不可确认字段，而不是用自然语言补全提交数量、作者或文件列表。

具体例子

某远端仓库 refs/heads/main 历史 SHA 为 92d27ed，当前 SHA 为 e1a88c6，状态为 changed。可写该 ref 指针发生变化，属于远端版本变化线索；不可写当天新增 3 个提交并修复了登录问题，除非有 commit log 或 diff 证据。

常见误区

  • 认为 ref 变化就等于提交内容变化，或者 SHA 不同就能推断新增提交数量和功能修改。
  • Agent 总结越详细越好，因此在证据不足时补全提交信息、作者或文件列表。

概念关联

关联概念关系说明
Git 远端引用和 SHA 对象标识ref 指针变化只能通过历史 SHA 与当前 SHA 的比较来确认。
Agent 输出证据约束Agent 基于远端 ref 元数据生成总结时，必须把提交、文件和功能内容标为待确认或不可推断。
无变化措辞的证据门槛ref unchanged 或 ref changed 都只能支撑对应 ref 级措辞，不能扩展到整个仓库或提交内容。

概念之间的关联

三个概念形成从易到难的递进：先处理本地工作区里容易被误判的草稿状态，再处理 Git 历史中看似提交但可能属于系统自动行为的事件，最后处理远端 ref 指针变化这种最弱但最常见的版本线索。它们的共同点是：证据的类型、来源和等级决定报告能说什么。工作区状态不是提交证据，自生成提交不是工程变化证据，ref-only 证据不是提交或文件证据。把这些边界讲清楚，可以帮助学习者在面对 Agent 生成的总结时，判断哪些句子是事实，哪些句子只是待确认线索，哪些句子超出了证据范围。

工作区草稿、自动提交和 ref 变化都只是线索，必须按证据等级限制措辞。
