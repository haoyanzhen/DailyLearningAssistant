设计文档职责分层与历史归档

完整讲解

可以把一个项目的文档想象成学校里的资料柜。如果没有分类，合同、玩法说明、旧通知、界面规范全塞在一起，读者很难判断哪份是现在生效的。设计文档职责分层就是给资料柜贴标签：contracts 放契约，gameplay 放玩法，presentation 放展示，technical 放技术，validation 放验证，history 放历史。这样每份文档都有明确角色，谁引用谁、谁更新谁也更清楚。历史归档与当前状态分离是同一思路的时间维度：项目状态会不断变化，旧状态不能继续混在当前状态文档里，否则读者会把旧快照误当成当前事实。当天证据显示 00_project_status.md 被大幅删减，新增 docs/history/00_project_status_through_20261010.md 和 docs/history/96_documentation_restructure_20261012.md，说明旧状态被迁入历史目录。

原理逻辑

  1. 职责维度：把文档按功能角色分区，读者与工具都能凭目录判断一份文档承担什么职责，谁引用谁、谁更新谁变得更清楚。
  2. 时间维度：把当前状态与历史快照分离，旧状态不能继续混在当前状态文档里，否则旧快照会被误读为当前事实。
  3. 可判断性维度：文档职责和时间边界会影响读者与工具判断“哪一份是当前真源”，因此重组不只是排版美化，而是改变真源定位方式。

具体例子

当天 30689934 的提交主题是 docs: reorganize design docs by responsibility，并出现 docs/contracts/、docs/gameplay/、docs/history/、docs/presentation/、docs/technical/、docs/validation/ 等目录线索；00_project_status.md 大幅删减，同时新增 history 下的状态归档文件。这里能确认的是路径和统计线索，具体归档规则仍待确认。

常见误区

  • 把文档重组当成单纯的排版美化，觉得内容没变就不重要；实际上职责目录和时间边界会影响读者和工具判断哪一份是当前真源。
  • 把 history 当成随便丢旧文件的地方；实际上 history 目录是给旧状态一个稳定的时间边界，而不是杂物间。
  • 因为看到了 history 路径，就断言所有归档规则和自动审计已经完成——当天只有路径与统计线索，归档规则仍待确认。

概念关联

关联概念关系说明
设计真源路径迁移与引用一致性目录先按职责重组，才引发旧路径被替换，所以文档分层是路径迁移的前提。
文档-实现-测试同步契约清楚的文档职责是后续让工具和测试找到真源的基础，同步契约需要先有可定位的真源。
历史归档与当前状态分离history 目录为旧状态提供稳定的时间边界，是同一思路在时间维度上的体现。

设计真源路径迁移与引用一致性

完整讲解

路径看起来只是文件夹位置，但在工程系统里，它常常像身份证号或接口名。工具脚本、README、Agent 技能、QA 文档都通过路径找到设计真源。比如某个脚本要读 docs/41_character_art_design.md，如果这个文件被移动到 docs/presentation/ 下，而脚本还写旧路径，脚本就会找不到真源。当天两个提交正好展示这个过程：30689934 重组文档，55b8976f 更新工具链中的设计真源路径字符串，例如 art pipeline、music README 等对 docs/presentation/... 的引用同步。这里核心原理是引用完整性：对象移动后，所有指向它的引用都要一起迁移。局部 diff 能证明路径字符串被更新，但不能证明所有引用都已找到，也不能证明工具已经运行成功。

原理逻辑

  1. 引用完整性：路径是引用标识符，对象移动后所有指向它的引用都必须一起迁移，否则出现悬空引用。
  2. 检索范围问题：路径可能出现在脚本、配置、说明文档和 Agent 技能里，有的引用还可能经过变量拼接，不能只靠肉眼判断。
  3. 证据层级限制：局部 diff 属于路径级证据，只能证明某个字符串被更新，不等于所有引用被找到，更不等于工具链运行通过。

具体例子

当天 art pipeline 脚本把 docs/41_character_art_design.md 等旧路径更新为 docs/presentation/...；tools/music/README.md、AGENTS.md、审计 skill 等也出现同步路径线索。这些线索能证明路径字符串被更新，但不能证明引用已经完整。

常见误区

  • 以为文档移动只是写作者的事，工具和 README 不用管；实际上工具脚本、审计 skill、说明文档都会因为路径变化而断链。
  • 以为做一次全局字符串替换就万事大吉；实际上引用可能散落在脚本、配置、说明文档和 Agent 技能中，还可能经过变量拼接。
  • 因为看到一个路径被更新，就断言所有引用都完整、工具链已经完全可用——局部 diff 不能支撑这种结论。

概念关联

关联概念关系说明
设计文档职责分层与历史归档它由文档职责分层引发，因为目录按职责重组后旧路径失效，才需要迁移引用。
文档-实现-测试同步契约路径迁移不只影响文档，还影响工具、README、Agent 技能和测试相关引用，是同步契约的局部表现。
文档审计自动化入口当天只看到审计脚本和 validate_design_docs.py 的修改线索，具体是否会检查路径漂移尚未确认。

UI 配置项与数据源一致性断言

完整讲解

设置界面里通常有一排选项，比如窗口尺寸、音乐模式。界面上的选项不是凭空出现的，它应该来自某个数据源，例如 window_size_options() 返回一组 Vector2i。UI 配置项与数据源一致性断言，就是用测试代码检查：界面上显示的选择器数量对不对，每个选项的文字是否等于数据源格式化后的结果。当天 cffc5555 的测试先从控件树里找 OptionButton。它用 _descendants_of_type(menu.content, 'OptionButton') 收集选择器，再按语义过滤出窗口尺寸选择器，也就是排除 menu.music_mode_selector。这样做比只数 OptionButton 总数更稳，因为页面以后多一个按钮，不等于窗口尺寸选项错了。然后测试检查窗口选择器数量为 1、item_count 等于 window_options.size()，并逐项比较文本是否等于 '%d × %d' % [window_options[index].x, window_options[index].y]。这里同时嵌入三个原理：控件树遍历负责找到控件，语义选择器过滤负责区分角色，数据源一致性断言负责比较数量和文本，二维整数向量格式化负责把 Vector2i 的 x、y 变成“宽 × 高”的人类可读文本。

原理逻辑

  1. 控件树遍历与语义选择器过滤：先从控件树收集候选控件，再按角色区分窗口尺寸选择器和音乐模式选择器，避免依赖控件树中的偶然位置或总数。
  2. 数据源一致性断言：比对界面选择器数量与 item_count 是否等于数据源返回的选项集合，把展示层与配置源绑定成可执行契约。
  3. 二维整数向量格式化：把 Vector2i 的 x、y 映射成“宽 × 高”的人类可读文本，使逐项文本比较成为可执行的格式化规则。
  4. 证据层级限制：断言被修改只是 diff 级证据；即使测试通过，也只覆盖界面文本和控件状态，不能自动升级为运行时行为已验证。

具体例子

当天 scene_presentation_test.gd 从单一 OptionButton 数量断言，扩展为窗口尺寸选择器与音乐模式选择器的组合断言：窗口选择器数量为 1，item_count 等于 window_options.size()，逐项文本等于 Vector2i 的 x、y 格式化结果；总选择器数量为 2，包含 menu.music_mode_selector，其 item_count == 3。

常见误区

  • 只断言页面上有几个 OptionButton 就算测好了；其实按钮可能来自别的用途，数量相同不代表语义正确。
  • 把界面文本断言通过当成运行时行为已经验证通过；测试检查的是控件数量、选择器存在性和文本格式，不等同于音乐模式真的会切换或窗口真的会改变。

概念关联

关联概念关系说明
