研究域与知识域的读写职责分离

完整讲解

可以把系统想象成博物馆：知识域是展厅，只展示已经密封发布的版本；研究域是研究员工作台，可以写会话、记录创建回执，但不能直接改展厅里的展品。文件说明写明 “Research owns sessions and creation receipts; Knowledge remains read-only”，并且 knowledge_read.latest_published 只读取 sealed = true 的已发布知识版本。研究域引用知识域时，拿到的是已发布、已密封的稳定来源，而不是可被研究过程随意修改的草稿。这个设计的好处是责任清楚：研究过程产生的变化应留在研究域，知识源的变化应走发布流程。需要谨慎的是，材料只确认了说明和读取结构，数据库约束、触发器或应用层如何强制只读尚未采样，因此不能断言不可变性已经被某一层完全强制。

原理逻辑

  1. 领域边界：研究域负责可变研究状态，知识域负责稳定发布来源。
  2. 读取约束：latest_published 只读 sealed = true，使引用指向已发布版本。
  3. 变更路径：研究过程不直接修改知识版本，而是生成研究域记录或新的知识发布版本。

具体例子

一个研究项目引用知识版本 KV-100，研究会话中 latest_knowledge_version_id = KV-100。研究员想新增一条知识，正确做法是在研究域创建新的会话、回执或待发布版本，而不是直接 UPDATE 知识域中 KV-100 的内容。

常见误区

  • 把“知识域只读”当成一句注释约定，认为只要代码里写了只读就一定有强制机制。
  • 认为研究域引用了某个知识版本后，就可以直接修改这个版本，而不是基于它生成新的研究域记录或新的知识发布版本。

研究会话读模型的状态分层

完整讲解

读模型可以理解为给前端或调用方看的状态快照，它不是把数据库表原样丢出去，而是把不同时间维度和操作维度拆成清楚的字段。ResearchStore.view 同时暴露 latest_knowledge_version_id、last_execution_knowledge_version_id、current_attempt_id、available_actions 和 no_project_evidence。这些字段分别回答不同问题：当前已发布知识版本是哪个，最近一次执行绑定的是哪个版本，当前尝试是哪一次，现在允许做哪些动作，以及是否存在项目证据的派生标记。若把它们合并成一个 status 字段，就会丢失语义，比如无法区分当前发布版本和最近执行版本不一致的情况。需要谨慎的是，材料确认了这些字段存在，但完整状态机、空值语义和动作生成规则未完整采样，因此不能断言所有状态迁移规则已经实现。

原理逻辑

  1. 读模型是状态快照，不是数据库表原样输出。
  2. 不同时间维度需要不同字段：当前发布版本与最近执行版本不能合并。
  3. 动作字段 available_actions 是当前状态可迁移动作的投影，不只是前端按钮。

具体例子

某研究会话返回 latest_knowledge_version_id = V12，last_execution_knowledge_version_id = V11，current_attempt_id = ATT-9，available_actions 包含 retry 和 view_report，no_project_evidence = false。前端可以据此判断：当前已发布版本是 V12，但上次执行基于 V11，当前尝试是 ATT-9，用户现在可以重试或查看报告。

常见误区

  • 认为两个版本 ID 字段可以合并，因为它们看起来都是版本号。
  • 认为 available_actions 只是前端按钮，和数据模型无关，其实它是读模型对当前状态可迁移动作的投影。

原子创建回执与重复创建防护

完整讲解

创建命令经常会被客户端重试，比如网络超时后用户再次点击创建。系统需要判断第二次请求是同一个创建意图，还是另一个新请求。research_create_commands 以 project_id、actor_id、key 的复合主键锚定同一项目、同一操作者、同一调用键的创建意图，并且存在 fingerprint 字段与 content_digest 导入，提示载荷摘要可能参与区分同一键下的不同内容。这个结构提供了幂等回执的基础：调用方用 key 表达意图，服务端用回执表保存事实，唯一约束可以阻止完全相同意图的重复插入。需要谨慎的是，材料没有展示键冲突时返回旧结果、报错还是重放，也没有展示去重表清理、事务边界或运行验证，因此只能确认结构基础，不能声称完整幂等闭环已经实现。

原理逻辑

  1. 幂等创建需要稳定意图标识：project_id、actor_id、key 共同锚定同一创建意图。
  2. 载荷摘要 fingerprint 提供内容线索，帮助判断同一 key 是否对应不同内容。
  3. 完整幂等闭环还需明确冲突返回、重放语义、事务边界和清理策略。

具体例子

项目 P1 的用户 U1 用 key = create-session-001 创建研究会话，第一次成功写入 research_create_commands。客户端超时后重发同一 key，服务端可依据主键判断该创建意图已存在；如果 payload fingerprint 不同，则可能提示同一 key 对应不同内容，具体返回旧回执、409 还是 422 仍待确认。

常见误区

  • 认为只要数据库有复合主键，就自动拥有完整幂等能力。
  • 认为 fingerprint 能单独证明内容完全相同，因为材料未展示摘要算法、输入规范化和碰撞概率，它只是载荷摘要线索。
