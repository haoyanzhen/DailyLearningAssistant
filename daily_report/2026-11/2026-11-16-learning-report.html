项目作用域唯一键与全局主键的命名空间设计

完整讲解

想象一个学校有很多班级，每个班级内部都有学号。1 班的 7 号和 2 班的 7 号不是同一个人，所以如果系统里只写 7 号，就可能出现歧义。为了让每个人在全校范围内都能被唯一找到，学校还会给每个人发一个身份证号。项目作用域唯一键就像班级学号，通常由 project_id 和 id 组成，它适合项目内展示、项目内排序、项目内业务规则；全局主键就像身份证号，它在整个系统范围内唯一，适合数据库外键、跨项目引用、历史审计和迁移追溯。API 如果同时返回项目内 ID 和全局主键，就必须明确告诉调用方：展示给用户看的是哪一个，后续继续操作、引用其他对象或做审计时应该使用哪一个。数据库外键如果引用项目内 ID，就需要同时引用 project_id 和 id，并且要处理项目删除或迁移后可能出现的孤儿引用；如果引用全局主键，跨项目引用会更稳定，但 API 需要说明全局主键的用途，避免调用方把内部存储身份误当成业务展示身份。项目删除或迁移时，不能只删掉项目内 ID，还要保留 project_id、id 到全局主键的映射，否则历史审计、引用记录、审批记录可能会断链。这里基于当日材料可确认的是：最近 7 天 open 问题提出了 project_id、id、全局主键、API 返回身份、外键选择和删除迁移映射等问题；当天 work_summary 只确认无新增变化，未采样表结构、唯一约束、外键、API 契约或迁移映射实现，因此不能声称项目已经实现某种双层身份策略。

原理逻辑

  1. 对象身份需要分层：项目内身份解决局部唯一和展示，全局身份解决跨项目引用和审计。
  2. 外键和引用必须绑定稳定身份层，否则项目删除或迁移会产生孤儿引用和审计断链。
  3. API 契约必须说明不同 ID 的用途，避免调用方把内部存储身份误当成业务展示身份。

具体例子

假设论文项目 A 和论文项目 B 各有一篇论文，项目内 id 都是 101，但全局主键分别是 global_id=9001 和 global_id=9002。API 返回 project_id=A、id=101、global_id=9001。前端展示用 id=101，后端外键、跨项目引用和审计记录使用 global_id=9001。项目 A 删除时，保留 id_mapping 表中的 project_id=A、id=101、global_id=9001、deleted_at 时间，这样历史引用和审计仍可追溯。

常见误区

  • 认为一个 ID 可以同时满足展示和全局引用，或者认为项目内 ID 既然在数据库里，就可以直接当外键。
  • API 同时返回两个 ID 却不说明用途，调用方会随机选择，导致引用歧义、审计断链或跨项目误引用。

状态迁移合法边与审批审计记录的数据表达

完整讲解

状态字段只告诉系统对象现在在哪里，但业务真正关心的是它能不能从这里走到那里。比如一个对象从 active 变成 archived 可能允许，但从 archived 直接变回 active 可能需要人工审批。状态迁移合法边就是把这种允许关系从口头规则变成数据模型：状态是节点，合法迁移是节点之间的有向边，边上可以记录事件、权限、审批条件。应用层状态机适合表达复杂业务规则，例如只有负责人能归档、只有审批通过才能恢复；但数据库层还需要兜底，因为并发请求、手工 SQL 或绕过应用层的脚本可能直接改表。数据库 CHECK 通常只能看当前行，不能天然回答 from_status 到 to_status 是否合法，因此可以用状态迁移表保存允许的边，用触发器在更新前检查，或者用应用层状态机加数据库约束共同兜底。审批也不能只写在日志文本里，而应成为可查询的迁移记录，包含对象身份、迁移前状态、迁移后状态、事件、操作者、审批状态、审批依据和时间戳。这样系统不仅能回答当前状态，还能回答这个状态是如何到达的、谁批准了这次迁移、是否满足合法边。这里基于当日材料可确认的是：最近 7 天 open 问题提出了应用层状态机之外的数据库最低约束、archived 到 active 是否需要审批、CHECK 只能看当前行、触发器或状态迁移表表达合法边等线索；当天无新增 diff，因此不能声称已有状态迁移表、触发器、审批表或数据库兜底约束实现。

原理逻辑

  1. 状态是节点，合法迁移是节点之间的有向边，边上可以记录事件、权限、审批条件。
  2. 应用层状态机适合复杂业务规则，数据库 CHECK 通常只能看当前行，因此可用状态迁移表、触发器或约束共同兜底。
  3. 审批不能只写日志文本，而要成为可查询、可约束、可关联对象状态的迁移记录。

具体例子

假设论文对象状态有 active、archived、pending_review。状态迁移表允许 active 到 archived，事件为 archive；允许 archived 到 active，事件为 restore，但 requires_approval=true。触发器在 UPDATE status 前检查 from_status 和 to_status 是否在允许边中；如果是 archived 到 active，还检查是否存在 approval_id 且 approval_status=approved。同时插入迁移记录：object_global_id、from_status=archived、to_status=active、event=restore、operator、approval_id、created_at。非法迁移会报错，合法迁移可审计。

常见误区

  • 只校验 status 是否属于 active、archived、pending 等枚举值，却不检查从哪个状态变到哪个状态。
  • 把审批结果只写进日志文本，日志看起来有记录，但数据库无法查询、无法约束、无法和对象状态关联。
  • 认为应用层已经做了状态机校验，数据库就可以不管，忽略并发、手工 SQL 和绕过应用层修改的风险。

迁移保护中检查、清理与放行的原子性边界

完整讲解

迁移保护常常不是一条 DROP TABLE 或 ALTER TABLE，而是一串动作：先检查是否满足保护条件，再清理可清理数据，最后放行降级或继续操作。不同表可能有不同策略：有些表一旦有数据就禁止破坏性降级，有些表可以先归档再清理，有些表只能在没有外部引用时才能删除。难点在于检查通过不等于执行时仍然安全。比如检查时发现某表没有数据，准备删除；但在检查和删除之间，另一个进程又写入了数据，这就是 TOCTOU，也就是检查时刻与执行时刻之间的时间窗口。如果不能长期锁表，可以用短事务、版本戳或重新检查来缩小窗口：先读取 schema_version 或 data_version，在短事务里重新确认版本没有变化，再执行清理；若版本变化，就停止并重新检查。清理失败时也不能留下半清理状态，需要明确恢复路径：能回滚就回滚，不能回滚就标记 migration_failed 并进入补偿队列，由后续任务补齐清理或恢复。表级保护策略最好写成配置或迁移脚本中的显式规则，而不是靠操作人员记住哪些表危险、哪些表可清理。这里基于当日材料可确认的是：最近 7 天 open 问题提出了禁止破坏性降级表、可归档后清理表、迁移脚本或配置表达表级策略、短事务、版本戳、重新检查、清理失败补偿和半清理状态等线索；当天无新增 diff，因此不能声称已有迁移脚本、锁策略、版本戳、补偿队列或表级保护配置实现。

原理逻辑

  1. 检查、清理、放行必须放在原子或可补偿边界中，否则检查时刻与执行时刻之间可能发生变化。
  2. 不能长期锁表时，可用短事务、版本戳或重新检查缩小 TOCTOU 窗口，版本变化就停止并重新检查。
  3. 表级保护策略应写成配置或迁移脚本中的显式规则，而不是靠操作人员记忆。

具体例子

假设系统要从 schema_version=12 降级到 schema_version=11。迁移脚本先读取 table_protection 配置：papers 表禁止破坏性降级，temporary_runs 表可归档后清理。脚本读取 data_version=100，在短事务中重新确认 data_version 仍为 100 且 papers 表没有新增未归档数据，然后归档 temporary_runs 表。如果归档后清理失败，事务不能假装成功，而是标记 migration_status=failed，写入 compensation_queue 记录待清理对象，后续任务重试或人工确认。

常见误区

  • 认为检查一次就永久安全，忽略检查后状态可能变化。
  • 用长期锁表解决所有并发问题，虽然简单，但会影响正常业务写入。
  • 所有表使用同一种保护策略，没有区分禁止破坏性降级、可归档后清理和可安全删除，导致迁移脚本要么过于保守，要么误删数据。

今日最值得记住的一句话
