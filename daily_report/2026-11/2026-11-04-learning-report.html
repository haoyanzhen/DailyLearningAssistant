结构化目标选择契约与显式校验错误

完整讲解

这段代码处理的是当 scope 等于 selected 时的请求。它要求顶层只能有 scope 和 targets；targets 必须是非空列表；每个 target 只能有 kind 和 id；kind 只能是 paper 或 material；id 必须是字符串。不合法时返回 VALIDATION_FIELD_INVALID 和 422。背后的理念是：先定义合法请求域，把不符合形状的输入挡在业务逻辑外面，让后面的排除决策只处理可预期数据。它像填表时必须按栏目填写，不能多填、漏填或把项目写错——像体育比赛报名表，一张表只允许填姓名和项目，项目只能是跑步或跳远；多填一栏、项目写错、名单为空，报名系统直接退回，而不是让裁判到赛场再猜。

原理逻辑

  1. 先定义合法请求域：顶层只允许 scope 与 targets，targets 必须为非空列表，从入口收窄输入空间。
  2. 再约束成员形状与取值：每个 target 只允许 kind 与 id，kind 是 paper 或 material 的枚举，id 必须是字符串。
  3. 不合法时立即以 VALIDATION_FIELD_INVALID 和 422 显式失败，使后续排除决策只面对可预期数据，与状态类失败 409 分层。

具体例子

scope 为 selected，targets 里放一个 {kind:"paper", id:"p1"} 是合法形状；如果 target 多出 title 字段、kind 写成 dataset，或 targets 为空，就会进入 VALIDATION_FIELD_INVALID 或 422。

常见误区

  • 以为接口收到 paper 或 material 就能处理，忽略了字段集合、枚举取值与非空列表这些形状约束。
  • 把 422 和 409 混为一谈：422 表示请求结构或字段值不合法，409 表示结构可能合法但当前状态不允许操作。

概念关联

关联概念关系说明
显式排除作为版本化派生决策前者规定哪些目标形状可以进入排除决策，后者再处理这些目标相对于哪个已发布版本被排除。
终态运行对构建固定保护的受控释放前者是外部请求的结构校验，后者是数据库触发器执行的内部不变量，两者处在不同边界，不能互相替代。

显式排除作为版本化派生决策

完整讲解

在今天的提交主题中，显式排除不是把论文或材料实体从数据库里删掉，而是记录“相对于某个已发布版本、这些固定成员中的哪些目标被排除”。局部证据显示操作会读取项目当前 heads.version_id；不存在时返回 409。固定清单线索进一步说明，系统通过 pinned_manifest 和 pinned_revisions 用不可变 ID 表达成员关系，而不是打开论文实体按当前内容临时判断。这样，排除决策绑定的是精确的已发布修订和成员集合。文件说明还提到写入冲突，说明如果版本在检查和提交之间发生变化，需要有冲突保护；但完整移除、冲突和回收算法在采样中被截断，只能确认设计方向。它像博物馆的某一版展品目录：决定某件展品“本次不展”时，不是把藏品销毁，而是在这一版目录上做标记；下一版目录可以重新决定，若目录版本换了，旧标记不能悄悄套到新目录上。

原理逻辑

  1. 排除的对象是派生决策而非实体：论文或材料实体保留，排除结果只存在于针对某个已发布版本的派生层。
  2. 决策绑定精确快照：读取项目当前 heads.version_id，成员关系由 pinned_manifest 与 pinned_revisions 的不可变 ID 表达，不按实体当前内容临时判断。
  3. 版本状态是前置条件：head 不存在时返回 409；版本在检查与提交之间变化时需要冲突保护，具体算法待确认。

具体例子

版本 A 的固定清单包含论文 p1 和材料 m1，用户选择从版本 A 排除 p1；论文实体 p1 仍在，只是版本 A 的这次发布派生结果不含它。若操作期间 head 已切到版本 B，则需要冲突保护或拒绝，不能把针对 A 的排除直接作用到 B。

常见误区

  • 把排除理解成删除原实体，以为排除之后论文或材料本身就不存在了。
  • 以为 head 一变旧的排除还能自动适用，忽略排除应绑定已发布修订和固定成员，冲突检测算法仍待确认。

概念关联

关联概念关系说明
结构化目标选择契约与显式校验错误前者用 scope 和 targets 规定可进入排除请求的目标形状，后者再把这些目标绑定到已发布版本和固定成员集合。
终态运行对构建固定保护的受控释放前者依赖版本是否已发布、是否密封等状态，后者的触发器也检查版本未密封等条件，二者都说明版本状态会影响允许的操作。

终态运行对构建固定保护的受控释放

完整讲解

迁移 0019_run_temporary_cleanup.py 重定义了 rpb_guard_build_pin_mutation()。在 DELETE 场景下，一个运行要释放自己的构建固定保护，必须同时满足多个条件：construction_runs 状态是 failed、cancelled 或 succeeded；payload 里的 temporary_cleanup.state 是 queued；source_run_id 与当前运行匹配；版本未密封；ready_proof 里的 attempt_id 与当前尝试匹配。否则触发器抛出 build protection needs controlled release。这个机制把“能不能释放保护”从单一判断变成数据库边界上的不变量：运行终态只是条件之一，资源归属、清理请求、版本状态和尝试身份也必须对上。它像银行保险库的多把钥匙：账户已结清只是第一把钥匙，还要有清理申请、本人身份、保险库未被封存、本次操作编号一致，缺一项都不能开门。

原理逻辑

  1. 释放条件是多条件合取：运行终态、清理请求状态、运行归属、版本密封状态、尝试身份五项必须同时成立，缺一项即失败。
  2. 保护由数据库层执行：触发器在 DELETE 时判断条件并抛出 build protection needs controlled release，应用层检查过也不足够。
  3. 版本状态作为共享前置条件：与版本化派生决策一样，未密封状态决定了操作是否被允许。

具体例子

一个运行已经 succeeded，但 ready_proof.attempt_id 与当前尝试不一致，或版本已经 sealed，或 source_run_id 不匹配，那么 DELETE 释放保护会被触发器拒绝，并给出 build protection needs controlled release。

常见误区

  • 以为运行成功或失败之后就能直接删除保护，忽略了整理清理请求、运行归属、版本状态与尝试身份。
  • 以为应用层检查过就够了，忽略这里的证据显示触发器会在数据库层拒绝不满足组合条件的释放。

概念关联

关联概念关系说明
显式排除作为版本化派生决策后者的排除决策依赖已发布版本和固定成员，前者的释放条件也检查版本未密封与运行身份，说明版本状态是多种操作共同的前置条件。
结构化目标选择契约与显式校验错误一个是接口层 422 结构校验，一个是数据库层触发器不变量；材料分别展示二者，但没有证明触发器异常如何映射成外部 API 错误。
