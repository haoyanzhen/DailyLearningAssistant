机器可读错误分类与字段级错误契约

完整讲解

可以把 API 错误想象成快递异常通知。如果系统只说“出错了”，调用方就像收到一张只写“包裹异常”的纸条，不知道是地址错、权限不足、还是货物冲突。机器可读错误契约要求把失败分成三层：第一层是 HTTP 状态码，表达失败的大类，例如 403 表示权限不足，409 表示冲突，422 表示请求内容校验失败；第二层是错误码或错误字段，表达机器可解析的原因，例如 permission_denied、conflict、validation_failed；第三层是字段级定位，告诉调用方具体该改哪个字段，例如 targets 为空、id 格式错误、scope 不允许。这样调用方不需要人工阅读模糊文本，就能自动判断下一步是改权限、刷新版本还是修改输入。OpenAPI 的 additionalProperties 策略和未知字段拒绝也是这个契约的一部分：如果契约声明不接受未知字段，系统就应该明确拒绝，而不是部分接口静默忽略，否则调用方可能以为字段生效了，实际上被丢掉。这里基于当日材料可确认的是：该概念来自最近 7 天 open 问题中的 403、409、422、字段级错误、OpenAPI additionalProperties、未知字段拒绝、前端 AssociationRemoval.tsx 映射等线索，证据层级为 C，不能据此断言完整错误 schema、契约一致性或前端映射已经实现。

原理逻辑

  1. 第一层 HTTP 状态码表达失败大类，让调用方快速判断是权限、冲突还是校验问题。
  2. 第二层错误码表达机器可解析原因，避免通用文本导致人工判断和不可自动处理。
  3. 第三层字段级定位把失败落到具体字段，支持前端映射、自动修复和契约一致性检查。

具体例子

一个关联删除请求提交时 targets 为空，接口返回 422，错误体包含 code 为 validation_failed，fields 数组中有一条 name 为 targets、rule 为 min_items、message 为“至少选择一个目标”的字段级错误；如果当前用户只读，则返回 403 和 permission_denied；如果版本已被他人修改，则返回 409 和 conflict。前端可以把 fields 中 name 为 targets 的错误显示在对应输入项旁边。

常见误区

  • 认为返回 500 加一句通用错误文本就够了，或者把权限拒绝、冲突、校验失败混成同一类错误。
  • 未知字段被静默忽略，调用方以为字段生效，实际上契约外字段被丢掉了。

无快照标识下的集合完整性证明与分页漂移控制

完整讲解

集合完整性证明要回答的问题是：我从一个提供方分页读取了一批数据，最终拿到的集合到底完整不完整。如果有 snapshot_id，事情会简单很多，因为它像一个稳定照片编号，表示“我读的是哪一个固定版本”。但如果没有 snapshot_id，系统只能依靠 total、cursor 和集合比较来约束完整性。total 提供期望基数，回答“应该有多少个”；cursor 提供遍历位置，回答“我从哪里继续读”；集合比较提供元素归属判断，回答“我拿到的元素是否属于期望集合，是否有遗漏、多余、重复或超范围”。分页漂移是指同一逻辑集合在不同时间呈现不同顺序或边界，例如数据被新增、删除、重新排序，导致第一页读到的内容和后面页读到的内容不再属于同一个稳定集合。此时不能把来源异常直接误报为集合缺失，而要把差异分类为 missing、extra、duplicate、out_of_scope：missing 表示应有但没有拿到，extra 表示拿到了但不在期望范围，duplicate 表示同一元素重复出现，out_of_scope 表示元素属于其他范围。这里基于当日材料可确认的是：该概念来自最近 7 天 open 问题中 snapshot_id 缺失、total、cursor、集合比较、重试策略和四类差异字段线索，证据层级为 C，未采样具体证明算法、分页实现或运行验证。

原理逻辑

  1. 没有 snapshot_id 时，不能用单一请求成功证明集合完整，需要绑定 total 和 cursor 的读取过程。
  2. 分页漂移会让同一逻辑集合在不同时间呈现不同边界，因此必须识别新增、删除、重排带来的边界变化。
  3. 差异分类把 missing、extra、duplicate、out_of_scope 分开，才能区分数据缺失、来源异常、重复读取和范围错误。

具体例子

系统期望读取 120 个知识条目 ID，实际分页收集到 120 个 ID，但集合比较发现 missing 2 个、extra 1 个、duplicate 1 个、out_of_scope 1 个。系统不应直接宣布完整，而应标记差异来源并触发重取；重试后如果 missing 为 0、total 稳定、cursor 正常完成，且 extra、duplicate、out_of_scope 都能归因于来源异常或范围错误，才输出完整证明。

常见误区

  • 认为 HTTP 请求成功就代表集合完整，或者只比较 total 数量就认为集合相同。
  • 把来源超时、权限异常、提供方故障直接当成 missing，从而把系统问题误报为数据缺失。

概念关联

关联概念关系说明
参数冻结请求中上游依赖失效的显式失败边界冻结请求可能依赖模型目录、参数集合或知识结果集合，必须先判断集合完整再决定是否执行。
机器可读错误分类与字段级错误契约集合相等失败时的 missing、extra、duplicate、out_of_scope 可以映射为机器可读错误字段，帮助调用方区分集合缺失、来源异常和范围错误。

参数冻结请求中上游依赖失效的显式失败边界

完整讲解

参数冻结请求可以理解为一次“带着固定参数走完全程”的请求：模型、模型版本、推理参数、状态版本等都被固定下来，请求执行过程中不应悄悄替换。上游依赖失效指的是这些固定参数依赖的东西发生变化，例如模型目录中某个模型下线、模型版本窗口冲突、或上游服务不可用。此时系统需要明确失败边界：模型目录负责声明模型不可用，请求网关负责拦截请求并返回明确错误，业务服务负责解释失败、记录日志并通知调用方。不能由某一层静默替换模型、静默降级或继续执行，因为这会破坏参数冻结的意义。版本窗口冲突可以用比较并交换或乐观锁来收窄：请求声明“我依赖当前版本 X，只有版本仍是 X 时才继续”，如果版本已经变成 Y，就返回可识别冲突错误，而不是继续执行旧条件。重试幂等则要求同一冻结请求不能产生重复副作用，例如重复调用模型、重复写入结果或重复扣费。这里可以结合请求摘要、幂等键或服务端去重表来判断“这是同一次请求的重试，还是新的请求”。这里基于当日材料可确认的是：该概念来自最近 7 天 open 问题中模型下线、模型目录、请求网关、业务服务、比较并交换、乐观锁、请求摘要、幂等键和服务端去重表等线索，证据层级为 C，未采样模型目录、网关、业务服务或幂等实现。

原理逻辑

  1. 参数冻结请求要求执行过程中保持模型、版本和推理参数不变，上游依赖变化会破坏冻结语义。
  2. 显式失败边界要求不同服务层各司其职：目录声明不可用，网关拦截并返回错误，业务服务解释失败并记录。
  3. 乐观锁或比较并交换把版本窗口冲突变成可识别错误，幂等控制保证重试不产生重复副作用。

具体例子

一次参数冻结请求固定 model_version 为 2026-10-01 和一组推理参数。执行前模型目录返回该版本 offline，请求网关返回 409 和 model_version_unavailable，业务服务记录 idempotency_key 和 request_digest，不重复调用模型。如果版本窗口被其他请求更新，则返回 409 和 state_revision_conflict，调用方需要重新读取版本后再决定是否重试。

常见误区

  • 模型下线时静默换模型或降级执行，让调用方以为原参数仍然有效。
  • 网关吞掉上游错误并返回成功，导致业务层无法判断失败原因。
  • 重试没有幂等保护，导致同一冻结请求产生重复副作用。
