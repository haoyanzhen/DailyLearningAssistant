字段级错误路径的规范化与聚合表达

Field-Level Error Path Normalization and Aggregation

字段错误不是“哪里有问题”，而是“哪个字段、什么类别、能不能重试”。

核心要点

  • path 是机器可解析的稳定坐标，message 才是给人看的解释。
  • 数组对象字段优先使用 items[0].name 这类先定位元素再定位字段的稳定写法。
  • 多字段错误可返回全部但设上限，并按 path 或 severity 排序，便于前端标红和测试断言。
  • 错误对象应包含 code、severity、retryable，帮助调用方判断类别、轻重和是否可重试。

副作用可逆性约束下的恢复动作排序

Recovery Action Ordering Under Side-Effect Reversibility

可重试不等于安全重试，先保证据，再保资金，再保体验。

核心要点

  • 副作用分档：无副作用、可逆副作用、不可逆副作用、跨系统副作用、计费副作用。
  • 恢复动作分档：自动重试、降级、回滚、人工确认、挂起等待、丢弃并留痕。
  • 排序原则：先保护用户输入和审计证据，再避免不可逆副作用扩大，再控制资金和外部资源风险，最后考虑自动恢复。
  • 人工确认必须持久化请求、失败证据、建议动作和回执，防止请求静默丢失。

字段级错误路径的规范化与聚合表达

完整讲解

这里基于当日材料可确认的是：本节来自 concept_relevance.md 中 2026-11-19 和 2026-11-17 的历史 open 问题延展，证据层级为待确认，不声称已有实现。字段级错误路径的核心，是把“参数错误”这句话拆成机器能读的位置、原因和处理建议。对高中读者来说，可以把它想象成批改作文：老师不能只说“这篇文章有问题”，而要指出“第三段第二句缺主语”。API 也一样，如果请求是一个嵌套结构，错误路径要能定位到具体字段；如果数组元素本身是对象，稳定写法通常是 items[0].name，而不是 items.name[0]，因为前者先定位第 0 个元素，再定位该元素内的 name 字段。未知字段可以表示为 body.unknownField 或 parent.unknownField，关键不是某一个绝对写法，而是全系统统一、可解析、可测试。错误对象还应包含 code、message、severity、retryable 等字段：path 告诉位置，code 告诉类别，message 给人看，severity 告诉轻重，retryable 告诉调用方是否值得原样重试。多个字段错误时，可以选择只返回第一个，也可以返回全部；更稳定的是返回全部但设上限，并按 path 或 severity 排序，这样前端可以一次性标红多个输入项，测试也能断言固定集合。它也是对本月已讲字段级错误路径的深化：从“要有字段路径”推进到“数组路径、未知字段、聚合上限和测试断言如何稳定”。一家餐厅只说“这桌菜不行”，顾客不知道是盐放多了、菜名写错，还是优惠券不能用；字段级错误就像服务员拿着菜单编号说：第 2 道菜的辣度字段超出范围，第 5 道菜的优惠券字段已过期，顾客可以立刻改单，而不是整桌重做。

原理逻辑

  1. 把“参数错误”拆成位置、原因和处理建议，形成机器可读契约。
  2. path 负责定位，code 负责分类，message 负责解释，severity 和 retryable 负责处理策略。
  3. 聚合多个错误时，用上限、排序和稳定集合避免响应爆炸和测试不稳定。

具体例子

批量标签接口收到 payload：tags 是数组，第 0 个元素 name 为空，第 1 个元素 color 不在允许枚举中。响应返回 422，errors 数组包含两条：第一条 path 为 tags[0].name，code 为 required，message 为标签名称不能为空，retryable 为 false；第二条 path 为 tags[1].color，code 为 enum，message 为颜色必须是 red、blue 或 green，retryable 为 false。前端可按 path 定位到具体输入项，公共测试可断言这两条错误都存在且顺序稳定。

常见误区

  • 把 path 当作用户文案，或只返回第一个错误就认为已经足够。
  • 未知字段静默忽略，会掩盖调用方传错结构，导致线上问题更难定位。

副作用可逆性约束下的恢复动作排序

完整讲解

这里基于当日材料可确认的是：本节来自 concept_relevance.md 中 2026-11-21 的历史 open 问题延展，证据层级为待确认，不声称项目已实现恢复矩阵。失败发生后，系统不能只问“错误码是什么”，还要问“这个动作已经造成了什么副作用，这个副作用能不能撤销”。可以把副作用分成几档：无副作用，比如只读查询；可逆副作用，比如写入本地草稿、创建可删除任务；不可逆副作用，比如已发送消息、已删除数据；跨系统副作用，比如外部 API 已接受请求；计费副作用，比如已扣款或已产生费用。恢复动作也要分档：自动重试、降级、回滚、人工确认、挂起等待、丢弃并留痕。排序原则是：先保护用户输入和审计证据，再避免不可逆副作用扩大，再控制资金和外部资源风险，最后才考虑自动恢复。对于计费或跨系统副作用，自动重试尤其危险，因为可能重复扣款或重复创建外部资源。人工确认不能只是弹一个框，而应把请求、失败证据、建议动作和回执写入持久化队列，防止请求静默丢失。它也是对 2026-11-21 已讲副作用可逆性驱动的恢复动作选择的深化：从原则推进到用户输入、外部资源、计费并存时的优先级和人工确认队列。后厨处理订单时，沙拉没做好可以重做，这是可逆；外卖已经送到顾客门口就不能收回，这是不可逆；账单已经扣款就需要对账，这是计费副作用。聪明的后厨不会对所有失败都直接重做，而是先判断哪道菜还能改、哪笔钱已经出去、哪张单必须经理确认。

原理逻辑

  1. 恢复决策由副作用等级和可逆性驱动，而不是由错误名称单独驱动。
  2. 计费和跨系统副作用可能不可逆，盲目重试可能造成重复扣款或重复创建外部资源。
  3. 人工确认要成为可执行、可审计、不丢失请求的恢复路径，而不是临时弹窗。

具体例子

一个论文分析任务同时包含用户输入、外部模型调用和计费。用户输入已保存，外部模型调用返回成功，但计费回执丢失，内部状态没有更新。合理恢复排序是：先持久化请求 ID、外部调用证据和计费失败证据；不自动重发计费，因为计费可能不可逆；对内部可逆状态可回滚或标记待对账；对外部资源发起只读查询确认是否已执行；如果无法确认，则进入人工确认队列，并返回 receipt_id 让用户和运维都能追踪。

常见误区

  • 认为“可重试”就等于“安全重试”，忽略外部系统可能已经执行成功但响应丢失。
  • 把人工确认设计成临时弹窗，没有持久化请求状态和回执，一旦页面关闭或进程重启，请求就静默丢失。

多观测点故障证据的时间窗、来源层与证据强度归一化

完整讲解

这里基于当日材料可确认的是：本节来自 concept_relevance.md 中 2026-11-21 的历史 open 问题延展，证据层级为待确认，不声称已有事件合并或告警抑制实现。多观测点故障归因的核心，是把不同位置看到的故障信号翻译成同一套证据语言。网关可能看到 timeout，业务服务可能看到 upstream_unavailable，日志可能看到 connection refused，监控可能看到 CPU 正常。这些信号不一定矛盾，只是站在不同来源层、不同时间、不同证据强度上观察同一件事。因此需要先定义统一字段：time_window 表示事件发生的时间范围，source_layer 表示网关、服务、日志、监控或模型提供方，evidence_strength 表示证据强弱，correlation_id 表示同一调用链，root_cause_id 表示疑似同一根因，fault_category 表示稳定故障类别，responsible_layer 表示责任层，minimal_evidence 表示合并后至少保留的证据摘要。合并规则不能只看名称相似：两个故障类别相似但证据强度不同时，弱证据不能单独把不同故障合并到一起；需要同一 root_cause_id、相近时间窗和足够证据强度。矛盾归因时，可以用优先级规则，例如更靠近责任层的观测优先、更强证据优先、更具体错误优先，但规则必须显式写明。告警抑制也不是把重复事件全部丢掉，而是在时间窗内降噪，同时保留首次事件、最强证据、最新状态、影响计数和最小证据摘要。稳定故障类别枚举也很重要，例如 network_timeout、permission_denied、resource_not_found、upstream_unavailable，避免用自由文本导致无法聚合。它也是对 2026-11-21 已讲多观测点故障证据归一化和重复故障事件合并的深化：从“要归一化”推进到时间窗、来源层、证据强度、抑制窗口和矛盾裁决如何组合。小区停电时，电梯卡住、路灯闪烁、多户业主打电话，物业如果把这些都当成独立故障，会乱成一团；更好的做法是建立一张事件表：时间窗是 10 点到 10 点半，来源层是电梯、路灯、业主电话，证据强度是现场巡检最强、电话最弱，根因可能是同一变压器故障，这样既能合并重复报告，又不会把真正独立的电梯故障误并入停电事件。

原理逻辑

  1. 不同观测点看到的信号不一定矛盾，只是来源层、时间窗和证据强度不同。
  2. 稳定故障类别枚举让事件可聚合，避免自由文本导致无法统计和归因。
  3. 合并与抑制的目标不是丢事件，而是把重复信号压缩成可解释、可追踪的故障证据。

具体例子

模型下线场景中，网关在 10:00:01 返回 504 timeout，source_layer 为 gateway，evidence_strength 为 weak；业务服务在 10:00:00 记录 model_unavailable，source_layer 为 service，evidence_strength 为 strong，root_cause_id 为 mc-123；监控显示 CPU 正常，作为弱相关证据。系统在 30 秒时间窗内按 root_cause_id 和时间窗合并这些事件，最终类别归为 upstream_unavailable 或 model_unavailable，责任层指向模型目录或上游服务。重复 timeout 被告警抑制，但保留首次时间、最强证据、影响计数和 root_cause_id。

常见误区

  • 看到 timeout 就立刻判断为网络故障，忽略上游不可用、权限拒绝或资源不存在等可能。
  • 告警抑制时把首次证据也丢掉，导致运维只看到“已抑制”，却不知道最早开始时间、最强证据和影响范围。

概念之间的关联

三个概念不是孤立工具，而是一条异常处理链路。字段级错误路径回答“哪里错”，让调用方能定位到具体字段、数组元素或未知字段；副作用可逆性约束下的恢复动作排序回答“怎么办”，让系统根据副作用等级选择自动重试、降级、回滚、人工确认或保留证据；多观测点故障证据归一化回答“为什么这样判断”，让多个观测点的信号在时间窗、来源层和证据强度上形成可合并、可抑制、可归因的证据。

今日最值得记住的一句话

恢复动作排序不能只看错误码，而要看副作用是否可逆、是否涉及用户输入、外部资源、计费或跨系统状态，人工确认必须持久化并回执。

可继续探索的问题

  1. 如何建立跨接口统一字段路径命名规范，并让 403、409、422 都能返回机器可解析的字段级错误？
  2. 当用户输入、外部资源和计费同时失败时，如何定义先保证据、再保资金、再保体验的恢复优先级？
  3. 当多个观测点给出矛盾故障类别时，如何用时间窗、来源层和证据强度阈值形成可解释且可测试的归因？
