状态机合法迁移边在数据层的表达与兜底

State Machine Legal Transition Edges in Data Layer

核心要点

  • CHECK 约束通常只能检查当前行状态值是否合法，难以直接表达旧状态到新状态的迁移边。
  • 应用层状态机适合复杂业务规则，数据库层应保留状态枚举、迁移表、触发器或审计记录等最低限度兜底。

Compare-And-Swap Atomic Check in Version Window

核心要点

  • 版本窗口表示请求只允许在某个版本范围内继续，例如 state_revision 落在允许区间内。
  • CAS 或乐观锁在写入前检查当前版本是否仍等于读取时版本，若不等则说明中间有变更。

状态机合法迁移边在数据层的表达与兜底

完整讲解

由于没有新增 diff 或实现验证，这里只讲原理，不声称项目已经实现。状态可以想象成车站，合法迁移边是允许通行的轨道。订单可能处于 draft、submitted、approved、archived 等状态，但并非任意两个状态之间都能直接切换。数据库 CHECK 通常只能检查当前行状态值是否合法，例如 status 是否属于允许列表；它不容易直接表达从旧状态到新状态是否合法，因为迁移关系需要一次更新动作才能体现。因此数据层要分层兜底：应用层状态机表达审批、权限、配额和跨表条件；数据库层保留状态枚举约束、状态迁移表、触发器或审计记录。当手工 SQL、并发更新或旧客户端绕过应用层时，数据库层可以拒绝明显非法迁移，并把拒绝原因写入日志或审计表。对于 archived 到 active 这类高风险恢复操作，还可以要求审批记录先存在，再允许状态迁移，使每次恢复都能追溯到审批人、审批时间、审批结果和失败原因。

原理逻辑

  1. 当前状态合法只是必要条件，不是充分条件；迁移合法性取决于 from_status 到 to_status 的边。
  2. 数据库层不能替代应用层复杂规则，但必须提供最低限度约束，防止绕过应用层写入非法状态。
  3. 审计记录把失败原因、操作者和审批结果结构化，使拒绝可解释、可追溯、可重试。

具体例子

假设订单有 draft、submitted、approved、archived 四个状态。业务规则允许 draft 到 submitted、submitted 到 approved、approved 到 archived，但 archived 到 active 必须经过人工审批。数据库可以保留 status 枚举约束，再用 status_transitions(from_status, to_status, requires_approval) 表保存合法边；UPDATE 触发器读取旧状态和新状态，若边不存在或需要审批但没有有效审批记录，就拒绝更新并写入 status_transition_log，记录 order_id、from_status、to_status、actor、approval_id、reason、created_at。

常见误区

  • 以为 CHECK status IN (...) 足够，只能保证当前状态不越界，不能保证迁移边合法。
  • 以为应用层校验后数据库就可以不管，手工 SQL、并发更新或旧客户端仍可能产生非法状态。

版本窗口中的比较并交换式原子检查

完整讲解

由于没有新增 diff 或实现验证，这里只作为一般原理讲解，不声称项目已经实现。版本窗口可以理解为这次请求只允许在某个版本范围内继续。请求开始时读取模型、目录或资源的状态版本，例如 state_revision=7，并确认 7 落在允许窗口内。执行前或提交前，系统再检查这个版本是否仍然成立。比较并交换，简称 CAS，是其中的原子操作：如果当前版本仍等于我看到的旧版本，就允许更新；如果不等于，就说明中间有人改过，操作失败并返回可识别错误。乐观锁的思路类似：先读版本，不做长时间阻塞；写入时带上版本条件，条件不满足就冲突。这样做的好处是避免检查时可用、执行时已下线的窗口。若冲突，系统不应静默改用新版本，也不应假装成功，而应返回类似 STATE_REVISION_CONFLICT 的错误，让调用方知道失败来自版本边界变化，并决定重试、刷新或放弃。这里的关键不是锁住所有写操作，而是把版本边界变成可检查、可比较、可报错的显式条件。

原理逻辑

  1. 版本窗口把外部状态变化转化为可比较的边界条件，而不是依赖最终调用失败。
  2. CAS 的原子性保证检查与更新之间没有窗口，避免读到旧版本后又被并发修改。
  3. 冲突错误必须可识别，调用方才能区分版本边界变化、业务冲突、网络抖动和权限问题。

具体例子

假设模型目录表 model_directory 有 model_id、status、state_revision 字段。请求冻结 model_id=m1、state_revision=7，允许窗口是 [5,8]。执行前用 UPDATE model_directory SET state_revision=8 WHERE model_id='m1' AND state_revision=7 做 CAS；如果影响行数为 0，说明状态已被其他请求或管理员改变，系统返回 STATE_REVISION_CONFLICT，并记录 request_id、model_id、expected_revision=7、actual_revision、error_owner=version_window。

常见误区

  • 以为读一次版本就足够，读一次只能证明读取时刻可用，不能证明执行时刻仍可用。
  • 冲突时自动重试或静默使用新版本，可能把业务冲突掩盖成网络抖动，或在用户未同意的模型或参数下继续执行。

上游依赖失效的显式失败边界与错误归属

完整讲解

由于没有新增 diff 或实现验证，这里只讲可迁移原理，不声称项目已经实现。上游依赖失效指的是系统依赖的外部对象不再满足执行条件，例如模型下线、模型版本不可用、目录状态过期或参数冻结条件不再成立。此时系统不能只靠最后调用模型失败来发现问题，而要在每一层设置显式失败边界。模型目录负责声明模型是否可用、版本是否有效；请求网关负责在请求进入业务逻辑前拦截明显不可用的模型或版本；业务服务负责检查与本次请求绑定的前置条件，例如审批、配额、状态版本窗口。错误归属要求每类失败都有明确责任层和可识别错误码。比如模型目录状态为 offline，应返回 MODEL_OFFLINE 并归属目录或网关；版本窗口冲突应返回 STATE_REVISION_CONFLICT 并归属版本检查层；业务前置条件不满足应返回业务错误。这样调用方才知道失败来自哪里，运维才知道该修哪一层，重试和幂等控制也才有明确依据。显式失败边界的核心不是尽量不报错，而是一旦边界不满足，就让失败在正确的位置以正确的身份出现。

原理逻辑

  1. 依赖失效检测要前置到目录、网关和业务服务，而不是等到最终模型调用失败。
  2. 错误归属把失败绑定到责任层，使调用方、运维和重试策略能区分处理路径。
  3. 显式失败边界优先于静默降级，避免在用户未同意的模型、版本或参数下继续执行。

具体例子

假设请求携带 model_id=m1、state_revision=7 和幂等键 request_id=req-001。模型目录中 m1 状态为 offline，state_revision=9。网关查询目录后发现模型不可用，直接返回 HTTP 409 或 410，错误码 MODEL_OFFLINE，error_owner=model_catalog，details 包含 model_id、expected_revision=7、actual_revision=9。业务服务不执行模型调用，日志记录 request_id、model_id、state_revision、error_owner 和 action_taken=blocked_at_gateway。调用方看到错误后可提示用户选择其他模型或刷新目录，而不是继续等待或重复提交。

常见误区

  • 以为只要最终调用模型失败就够了，最终调用失败太晚，错误信息可能混入网络、超时和模型下线。
  • 所有层都返回同一个 500，会让调用方无法区分可重试、需刷新、需人工处理还是依赖已下线。
