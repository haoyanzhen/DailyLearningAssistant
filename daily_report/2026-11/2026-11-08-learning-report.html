机器可读契约同步与契约检查

完整讲解

可以把接口契约想成餐厅菜单和插座标准。菜单如果只靠口头说，厨房可能做出和顾客点到的不一样；插座如果只靠大家自觉，插头就可能对不上。机器可读契约就是把接口应该长什么样、覆盖哪些行为、失败时返回什么公共错误，写成程序能读、能比较、能检查的文件。最近有效日材料里出现了 contracts/p0.openapi.json、contracts/p0.coverage.json、scripts/check_api_contracts.py、test_api_contracts.py 和 test_public_errors.py 这些路径线索，说明接口形状、覆盖范围和公共错误被放进了同一个机器检查面。它的核心原理不是「多写文档」，而是让实现和契约之间的漂移更早暴露出来。像一家连锁店把菜单印成标准表，后厨每改一道菜都必须同步改表，系统再自动比对「菜单上有的」和「后厨能做的」是否一致，这样顾客点单时就不会遇到菜单写了但厨房根本做不出来的情况；契约检查就是这种自动比对，只是对象换成了接口、字段、覆盖项和错误响应。

原理逻辑

  1. 把接口形状与公共错误写进程序可读的文件，实现与契约才能被机器逐项比较，而不是靠人工记忆。
  2. 检查脚本与契约测试把「实现漂移」从评审会上的口头提醒，变成可重复执行的比对动作。
  3. 覆盖范围也被纳入同一检查面，说明检查对象不只是字段名，还包括行为与失败响应是否被覆盖。

具体例子

假设某个接口新增一个字段或错误码，但实现改了、契约文件没改。机器检查脚本或契约测试就可能发现两边不一致，提醒开发者同步。这里可确认的是材料中存在 OpenAPI、coverage、检查脚本和测试的路径与更新线索；具体检查了哪些字段、如何判断覆盖、运行结果如何，仍待补充。

常见误区

  • 认为只要仓库里有 OpenAPI 文件或测试文件，就说明契约已经完整、测试已经通过、未知字段一定被拒绝。
  • 认为有了契约检查就等于只读写入边界已被强制；材料没有展示具体只读错误映射，不能把契约检查说成已经强制了只读边界。

概念关联

关联概念关系说明
有数据拒绝降级的 schema 回退保护两者都体现「变更前先检查、失败要显式」的原则，但契约检查面向接口形状和公共错误，降级保护面向数据库回退和数据丢失风险。
不可变发布的约束-触发器-应用层强制边界公共错误测试可能表达只读拒绝或冲突错误，但材料未展示具体错误码映射，因此不能据此断言只读写入已经被契约强制。
可检查的安全边界：谁在什么位置拒绝什么今日主题作为三张知识卡之外的统摄概念，用来说明这些概念如何共同指向同一条学习主线。

有数据拒绝降级的 schema 回退保护

完整讲解

schema 迁移可以理解为给数据库换房间布局，降级则是把布局改回旧版本。问题在于，旧布局可能没有新布局里那些柜子，如果直接回退，就可能把已经放进去的数据丢掉。有数据拒绝降级的保护做法是：回退前先给相关表加 ACCESS EXCLUSIVE 锁，让别的写入先停下或排队，再检查表里有没有数据；如果 research_catalogs、research_sessions、research_create_commands 这些表已有数据，就抛 RuntimeError 拒绝降级。这样，原本可能静默丢数据的回退，变成了一个明确的失败信号。比喻来说，仓库要把新货架拆回旧货架，工人先锁上仓库门，检查里面还有没有货；只要发现还有货，就停止拆迁，要求先安排出库或转移，而不是直接把货架连货一起拆掉。锁门和检查就是排他锁与数据存在性检查，停止拆迁就是显式拒绝降级。

原理逻辑

  1. 破坏性回退的风险在于旧结构承载不了新数据，因此第一道动作是把可能并发的写入先挡住。
  2. 锁之后再做数据存在性检查，让「有没有会丢的数据」成为可判定的条件，而不是事后才发现。
  3. 条件成立时抛错拒绝降级，把静默的数据损失转化为一次必须人工处理的显式失败。

具体例子

假设 research_sessions 里已经有一条研究会话记录，此时执行降级脚本。保护逻辑先加排他锁，再检查到表非空，于是抛出 RuntimeError 拒绝降级，而不是直接删表或丢列。这个例子能说明「有数据即拒绝」的边界；至于拒绝后如何导出、清理、再降级，材料没有展示完整流程。

常见误区

  • 认为「有检查就一定有完整并发安全」；材料只确认锁后检查，完整事务边界与锁持有范围未采样。
  • 认为「拒绝降级就等于数据导出清理流程已经实现」；拒绝之后如何安全导出、清理再降级，材料未展示。

概念关联

关联概念关系说明
机器可读契约同步与契约检查两者都强调变更前检查，但契约检查约束接口形状和公共错误，降级保护约束数据库回退不能静默破坏已有数据。
不可变发布的约束-触发器-应用层强制边界二者共同构成数据保护面：前者防止 schema 回退丢数据，后者讨论已发布对象写入不可变由哪一层强制，都要求不安全的写或迁移显式失败。

  3. 在拒绝丢弃之前，如何安全导出并清理已有数据，再允许降级？这个补偿流程在当天材料中未展示。

精读文章 · 软件工程 / 数据库 / 安全 / 数据建模

不可变发布的约束-触发器-应用层强制边界

完整讲解

不可变发布可以想成博物馆展品：观众看到的是密封展柜里的版本，读取查询只取出 sealed = true 的已发布知识版本，这属于读取侧过滤和消费边界。但「展品不能被改写」还需要另一种保证：书库门是否上锁、封条是否有效、管理员是否拒绝修改。对应到系统里，就是数据库约束、迁移触发器或应用层写入规则到底哪一层在强制不可变。材料可确认的是文件说明写着研究侧负责会话和创建回执，知识侧保持只读，以及 knowledge_read.latest_published 只读取 sealed = true 的版本；但数据库约束、触发器或应用层写入规则是否已经强制不可变，未采样，属于待确认线索。像图书馆只把盖过章的书放上阅览架，读者看到的都是已发布版本，但读者看不到书库后门：如果后门没锁，管理员或别的程序仍可能进去改书。阅览架过滤只能证明读者看到的是已发布版本，不能证明书本身被制度、门锁或管理员规则真正保护起来。

原理逻辑

  1. 读取侧过滤只决定「谁被看到」，它约束的是查询输出，而不是写入路径是否可能改写已发布对象。
  2. 领域只读说明和接口契约属于约定与表达层，只有在写入侧被某一层真正拒绝，才构成强制。
  3. 数据库约束、触发器、应用层写入规则是三种不同的强制位置，必须逐一确认谁在什么条件下拒绝了什么操作。

具体例子

假设知识版本表里有一条 sealed = true 的记录，读取接口只返回这种已发布版本。但如果没有数据库约束、触发器或应用层写入规则拒绝更新，其他写入路径仍可能改到这一行。材料目前只展示了读取过滤和领域只读说明，因此这个例子只能用来说明「读取过滤不等于写入强制」，不能断言实际强制层已经存在。

常见误区

  • 认为查询里写了 sealed = true，就等于数据库已经禁止更新。
  • 认为文档说 Knowledge remains read-only，就等于触发器或应用层写入规则已经实现。
  • 把读取侧过滤、接口契约和领域说明当成写入侧强制的证据。

概念关联

关联概念关系说明
机器可读契约同步与契约检查两者都在意「边界是否可验证」：契约测试可能表达只读拒绝或冲突错误，但材料未展示具体错误映射，不能把接口契约当成数据库写入强制。
有数据拒绝降级的 schema 回退保护两者都要求不允许的操作显式失败，但前者关注已发布对象写入不可变，后者关注数据库回退时不要静默丢数据，强制位置和风险面不同。
