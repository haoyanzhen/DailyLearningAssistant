Evidence Reference Consistency Check

引用要能查、版本要对、内容要一致。

核心要点

  • 引用校验要同时检查 project_id、knowledge_version_id 和 evidence id，确认引用属于当前项目与知识版本。

证据引用一致性校验与生成内容证据锚定

完整讲解

这个概念可以理解为“作文引用不能只写编号，还要核对编号是否真的属于当前资料”。当天 c8afb0f1 中的 verify_chapter_references 会读取章节里的 evidence 引用，然后按 project_id、knowledge_version_id 和 evidence id 去查询 knowledge_evidence 表，并把查询结果与章节引用对象逐项比较。如果证据缺失、不属于当前项目或当前知识版本，或者引用内容 body 与注册证据不一致，系统会抛出 PERMISSION_RESOURCE_UNAVAILABLE 和 404。这里基于当日材料可确认的是引用校验逻辑和 knowledge_evidence 表创建、不可变保护；LLM 如何生成引用、prompt 或模型调用细节未展示，因此仍属于待确认线索。它背后的原理是：生成内容不能只是自由文本，而要被“证据锚定”到稳定对象上；只有引用对象可查、版本一致、内容一致，生成内容才可追溯。

原理逻辑

  1. 生成内容必须可追溯，因此引用不能只是自由文本，而要锚定到稳定证据对象。
  2. 证据对象要可比较，因此必须绑定 project 和 knowledge_version_id，避免跨项目或旧版本引用。
  3. 证据内容要稳定，因此 body 必须与注册证据一致，否则引用不能证明生成内容来源。

具体例子

某个章节草稿引用了 evidence id E123。系统按 project P1、knowledge version V7 查询 E123：如果 E123 属于 V6，或者 E123 的 body 与章节引用中保存的内容不一致，系统就返回 404 和 PERMISSION_RESOURCE_UNAVAILABLE，不进入后续确认或发布流程。

常见误区

  • 认为只要保存了 evidence id，引用就可追溯。
  • 实际上 evidence id 可能属于旧版本、其他项目，或者内容已经变化，必须联合 project、knowledge version 和 body 校验。

概念关联

关联概念关系说明
版本绑定与不可变依赖引用必须属于同一 project 和 knowledge version，才能被证明有效。
不可变证据存储与触发器保护evidence body 必须稳定，逐项比较才有意义。
多轮研究会话的版本绑定与原子接受引用校验为生成内容进入知识体系提供校验边界。

确认凭据哈希与确认失效

完整讲解

这个概念可以理解为“人工确认不是点一下按钮就永久有效，而是一张绑定场次和座位的票”。当天 c8afb0f1 中 review_protection.py 会把确认依据 basis 纳入 target 的 confirmed_revision 字段和 content 的 content_state 字段，并用 hashlib.sha256(json.dumps(basis, sort_keys=True).encode()).hexdigest() 计算 basis_hash。basis_hash 的作用是把“当时确认的是哪个版本、哪份内容状态”压缩成一个稳定指纹。当天还确认：当章节目标且 action 为 generate 且 protected 时，会追加 content_change；如果存在 confirmed_revision，会追加 confirmation_invalidation，reason 为“新稿成功提交后，当前章节的确认失效。”原理是：人工确认必须绑定确认版本和内容状态；内容或版本变化后，旧确认不能继续作为有效凭据。

原理逻辑

  1. 人工确认要可审计，因此不能只记录 confirmed 布尔值，而要记录确认依据 basis。
  2. basis_hash 用稳定指纹固定 confirmed_revision 和 content_state，使确认能绑定版本与内容状态。
  3. 内容或版本变化后，旧凭据不再代表当前事实，因此要显式追加 confirmation_invalidation。

具体例子

用户确认了章节 V7 的 content_state S1，系统计算 basis_hash。后来用户触发 generate 并成功提交新稿，content_state 变为 S2。系统追加 confirmation_invalidation，reason 为“新稿成功提交后，当前章节的确认失效。”此时旧的 basis_hash 不再代表有效确认，必须基于新版本和新内容状态重新确认。

常见误区

  • 把 confirmed 当成布尔值，认为 true 就代表永久有效。
  • 确认必须绑定版本和内容状态，否则内容变化后系统无法判断旧确认是否仍然有效。

概念关联

关联概念关系说明
版本绑定与不可变依赖confirmed_revision 和 content_state 是版本与内容状态字段，确认凭据建立在版本绑定之上。
幂等命令和预览契约confirm_chapter 是写命令，需要幂等、过期和来源追踪。
证据引用一致性校验章节确认前应先证明引用属于同一版本且内容一致。

精读文章 · 数据库 / 软件工程 / 计算机科学

数据库约束延迟与迁移数据保护

完整讲解

这个概念可以理解为“检查不一定越早越好，有些检查要等到事务末尾才安全”。当天 32dd12fc 中的 0028_review_pin_deferral.py 将 review_generation_tasks_project_id_knowledge_version_id_fkey 改为 DEFERRABLE INITIALLY DEFERRED，迁移说明是“Check Review version pins after all same-transaction Project cascades.”。意思是：同一个事务里可能先发生项目级联变更，再更新评审任务与版本 pin；如果外键约束立即检查，可能在中间状态就失败，导致整个事务无法完成。把约束设为可延迟且初始延迟后，数据库会在事务提交前统一检查版本 pin，从而既保留原子性，又允许级联变更先完成。另外，多个迁移 downgrade 时会先加锁，如果表中已有数据，就抛出 RuntimeError 或拒绝删除，防止已落盘事实被 schema 回退静默清除。这里基于当日材料可确认的是迁移 diff 和约束延迟机制；并发性能、锁范围成本未展示，不能声称当天评估了性能成本。

原理逻辑

  1. 同事务内可能存在项目级联变更，外键立即检查会在中间状态失败。
  2. DEFERRABLE INITIALLY DEFERRED 把版本 pin 检查推迟到事务提交前，保留原子性并允许级联完成。
  3. 迁移回退可能删除已有数据，因此 downgrade 要在数据存在时显式拒绝，保护已落盘事实。

具体例子

一个事务内要同时更新项目级联字段和 review_generation_tasks 的版本 pin。如果外键立即检查，可能因为项目字段还没更新完而报版本 pin 不一致；改为 DEFERRABLE INITIALLY DEFERRED 后，事务末尾统一检查版本 pin，全部一致才提交。若后续执行 downgrade 想删除相关表，但表中已有数据，迁移脚本会拒绝删除，避免静默丢数据。

常见误区

  • 认为外键约束越早检查越好。
  • 认为迁移回退只是改表结构、不会伤数据；过早检查可能阻塞合法级联，回退删除已有业务数据会静默抹掉历史事实。

概念关联

关联概念关系说明
版本绑定与不可变依赖版本 pin 外键需要事务末尾校验，支撑版本绑定与不可变依赖。
不可变证据存储与触发器保护同属数据库层保护，一个控制检查时机，一个控制对象不可变。
项目级联取消和运行事实采集项目级联变更和取消需要知道版本与任务事实。
