精读文章 · 软件工程 / 数据库

项目作用域聚合与会话生命周期约束

完整讲解

可以把“项目”想成一间教室，“研究会话”是教室里的座位。座位不能脱离教室单独存在，也不能随便写一个非法状态。当天 5d17517 的 research_tables.py 和 0020_research_sessions 迁移里，research_sessions 通过 project_id 外键绑定 projects.id，并设置级联删除；它还有 (project_id, id) 唯一约束，保证项目内地址稳定；status 只允许 active/archived；标题长度限制为 1–200。这些约束共同表达一个底层理念：研究会话是项目聚合内的对象，生命周期从属于项目，合法状态由数据库边界兜底，而不是只靠应用代码自觉检查。

原理逻辑

  1. 聚合归属：project_id 外键把研究会话绑定到项目，级联删除把生命周期从属关系写进数据库结构。
  2. 稳定性与合法性：(project_id, id) 唯一约束保证项目内地址稳定，status 枚举和标题长度检查限定合法状态与输入范围。
  3. 边界兜底：约束在数据库层生效，即使调用方绕过应用代码，也不能随便写入非法状态或制造无归属会话。

具体例子

项目 P1 下创建一个标题为“文献综述”、状态为 active 的会话可以成功；如果把标题写成空字符串，或把状态写成 pending，就会被约束拒绝。删除项目 P1 时，其研究会话按级联规则一起删除；项目 P2 下的会话不受影响。

常见误区

  • 以为外键只是“引用一下”，不表达生命周期；这里的外键加级联删除明确表达了从属关系。
  • 以为状态合法性和长度限制只该写在前端或业务代码里；数据库约束提供最后一道结构边界。

概念关联

关联概念关系说明
后台刷新与本地编辑状态保护项目处于 active 是启动轮询的条件之一，项目状态约束因此成为前端刷新的触发条件之一。
已发布知识头指针解析与读模型投影项目作用域提供 project_id 关联，默认知识版本和研究会话读模型都围绕项目定位。

精读文章 · 软件工程 / 前端状态管理

后台刷新与本地编辑状态保护

完整讲解

当前端项目已经 active、但还没有 default_knowledge_version_id 时，12c408b 的 BusinessApp.tsx 会启动约 5 秒一次的后台轮询，等待这个字段出现。关键不在于“定时刷新”，而在于刷新方式：页面隐藏时跳过轮询；用 AbortController 取消过期请求；处理 401/403/404；拿到新默认版本后只更新当前项目的 default_knowledge_version_id，而不是替换整个项目对象。测试代码还断言后台刷新期间正在编辑的名称和焦点仍保留。底层理念是：服务器后台数据和用户本地编辑是两个状态源，合并时必须做字段级更新和请求生命周期管理，否则刷新会把用户正在写的内容冲掉。

原理逻辑

  1. 双状态源：服务器后台数据与用户本地编辑状态分离，合并时必须做字段级更新，而不是整体对象覆盖。
  2. 请求生命周期：用 AbortController 取消过期请求，并显式处理 401/403/404，防止旧响应晚到覆盖新状态。
  3. 触发条件：项目 active 且缺少 default_knowledge_version_id 时才低频轮询，页面隐藏时跳过，减少无意义请求。

具体例子

用户正在把项目名称改成“2026 实验”，此时后台轮询发现 default_knowledge_version_id 从空变成 v3。前端只把 v3 写进该字段，项目名称输入框里的文字和光标位置保持不变；如果页面切到后台隐藏，轮询就跳过，避免无意义请求。

常见误区

  • 以为后台轮询就是定时整页刷新或整个对象覆盖；这里的实现恰恰相反，是字段级合并。
  • 认为只要请求成功就更安全；如果旧请求晚回来覆盖新状态，也会制造竞态，所以需要 AbortController 取消过期请求。

概念关联

关联概念关系说明
已发布知识头指针解析与读模型投影后台刷新等待并消费项目读模型中的 default_knowledge_version_id，因此它是头指针投影的下游使用者。
项目作用域聚合与会话生命周期约束项目处于 active 是启动轮询的条件之一，这与项目作用域和项目状态约束相连。

精读文章 · 计算机科学 / 数据建模 / 软件工程

已发布知识头指针解析与读模型投影

完整讲解

可以把知识版本想成图书馆里的书，heads.version_id 是“当前推荐书架”的标牌，versions.sealed = true 表示这本书已经正式上架密封。12c408b 的 project_commands.py 通过 heads.version_id 标量子查询，把默认版本投影成 default_knowledge_version_id；5d17517 的 knowledge_read.py 和 research.py 再通过 latest_published 按 project_id、version_id 关联解析最新已发布版本，找不到时抛出 PERMISSION_RESOURCE_UNAVAILABLE 404。底层理念是：版本事实表和当前头指针分开，读模型不直接暴露原始表，而是把“当前指向哪个版本”和“该版本是否已发布”解析成可用字段。当天能确认的是读路径：heads 指向、sealed 条件、关联解析、字段投影和显式失败；头指针切换时如何保证事务一致性，材料没有完整展示。

原理逻辑

  1. 事实与指针分离：版本记录回答系统有哪些知识版本，head 指针只说明当前对外指向哪一个版本。
  2. 解析与投影：读模型不直接暴露原始表，而是联合 heads 指向、sealed 条件和 latest_published 关联生成可用字段。
  3. 显式失败：找不到 sealed = true 的可用版本时抛出 PERMISSION_RESOURCE_UNAVAILABLE 404，避免把不可用误当成空结果。

具体例子

项目 P 的 heads.version_id 指向 v2，而 v2 的 sealed = true，于是读模型得到 default_knowledge_version_id = v2，研究会话读模型也能暴露 latest_knowledge_version_id = v2。若 heads 缺失，或指向的版本不是已发布状态，latest_published 找不到可用版本，就抛出 PERMISSION_RESOURCE_UNAVAILABLE 404。

常见误区

  • 把 head 指针当成版本内容本身；头指针只是“当前指向哪个版本”的线索，内容还在版本记录里。
  • 以为有版本记录就能读；当天实现只读取 sealed = true 的已发布版本。
  • 以为读模型字段就是原表字段的复制；default_knowledge_version_id 是解析和投影出来的派生字段。

概念关联

关联概念关系说明

三个概念连成一条状态边界链：数据库约束先定义项目聚合内哪些会话结构合法，头指针解析再把已发布知识版本解析并投影成项目读模型字段，前端后台刷新最后消费这个字段，并且只合并缺失字段以保护本地编辑。它们共同说明：状态一致性不是靠一个“刷新”或一个“字段”完成，而是靠约束、只读边界、显式失败和合并策略协作。

今日最值得记住的一句话

状态一致性不是靠一次刷新或一个字段完成，而是靠约束、只读边界、显式失败和合并策略协作。
