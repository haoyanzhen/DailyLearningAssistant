项目作用域唯一键与全局主键的命名空间设计

完整讲解

项目作用域唯一键与全局主键的命名空间设计，核心是区分局部身份和全局身份。项目内 ID 只在项目内有效，跨项目可能重复；全局主键在整个系统内唯一，适合跨项目引用、外键关联和审计追溯。复合唯一约束 (project_id, id) 用来保证项目内 ID 稳定，全局主键用来避免跨项目歧义。API 返回时可以同时给展示身份和存储身份，数据库外键和跨项目引用优先使用全局主键，项目删除或迁移时要保留映射或显式失败，避免孤儿引用和审计断链。这里基于当日材料可确认的是 open 问题提出了身份层选择、映射完整性和跨项目引用问题；未采样完整 DDL、API 契约、外键策略或迁移脚本，因此具体实现仍待确认。

原理逻辑

  1. 身份分层：局部 ID 降低业务展示成本，全局主键保证系统级唯一性。
  2. 引用稳定：跨项目引用、外键和审计需要可解析的稳定身份，避免 project_id 缺失造成歧义。
  3. 迁移保护：项目删除或迁移时保留身份映射，旧引用可继续解析或显式失败。

具体例子

研究项目 A 和 B 都有 note id=1001。API 返回 project_id=A、id=1001、global_id=g-note-1；跨项目引用使用 global_id，项目 A 迁移时保留 project_id、id 到 global_id 的映射，旧引用仍可解析。

常见误区

  • 认为一个 ID 可以同时满足展示、存储、跨项目引用和审计。
  • 认为项目内 ID 可以跨项目复用而不携带 project_id，或全局主键只是换一种字符串。

迁移保护中检查、清理与放行的原子性边界迁移保护依赖全局主键和 project_id 判断引用是否完整，避免清理后出现孤儿引用。

状态迁移合法边与审批审计记录的数据表达

完整讲解

状态迁移合法边与审批审计记录的数据表达，核心是把状态系统从取值集合升级为路径约束。状态取值约束只能回答当前状态是否合法，状态迁移边约束还要回答这次变化是否合法。例如 active 到 archived 可以是一条允许边，archived 到 active 可以是禁止边或需要审批的边。数据库 CHECK 通常只能看当前行，难以直接表达 from_status 到 to_status，因此可以用触发器比较 OLD 和 NEW，也可以用状态迁移表记录哪些边允许、哪些边需要审批。应用层状态机是主要业务校验，数据库层兜底可以防止手工 SQL、并发或绕过应用层写入。审批结果不应只是普通日志，而应成为迁移事件的一部分，记录对象身份、from_status、to_status、操作者、审批者、原因、审批单和时间。这里基于当日材料可确认的是 open 问题提出了 CHECK 局限、触发器、状态迁移表、审批和审计记录问题；未采样触发器、迁移表或审批实现，因此具体行为仍待确认。

原理逻辑

  1. 状态取值是点约束，状态迁移边是路径约束。
  2. 数据库约束需要覆盖应用层之外的写入路径，如手工 SQL 和并发写入。
  3. 审批不是附属日志，而是迁移事件的一部分，必须与状态变化绑定。

具体例子

研究会话有 active 和 archived 两个状态。active 到 archived 允许；archived 到 active 需要人工审批。触发器发现 OLD.status=archived 且 NEW.status=active 时，检查是否存在 approval_id=appr-123 的审批记录；不存在则拒绝，并写入迁移记录。

常见误区

  • 认为 status 枚举合法就足够，应用层校验后数据库就可以不管。
  • 认为审批日志可以事后补写，只要最终状态正确就行。

迁移保护中检查、清理与放行的原子性边界某些状态允许归档后清理，某些状态禁止破坏性降级，迁移保护可能依赖合法状态边。

迁移保护中检查、清理与放行的原子性边界

完整讲解

迁移保护中检查、清理与放行的原子性边界，核心是检查、清理、放行之间有时间窗口，不能把检查通过当成永久安全。TOCTOU 风险指检查时条件成立，执行时条件可能变化，例如检查时表里没有新数据，清理前又有新数据写入。短事务可以缩小窗口，版本戳或重新检查可以验证状态没有变化，锁表更强但会影响可用性。清理失败时，系统可以选择回滚、标记失败或进入补偿队列，但不能留下看起来清理了一半的状态。表级保护策略也要区分禁止破坏性降级和可归档后清理，迁移脚本或配置要能表达不同表的策略。这里基于当日材料可确认的是 open 问题提出了表级策略、TOCTOU、短事务、版本戳、重新检查、补偿队列和半清理状态问题；未采样迁移事务、锁范围、补偿队列或运行验证，因此具体实现仍待确认。

原理逻辑

  1. TOCTOU 的本质是检查与执行之间状态可能变化。
  2. 原子边界可以通过事务、锁、版本戳或重新检查来缩小风险窗口。
  3. 失败恢复必须显式表达失败状态、补偿路径和禁止半清理。

具体例子

降级前检查表 T 是否还有数据。若不能长期锁表，可记录 version=7，清理前重新检查 version 是否仍为 7 且 count 为 0；若变化则拒绝，清理失败时标记 cleanup_failed 并进入补偿队列。

常见误区

  • 认为检查通过就永远安全，或长期锁表是最简单可靠的方案。
  • 认为清理失败只要重试就行，不需要失败状态、补偿队列和半状态隔离。
