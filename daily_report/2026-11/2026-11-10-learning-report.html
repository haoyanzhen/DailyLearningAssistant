状态迁移约束与合法路径表达

完整讲解

状态字段最常见的约束是取值约束，例如 status 只能取 active 或 archived。这种约束回答的是：这个值本身合不合法？但业务真正关心的常常是：从当前值变到另一个值合不合法？如果把状态看成图里的节点，合法迁移就是节点之间的有向边。取值约束只检查节点是否存在，状态迁移约束还要检查边是否存在。数据库层面，CHECK 约束通常只能看当前行，难以直接表达上一状态到当前状态的关系；触发器、状态迁移表、应用层状态机或写入中间件可以补充路径约束。当前 open 问题只提出设计问题，未采样 DDL、触发器、状态机配置或运行验证，因此这里只能把它作为状态迁移约束问题讨论，不能声称项目已经实现某种状态机。

原理逻辑

  1. 把状态看成节点，把合法迁移看成有向边，取值合法只说明节点存在，路径合法还要说明边存在。
  2. 数据库 CHECK 通常只能检查当前行，难以直接表达 from_status 到 to_status 的关系，因此需要触发器、状态迁移表、应用层状态机或写入中间件补充路径约束。
  3. 应用层状态机和数据库约束不是替代关系，而是分层兜底关系，防止手工 SQL、并发写入或迁移流程绕过路径规则。

具体例子

精读例子：研究项目有 active 和 archived 两种状态。创建项目时状态为 active；归档时允许 active 到 archived；若 archived 项目直接改回 active，应被拒绝或走恢复流程。如果数据库只写 CHECK status IN ('active','archived')，那么 UPDATE 从 archived 改到 active 时，数据库不会报错，非法路径就可能漏过。

常见误区

  • 以为 CHECK status IN ('active','archived') 就足够，因为取值都合法。
  • 以为应用层做过状态机校验，数据库就可以不再关心。
  • 以为状态名不同就自动禁止回退，其实必须显式定义合法边。

关联概念关系说明

集合完整性证明中的快照语义与分页漂移两者都要求把当前取值扩展为过程可验证，前者验证状态路径，后者验证集合读取过程。

迁移保护中检查、清理与放行的原子性边界

完整讲解

破坏性降级或 schema 回退前，系统常需要检查某张表是否有数据，再决定是否允许丢弃、导出或清理。问题在于：检查通过和真正执行清理之间可能有一个时间窗口。检查时表是空的，清理前又可能有新数据写入，那么先前检查结论就失效了。这类问题常被称为 TOCTOU，即检查时与使用时不一致。锁、事务、隔离级别、补偿清理和表级保护分类共同决定检查、清理、放行是否原子。所谓原子性边界，不是说每一步都绝对不可能失败，而是说系统必须明确：检查结论在什么条件下仍然有效，失败后如何回滚、补偿或标记不可用。当前 open 问题只给出局部迁移线索，未采样锁范围、事务边界、补偿任务或运行验证，因此这里只能作为迁移保护原子性问题讨论，不能声称项目已经采用某种锁或补偿机制。

原理逻辑

  1. 破坏性操作前需要检查数据存在性，但检查与执行之间必须保持同一受控边界，否则旧结论可能失效。
  2. 如果没有排他锁、事务边界、清理前重查或表级保护分类，外部写入可能让检查通过后的清理动作变成破坏性操作。
  3. 原子性边界不仅要防止误删，还要定义失败后的回滚、补偿、标记不可用和半清理状态恢复路径。

具体例子

精读例子：降级前检查 papers 表是否有数据。若检查为空，准备 DROP TABLE；但另一个事务正在插入一条 paper。如果没有排他锁、事务边界或清理前重查，可能插入成功而表随后被删。保护策略可以是对表加锁、使用事务、在清理前重查、标记禁止破坏性降级，或先归档导出再清理。

常见误区

  • 以为 SELECT COUNT 等于 0 之后 DROP TABLE 就安全。
  • 以为事务能自动覆盖所有外部写入。
  • 以为有数据拒绝降级已经等于整个清理流程原子，忽略锁范围、隔离级别、补偿失败和半清理状态。

概念关联

关联概念关系说明
状态迁移约束与合法路径表达状态迁移规则如果只在应用层判断，可能在并发迁移或清理流程中被绕过，需要事务和锁保护。
集合完整性证明中的快照语义与分页漂移两者共享检查或读取时成立、执行或读取完成后失效的时间窗口问题，都需要快照、重试、补偿或原子边界。

集合完整性证明中的快照语义与分页漂移

完整讲解

从分页、游标或总数接口读取一个集合时，如果数据源在读取期间变化，最初确定的期望集合可能不再成立。比如系统先看到 total 是 100，读取第一页和下一页时，数据源又新增或删除了记录，最后拼出来的集合可能少一项、多一项、重复一项，或出现不属于当前查询范围的项。完整性证明不能只说数量对上了，而要说明读取语义：读取的是某个快照、某个时间点，还是允许重试直到稳定。集合相等需要双向比较，即 A 包含于 B 且 B 包含于 A；失败时还要把差集、重复项、越界项、空结果和来源服务异常分开表达。空集合可能是合法结果，也可能是来源服务异常，不能合并为同一个失败。retrieval_proof_version 变化会影响旧证明是否可复用，因为证明绑定的条件变了。当前 open 问题只给出字段和场景线索，未采样证明结构、分页实现或运行验证，因此这里只能作为集合完整性证明问题讨论，不能声称项目已经实现某种证明算法。

原理逻辑

  1. 分页读取不是原子操作，跨页期间数据源新增、删除或重复，都会造成集合漂移。
  2. 集合相等必须双向比较，数量相等不能证明成员一致，因此需要 missing、extra、duplicate、out_of_scope 等分类字段。
  3. 证明需要绑定 proof_version、查询条件、读取窗口或快照标识，并在失败时区分合法空结果与来源服务异常。

具体例子

精读例子：论文检索返回 total 等于 100，系统读取第一页 1 到 50，再读取第二页 51 到 100。读取期间新增一篇论文，旧 total 100 变成 101，第二页可能少一篇或多一篇。完整性证明应记录 proof_version、查询条件、读取窗口或快照标识，并报告 missing_ids、extra_ids、duplicate_ids、out_of_scope_ids；空结果要区分合法无结果和来源服务异常。

常见误区

  • 以为 total 对上就完整。
  • 以为空列表一定是错误。
  • 以为集合比较只看数量，忽略重复项和越界项。
  • 把来源异常和合法空结果混在一起。

概念关联

关联概念关系说明
迁移保护中检查、清理与放行的原子性边界前者是读取期间集合变化，后者是检查后数据变化，二者都需要明确快照、重试或补偿边界。
状态迁移约束与合法路径表达两者都要求过程可验证，状态迁移验证对象路径，集合证明验证成员读取过程。
