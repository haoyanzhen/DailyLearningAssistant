项目作用域唯一键与全局主键的命名空间设计

完整讲解

可以把项目内 ID 想象成班级学号，把全局主键想象成全校学籍号。班级学号在班里够用，但两个班都可能有 1 号学生；全校学籍号则跨班级唯一，适合转学、档案查询和跨部门引用。数据系统里也常有这种两层身份：(project_id, id) 保证某个项目内部 ID 稳定且无重复，全局主键保证跨项目存储、引用和迁移时不会混淆。这里基于当日材料可确认的是，concept_relevance.md 汇总的历史问题提出了 (project_id, id) 复合唯一约束与全局主键关系的设计问题，但没有采样 DDL、索引、外键、引用路径和运行验证，因此不能声称项目已经采用某种主键策略。讲清楚这一概念的关键，是明确查询、引用、删除、审计和迁移分别使用哪一层身份：如果 API 面向业务，可以返回项目内 ID 并始终携带 project_id；如果内部存储和跨项目引用需要唯一性，则使用全局主键。两层身份并不冲突，关键是映射关系要稳定。

原理逻辑

  1. 项目内 ID 解决业务命名空间中的稳定识别，不要求跨项目唯一。
  2. 全局主键解决跨项目存储、引用、迁移和审计中的无歧义身份。
  3. 两层身份通过稳定映射连接，避免把数据库主键直接等同于业务 ID。

具体例子

项目 A 和项目 B 都有一条知识版本 id=42。如果读模型只返回 id=42，跨项目引用会歧义；如果返回 project_id=A 且 id=42，业务侧知道它属于项目 A；如果内部还需要全局唯一，则再映射到 global_id=9001，用于存储、审计和跨项目查询。

常见误区

  • 把数据库主键直接等同于业务 ID。
  • 认为项目内 ID 必须全局唯一，忽略业务命名空间和存储身份可以分层。

概念关联

关联概念关系说明
读模型中引用存在与执行完成的空值语义为 latest_knowledge_version_id 等字段提供稳定身份基础，先确认引用的是项目内 ID 还是全局主键。
幂等键与内容指纹不一致的冲突语义都要求身份字段在重试、引用、删除和审计中保持稳定，避免同一业务对象被误判为不同对象。

读模型中引用存在与执行完成的空值语义

完整讲解

读模型像把数据库里的原始字段翻译成用户能理解的状态。latest_knowledge_version_id 存在，表示系统里有一个可引用的知识版本，类似“订单已经创建”；last_execution_knowledge_version_id 为空，表示还没有执行版本绑定或执行完成，类似“骑手还没有接单”。这两件事不是同一状态，不能合并成“没有知识版本”。这里基于当日材料可确认的是，concept_relevance.md 汇总的历史问题提出了 latest_knowledge_version_id 存在但 last_execution_knowledge_version_id 为空时应返回 404、空值还是派生状态的问题，但没有采样读模型代码、状态枚举、前端轮询处理和测试断言，因此不能声称系统已经采用某种映射。讲清楚这一概念的关键，是区分三种外部语义：404 表示资源不存在；空值表示资源存在但某个字段尚未填充；派生状态如 pending、not_executed 表示系统能解释当前组合。available_actions 也依赖这种状态组合，例如“有可用版本但尚未执行”时可以给出 execute 动作。

原理逻辑

  1. 引用存在和执行完成是两个独立事实，不能合并成同一个状态。
  2. null、404 和派生状态分别表达字段未填充、资源不存在和可解释状态。
  3. available_actions 应根据状态组合计算，而不是只依赖单个字段。

具体例子

API 返回 latest_knowledge_version_id 为 7、last_execution_knowledge_version_id 为空、available_actions 包含 execute。前端应展示“已有可用版本，但尚未执行”，而不是提示“知识版本不存在”；如果 latest_knowledge_version_id 也为空，则可能需要展示“暂无可用版本”或触发其他加载逻辑。

常见误区

  • 把 null 一律当成 404。
  • 把 latest 为空和 last_execution 为空混成同一个“未完成”。

概念关联

关联概念关系说明
项目作用域唯一键与全局主键的命名空间设计latest_knowledge_version_id 和 last_execution_knowledge_version_id 的解析需要先确认引用的是项目内 ID 还是全局主键。
幂等键与内容指纹不一致的冲突语义都要求把内部状态组合翻译成调用方可理解的外部语义，避免把未完成误报为不存在或冲突。

幂等键与内容指纹不一致的冲突语义

完整讲解

幂等键像银行转账的流水号，内容指纹像转账金额、收款账户和用途的摘要。网络重试时，如果流水号相同且摘要相同，服务端可以返回旧回执，避免重复扣款；如果流水号相同但摘要不同，说明同一身份被用于不同内容，系统必须裁决：返回旧回执、409 冲突，还是 422 校验错误。这里基于当日材料可确认的是，concept_relevance.md 汇总的历史问题提出了 project_id、actor_id、key 已存在但 fingerprint 不同时如何返回的问题，但没有采样服务端去重表、摘要算法、错误码实现和运行验证，因此不能声称 ResearchPaperBase_codex 已经实现上述机制。讲清楚这一概念的关键，是把三层机制分开：幂等键处理“同一请求身份是否重复”，fingerprint 处理“请求内容是否变化”，服务端去重表保存“服务端已经见过什么”。如果只按幂等键判断，会把内容变更误当成重复；如果只按指纹判断，会丢失重试语义。

原理逻辑

  1. 幂等键识别请求身份，用于判断是否重复请求。
  2. 内容指纹识别请求内容变化，用于判断是否同一身份对应不同载荷。
  3. 服务端去重表保存事实，使重试、冲突和审计可以可靠裁决。

具体例子

创建命令使用 project_id=1、actor_id=7、key 为 create-report。第一次请求 fingerprint 为 abc123，服务端保存回执；重试时 fingerprint 仍为 abc123，服务端返回旧回执；若客户端把参数改成 fingerprint 为 xyz789 但仍使用同一 key，服务端可返回 409“同一幂等键已对应不同内容”，而不是直接覆盖旧回执。

常见误区

  • 认为幂等键能解决所有重复问题。
  • 认为 fingerprint 相同就一定能安全返回旧结果，忽略服务端事实保存和业务规则。

概念关联

关联概念关系说明

读模型中引用存在与执行完成的空值语义都要求把内部状态组合映射为明确外部语义，例如旧回执、409、422、404、空值或派生状态。
