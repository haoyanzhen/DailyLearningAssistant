模型上下文窗口容量配置与参数校验

完整讲解

可以把模型上下文窗口想成一张有限大小的工作台：一次能摊开的资料和写下的内容都有上限。当日材料里，llm.py 在模型选项中增加 context_window_tokens，在配置输出中加入 model_context_windows，并引入 context_window、validate_context_windows 这些入口；这里能确认的是“容量进入了模型配置与参数校验”，不能确认具体容量公式或 token 估算算法，因为 context_capacity.py 只有路径线索。它的底层理念是：既然上下文窗口是有限资源，就不要等到运行时才突然发现输入太长或配置不对，而应把容量写成可配置、可检查的参数，让超限或不一致在请求之前或请求边界暴露。这样做不是为了追求某个复杂算法，而是为了让系统对“一次能处理多少内容”有明确契约。

原理逻辑

  1. 上下文窗口是有限资源，容量应像尺寸表一样被显式登记在配置里，而不是隐含在代码行为中。
  2. 把容量写成可配置、可检查的参数，等于给系统一条可验证的契约：超限或不一致应在请求前暴露。
  3. 这里追求的是边界清晰而非算法复杂：先明确“一次能处理多少”，再谈处理结果是否合格。

具体例子

假设配置表里模型 A 的 context_window_tokens 是 8000，模型 B 是 32000。一次分析请求预计输入 7000 token、输出 3000 token，那么使用模型 A 就应在请求前被校验发现可能超限，而不是等模型运行到一半才失败；若配置值缺失或不合规则由 validate_context_windows 这类入口报错。

常见误区

  • 以为只要配置了上下文窗口字段，系统就会自动截断、摘要或正确处理超长输入。
  • 以为窗口越大结果一定越正确，忽略了容量只是资源边界而非质量保证。
  • 把配置字段与校验入口的存在，当成已经具备容量算法或运行验证的事实。

概念关联

关联概念关系说明
单次冻结参数请求与显式失败边界它为单次冻结参数请求提供可检查的输入边界：容量和参数不合规时，应在请求边界显式失败，而不是留到运行中隐式处理。
人审确认作为知识写入前置边界两者共同限制知识域：容量决定一次分析能看到和生成什么，人审确认决定这些分析结果是否进入正式知识。
固定 JSON 结构化输出与长度/条目约束它延续了固定 JSON 输出约束中的“边界”思想，但关注的是模型可处理规模，而不是字段与数组条目的具体结构。

单次冻结参数请求与显式失败边界

完整讲解

一次请求可以类比为一次有记录的实验：开始前确定实验条件，执行期间不偷偷换条件。当日材料中，paper_analysis_provider.py 的 docstring 写明“One full-text analysis request with frozen parameters; no implicit fallback or retry.”，能确认的是一种设计承诺：一次全文分析请求使用冻结参数，不通过隐式回退或重试来改变调用语义。为什么要冻结参数？因为如果系统内部悄悄换成备用模型、改掉参数再重试，调用方就不知道结果究竟来自哪组条件，也不知道是否产生了重复副作用。显式失败边界的意思是：失败、冲突或契约不满足时，让错误清楚地暴露出来，由上层决定是否重试、是否换路径、是否提示用户。这里不是说所有重试都坏，而是说重试必须是显式策略，不能藏在调用链里把失败伪装成成功。

原理逻辑

  1. 冻结参数保证结果与条件可对应：结果来自哪组模型与参数必须是确定的，而不是事后推测的。
  2. 隐式 fallback 或 retry 会改变调用语义，可能产生调用方无法解释的重复副作用。
  3. 显式失败边界把决策权交还上层：失败先暴露，再决定是否重试，而不是由调用链偷偷决定。

具体例子

一次论文全文分析请求已经冻结了模型、输入范围和输出契约。如果模型返回内容缺少必需字段，系统应明确报告契约失败，而不是自动换一个模型重试并把第二次结果当作第一次结果交付。若上层决定重试，也应作为显式动作记录下来，并考虑幂等性和是否产生重复副作用。

常见误区

  • 认为自动重试越多越可靠，或 fallback 总是提升可用性；实际上它们可能改变模型、参数或副作用语义，让结果无法比较。
  • 把 docstring 中的设计承诺当成已经运行验证的事实；材料没有展示失败日志、重试策略实现或运行验证。
  • 以为显式失败会降低健壮性，忽略了失败被隐藏才是调用方最难以处理的情况。

概念关联

关联概念关系说明
模型上下文窗口容量配置与参数校验它承接容量与参数校验：容量或参数不合法时，应在请求边界显式失败，而不是运行中静默处理。
人审确认作为知识写入前置边界请求失败、冲突或结果不确定时，不应自动升级为知识，人工确认或明确状态条件决定是否采纳运行结果。
STATE_REVISION_CONFLICT 类开放问题冲突需要显式暴露并进入明确恢复路径，恢复动作不能通过隐式重试掩盖重复副作用。

人审确认作为知识写入前置边界

完整讲解

运行局部分析结果不是正式知识，而更像一份“分析提案”。当日材料中，paper_analysis.py 的 docstring 写明“Run-local analysis commands. No knowledge writes or implicit content adoption.”；writable 要求 waiting_user 和特定 phase；worker 在 commit 前检查 processing_confirmation。这里能确认的是：材料把局部分析与正式知识写入分开，并设置人工确认或明确状态条件作为写入前置边界。它的核心逻辑是：执行成功不等于业务完成。模型返回了一段看似合理的内容，只说明这次运行完成了，不代表这段内容应该进入正式知识库。人工确认或特定状态条件像一道闸门，只有闸门打开，运行结果才从“候选内容”变成“被采纳知识”。这道闸门既保护知识质量，也保护责任边界。

原理逻辑

  1. 运行局部与正式知识是两层：局部分析可以自由生成候选结论，但默认不具备写入权。
  2. 状态门控把“是否采纳”编码为可检查条件：waiting_user、phase 与 commit 前的 processing_confirmation 检查。
  3. 这道闸门同时保护两件事：知识质量不被未审核内容污染，责任边界不被模糊。

具体例子

一次论文分析在运行局部生成候选结论“这篇论文的方法属于某类”。系统把它保持在 run-local 状态，只有进入 waiting_user 且 phase 符合要求，并且 worker 在 commit 前检查到 processing_confirmation 后，才允许进入正式知识写入。否则它只是提案，不能被当作已确认知识。

常见误区

  • 认为模型返回结果就应该自动写入，自动写入只是提高效率；实际上没有确认边界时，错误、过期或冲突的分析会直接污染知识域。
  • 认为有一个人工按钮就足够了；材料还显示状态门控和 commit 前检查，但并未证明完整事务或并发原子性。
  • 把状态检查当成已经具备原子提交证明，把设计线索写成已完成的运行事实。

概念关联

关联概念关系说明
单次冻结参数请求与显式失败边界失败、冲突或结果不确定时，不应自动升级为知识；人审确认或明确状态条件决定是否采纳这次运行结果。
模型上下文窗口容量配置与参数校验两者共同限制知识域：容量决定一次分析能看到什么，人审确认决定这些结果是否进入正式知识。
固定 JSON 结构化输出与长度/条目约束结构合格只是候选资格，不等于可以自动采纳；契约正确性与是否写入是两道独立的关。
