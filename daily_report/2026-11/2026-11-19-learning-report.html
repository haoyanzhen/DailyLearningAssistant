字段级错误路径的规范化表达与聚合

完整讲解

字段级错误路径的核心，是把接口失败从一句通用提示，变成调用方可以自动处理的错误清单。该主题来自 2026-11-17 和 2026-11-14 的历史 open 问题延展，没有当日 diff 或运行验证，因此只能作为待确认原理讲解。理解它可以从三个层次开始：第一，状态码负责分类，422 通常表示输入校验失败，403 表示权限不足，409 表示资源状态冲突；第二，字段路径负责定位，它要能表达顶层字段、嵌套对象和数组下标；第三，错误聚合负责把多个问题一次说清楚，而不是只返回第一个错误。对于 OpenAPI 中 additionalProperties=false 的场景，未知字段不能悄悄忽略，而应被一致拒绝，并返回可解析路径，让调用方知道哪个字段不该出现。

原理逻辑

  1. 状态码负责分类失败类型，让调用方先判断是权限、冲突还是校验问题。
  2. 字段路径负责定位违规位置，需要稳定表达顶层字段、嵌套对象和数组下标。
  3. 错误聚合负责一次返回多个问题，避免只暴露第一个错误导致反复试错。

具体例子

一个创建项目接口返回 422，响应中包含 errors 数组：第一项 path 为 members[1].email，code 为 format，message 为邮箱格式不正确；第二项 path 为 title，code 为 required，message 为标题不能为空。前端可以据此把红色提示直接定位到第二个成员邮箱输入框和标题输入框。

常见误区

  • 以为错误消息只要给人看得懂就够了，忽略机器可解析路径和错误码。
  • 把 403、409、422 混用，导致调用方无法区分换身份、刷新状态或修改输入。

概念关联

关联概念关系说明
无快照集合的边界绑定与差异分类两者都要求把失败定位到稳定可解析单元：字段错误定位字段，集合差异定位 missing、extra、duplicate、out_of_scope。
幂等身份键与内容指纹的冲突裁决两者都要求错误可机器解析，调用方需要知道是权限、冲突还是字段校验问题。

无快照集合的边界绑定与差异分类

完整讲解

无快照集合的边界绑定与差异分类，解决的是“我读到的这一批数据，是不是完整集合”的问题。该主题来自 2026-11-17、2026-11-14、2026-11-12 的历史 open 问题延展，没有当日 diff 或运行验证，因此只能作为待确认原理讲解。如果没有 snapshot_id，total 和 cursor 可能来自不同时间点或不同范围：第一页看到 total 是 100，翻页时上游新增或删除了数据，最后读到的集合可能已经漂移。此时不能只问“请求成功吗”，而要问“我读到的元素集合是否和预期边界一致”。差异分类就是把这个判断拆开：missing 表示应有但没有读到，extra 表示读到了但不在预期范围，duplicate 表示同一元素重复出现，out_of_scope 表示元素越界或不属于当前集合。集合完整性因此不只是一个数量问题，而是边界、成员、计数和版本条件共同构成的判断。

原理逻辑

  1. 没有 snapshot_id 时，total 和 cursor 可能来自不同时间点，集合边界会漂移。
  2. 集合比较要拆成 missing、extra、duplicate、out_of_scope 等可判定差异类别。
  3. 完整性证明需要边界、成员、计数和版本条件共同指向同一集合。

具体例子

一个导出接口声称 total=100，调用方分页读完所有 cursor 后，把读到的记录集合与预期集合比较，发现缺 3 条、多 2 条、重复 1 条。系统不应返回成功，而应返回 incomplete，并给出 missing、extra、duplicate 的具体 ID 或摘要，让调用方决定补拉、重试或人工处理。

常见误区

  • 以为 total 匹配或请求成功就代表集合完整。
  • 数量一致只说明计数可能一致，不能证明成员一致，重复和越界也可能让数量看起来正确。

概念关联

关联概念关系说明
字段级错误路径的规范化表达与聚合集合差异需要 missing、extra、duplicate、out_of_scope 分类，字段错误需要稳定路径，二者都依赖稳定可解析单元。
幂等身份键与内容指纹的冲突裁决两者都涉及一致性边界：前者保证读取集合边界稳定，后者保证同一请求身份在不同内容下不产生不一致副作用。

  2. missing、extra、duplicate、out_of_scope 四类差异应如何汇总，调用方才能决定重试、补拉或人工处理？
  3. 分页过程中上游数据新增或删除时，应返回漂移错误还是允许调用方按最终集合重新拉取？

幂等身份键与内容指纹的冲突裁决

完整讲解

幂等身份键与内容指纹的冲突裁决，处理的是“同一个请求身份，但请求内容不一样”时系统该怎么办。该主题来自 2026-11-15、2026-11-12、2026-11-17、2026-11-14 的历史 open 问题延展，没有当日 diff 或运行验证，因此只能作为待确认原理讲解。幂等键像订单号，回答“是不是同一请求”；fingerprint 像内容摘要，回答“这次请求内容和上次是否一致”。如果幂等键相同但 fingerprint 不同，系统不能简单按旧请求执行，也不能默默按新请求执行，而必须根据业务规则裁决：可以返回旧回执，可以返回 409 冲突，也可以返回 422 校验错误。fingerprint 应覆盖会改变副作用的字段，比如金额、对象 ID、操作类型；不应覆盖时间戳、客户端随机 ID 或纯展示字段，否则正常重试会被误判为冲突。去重表还要有保留窗口，既要覆盖网络重试时限，也要满足审计周期，清理时不能直接删掉整条回执，而应保留最小审计字段。

原理逻辑

  1. 幂等键回答是否同一请求身份，用于识别重复请求。
  2. fingerprint 回答请求内容是否一致，用于检测副作用相关字段变化。
  3. 身份键相同但指纹不同时，必须显式裁决旧回执、409 冲突或 422 校验错误。

具体例子

一个创建支付请求使用 idempotency_key=order-123。第一次请求 fingerprint=A，系统创建支付并返回回执。第二次请求仍使用 order-123，但金额变化导致 fingerprint=B。系统应返回 409 IDEMPOTENCY_KEY_CONFLICT，并说明同一幂等键对应不同内容，而不是再次扣款或返回旧回执。

常见误区

  • 以为幂等键相同就一定是同一请求。
  • 把 fingerprint 当成身份键，忽略身份键与内容指纹的分工。

概念关联

关联概念关系说明
状态机合法迁移边在数据层的表达与兜底两者都涉及状态或版本一致性：幂等冲突防止同一身份键在不同内容下产生不一致副作用，状态迁移边防止非法状态迁移。
上游依赖失效的显式失败边界与错误归属两者都涉及重试和副作用控制：幂等机制避免重复副作用，依赖失效机制避免失败来源不明时继续执行或误报。
