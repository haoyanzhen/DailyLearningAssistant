Godot `.uid` 文件

完整讲解

在 Godot 4.x 中，每个需要稳定引用的资源（如脚本）旁边会生成一个同名后缀为 .uid 的小文件，里面存放一串随机生成的唯一 ID。引擎在解析资源引用时，优先以这个 ID 为凭据，而不是路径。因此当资源文件被移动、重命名或所在文件夹调整后，只要 UID 不变，场景中的引用依然有效，不会出现红色报错。本地 tiny-sea-war 的提交中新增了多个 .uid 文件（如 terrain_collision_field.gd.uid 和 navigation_collision_field_test.gd.uid），这正好为 '.uid 文件用于资源唯一标识'提供了实例。

原理逻辑

  1. Godot 4.x 在生成资源时为其分配随机唯一 ID，并写入同名 .uid 文件。
  2. 引擎引用解析先查 UID 映射表，再映射到当前路径，因此路径变化不影响最终定位。
  3. UID 是稳定的标识符，与内容哈希无关，也不应被当作缓存文件删除。

具体例子

一个“英雄”脚本原本住在 scripts/hero.gd，项目大整理后路径变成 characters/hero.gd。按照老办法，所有引用它的场景都会找不到它；但 Godot 通过 .uid 文件里的 ID 仍然能找到它，就像快递员扫身份证件一样，不受地址变化影响。

常见误区

  • 误以为 .uid 文件是编译缓存或垃圾文件，可以随意删除。实际上它们是资源索引，删除可能导致引用暂时失效。
  • 误以为 .uid 内容是文件内容或路径的哈希。实际上它是随机生成的唯一标识。

概念关联

关联概念关系说明
Git 状态指纹 SHA.uid 文件与 Git 的 SHA 都是一种稳定标识，让对象不被路径或名字的变化所迷惑。
碰撞场资源.uid 文件服务于 Godot 的资源唯一标识机制，与地形碰撞场、导航碰撞场等脚本资源紧密关联。
指针级证据与文件级证据的差异在变更检测中，.uid 文件的新增为文件级证据提供了一个具体条目，帮助确认提交涉及了哪些资源。

关卡索引与边界偏移

完整讲解

关卡索引即用数字给关卡排序，程序通常将关卡数据存在数组里，而数组下标从 0 开始。若用户看到的“第 1 关”对应数组下标 0，则在用用户输入作为下标时需要做 -1 转换。如果遗漏或写错，就会产生 off-by-one（栅栏柱）错误：玩家选择第 n 关，实际加载了第 n+1 关的数据，或者访问越界崩溃。这个错误的影响会传导到地图、碰撞场和敌人配置等所有依赖索引的模块。例如，一个三关游戏列表为 [森林关, 沙漠关, 雪地关]，若直接用玩家输入的 2 作为下标，就会取到雪地关而不是沙漠关。修复这类问题常需要同步调整测试脚本，以覆盖边界用例。

原理逻辑

  1. 数组下标从 0 开始，用户界面编号从 1 开始，两者需要显式转换。
  2. 关卡索引是配置入口，偏移会连带影响地图、碰撞场、敌人等所有关联数据。
  3. off-by-one 错误常被 UI 掩盖，只有通过边界测试才能暴露。

具体例子

一个小游戏有 3 个关卡，列表是 [森林关, 沙漠关, 雪地关]，索引分别是 0、1、2。如果玩家选择“第 2 关”时代码直接用 selectedLevel（值为 2）去取列表，就会取到“雪地关”，而不是“沙漠关”。修复方法可以是在取列表前做一次转换 list[selectedLevel - 1]，或者把用户输入从 1 开始的编号先变成内部从 0 开始的索引。

常见误区

  • 误以为索引错误只是改一个数字的小问题。实际上关卡索引是配置入口，偏移会影响所有下游子系统。
  • 误以为界面显示正常就没有索引错误。实际上用户界面会掩盖 off-by-one，只有仔细对比或测试才能发现。

概念关联

关联概念关系说明
碰撞场关卡索引偏移会直接影响地形碰撞场和导航碰撞场的加载，因为不同关卡可能对应不同的碰撞配置。
自动化测试与回归验证修复关卡索引时同步更新测试脚本，体现了测试与回归验证在工程中的反馈闭环。
Godot `.uid` 文件关卡索引的正确性依赖于用户可见编号到程序内部索引的映射规则，这与资源唯一标识要解决的问题都属于引用可靠性问题。

指针级证据与文件级证据的差异

完整讲解

在监控远程仓库时，git ls-remote 只读取远端引用（ref）指针指向的提交哈希，这属于指针级证据。它能够告诉我们某个分支的指针是否移动，但无法得知具体提交信息和文件改动。若要查看文件级证据，必须使用 git fetch 将提交对象下载到本地，才能查看 commit message、改动文件列表和 diff。以公共仓库 public-library 为例，ls-remote 显示 refs/heads/main 的 SHA 未变化，只能说明远端主分支指针没有移动；而本地 tiny-sea-war 的提交记录则给出了 6 个文件变更，属于文件级证据。两种证据适用场景不同：低成本只读监控可选用指针级，详细审查则必须获取文件级。

原理逻辑

  1. ref 指针保存提交哈希，比较前后哈希即可判断是否变化，信息粒度极低。
  2. commit 对象中保存 tree，tree 保存文件列表，只有 fetch 到本地才能读取这些细节。
  3. 监控目的决定证据粒度，最小权限原则倾向使用指针级，审查则需文件级。

具体例子

public-library 仓库的监控脚本通过 SSH 执行 git ls-remote，得到历史 SHA 与当前 SHA 相同，于是记录为 unchanged。这个结论只能说明远端 main 指针此刻没有移动，不能说明期间是否发生过提交后回滚等操作。而 tiny-sea-war 仓库的提交 87faa464 显示 HEAD -> main, origin/main 指向同一提交，并且文件列表中 6 个文件变更，这是文件级证据，能直接看到改动范围。

常见误区

  • 误以为 ls-remote 返回的 SHA 相同就说明仓库完全没有变化。实际上只能说明检查的 ref 没有变，其他分支或标签可能已变。
  • 误以为本地提交记录一定比远端 ref 证据更可信。实际上它们回答的问题不同，不能简单比较可信度。

概念关联

关联概念关系说明
Git 引用（ref）指针指针级证据对应 git ls-remote 的可观测性边界，而文件级证据来自本地提交记录或 git fetch 后的对象。
状态指纹 SHA状态指纹 SHA 是指针级证据的核心，通过比较前后两次 SHA 是否相同来判断 ref 是否变化。
最小权限访问原则最小权限访问原则支持使用指针级证据，在不需要文件细节时，只给 ref 读取权限，缩小安全暴露面。
关卡索引与边界偏移关卡索引修复的提交记录属于文件级证据，说明本地提交可以提供比远端监控更细粒度的变更信息。
