最小权限接口

完整讲解

最小权限接口的意思是：一个程序或工具去访问另一个系统时，只请求完成当前任务所必需的最小信息，不多拿一样东西。就像你去图书馆借书，只需要凭条在柜台取书，不需要拿到库房总钥匙。public-library 的监控脚本只执行 `git ls-remote`，这个命令只会返回远端仓库里 ref 的名称和对应的 SHA，既不会 clone 整个仓库，也不会 fetch 对象内容。这么做的好处是：暴露面小、速度快、对远端的影响也小。如果换成克隆整个仓库，虽然也能判断 commit 是否变化，但会白白下载大量数据，还会让监控脚本拥有超出需求的数据访问权。最小权限接口的核心不是“功能弱”，而是“刚刚好”；它让监控工具只拿到判断“分支有没有动”所需的指纹，而不去触碰更重、更有风险的内容。

原理逻辑

  1. 最小权限的核心是“只拿完成任务所需的最小信息”，不多拿一样东西。
  2. 在 Git 监控中，判断分支是否变化只需要 ref 名称和 SHA，因此 `git ls-remote` 比 clone/fetch 更合适。
  3. 控制信息暴露面能降低数据风险、传输成本和信任复杂度。

具体例子

假设我们只关心远端 `main` 分支是否从昨天开始移动过。执行 `git ls-remote <url> refs/heads/main` 得到新 SHA，与基线 SHA 比较即可判断 unchanged/changed。整个过程不下载任何提交对象或文件内容，只获得一行 ref 数据。

常见误区

  • 认为“能拿到更多信息的接口一定更好，因为功能更强”。
  • 认为最小权限是能力妥协，实际上它是风险控制。

概念关联

关联概念关系说明
远端只读监控public-library 只调用 git ls-remote 而不是 git clone，体现了只获取所需元数据的原则。
可观测性边界接口暴露的信息越少，能观察到的状态维度也越窄；ls-remote 看不到对象内容，所以监控边界止步于 ref 指针。
凭据透明性边界远端身份信任依赖本机 key/agent，状态文件不记录密钥，接口本身也不暴露凭据细节。

提交元数据与变更内容分离

完整讲解

一个 Git 提交其实包含两层信息：一层是“元数据”，包括提交标题、提交说明、作者、提交时间、涉及到的文件列表和增删行数；另一层是“变更内容”，也就是真正每一个文件里的 diff——哪些行被删掉、哪些行被加进来。元数据告诉我们“有人声称做了什么”，变更内容告诉我们“他实际改了什么”。两者不能划等号。今天 tiny-sea-war 的提交标题是 `fix: fix rotating angle`，统计显示 28 个文件变化、184 行新增、29 行删除。材料没有提供 diff，所以我们只能确认提交者的意图是修复旋转角，而不能确认他到底是用什么方式修好的：是改了角度符号、调整了角度取值范围，还是修改了旋转插值方向？这些都要看 diff 才能知道。把提交标题当成实现机制，等于把快递单上的“易碎品”当成包裹里摔碎的证据，是不严谨的。

原理逻辑

  1. 提交由元数据层和内容层组成，元数据是“人声称做了什么”，内容层是“机器实际改了什么”。
  2. 没有 diff 时，我们只能获得提交者的意图声明，无法验证具体实现方式。
  3. 将“意图”与“事实”分离，才能避免把未经证实的标题当作结论。

具体例子

一个提交的标题是 `fix: fix rotating angle`，统计显示 28 个文件变化、184 行新增、29 行删除，但没有 diff。我们能确认提交者声称在修旋转角，但不能确认具体改法——是改了角度符号、调整取值范围，还是修改旋转插值方向？这些只能在 diff 里看到。

常见误区

  • 把提交标题当作提交内容的可靠摘要。
  • 认为“标题是 fix rotating angle，那就等于旋转角已经被正确修复”。

概念关联

关联概念关系说明
证据粒度标题和文件统计是粗粒度元数据，diff 才是细粒度内容证据，证据粒度决定了能回答的问题层次。
状态指纹SHA 是提交对象的指纹，但标题和统计无法从指纹直接推导出来，需要读取提交对象和 diff 才能获得。
自动化测试作为行为契约没有 diff 时，测试是否随实现同步变更成为判断修复意图的重要旁证。

证据粒度

完整讲解

证据粒度是指一次观测所能提供的最小信息单位有多细。粒度越粗，你能回答的问题越少；粒度越细，你能回答的问题越多，但获取成本也越高。public-library 使用 `git ls-remote` 得到的证据粒度是“ref 指针级”：只能知道某个分支的指针现在指向哪个 SHA。这个粒度足以回答“分支有没有动”，但不足以回答“动了多少次提交、提交者是谁、改了什么文件、diff 是什么”。因为 ls-remote 只返回 ref 名称和 SHA，不返回对象数据库里的任何内容。如果把观察切换到 `git fetch`，把远端对象下载到本地，证据粒度就会变细，变成“提交级”甚至“文件级/行级”。但获取更细的粒度需要更多的数据、更大的权限和更复杂的处理。理解证据粒度的意义在于：不要指望用一个粗粒度工具去回答细粒度问题，也不要以为指针变了就等于掌握了详细的变更历史。

原理逻辑

  1. 证据粒度由观测通道的能力决定，ls-remote 只能返回 ref 指针级信息。
  2. 指针级证据足以回答“分支有没有动”，但不能回答“动了多少次、改了什么文件、diff 是什么”。
  3. 要获得更细粒度证据需要升级观测通道（如 git fetch），并付出更多数据、权限和处理成本。

具体例子

public-library 通过 `git ls-remote` 监控远端 `refs/heads/main`，发现 SHA 从 `1234567` 变成 `89abcde`。我们能确认 ref 移动了，但不能确认是 1 次还是 5 次提交、提交者是谁、改了什么文件。要了解这些，需要通过 `git fetch` 把对象下载到本地，再用 `git log`、`git show` 获取更细粒度证据。

常见误区

  • 以为“SHA 变了”就等于“我们获得了这次变化的所有细节”。
  • 认为证据粒度越细越好，忽视了获取成本和数据冗余。

概念关联

关联概念关系说明
可观测性边界ls-remote 的接口能力决定了证据只能达到 ref 指针级，无法进入文件级和 diff 级，因此可观测性边界也随之固定。
状态基线只有基线存在之后，指针级证据才能做出 unchanged/changed 判断；基线本身不携带任何内容细节。
待确认变化线索未提交变更在 Git 中只有“有差异”这一指针级事实，缺少时间与成因，因此只能标记为待确认线索。
