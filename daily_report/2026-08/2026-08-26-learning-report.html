quarantine 临时对象库的物理布局与并发隔离

完整讲解

想象一个大型仓库的收货区。每次收到一批货物，先不直接放进主仓库，而是放在一个标着“incoming-”的临时棚子里。多个送货员同时送货，各有各的棚子，互不干扰。只有验收通过后，货物才被移入主仓库；验收不合格，整个棚子直接清空。Git 的 receive-pack 就是这样的收货员：它为每次推送创建一个独立的临时对象目录，名字以 `incoming-*` 开头，通常位于主对象库之下。钩子运行期间，Git 通过环境变量让新对象只对这些临时目录可见，同时保留主对象库作为可读后备。这样多个并发推送各自持有独立的隔离目录，谁也不会看到谁的半成品对象。

原理逻辑

  1. receive-pack 收到推送时，先将对象写入独立的 `incoming-*` 临时目录，而不是主对象库。
  2. 每次 push 生成一个独立的临时目录，从物理上隔离并发推送。
  3. 通过环境变量让钩子等进程只能看到临时目录中的新对象，主对象库仅作为只读后备。

具体例子

两位开发者几乎同时执行 git push。服务端 receive-pack 创建了两个独立的临时目录，比如 incoming-1234 和 incoming-5678。开发者 A 的 pre-receive 钩子检查自己的新对象，开发者 B 的钩子完全看不到 A 的临时目录。即使 A 推送成功、对象被移入主对象库，B 的隔离区里也没有 A 的任何对象。

常见误区

  • 误区：以为 quarantine 目录在仓库外面。实际它在主对象库内部。
  • 误区：以为所有推送共用一个隔离区。实际每次 push 都有独立的 `incoming-*` 目录。

概念关联

关联概念关系说明
post-receive 钩子的对象可见性时间先后与可见性变化：quarantine 是对象进入主库前的隔离区，post-receive 是对象进入主库后的观察点。
packed-refs 延迟重写两者都用暂存/延迟换取性能，同时维持语义正确性。

精读文章 · 软件工程 / 计算机科学

post-receive 钩子的对象可见性与部分成功推送的事后审计

完整讲解

post-receive 是服务端推送流程中最后一个钩子，它在所有 ref 更新完成后运行。到这时，quarantine 对象已经迁移进主对象库，所以 post-receive 能够读取本次推送上传的全部对象，包括那些因 update 被拒绝而没有被任何 ref 引用的对象。但是，post-receive 的 stdin 只列出实际被更新的 ref，每行是“旧值 新值 ref名”。被拒绝的 ref 不会出现在这个列表中。于是形成了一种不对称：对象库全可见，结果列表只含成功项。因此，post-receive 适合做通知、记录和审计，而不能改变推送结果，因为 ok/ng 状态报告在它运行之前已经确定并回传给客户端了。

原理逻辑

  1. post-receive 在所有 ref 更新完成后运行，对象已从 quarantine 迁移进主对象库。
  2. stdin 只包含实际成功更新的 ref 行（旧值 新值 ref名）。
  3. 被拒绝的 ref 不会出现在 stdin，但其对象可能已存在于对象库中，形成不对称。

具体例子

一次推送同时更新 main 和 dev 两个分支，但 dev 被 update 钩子拒绝。post-receive 运行时，对象库中其实已经有 dev 新提交对应的对象了，只是没有任何 ref 指向它。post-receive 的 stdin 只显示 main 的旧值、新值和 ref 名。外部审计系统如果只读 post-receive 日志，会以为本次推送只更新了 main；只有进一步检查对象库，才能发现那个被拒绝的提交对象依然以悬空形式存在。

常见误区

  • 有人以为 post-receive 的退出码可以影响客户端的推送结果。实际上客户端在 post-receive 运行前已收到 ok/ng 状态报告，退出码不影响协议结果。
  • 有人以为 post-receive 的 stdin 会包含被拒绝的 ref。实际上不会。

概念关联

关联概念关系说明
quarantine 临时对象库可见性变化：隔离期看不到完整对象库，post-receive 阶段才能看到完整对象库。
fsck 与 gc对象状态延续：post-receive 后未被引用的对象成为悬空对象，后续 fsck 可将它们作为检查恢复对象，gc 可将它们作为清理候选。

精读文章 · 计算机科学 / 软件工程

fsck 与 gc 并发执行时的对象生命周期保护

完整讲解

fsck 负责检查对象库，gc 负责清理和压缩对象库，它们如果同时运行会怎样？Git 并没有在两者之间设置全局互斥锁，而是依靠几个底层机制来避免仓库损坏。第一，对象文件一旦写入就不可变，fsck 读到的对象内容不会变。第二，gc 默认有 `gc.pruneExpire` 保留窗口，通常保留两周内不可达对象，所以它不会刚创建完对象就立刻删除。第三，在 POSIX 系统上，即使对象文件被 unlink，已经打开的文件描述符仍然可以继续读取，所以 fsck 只要先打开了文件，就能读完。第四，gc 重写 packfile 时先写新包再删旧包，让持有旧包文件描述符的进程可以读完。即使在极端情况下对象真的消失，fsck 也会报告 missing object 而不是崩溃。所以准确地说，Git 不是消除竞态，而是把竞态风险压低到可恢复的范围。

原理逻辑

  1. 对象文件不可变，保证 fsck 读取内容一致。
  2. `gc.pruneExpire` 保留不可达对象一段时间，避免新对象被立即清除。
  3. 已打开的文件描述符在 unlink 后仍可读，packfile 写新删旧，保证持有者能读完。

具体例子

管理员在终端运行 git fsck，同时另一个进程自动触发 git gc。gc 决定删除一个不可达的松散对象文件。如果 fsck 已经打开该文件，即使 gc 删除了目录项，fsck 仍能通过已打开的文件描述符读取内容；如果 fsck 还没打开，它可能会报告 missing object，但不会崩溃。由于默认保留窗口是两周，这种情况实际很少发生。

常见误区

  • 很多人以为 Git 会用锁来让 fsck 和 gc 互斥，或者两者绝对不能同时运行。实际上它们可以并发。
  • 有人以为 fsck 遇到 missing object 会崩溃。实际上 fsck 会报告而不是崩溃。

概念关联

关联概念关系说明
post-receive 钩子对象状态延续：post-receive 后未被引用的对象成为悬空对象，gc 可能将其作为清理候选。
packed-refs 延迟重写仓库维护一致性主题：两者都在不设全局锁的前提下维持一致性，对象侧靠不可变性与保留窗口，ref 侧靠 lockfile 与松散覆盖。
