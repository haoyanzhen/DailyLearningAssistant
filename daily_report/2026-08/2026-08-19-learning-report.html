间接引用层与可变命名

Indirect Reference & Mutable Naming

分支名是书签，哈希是地址，书签永远不变，地址可以更换。

核心要点

  • 分支名不是直接等于提交哈希，而是指向一个可更新的指针。
  • 提交哈希由内容决定，直接用哈希当名称会导致每次提交都需要改名。
  • 间接引用层将名称与对象解耦，名称稳定，对象可替换。

引用变化与新增提交的非等价性

Ref Change ≠ New Commit

指针移动不等于新提交，就像相册封面换了可能是换了旧照片。

核心要点

  • SHA 变化是指针移动的信号，不代表对象库有新增对象。
  • ref 移动可能指向旧提交（回退）或新提交（新增）。
  • 必须检查 ref 最终指向的对象是否在对象库中首次出现，才能确认是否新增。

Transient Loss & Audit Compensation

间接引用层与可变命名

完整讲解

想象一个手机通讯录，联系人“妈妈”后面存着一串电话号码。号码可以换成新的，但“妈妈”这个名称始终不变。Git 的分支也是这样：分支名（比如 main）不是直接等于某个提交哈希，而是指向一个可以更新的“指针”，这个指针里保存着当前最新提交的 SHA。因为提交哈希是由内容算出来的，内容一变哈希就变，如果直接用哈希当分支名，那么每次新提交都要把分支名整体改名，那开发就没法稳定使用 main 这个名字了。Git 加了一层间接引用，让“名字”和“对象”分离：名字稳定存在，对象可以被替换。

原理逻辑

  1. 提交哈希由内容决定，内容变化必然导致哈希变化。
  2. 如果直接用哈希作为分支名，每次提交都会使名称失效。
  3. 通过引入一层间接指针，名称与对象解耦，名称可稳定引用可变目标。

具体例子

比如开一家小店，店名“老王小卖部”一直不变，但店铺地址因为搬迁换过三次。顾客只需知道店名，导航软件会去查当前地址。Git 的 ref 就是那本“地址簿”，分支名是“老王小卖部”，commit hash 是“当前地址”。

常见误区

  • 很多人以为分支名就是最新提交的哈希，直接画等号。
  • 实际上分支名是一个指针的名字，指针内容是一个哈希，可以移动到任意提交。

概念关联

关联概念关系说明
引用命名空间间接引用层是 refs/heads、refs/tags 等命名空间的基础，不同前缀用不同规则管理名称。
引用变化与新增提交的非等价性正因为有间接层，ref 可以被自由移动，才会出现引用变化但对象不是新增的情况。
域名解析/符号链接这种命名与对象解耦的设计与域名解析、符号链接相似，是常见的间接层思想。

引用变化与新增提交的非等价性

完整讲解

看到分支的 SHA 变了，第一反应可能是“有新提交了”。但不要急着下结论。SHA 是 ref 指针保存的一个名字，指针变了，只说明它指向的对象变了。这个对象可能是刚刚生成的全新提交，也可能是仓库里早就存在的旧提交。比如有人执行 `git reset --hard <旧提交>` 再强制推送，ref 就会从新提交退回旧提交，SHA 当然变了，但对象库里没有新增任何东西。反过来，即使 SHA 不变，也不能保证什么都没发生——可能是因为中间推了新提交又被回退。所以“ref 变化”只是一个信号，告诉我们“值得去看一眼”，但它本身不等于“新增提交”。

原理逻辑

  1. 间接引用层允许 ref 指向任意对象，所以 ref 变化既可以指向新对象，也可以指向旧对象。
  2. 新增提交意味着对象库产生了从未有过的新对象，而 ref 变化只是指针位置改变，两者是不同层面的事实。
  3. 要判断是否新增，需要检查 ref 指向的对象在对象库中是否存在且是否为第一次出现。

具体例子

开发者在本地基于 commit A 写 commit B，push 后远端 main 从 A 变到 B，这是新增。另一天，开发者把本地分支强制 git reset --hard A，再 push -f origin main，远端 main 从 B 变回 A，SHA 变了，但没有任何新提交对象产生。

常见误区

  • 常见的错误是把“变更检测”直接等同于“新增检测”。
  • SHA 变化是“指针移动”的检测，新增提交是“对象库出现新对象”的检测。

概念关联

关联概念关系说明
间接引用层间接引用层允许指针指向任意对象，这是 ref 变化与新增提交非等价性的根本原因。
提交对象重写amend/rebase 会创建新对象，但这不是普通新增而是历史替换，是非等价性的典型来源。
引用级观测的瞬态丢失引用级观测的瞬态丢失进一步说明，不能用 ref 变化作为新提交的唯一判据。

精读文章 · 软件工程 / 计算机科学

引用级观测的瞬态丢失与审计补偿

完整讲解

如果你用 `git ls-remote` 每隔一小时看一眼仓库的 ref，你得到的是一个个时间点上的“快照”。快照之间发生了什么，工具完全不知道。假设在 10:00 和 11:00 两次检查之间，有人推送了一个新提交，又在 10:30 强制推送回原来的旧提交，那么你两次看到的 SHA 完全一样，你会得出“这个仓库没有任何变化”的结论。但事实上中间发生了两次操作。这种“瞬态变化”被引用级采样彻底漏掉了。这就是可观测性问题：观测的粒度越粗，能还原的过程越少。要补偿这种丢失，不能只靠增加采样频率（因为永远有更快的操作），而需要额外的记录来源：比如远端服务器上配置 push hook 把每次推送写进日志，或者通过代理服务器记录 HTTPS 请求，或者依赖下游用户在某段时间内 `git fetch` 留下的引用记录。审计系统不应该自我安慰“SHA 没变就等于没发生”，而要说“在现有证据粒度下，我们无法确认这段时间没有发生临时变化”。

原理逻辑

  1. 状态采样是离散的，只能证明采样瞬间的状态，无法证明两次采样之间没有事件。
  2. 观测粒度越粗，能还原的过程越少，增加采样频率只是缩小盲区，不能根除。
  3. 要补偿丢失，需要独立于状态的记录流，如事件日志（push hook）等。

具体例子

你想判断一只猫有没有在一天里进过房间，于是你只在早上和晚上各拍一张照片。如果猫中午偷偷进来玩了一会儿又出去，两张照片里房间一模一样，你会以为猫根本没来过。除非你装了摄像头，才能记录这个瞬态。Git 的 ls-remote 就是那两张照片，push hook 就是摄像头。

常见误区

  • 许多人把“状态采样相同”理解成“未发生变更”。
  • 实际上，状态采样只能证明“采样瞬间的状态”，不能证明“两次采样之间没有事件”。

概念关联

关联概念关系说明
证据粒度证据粒度决定了瞬态是否可见：引用级粒度只看最终指针，无法看到中间过程。
事件时间与处理时间事件时间与处理时间的分离建模是补偿方案的基础，需要记录事件实际发生时间。
观察窗口边界观察窗口的边界语义也会影响补偿，边界附近的事件归属需要额外记录。
