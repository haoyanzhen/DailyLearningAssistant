SHA 引用作为状态指纹

完整讲解

在 Git 中，每一次提交的内容（包括文件快照、父提交、提交信息、作者等）都会被算出一个固定长度的 SHA-1 哈希值，通常表示为 40 位的十六进制字符串。这个哈希值是由内容本身决定的，只要内容有一个字节的差异，算出来的哈希就会完全不一样。因此，我们可以把 SHA 看作仓库某个状态的“指纹”：不需要打开仓库看每一个文件，只需要比较指纹是否一致，就能判断状态有没有变。在远端监控场景中，我们用 `git ls-remote` 拿到一个分支当前指向的 SHA，然后和之前记录下来的 SHA 进行比较：相同，就说明分支指针没有动；不同，就说明指针移动了。这就是 SHA 作为状态指纹的核心思想。

原理逻辑

  1. 提交内容（文件快照、父提交、提交信息、作者等）经哈希运算生成固定长度的 SHA-1 值
  2. SHA 值由内容完全决定，内容任意字节变化都会导致哈希不同
  3. 通过 `git ls-remote` 获取 ref 当前 SHA，与历史基线比较
  4. 相同则指针未移动，不同则指针移动，由此判断仓库状态是否变化

具体例子

public-library 的脚本执行 `git ls-remote` 得到 `refs/heads/main` 的 SHA，假设历史基线是 `8a6b...`，当前读取到的也是 `8a6b...`，那就判定“未变化”。某一天脚本发现当前 SHA 变成了 `c3d9...`，即使我们不知道中间经历了哪些提交、作者是谁、改了哪些文件，也能确定 main 分支的指针确实移动了。

常见误区

  • 误区：SHA 变了就代表仓库发生了很多修改。实际上，哪怕只改一个空格，SHA 也会变化。
  • 误区：SHA 没变就代表仓库一切正常。实际上，如果发生 force push 后又回到原 SHA，或其它 ref 变化，只监控此 ref 时仍会判定未变化。

概念关联

关联概念关系说明
远端只读监控（ls-remote）SHA 指纹是其核心依据，通过比较当前与历史 SHA 判断 ref 是否变化。
指针级证据与文件级证据的差异SHA 指纹属于指针级证据，无法提供文件级细节，这是两者分界。
状态基线与首次基线首次观察到的 SHA 会被记为基线，这自然引出状态基线与首次基线的概念。

状态基线与首次基线

完整讲解

任何变化检测都需要一个“参考零点”，这个零点就是基线。基线是我们在时间轴上选定的已知状态，之后每次观察都拿当前状态和基线比较：当前值等于基线，就是“未变化”；不等，就是“已变化”。当天材料里提到，第一次看到某个 ref 时，只记录基线，不视为新增提交。原因很简单：第一次接触时，我们没有任何历史信息，不能判断这个指针是刚移动过还是几个月前就在那里。所以只能把这一刻的状态记下来，作为以后比较的起点。基线思想看似简单，却是所有监控系统正确工作的前提：没有基线，变化就无从谈起。

原理逻辑

  1. 变化检测需要一个参考零点，即基线
  2. 首次观察到某个 ref 时，因为没有历史信息，只能记录为基线，不视为新增变化
  3. 后续每次观察都拿当前值与该基线比较，相等为未变化，不等为已变化
  4. 基线一旦建立，监控变成循环比较过程

具体例子

假设你从今天开始监控某个仓库的 main 分支，第一次运行 `git ls-remote` 得到的 SHA 是 `abc123`。你不能说“我发现了一个新提交 abc123”，因为你不知道它是什么时候创建的。你只能把 `abc123` 记入基线库。第二天再查，如果仍然是 `abc123`，则判断“未变化”；如果变成了 `def456`，才能说“相对基线发生了变化”，而且这个变化发生在第一次和第二次观察之间。

常见误区

  • 误区：把第一次看到的状态当作新增变化。实际上，第一次观察只作为基线。
  • 误区：基线一旦设定就永远不变。当仓库被强制重置或删除重建时，需要主动重置基线。

概念关联

关联概念关系说明
SHA 引用作为状态指纹状态基线是 SHA 指纹比较的参照点，没有基线，当前哈希就没有‘变化’的含义。
变更检测的正确性首次看到 ref 只记录基线，避免把历史存量误判为新增变化。
远端只读监控（ls-remote）基线一旦建立，监控就变成‘当前值 vs 基线’的循环比较。

证据链的时间归属

完整讲解

证据链的时间归属，是指把一次修改“钉”在时间轴上的能力。在 Git 中，提交记录自带作者时间和提交时间，可以说明“这个提交在某时某刻被创建”。但工作区中未提交的改动没有这样的时间锚点：我们只能看到“当前工作区相对 HEAD 有这些差异”，却无法让 Git 证明这些差异是何时产生的。因此，如果我们需要复盘某天到底做了哪些工作，缺少提交记录的改动就不能被确认为“那一天完成的事实”，只能称为“待确认变化线索”。要补全时间归属，必须借助 Git 之外的证据，比如 shell 历史、编辑器自动保存日志、文件系统时间戳、外部系统记录或人工确认。但这些外部证据的可信度通常低于 Git 提交元数据，所以证据链仍然存在缺口。

原理逻辑

  1. Git 提交记录自带作者时间和提交时间，可作为修改的时间锚点
  2. 工作区未提交改动没有 Git 时间戳，无法证明改动何时产生
  3. 缺少时间锚点的改动只能标记为待确认变化线索
  4. 要补全时间归属，需借助 Git 之外的外部证据，但可信度较低

具体例子

tiny-sea-war 仓库在 2026-08-10 的观察窗口内没有任何提交，但 `git status` 显示工作区有 28 个文件变更，包括设计文档、角色配置和脚本。比如一个角色绑定点配置被批量修改了，但 Git 只知道“当前文件与 HEAD 不同”，不知道这些改动是昨天做的、今天做的还是几天前开始的。因此，这份变更清单只能被记录为“待确认变化线索”。要确认这些改动发生的时间，需要查看开发者 shell 中的编辑命令、编辑器的恢复记录、或者直接询问开发者。

常见误区

  • 误区：认为工作区有改动就等于改动发生在最近。实际上，Git 无法证明未提交改动的时间。
  • 误区：认为没有提交记录就说明没有工作成果。实际上，未提交改动可能是进行中的工作，只是缺少时间凭证。

概念关联

关联概念关系说明
待确认变化线索未提交变更缺少提交动作，导致时间归属断链，这是证据链时间归属的核心场景。
指针级证据与文件级证据的差异指针级证据只能确认 ref 是否变化，而时间归属需要更丰富的提交元数据，两者对应证据链的不同粒度。
可观测性边界要补全证据链，需要引入外部证据，这是对可观测性边界的一种超越与补充。

概念之间的关联

今天的三个概念构成了一个完整的逻辑链：SHA 引用作为状态指纹，是变化检测的最小信号单元；状态基线与首次基线，为指纹比较提供了参考零点；证据链的时间归属，则决定了这些变化能否被钉在时间轴上，成为可信的历史事实。三者层层递进，帮助我们理解为什么 `ls-remote` 只能提供指针级证据，以及为什么未提交变更只能作为待确认线索。

今日最值得记住的一句话

证据是有层级的，每一层都定义了“我们到底知道了什么，以及还有哪些不知道”。
