pre-receive / update / post-receive 的推送决策顺序

Decision Order of pre-receive / update / post-receive

pre 整批拒绝，update 单个拦截，post 只能旁观记录。

核心要点

  • pre-receive 在整批推送到达后、任何 ref 改变前运行一次，非零退出则拒绝整批。
  • update 在每个将要更新的 ref 之前分别运行，非零退出只拒绝该 ref。
  • post-receive 在所有 ref 更新成功后运行，退出码不影响已完成的更新。
  • 三者的决策能力递减：整批拒绝、单个拒绝、事后记录。

全零 SHA 与 ref 生命周期边界事件的编码语义

完整讲解

全零 SHA 就是一排 40 个 0（如果仓库使用 SHA-256，则是 64 个 0）。你可能会想：它是不是一个特殊的 Git 对象？不是。Git 对象库里没有任何对象的哈希是全零，它只是一个“占位符”，专门用来表示“这里什么都没有”。Git 把每一次 ref 变化都写成一行三列的记录：旧值、新值、ref 名。一个 ref 从没有到有，叫做创建；从有到没有，叫做删除。创建时，旧值没有真实哈希可写，于是用全零 SHA 占位；删除时，新值没有真实哈希可写，也用全零 SHA 占位。所以看到“全零 → 非零”就是创建，看到“非零 → 全零”就是删除。全零 SHA 不能当普通提交哈希使用，它不会出现在对象图里，不能参与合并计算，只用来描述生命周期边界。

原理逻辑

  1. Git 将每次 ref 变化编码为一行三列：旧值、新值、ref 名。
  2. 创建 ref 时不存在旧值，用全零 SHA 占位；删除 ref 时不存在新值，也用全零 SHA 占位。
  3. 全零 SHA 只是“不存在”的标记，不指向任何对象，因此不能被当作普通提交哈希使用。
  4. 通过检查三元组的哪一端为全零，即可判断该 ref 是创建还是删除。

具体例子

在一份 post-receive 日志中看到：0000000000000000000000000000000000000000 3f2a1b... refs/heads/main。旧值全零，说明 main 分支在这一刻被创建。反过来：3f2a1b... 0000000000000000000000000000000000000000 refs/heads/main。新值全零，说明 main 分支在这一刻被删除。

常见误区

  • 有人以为全零 SHA 是 Git 的初始提交或空树，其实空树哈希是另一个固定值，全零 SHA 与它完全不同。
  • 还有人以为可以用 git show 查看全零 SHA，实际上对象库里没有这个对象，所以会报错。

概念关联

关联概念关系说明
pre-receive / update / post-receive 钩子全零 SHA 为创建和删除提供了统一的事件流格式，是解读 pre-receive、update、post-receive 钩子日志的基础。
tag 强制移动tag 如果采用删除再重建的方式强制移动，事件流中会出现“非零→全零”和“全零→非零”两条边界记录，因此全零 SHA 也能帮助识别 tag 的完整生命周期操作。

tag 强制移动的传播效应与标签对象差异

完整讲解

tag 的英文原意是“标签”，Git 设计它时希望它像一个出版物的版本号：v1.0 一旦贴上去，就不应该再移动。但 Git 也给了你强制手段：git tag -f 或先删除再重建。强制移动后，远端仓库的 refs/tags/v1.0 确实变成了新哈希，但已经克隆过这个 tag 的其他仓库不会自动更新。原因是普通 git fetch 有一条保守规则：如果本地已经有一个同名 tag，Git 不会用远端的新值覆盖它。为什么要这样？因为 tag 被当作“固定锚点”，假设你不会轻易改动它；如果每次 fetch 都悄悄改 tag，那 tag 的可靠性就没了。所以 tag 的强制移动需要下游显式地 git fetch --force，或者先删掉本地 tag 再拉取，才能同步。轻量标签和附注标签在强制移动时表现不同。轻量标签只是 refs/tags/v1.0 这个引用直接指向某个提交对象，强制移动就是把这个引用改指到另一个提交，旧提交可能变成悬空对象。附注标签则不同：它指向一个额外的 tag 对象，这个 tag 对象里写着标签名、打标签者、邮箱、时间、消息，并且 tag 对象再指向目标提交。由于 Git 对象内容不可变，你无法修改旧 tag 对象；强制移动附注标签时，Git 会创建一个全新的 tag 对象，新的 refs/tags/v1.0 指向这个新 tag 对象，旧 tag 对象仍然留在对象库里。因此，下游即使后来拿到新 tag，也仍然能通过旧哈希找到原来的标签信息。

原理逻辑

  1. tag 被设计为固定锚点，因此普通 fetch 对已存在的同名 tag 采用保守的不覆盖策略。
  2. 轻量标签只是 refs/tags/* 直接指向提交对象，强制移动即修改引用指针。
  3. 附注标签通过额外的 tag 对象指向提交，由于对象不可变，强制移动会创建新 tag 对象，旧 tag 对象被保留。

具体例子

你维护开源库，发布 v1.0 指向提交 A。后来发现 A 有严重 bug，于是执行 git tag -f v1.0 B，然后 git push origin v1.0 --force。远端的 tags/v1.0 从 A 变成 B。你的朋友小明早已 clone 过仓库，他的本地 tags/v1.0 仍指向 A。他执行 git fetch origin，Git 不会用 B 覆盖他的 v1.0，所以他依然在旧版本上。他只有执行 git fetch --force --tags，本地 tags/v1.0 才会指向 B；如果 v1.0 是附注标签，他的对象库里还会保留旧的 tag 对象，旧标签的说明、时间和打标签者信息都可以通过旧哈希查看到。

常见误区

  • 最大的误区是“tag 和分支一样会同步”：以为远端 tag 被强制移动后，自己本地 git fetch 就会自动跟着变。实际上 Git 默认不会让 fetch 覆盖已存在的本地 tag，所以 tag 的强制移动不会平滑传播到所有克隆仓库。
  • 另一个误区是把轻量标签和附注标签的区别只理解为“有没有备注”；在对象模型上，附注标签多出一个独立的 tag 对象，这个对象有自己的哈希和不可变性，导致强制移动时的对象层行为完全不同。

概念关联

关联概念关系说明

全零 SHA如果强制移动采用先删除再重建的方式，事件流中会出现全零 SHA 边界记录，说明 tag 生命周期经历了从有到无、再从无到有的完整切换。

pre-receive / update / post-receive 的推送决策顺序

完整讲解

当开发者把本地提交推送到远端的 Git 仓库时，远端的 receive-pack 进程会按固定顺序调用三个钩子。可以把它们理解成三个不同权限的检查站。第一个是 pre-receive。它只在整批推送刚刚到达、任何 ref 还没有改变时运行一次。它从标准输入读取所有将要被更新的行，每行格式是“旧值 新值 ref 名”。只要这个钩子以非零状态退出，整批推送都会被拒绝，一个 ref 都不会更新。它适合做全仓库级别的策略检查，例如禁止包含某个文件、检查提交信息规范。第二个是 update。它会在每一个将要被更新的 ref 之前分别运行一次。它拿到的信息是同一个三元组：ref 名、旧值、新值。如果某个 ref 对应的 update 钩子以非零状态退出，只有这一个 ref 会被拒绝，其他 ref 仍然可以更新。它适合做分支或标签级别的精细策略，例如保护 refs/heads/main、禁止删除特定 tag。第三个是 post-receive。它在所有 ref 更新成功之后运行一次，同样拿到一批“旧值 新值 ref 名”三元组，但这些更新已经生效，无法再反悔。post-receive 即使退出非零，也不能回滚已成功的更新。它适合做通知、审计、触发 CI 等事后动作。所以三者的决策能力是递减的：pre-receive 一票否决整批，update 单独拦截某个 ref，post-receive 只能看着结果并记录。

原理逻辑

  1. receive-pack 按固定顺序调用钩子：pre-receive → 多个 update → post-receive。
  2. pre-receive 读取整批三元组，基于全仓库状态做整体决策。
  3. update 按 ref 逐个执行，实现分支/标签级别的精细控制。
  4. post-receive 在更新生效后执行，用于通知和审计，不能反悔。

具体例子

一次推送同时更新 refs/heads/main（从 A 到 B）和 refs/tags/v2.0（从 C 到 D）。pre-receive 先运行，拿到两行三元组；如果它退出非零，两个 ref 都不会更新。如果 pre-receive 通过，Git 在更新 main 前调用一次 update，在更新 v2.0 前再调用一次 update。假设 v2.0 的 update 返回非零，那么 main 成功变为 B，v2.0 保持 C。最后 post-receive 运行，它只能看到已经真正生效的更新：main 从 A 变为 B。

常见误区

  • 最常见的误区是以为 post-receive 与 pre-receive 一样可以拒绝推送，只是时机稍晚。实际上 post-receive 在更新生效后运行，退出码不影响已完成的 ref 更新，不能阻止任何东西。
  • 另一个误区是以为 update 钩子会对整批 ref 做整体裁决；实际上 update 是逐 ref 运行的，一个 ref 被拒不影响其他 ref。
