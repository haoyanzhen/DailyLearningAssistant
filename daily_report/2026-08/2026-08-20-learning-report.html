精读文章 · 计算机科学 / 软件工程

ref 的物理存储形态与 packed-refs 的松散优先覆盖模型

完整讲解

可以把 ref 理解成贴在仓库里的一排书签。普通情况下，一个分支 ref 在磁盘上就是个很小的文本文件：文件路径是 `.git/refs/heads/main`，文件内容只有一行，写着当前指向的提交哈希。读 ref 就是读这个文件，简单直接。 但当仓库越来越大，分支和标签可能有几百上千个。每个 ref 都用一个几字节的小文件来存，文件系统会背上很多目录项和 inode 压力。Git 的解决方案是 `packed-refs`：它像一个总目录，把大量 ref 的名字和哈希集中写在一个大文件里，每一行像 `a1b2c3... refs/heads/feature`。 关键是读取规则：Git 先找松散文件，如果 `.git/refs/heads/main` 存在，就以它为准；只有不存在这个松散文件时，才去 `packed-refs` 里查。这个规则叫“松散优先”。新建或更新一个 ref 时，Git 只写一个松散文件，旧值可能还被 `packed-refs` 留着，但已经不会被读到。只有当执行 `git pack-refs --all` 这类整理时，Git 才会把现存的松散 ref 合并进打包文件，让读取路径重新变干净。

原理逻辑

  1. 普通 ref 是文本文件，内容为一行哈希。
  2. packed-refs 聚合大量 ref，读取时松散优先。
  3. 更新时写松散文件，旧行暂时留在 packed-refs 中，直到重新 pack。

具体例子

假设仓库里有 200 个标签，全部被 git pack-refs 收进 .git/packed-refs。现在要更新 refs/heads/main 从 111... 到 222...。Git 会直接创建 .git/refs/heads/main，里面写 222...。之后 git rev-parse refs/heads/main 返回 222...，不会去读 packed-refs 里的旧行。再过一段时间执行 git pack-refs --all，才会把 222... 合并进 packed-refs 并删掉这个松散文件。

常见误区

  • 很多人以为分支更新等于改写 packed-refs 里的那一行。实际上，更新一个已经打包的 ref 时，Git 通常不会立刻改 packed-refs，而是写一个新的松散文件来覆盖它。只要松散文件存在，packed-refs 里的旧行就会被忽略，直到重新 pack-refs 才会被更新或删除。

概念关联

关联概念关系说明
ls-remote松散优先的读取规则意味着，ls-remote 返回的 SHA 不会因为 ref 是松散文件还是 packed-refs 而改变，所以取证路径可以完全不关心底层存储差异。
对象图无论松散 ref 还是 packed-refs，本质上都是对象图的入口；入口集合决定了哪些提交对象仍然可达。
post-receive 钩子post-receive 钩子记录的是更新动作，存储层决定的是读取结果；两者配合才能重建“哪一次更新改变了哪个 ref”的完整时间线。

精读文章 · 计算机科学 / 软件工程

从 ref 状态信号到对象级证据的取证路径

完整讲解

`git ls-remote` 是一个非常轻量的远端观测工具，它只做一件事：列出远端 ref 的名字和当前 SHA。所以它给出的是“状态信号”——此刻某个分支的门牌号是什么。门牌号变了，只能说明“箭头移动了”，不能说明这次移动是向前长出一个新提交，还是向后退回旧提交，或是把整段历史重写了。 要把变化分类，需要进入对象级证据层。第一步先保存基线 SHA；第二次 `ls-remote` 发现不同后，用 `git fetch` 把新 SHA 及其相关对象抓到本地。对象到本地后，就可以用两个方向的集合差来判断。`git rev-list old..new` 列出从 new 可达、但从 old 不可达的提交；`git rev-list new..old` 则相反。再用 `git merge-base old new` 找共同祖先。 分类规则是：如果只有 `old..new` 有提交，且共同祖先就是 old，说明是快进新增；如果只有 `new..old` 有提交，说明是回退；如果两个方向都有提交，且共同祖先不是两端，说明历史被重写；如果 merge-base 找不到共同祖先，则两边是互不相干的历史。整个过程是典型的渐进式取证：低成本的签名信号负责触发，高成本的对象下载和提交图分析负责给出证据。

原理逻辑

  1. 保存基线 SHA 后，第二次 ls-remote 发现不同触发取证。
  2. git fetch 将新对象下载到本地，使提交图可见。
  3. 通过 rev-list 集合差与 merge-base 共同祖先按规则分类。

具体例子

设基线 SHA 是 `abc111`，第二次看到远端 main 变成 `def222`。执行 `git fetch origin main` 后：`git rev-list --count abc111..def222` 返回 3，`git rev-list --count def222..abc111` 返回 0，`git merge-base abc111 def222` 返回 `abc111`。这说明 `abc111` 是 `def222` 的祖先，远端只是沿原历史向前新增了 3 个提交，是快进新增。如果第一个方向返回 0、第二个方向返回 2、共同祖先仍是新 SHA，那就是回退。

常见误区

  • 只看到两次 ls-remote 的 SHA 不同，就断定本次 push 带来了新提交，这是把“指针变化”和“新增提交”混为一谈。必须比较提交图上的可达集合，才能知道新提交是否真的出现。
  • 另一个常见误区是认为 git fetch 会改动本地工作区；实际上 fetch 只把远端对象下载到对象库并更新远端跟踪 ref，不会碰工作区。

概念关联

关联概念关系说明
状态信号与事件日志状态信号是离散快照，事件日志是连续流；事件日志能捕捉两次快照之间的瞬态，状态信号能校验事件日志是否完整。
对象生命周期如果取证判定为回退或重写，原来被 ref 指向的提交会失去引用，变成悬空对象，进一步影响对象生命周期。
存储层取证路径不依赖 ref 是松散文件还是 packed-refs，因为 ls-remote 得到的是同一语义的 SHA；存储层支撑观测。

精读文章 · 软件工程 / 计算机科学

服务端 push 钩子的事件日志与外部补偿通道

完整讲解

Git 仓库的服务端可以在 push 成功之后运行 `post-receive` 钩子。这个钩子从标准输入逐行收到 `<旧SHA> <新SHA> <ref名>`。每行代表一个 ref 的更新事件。如果旧 SHA 全是 0，表示这个 ref 刚被创建；如果新 SHA 全是 0，表示这个 ref 被删除。把每一行加上时间和操作者，追加到日志文件，就得到了一条审计事件流。 关键点在于钩子的时机。`pre-receive` 和 `update` 在更新发生之前运行，因此可以拒绝推送，适合做准入控制；`post-receive` 在更新已经完成之后运行，不能再阻止任何事，但它能看到旧值和新值，所以特别适合做审计记录。 如果托管平台不允许安装自定义钩子，就需要外部补偿。常见做法包括：用平台提供的 push webhook 接收 before、after、ref、pusher 等事件；维护一个镜像仓库并定时 fetch，用镜像的 reflog 留下观测到的变化；调用平台审计 API 获取操作者和时间；同时保留定时 `ls-remote` 状态指纹作为独立校验。事件流回答“期间发生过什么”，状态指纹回答“最终状态和事件流是否一致”。

原理逻辑

  1. post-receive 钩子从标准输入接收每行更新记录。
  2. 记录时间与操作者，追加为审计日志。
  3. 外部补偿通道包括 webhook、镜像仓库、审计 API 和状态指纹。

具体例子

在 `hooks/post-receive` 中读取标准输入，把时间戳、旧 SHA、新 SHA、ref 名追加到日志文件。一次强行回推会留下 `2026-08-20T10:15:00+08:00 111... 222... refs/heads/main` 这样的记录。即使稍后又被推回 `111...`，这条日志仍然记录着中间发生过一次更新，这正是 ls-remote 状态指纹无法恢复的瞬态。

常见误区

  • 很多人以为 post-receive 能阻止坏人推送，其实它发生在更新之后，拦不住；要拦截必须用 pre-receive 或 update。
  • 另一个误区是认为两次 ls-remote 结果相同就说明没有 push 发生；实际上先推后回推会让状态指纹回到原样，只有事件日志能暴露这次瞬态。

概念关联

关联概念关系说明
状态信号事件流与状态信号互补：post-receive 或 webhook 提供连续事件，ls-remote 提供独立状态指纹，两者可以互相校验。
对象生命周期事件日志记录的旧 SHA 在强制回退后格外有用；只要旧对象尚未被 gc 清理，审计方就能用旧 SHA 重新指向悬空对象并恢复证据。
ref 存储层钩子记录的是更新动作，ref 存储层决定读取结果；二者配合才能重建完整的 ref 更新时间线。
