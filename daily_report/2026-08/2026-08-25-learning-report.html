pkt-line 分帧与 receive-pack 状态报告的传输层结构

完整讲解

想象两个人传便条，每张便条上都用固定格式先写明“这张便条有多长”，接收者先读前4个字符，按长度精确取出内容，就不会因为便条里有没有换行而搞混。Git的pkt-line就是这么做的：每条消息由“4位十六进制长度前缀 + 实际内容”组成，而`0000`表示“没有更多消息了”。在推送时，receive-pack用这种格式返回每个ref的更新结果：`ok refs/heads/main`表示接受，`ng refs/heads/dev <原因>`表示拒绝。这些状态行不是普通文本流，而是按pkt-line帧切好的协议数据。另一方面，传输对象时的进度信息（比如“Counting objects”）会放在side-band通道里：带side-band的包会在数据区第一个字节写上通道号，band 1是进度，band 2是错误信息。这样客户端可以根据通道号和行前缀把“正在传输对象”的进度和“分支是否被接受”的状态报告准确区分开。

原理逻辑

  1. 长度前缀分帧：每条消息自带长度，接收方按长度精确读取，无需依赖换行符做边界。
  2. 多路复用：side-band 通过通道号（band 1/2）将进度、错误与主状态流分离，避免相互干扰。
  3. 逐 ref 报告：receive-pack 对每个 ref 发送独立 pkt-line 帧，客户端逐条解析，从而支持部分成功。

具体例子

运行 `git push origin main dev` 时，客户端先收到进度（如“Enumerating objects”）走 side-band band 1；推送结束后，receive-pack 在主 pkt-line 流发送“ok refs/heads/main”或“ng refs/heads/dev hook declined”等帧，客户端解析长度前缀后展示成功或 `! [remote rejected]`。

常见误区

  • 把 ok/ng 状态报告当普通文本按换行读取，忽略长度前缀，遇到内容中的特殊字符会出错。
  • 以为进度信息和状态报告混在同一流中，其实它们走了不同通道，由 side-band 的通道号区分。

概念关联

关联概念关系说明
quarantine 对象隔离区同属于一次 receive-pack 会话：pkt-line 先交换命令与状态，随后 receive-pack 在 quarantine 中安置对象。
reflog 逻辑事务边界pkt-line 状态报告按 ref 逐条暴露信息，reflog 条目也按 ref 记录，两者都没有全局事务 ID，只能逐条重建整体操作。

quarantine 对象隔离区在部分成功推送中的迁移与丢弃规则

完整讲解

receive-pack 接收推送对象时，不会马上把它们写进主对象库，而是先放进一个临时隔离目录，叫 quarantine。钩子脚本（pre-receive 和 update）运行时，看到的是这个临时对象库，而不是主对象库，因此未经检查的对象不会污染正式仓库。如果 pre-receive 整批拒绝，说明整个推送不被接受，receive-pack 会直接把隔离目录整体丢弃，一个对象都不进主对象库。如果 pre-receive 通过，但某个 ref 被 update 钩子拒绝，事情变成部分成功：receive-pack 仍会把整个对象包迁移进主对象库，因为协议已经进入接受流程；那个被拒绝的 ref 虽然不会被更新，但它所依赖的新对象已经进了库，只是没有任何 ref 引用它们，成为悬空对象。这些悬空对象不会马上被删，而是等待 fsck 检查或 gc 按保留窗口清理。

原理逻辑

  1. 隔离优先：推送对象先进入临时目录，使钩子检查在安全环境中进行，未通过检查的对象不进入主对象库。
  2. 整批与逐个决策分离：pre-receive 控制整批是否可接受，update 控制单个 ref，导致部分成功时对象包已经迁移。
  3. 无引用对象成为悬空对象，进入对象库维护流程，由 fsck/gc 后续处理。

具体例子

本地执行 `git push origin main dev`，receive-pack 把两笔新提交先写入 quarantine。pre-receive 运行后返回 0（通过）。接着 update 钩子对 main 返回 0，对 dev 返回非 0（拒绝）。最终 main 被更新，dev 被拒绝，但整个 quarantine 对象包已经进入主对象库。运行 `git fsck` 会看到 dev 对应的提交显示为 `dangling commit <sha>`。如果 pre-receive 一开始就返回非 0，则两个分支都不会更新，对象包也被丢弃，主对象库中不会出现任何新对象。

常见误区

  • 以为 pre-receive 拒绝后，推送对象还会留在对象库里等待 gc 清理；实际上 quarantine 目录被整体丢弃，对象从未进入主对象库。
  • 以为某个 ref 被 update 拒绝后，它所指向的对象不会入库；实际上对象包已经整体迁移进主对象库，只是没有 ref 引用它们，所以表现为悬空对象。

概念关联

关联概念关系说明
pkt-line 状态报告同处于一次推送会话：客户端通过 pkt-line 一条条看到 ref 的 ok/ng，服务端同时根据钩子决定 quarantine 中对象的迁移或丢弃。
git fsck 与 git gcupdate 拒绝产生的悬空对象，正是之后 fsck 可以检查、gc 可以按窗口清理的对象。

git fsck 与 git gc 的双重角色

完整讲解

git fsck 和 git gc 都从一组“根”出发——refs、reflog、index——对对象图做可达性扫描。两者跑的是同一套遍历逻辑，但目的完全相反。fsck 像体检医生：它把不可达对象当作需要报告的异常，会列出悬空提交、悬空树、悬空 blob，还能用 `--lost-found` 把悬空对象从对象库里捡出来，放到 `.git/lost-found/` 目录，让用户可以重新用分支或 tag 锚定它们。gc 像保洁员：它把不可达对象当作可以清理的垃圾，在打包、压缩对象的同时，把超过保留窗口的悬空对象删掉。gc 默认不会立即删除，而是通过 `gc.pruneExpire` 保留大概两周，给用户留下反悔时间。此外，未过期的 reflog 条目也会被视为根，所以即使分支被删，只要 reflog 还指向那个提交，gc 就不会把它当垃圾清掉。这说明“可达性”是相对于当前根集合而言的，根集合不同，结论就不同。

原理逻辑

  1. 共享可达性扫描基座：从当前根集合出发遍历对象图，可到达的对象被视为活跃，不可到达的为垃圾。
  2. 态度相反：fsck 将不可达对象视为异常，用于报告与恢复；gc 将不可达对象视为垃圾，用于压缩与删除。
  3. 保留窗口与保护：gc 默认保留两周，未过期的 reflog 条目也作为根，避免误删，给用户恢复时间。

具体例子

你删除了一个叫做 `tmp` 的分支。`git fsck` 显示 `dangling commit <sha>`，说明这个提交目前没有被任何 ref 引用。如果你运行 `git fsck --lost-found`，它会把这个 commit 写入 `.git/lost-found/other/`，然后你可以用 `git branch recovered <sha>` 重新锚定它。但如果你先运行 `git gc --prune=now`（强制清空所有保留窗口），这个提交可能就永久消失了。在默认配置下，gc 会保留它两周，留给你发现和恢复的时间。

常见误区

  • 把 fsck 和 gc 看作两个完全不同的算法，以为 fsck 专门查坏文件、gc 专门删文件；其实它们共用可达性扫描基座，区别在对不可达对象的态度。
  • 以为 gc 会立刻删光所有悬空对象；实际上默认有约两周保留窗口，且未过期的 reflog 对象仍被当作可达保护。

概念关联

关联概念关系说明
quarantine 对象隔离区quarantine 中被拒绝 ref 产生的悬空对象，正是 fsck 列出、gc 清理的对象来源。
reflog 生命周期未过期的 reflog 条目会被 gc 当作可达性根，因此一条多 ref 操作的 reflog 记录会保护该操作涉及的对象不被清理。
