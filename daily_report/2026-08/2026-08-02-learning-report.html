Observability Gap of Binary Assets (Missing LFS)

在未安装 git-lfs 的环境中，二进制资产变成了只读的指针文件，变更完全不可见，这让管线契约的验证能力大幅退化。

工作区快照作为待确认变更证据

完整讲解

在 Git 中，我们通常把修改划分成三个区域：工作区、暂存区和提交历史。工作区就是你正在编辑文件的地方，任何改动在 `git add` 和 `git commit` 之前，都只停留在工作区。一个“工作区快照”就是某个时刻对所有这些未提交改动的一份记录，比如通过 `git status` 和文件列表抓取到的信息。关键的地方在于：工作区快照不具备原子性。它可能包含写了一半的功能、临时调试日志、误复制进去的文件，甚至根本不知道这些修改是多久前留下的，是谁留下的。它没有提交时间戳，没有作者签名，没有说明“我为什么这样改”。因此在工程证据体系中，工作区快照的置信度最低，它只能告诉我们“正在发生什么方向”，而不能证明“已经做完了什么”。今天 tiny-sea-war 仓库的所有线索都来自这样一个快照：我们看到大量文件变动，能猜出在搞 16:9 比例适配，但我们不能声称这些变更已经被正式采纳或验证通过。理解这个层级，对后续任何自动化分析系统都至关重要——不能把快照当结论，只能把它当成追问的起点。

原理逻辑

  1. Git 的三区模型：工作区（未追踪/已修改）、暂存区（已暂存）、提交历史（已确认），工作区快照只包含未提交的瞬时状态
  2. 工作区快照缺乏原子提交所需的元数据（时间戳、作者、说明），无法保证修改的完整性和意图
  3. 快照中的文件可能包含临时文件、调试日志或废弃的试探性改动，必须经过过滤和确认才能作为有效线索

具体例子

你走进一间开着门的办公室，发现桌上摊着几十张设计图、半瓶咖啡和一张写着“改成16:9”的便利贴。显然有人在忙海岸地图的事情，可你不知道这些图纸是最终版还是废稿，不知道它们是不是今天摆在这里的，也不知道那个离开的人是否打算回头继续改。工作区快照就是这张凌乱桌面的照片。

常见误区

  • 误以为在 `git status` 里看到的大量修改就是最近的、代表项目最新进展的确定变更
  • 直接拿未筛选的工作区快照当作确认结论，忽略可能存在的临时文件或废弃改动

二进制资产的可观测性缺口（LFS 缺失）

完整讲解

在游戏开发等项目中，经常要存储贴图、模型、声音等二进制文件。这些文件动辄几十甚至几百 MB，如果直接放进 Git 仓库，仓库体积会急剧膨胀，每次 clone 都会超级慢。Git LFS（Large File Storage）就是用来解决这个问题的：它把大文件的实际内容存储在一个外部服务器上，而在 Git 仓库里只保存一个轻量的“指针文件”——就像一个写着“去 LFS 服务器取 ID 为 abc123 的原文件”的便条。当天 tiny-sea-war 仓库的环境报出了 `git-lfs: command not found`，说明该环境里没有安装 Git LFS 客户端。这时 Git 只会把那个如假包换的指针文件当作普通文本文件来追踪，你看到的只是几字节的哈希值，完全无法知道实际大图是否被修改、被替换。这就在版本控制层面造成了一个巨大的“可观测性缺口”——二进制资产的变化对你来说，在 `git diff` 里是凭空消失的。这个缺口带来的直接代价，就是无法自动验证资产清单里声明的贴图是否已经更新为 16:9 版本，也无法判断一张图是被错误替换，还是保持着旧版。我们唯一能依赖的只剩下文件存在性、文件大小或外部 MD5，这些手段远比 diff 要粗糙和脆弱。

原理逻辑

  1. Git LFS 通过指针文件将大文件的真实内容托管于外部存储，仓库内仅保留一个轻量的引用
  2. 当环境缺少 LFS 客户端时，Git 无法解析指针，只能展示指针文件的文本内容，无法获取真实二进制数据
  3. 由于二进制变更不可见，依赖版本 diff 的资产校验体系失效，必需设计外部校验机制（如独立哈希比对）来弥补

具体例子

想象一个图书馆里，放大型画册的书架为了节省空间，不会把整本厚重画册摆在架子上，而是在架子上插一张索引卡，写着“大画册第5号存放在隔壁仓库”。一位没有仓库钥匙的管理员来查架，只能看到这张索引卡，却看不到画册里的内容。如果今天有人换了一本新画册，管理员看到的仍然是那张索引卡，根本察觉不到变化。Git LFS 就是这个仓库，没有安装 LFS 客户端就像管理员无权进仓库，二进制资产的变更因此完全隐形。

常见误区

  • 以为只要文件大小或修改时间变了，就说明资产被改动了，但 LFS 缺失时指针文件大小固定，无法反映实际变更
  • 误认为 `git status` 中标记为 modified 的二进制文件一定发生了内容变化，其实可能只是指针哈希变动

声明式资产清单的多比例契约传播

完整讲解

所谓“声明式资产清单”，是指一种用数据（通常是 JSON 或 YAML 文件）来描述“我需要的所有资产有哪些、它们从哪里来、生成什么格式”的方式。它不像脚本那样用命令步骤来“怎么做”，而是直接声明“我想要什么”。这个清单就像一份正式的契约，签发给下游的一系列构建工具。当项目需要支持一个新的屏幕比例——例如 16:9——这个契约就需要被扩展：清单中必须明确写出“在 16:9 比例下，需要哪些新贴图、每一张贴图的源文件路径、输出尺寸等”。一旦清单完成更新，工具链中的每一个环节（地图拼接、导航烘焙、mini-map 生成等）都会读取这些新条目，按契约执行。这就像一张多米诺骨牌，推动第一块（清单），后面的所有步骤自动联动，避免了开发者到处找脚本、四处改参数。“传播”的意思是：比例变化不仅仅停留在清单里，而是通过清单→工具→产物的方向，有控制地扩散到整个管线的每个阶段。如果清单没写，工具就会认为不需要处理，于是静默跳过；如果清单写了但工具不能理解的新字段，可能产生错误产物甚至崩溃。因此，维护清单与工具之间的契约一致性，就是保障比例适配不翻车的关键。

原理逻辑

  1. 声明式清单把资产需求抽象为可解析的数据结构，分离了“要什么”与“怎么做”
  2. 工具链通过读取清单中的字段（比例、贴图路径、尺寸）来驱动构建，清单更新自动引发全链路重算
  3. 契约传播依赖于清单 schema 的稳定与工具对该 schema 的正确实现，任一方的断裂都会导致构建失败或产物缺失

具体例子

一家大型连锁餐厅，总部制定了一套菜单（资产清单），上面标注“本季饮品”会生成甜橙冰沙和苹果汽水。各地分店的厨房（构建工具）只要看到菜单上有某一项，就自动准备对应的原料和流程。现在总部决定推出 16:9 特别套餐，菜单上新增一行“16:9特供：大杯海盐焦糖冰”。厨房一看菜单更新，马上开始配料、调制，整个过程整齐划一。如果总部的菜单上没写这行，厨房根本不知道有新饮品；如果菜单写了但厨房看不懂“大杯”是什么意思，就会做出一杯奇怪的饮料。声明式资产清单就充当了这份总菜单，它让变化一次性宣告，然后传播到所有制作环节。

常见误区

  • 认为新增屏幕比例直接改美术文件或脚本参数就足够了，忽视清单作为契约中心的地位，导致后续维护困难
  • 以为只要清单中加了条目就万事大吉，忽略了对新字段的工具侧解析支持，最终造成静默失败
