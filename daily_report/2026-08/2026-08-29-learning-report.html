pkt-line 分帧与 side-band 通道编号的多路复用

pkt-line framing and side-band channel multiplexing

pkt-line 用长度前缀和通道编号，让状态、进度、错误信息在同一条数据流里互不干扰地传输。

核心要点

  • pkt-line 以 4 位十六进制长度前缀标记每个数据包的完整长度，接收方据此精确切分消息。
  • side-band 在 pkt-line 帧内增加通道编号，band 1 状态、band 2 进度、band 3 错误。
  • 客户端先按长度读到完整帧，再按通道编号决定交给逻辑层还是直接显示。
  • 状态、进度、错误信息可在同一条 TCP 连接中混传而不互相干扰。

Push Aggregation Judgment Rules

客户端判断推送结果必须遍历每个 ref 的 ok/ng 行，unpack ok 只是“试卷收到”，不是“考试通过”。

核心要点

  • 服务端对每个 ref 独立决定接受或拒绝，一次推送可能部分成功。
  • unpack ok 只表示对象包到达并解包，不代表所有引用更新成功。
  • 客户端必须遍历所有 ok/ng 行，按全成功、部分成功、全失败分类。
  • 聚合结果决定用户提示：全成功显示推送完成，部分成功列出成功与失败 ref，并给出建议。

fsck 与 gc 并发时的 packfile 描述符保护

Packfile descriptor protection during fsck/gc concurrency

gc 重写 packfile 时采用写新删旧 + 原子重命名，正在读取旧包的 fsck 进程靠“打开后删除仍可读”的语义安全完成扫描。

核心要点

  • gc 重写 packfile 时采用“写新包、原子重命名替换旧包”的策略。
  • 已打开旧包文件描述符的进程（如 fsck）在旧目录项被删除后仍可继续读取。
  • 该机制依赖操作系统“打开后删除仍可读”的语义，保证 fsck 扫描不被中断。
  • 原子重命名确保新包替换旧包不会产生半新半旧状态。

pkt-line 分帧与 side-band 通道编号的多路复用

完整讲解

想象你要寄一箱快递，箱子里有很多层隔板，每层放不同类别的物品。快递公司需要在箱子的外包装上写清楚每一层的编号和内容，收件人才能按编号取出自己想要的东西。Git 的传输层就是类似的设计。pkt-line 是 Git 协议里最基础的数据包格式：每个数据包开头用 4 位十六进制数字写明这个包的总长度，接收方先读这 4 位，就知道接下来该读多少个字节，从而精确地切分出一条条消息。这就像快递箱外贴着“内含物品清单”，每件物品都标了大小。 但光有长度还不够，因为同一条连接里可能同时传状态报告、进度条信息、错误信息。于是 side-band 在 pkt-line 的基础上又加了一个“通道编号”：band 1 放状态报告，band 2 放进度信息，band 3 放错误信息。客户端先按 pkt-line 的规则读到一个完整的帧，再看帧里的通道编号，就知道这一帧该显示给用户看，还是该交给逻辑层处理。这样，服务端可以把不同性质的信息混在同一条 TCP 连接里发送，而客户端不会把它们弄混。

原理逻辑

  1. 每个 pkt-line 帧以 4 位十六进制数字开头，表示该帧总长度，接收方先读长度再读内容，从而可靠切分数据流。
  2. side-band 在帧内加一个字节的通道编号，将不同性质的信息（状态、进度、错误）路由到不同处理逻辑。
  3. 客户端按“长度前缀 → 通道编号 → 内容”的顺序解析，保证多路复用信息的正确分离。

具体例子

假设服务端要发送一行 `ok refs/heads/main`。它会先计算整帧长度，比如长度是 23，然后写成 `0017` 作为前 4 位十六进制前缀，再接上一个 band 号 `\x01`，最后跟上真正的内容。客户端收到后，先读 `0017`，知道接下来要读 23 个字节，然后读到 `\x01`，就明白这是 band 1 的状态报告，于是把这行内容交给状态解析逻辑。

常见误区

  • 认为进度信息和状态报告通过两条独立连接传输。
  • 认为这些信息只是随意混合的文本，没有严格的帧边界和通道标识。

fsck 与 gc 并发时的 packfile 描述符保护pkt-line 在传输层保证消息完整切分，fsck 与 gc 并发保护在存储层保证对象完整读取，二者都是不同层级的可靠性保障。

客户端对部分成功推送的聚合判定规则

完整讲解

当你一次推送多个分支时，服务端并不是把整批推送当成一个整体来接受或拒绝，而是对每个 ref 单独做决定。这意味着一次推送完全可能一部分成功、一部分失败。客户端拿到服务端返回的状态报告后，不能只看最前面那句 unpack ok，因为 unpack ok 只表示“你寄来的包裹已经拆开检查了”，并不代表每个分支都更新成功。 客户端的正确做法是：把服务端返回的所有 `ok <ref>` 和 `ng <ref>` 行收集起来，逐条统计。如果所有 ref 都是 ok，那就是全成功；如果既有 ok 又有 ng，那就是部分成功；如果所有 ref 都是 ng，那就是全失败。得到这个聚合结果后，客户端再决定如何向用户展示：全成功就显示“推送完成”，部分成功就要同时列出成功和失败的 ref，并解释失败原因，比如 non-fast-forward、被钩子拒绝等，然后给出“先 pull 再 push”之类的建议。这个规则看似简单，却是把协议级状态转换成用户体验的关键一步。

原理逻辑

  1. 服务端在 receive-pack 中对每个 ref 独立执行更新规则，返回独立的 ok/ng。
  2. 客户端收集所有状态行，按 ref 聚合，判定整体结果属于全成功、部分成功、全失败。
  3. 客户端根据聚合结果映射为最终用户体验：状态提示、失败原因和建议动作。

具体例子

你执行 `git push origin main dev`，服务端返回：`ok refs/heads/main` 和 `ng refs/heads/dev non-fast-forward`。客户端聚合后判定这是“部分成功”，于是显示：main 已成功更新，dev 被拒绝，原因是 non-fast-forward，然后提示“本地 dev 与远端不同步，请先 pull 再推送”。你不会看到“推送成功”这样笼统的结论。

常见误区

  • 把 `unpack ok` 当作推送成功的标志（实际上它只代表对象包解包成功，与 ref 更新结果无关）。
  • 认为一次推送要么全成功要么全失败，忽略部分成功场景。

概念关联

关联概念关系说明
pkt-line 分帧与 side-band 通道编号的多路复用客户端要正确聚合 ok/ng，必须先依赖 pkt-line 分帧和 side-band 通道编号，准确切分出每一行状态报告。
fsck 与 gc 并发时的 packfile 描述符保护部分成功推送中被拒 ref 的对象会进入对象库成为不可达对象，这些对象的清理时机由 gc.pruneExpire 等保留窗口控制。

fsck 与 gc 并发时的 packfile 描述符保护

完整讲解

git gc 在压缩或重写 packfile 时，不会直接修改旧文件，而是先写一个新的 pack 文件和对应的索引文件，然后通过原子重命名操作把新文件替换旧文件。这个“写新删旧”的策略非常关键。假设此时有一个 git fsck 进程正在扫描对象，它可能已经打开了旧 packfile 的文件描述符。即使 gc 随后把旧 packfile 的目录项删除了，操作系统仍然会让这个已打开的文件保持可读，因为文件的内容还存在于磁盘的 inode 上，只要还有进程持有它的文件描述符，数据就不会消失。 这就像图书馆管理员把一本旧书从书架上撤掉，但在那之前已经有一位读者把书借走了。管理员在目录里划掉这本书的条目，但读者手里的书仍然可以继续读完。Git 正是依赖这种“打开后删除仍可读”的操作系统语义，让 fsck 在 gc 并发执行时不会因为对象包被替换而中断。这个机制保障了仓库完整性检查的可靠性，也是理解 Git 并发安全的一个重要基础。

原理逻辑

  1. gc 不直接修改旧 packfile，而是先写新 packfile + 索引，再通过原子 rename 替换旧文件。
  2. 一旦进程持有旧 packfile 的文件描述符，即使文件名被 unlink，inode 仍存在，数据可继续读取。
  3. 原子重命名保证任何时刻文件系统看到的要么是旧包要么是新包，不会出现中间状态，从而保证并发读取安全。

具体例子

fsck 正在扫描对象库，此时 gc 开始跑。gc 先写了一个新包 `pack-aaaa.pack` 和对应的索引，然后通过 rename() 把新包替换旧包 `pack-bbbb.pack`。fsck 已经在几毫秒前打开了 `pack-bbbb.pack`，句柄还保留着。即使 gc 把 `pack-bbbb.pack` 这个文件名从目录中移除，fsck 仍然能继续从已经打开的文件描述符中读取旧包里的对象，不会因为文件“消失”而崩溃。

常见误区

  • 认为 gc 在替换 packfile 时会“删除”正在被读取的旧文件，导致 fsck 崩溃（实际上只是删除目录项，已打开的文件描述符仍可读）。
  • 认为如果 fsck 在 gc 重命名之后才打开文件，就会读到半新半旧的状态（实际上原子重命名保证只会看到完整的新包或旧包）。
