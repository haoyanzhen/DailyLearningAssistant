Git 引用（ref）指针

完整讲解

把 Git 仓库想象成一本持续更新的书。书本身是很多提交对象，每个提交像一页快照，记录当时的文件状态。但读者不可能每次都说“请给我最新那页”，因为页与页之间互相链接，需要知道链的末端在哪。Git 引用（ref）就是解决这个问题的“书签”：它是一个可移动的命名指针，里面保存的是一个提交的哈希值。比如 `refs/heads/main` 这个 ref 指向 main 分支的最新提交哈希。ref 与提交历史的关系有点像“当前进度存档”和“完整游戏流程”的关系。流程是完整的历史，存档只是告诉你现在打到哪一关。你可以删除存档，历史还在；也可以移动存档，指向另一个进度。分支名并不真正“包含”提交，它只是指向提交的标签。今天 public-library 监控的正是 `refs/heads/main` 这个 ref。它不关心工作区文件长什么样，也不关心中间有多少提交，只关心这个指针现在指向哪一个 SHA。理解了 ref，才能理解后面 ls-remote 为什么不下载任何文件就能判断分支是否变化。

原理逻辑

  1. 每次提交生成一个唯一的 SHA-1 哈希，作为提交对象的指纹。
  2. 提交对象通过 parent 指针链接成有向无环图，ref 指向链的末端（即最新提交）。
  3. 读取 ref 的当前值，即可获得分支最新提交的哈希，无需遍历整个历史。

具体例子

监控脚本先保存历史 SHA `abcdef123456...`，然后执行 `git ls-remote origin refs/heads/main`，返回 `a1b2c3d4... refs/heads/main`，脚本发现两个 SHA 不同，就判定 `refs/heads/main` 这个 ref 指针移动了。整个过程没有下载仓库，也没有读取工作区。

常见误区

  • 常见的误区是把分支名当成一个装着一串提交的盒子。实际上分支名只是一个 ref 指针，它保存的是一个提交哈希；提交与提交之间通过父子关系连成历史，分支名只是给这条链的末端起了一个可移动的名字。
  • 另一个误区是混淆 HEAD 与分支：HEAD 通常是一个符号引用，指向当前所在的分支；而 `refs/heads/main` 是那个分支本身的指针。工作区还没提交的改动，ref 也完全不知道。

概念关联

关联概念关系说明
提交哈希Git 引用（ref）指针保存的是提交哈希，因此 ref 是提交哈希的命名别名。
远端只读监控（ls-remote）远端只读监控（ls-remote）直接读取 refs/heads/main 的当前值，说明 ref 是远程状态观测的基本单位。
工作区状态审计ref 只反映已提交历史；工作区未提交变更不写进 ref，所以需要工作区状态审计来补充。

远端只读监控（ls-remote）

完整讲解

`git ls-remote` 是一个向远端仓库问路的命令：它只索要远端所有引用（ref）的名字和对应的提交哈希，不下载提交对象、不 clone、不 fetch。因为提交哈希本身就是状态的指纹，所以只要比较“上次记录的 SHA”和“这次返回的 SHA”，就能判断某个分支是否被移动。这种监控方式非常符合最小权限思想：为了回答“远端分支变了吗”，最小必要信息是一个 ref 名字加一个 SHA。它不需要知道提交信息、作者、文件列表、diff，也不需要把仓库复制到本地。于是它可以很轻、很快、很低侵入地高频运行，适合做定时巡检。但它也有明确的可观测性边界：它只能证明 `refs/heads/main` 这个指针从旧 SHA 变成了新 SHA，不能证明这中间新增了几个提交、谁提交的、改了什么文件。就像看到门牌号变了，只能推断里面有变化，却不知道具体变化是什么。若需要具体内容，必须改用 `git fetch` 把对象下载到本地。

原理逻辑

  1. 远端仓库通过 refs 暴露引用状态，每个 ref 对应一个 SHA。
  2. ls-remote 只获取 ref 列表及哈希，不获取对象数据库内容，因此网络开销小。
  3. 对比历史 SHA 与当前 SHA，即可得到分支是否移动的布尔结论。

具体例子

public-library 的定时任务先记住 `refs/heads/main` 的历史 SHA，然后执行 `git ls-remote origin refs/heads/main`。假设返回 `9f3e1a2... refs/heads/main`，与历史 SHA `2b4c6d8...` 不同，于是它把状态标为 changed。但它没有本地对象可以查看提交说明，所以只能输出“远端版本变化线索”而不是“某某作者提交了某某改动”。

常见误区

  • 有些人以为 `git ls-remote` 会把远端提交记录下载到本地，或者至少会更新本地的 remote-tracking 分支。实际上它只返回远端 ref 的名单与哈希，不写对象数据库，也不更新 `refs/remotes/origin/*`。
  • 另一个误区是认为“远端 SHA 变了”就等于知道了具体提交内容；其实这只是状态层面的变化信号，内容层面的信息完全不可见。

概念关联

关联概念关系说明
Git 引用（ref）指针ls-remote 的观察对象是 Git 引用（ref）指针，比较对象是提交哈希，因此它把 Git 引用（ref）指针与提交哈希直接串起来。
最小权限访问ls-remote 只请求 ref 元数据，是典型的最小权限访问；它不 clone、不 fetch，所以不会把仓库内容读到本地。
可观测性边界ls-remote 能回答“ref 是否变化”，但回答不了“具体变了什么”，这正是可观测性边界的一个具体表现。

待确认变化线索

完整讲解

Git 的可靠快照只存在于提交对象里。未提交的修改、未暂存的文件、未跟踪的文件都停留在工作区，并没有形成提交哈希。`git status` 能列出它们，但 Git 的元数据不能证明这些改动是什么时候发生的，也不能证明它们是否已经完成。工作区状态审计就是做这样一次“现场检查”：看看当前工作区里有哪些与 HEAD 不同、但还没有进入版本控制的东西。tiny-sea-war 的检查发现：目标时间窗口内没有任何新提交，主工作区却有未提交变更和未跟踪文件。于是这些变化只能被记录为“当前存在”，而不能写成“昨天完成了这些工作”。为什么不能证明时间？因为 Git 对未提交内容不生成快照，没有写入对象数据库，自然也没有交给提交哈希来背书。文件系统的时间戳虽然存在，但它可以被修改、可能受同步工具影响，不能作为 Git 层面的可靠证据。因此，“待确认变化线索”是一种严谨的表述：不忽略现象，也不夸大结论。如果仓库启用了多个 worktree，这种审计还要分别查看每个 worktree，因为未提交变更可能分散在不同目录。今天 tiny-sea-war 提到存在 1 个 worktree 的待确认线索，说明状态审计不能只看主工作区。

原理逻辑

  1. Git 只对已提交内容生成不可篡改的哈希元数据。
  2. 未提交内容仅存在于工作区，没有进入对象数据库，因此没有 Git 层面的时间证明。
  3. 工作区状态审计基于 git status 的当前输出，只能反映“存在”，不能反映“何时”。

具体例子

tiny-sea-war 的总结里写着：目标日期前一天至今窗口内没有提交，但 `git status` 发现主工作区存在未提交变更和未跟踪文件，其中包括若干 `.uid` 文件。由于存在这些文件的时间无法被 Git 证明，总结没有把它们当成已确认的历史事实，而是标记为“待确认变化线索”。

常见误区

  • 常见误区是把“工作区有未提交改动”直接等同于“目标日期发生了这些改动”。`git status` 只能证明“现在有这个状态”，不能证明“它在什么时候出现”。
  • 另一个误区是以为未跟踪文件也已经被 Git 管理；实际上它只是放在工作区里、还没有被纳入版本控制的文件，因此它的证据效力更弱，只能作为线索。

概念关联

关联概念关系说明
工作区状态审计待确认变化线索来自工作区状态审计，而工作区状态审计观测的是 Git 尚未快照的内容，与 ref 指针所代表的已提交历史不在同一层面。
Git worktree多个 Git worktree 会使未提交变更分散在不同目录，因此审计时不能只看主工作区，否则会漏掉待确认线索。
可观测性边界待确认变化线索与可观测性边界本质相同：工具只能证明“当前存在状态”，不能证明“状态何时发生或是否完成”。
