碰撞场二进制格式（.tscf）

.tscf Binary Format

碰撞场二进制格式是数据存储的'网格胶带'——紧凑、高效，但需要验证工具来读懂。

核心要点

  • .tscf 是碰撞场的序列化格式，将二维网格数据转为紧凑二进制
  • 文件由头部信息（宽高、含义）和连续网格数据组成
  • 相比于 JSON，体积更小、加载更快，但人类不可读，需要验证工具

Fixed Tick

固定时间步是模拟世界的节拍器，保证每一步长度相同，结果才可复现。

核心要点

碰撞场二进制格式（.tscf）

完整讲解

碰撞场可以想象成一张棋盘，每个格子写着一个数字，表示这个地方能不能走、走的代价有多大。要把这张棋盘存到电脑里，有两种思路：一种写成 JSON 文本，如“第1行第1列是0……”——人读起来清楚，但电脑要逐行解析，速度慢且占用空间大。更聪明的办法是直接铺一块连续内存区域，按顺序把每个格子变成一个二进制数字，如 0 表示可通行、1 表示不可通行。.tscf 正是这样做的：它将二维碰撞场“拍扁”成一串数字，并在开头加上一小段说明信息（宽、高、每个数字的含义），形成紧凑且可直接读取的文件。这种将文本描述转换为机器友好的紧凑二进制的过程称为序列化，反向操作是反序列化。.tscf 的优点是体积更小、加载更快，缺点是普通人无法直接阅读，因此需要配套的验证工具保证正确性。

原理逻辑

  1. 序列化将结构化的碰撞场数据转换为线性字节流，便于存储和加载
  2. 头部字段记录元数据，保证反序列化时能正确解释数据
  3. 二进制存储利用计算机内存布局，避免文本解析开销

具体例子

以 4×4 碰撞场为例：JSON 表示是 `{"data": [[0,1,0,0],[0,1,1,0],[0,0,1,0],[0,0,0,0]], "width":4, "height":4}`，而 .tscf 只需用 2 字节位图或 16 字节 int8 加上宽高信息，总共不过二十多字节；运行时按固定偏移量直接读入，无需逐字符解析。

常见误区

  • 二进制格式不是加密或神秘文件，只是另一种数字表示方式，可通过工具解析回文本
  • 二进制文件也可能出错，而且更隐蔽，所以需要 validate 验证脚本检查

概念关联

关联概念关系说明
数据烘焙（Data Baking）.tscf 是地形定义经烘焙脚本转换后的输出结果
数据验证（Data Validation）.tscf 会经过验证脚本检查格式、逻辑和语义，确保正确性
基础设施加载器（Infrastructure Loader）加载器读取 .tscf 并转换为领域服务可用的碰撞场对象

固定时间步（Fixed Tick）

完整讲解

计算机模拟中，时间通常离散推进。固定时间步就是让逻辑每隔固定间隔更新，如每 1/60 秒。可变时间步的更新间隔取决于渲染耗时，导致模拟不可复现。固定时间步像节拍器，不管环境如何变化，逻辑更新始终按稳定节拍走。如果渲染一帧超过一个 tick，可能需要在一帧内补跑或推迟到下一帧，但每次逻辑更新的时间间隔恒定。最大好处是确定性：同样输入、同样随机种子、同样 tick 间隔，运行两次结果完全一致，这对轨迹验证至关重要——自动化测试可以断言轨迹是否经过某区域，而不会因机器性能变化时灵时不灵。

原理逻辑

  1. 离散时间推进以固定间隔为基本单位，保证模拟步长一致
  2. 确定性来源于恒定步长与相同的初始条件，排除外部时序干扰
  3. 自动测试依赖可复现结果，固定 tick 是回归测试的基础

具体例子

假设一艘船每 tick 前进 0.1 米，碰撞场中某个障碍物占一个格子。若时间步不固定，系统繁忙时更新距离可能不同，导致第二次运行撞上障碍物；固定时间步下，无论系统如何波动，每次更新船都恰好前进 0.1 米，绕障轨迹每次一致，测试稳定通过。

常见误区

  • 固定时间步不等于固定帧率：帧率指画面渲染次数，tick 指逻辑更新次数，二者独立
  • 固定时间步不保证画面流畅，但保证模拟世界的时间流速恒定

概念关联

关联概念关系说明
轨迹规划器（Trajectory Planner）依赖固定时间步按等间隔生成路径点，保证规划结果一致
船舶运动服务（Ship Motion Service）按固定 tick 推进船的位置，使运动学计算稳定可预测
per-tick 缓存固定时间步作为缓存失效的边界，tick 结束即清空

检测事实缓存（Per-Tick Detection Fact Cache）

完整讲解

在一个 tick 内，AI 可能对同一位置反复询问“这里能不能走”。每次询问都做昂贵检测非常浪费。检测事实缓存的做法是：同一 tick 内首次算出结果后存入临时存储，后续相同查询直接查缓存。这个小本本只在当前 tick 内有效，tick 结束就清空。为什么必须按 tick 清空？因为下一 tick 游戏状态可能变了，继续用旧结果会出错。因此 per-tick 既是优点也是边界：保证缓存数据不过期，固定时间步提供自然的失效时机。本质上是空间换时间，多花内存省重复计算。与记忆化思想一致，适合“输入相同、输出一定相同”的纯函数式查询。

原理逻辑

  1. 利用查询的纯函数特性：相同输入在同一个 tick 内输出不变
  2. 以额外内存存储结果，减少重复计算的开销
  3. tick 结束清空缓存，确保数据与当前游戏状态一致

具体例子

一个 tick 内，轨迹规划器尝试 20 次方向探测，其中 15 次都查询同一点 (x,y) 是否可通行。第一次查询后结果存入缓存，后面 14 次直接读取；若每次检测需 0.1ms，则省下 1.4ms，累计节省可观。

常见误区

  • 缓存并非越多越好、永远有效，失效处理不当会导致错误结果
  • 缓存不是银弹，如果命中率低，维护开销可能超过收益

概念关联

关联概念关系说明
碰撞场查询（Collision Field Query）per-tick 缓存优化的是同一 tick 内重复的碰撞场查询
固定时间步（Fixed Tick）tick 结束即清空缓存，保证缓存数据不会跨 tick 过期
性能基准（Performance Benchmark）通过基准测试验证缓存带来的性能提升和内存开销
