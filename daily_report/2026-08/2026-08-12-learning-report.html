固定种子可复现测试

Fixed-Seed Reproducible Test

种子相同，命运剧本就相同；AI 测试不再靠运气。

核心要点

  • 固定种子让伪随机序列完全可重复，测试结果摆脱运气波动。
  • AI 对战测试因此可以稳定复现失败，帮助定位算法缺陷或参数问题。
  • 固定种子不消灭随机性，只是把随机序列变成可控变量，仍可换多粒种子覆盖不同情况。
软件工程 ★★★☆☆

数据契约联动

Data Contract Linkage

一份合同变了，四份合同都要跟着变，否则数据就会各说各话。

核心要点

  • 数据契约是模块间约定的通用语言，常由 schema 集中管理。
  • 核心数据语义变化时，多个 schema 需联动更新，否则模块间读取错位。
  • schema 联动是跨模块的一致性保障，不只是文档层面的同步修改。
软件工程 ★★★★☆

横切变更模式

Cross-Cutting Change Pattern

一次装修动全屋管线，文档、数据、代码、测试都要同步跟上。

核心要点

  • 横切变更像一把刀切过系统多个层面，影响面呈面状而非点状。
  • 各层必须保持一致：只改代码忘了文档和数据，团队认知落后；只改数据忘了代码，系统可能无法运行。
  • 识别横切变更能提醒评审和测试不能只盯核心代码，还要检查所有被切到的层面。

固定种子可复现测试

完整讲解

程序中的随机并非真正随机，而由一个公式基于种子数产生。固定种子可复现测试在一开始把种子设为固定值，如 42，使整个测试过程里的随机完全可预测。运行十次，AI 每次面对的状况都一样，测试结果稳定；失败时可复现，便于找 bug。若没有固定种子，测试每次从不同起跑线开始，成绩差时难以分辨是策略问题还是运气问题。在 tiny-sea-war 的提交中新增了 submarine_ai_fixed_seed_test.gd，这是固定种子测试的文件级证据；具体如何调用种子函数、如何断言，因无 diff 只能合理推断。

原理逻辑

  1. 伪随机数生成器：相同种子产生完全相同的数字序列。
  2. 可复现前提：同一初始条件产生同一结果，与 SHA 指纹思想呼应。
  3. 自动化测试稳定性：固定种子隔离随机扰动，让失败可定位。

具体例子

测试潜艇 AI 躲避鱼雷时，固定种子为 20260812 后，AI 每次都会在同一时刻做出同样的转向，于是能清晰分辨算法 bug 与参数问题。

常见误区

  • 固定种子后测试就不随机、覆盖率降低。实际上固定种子只是序列可重复，仍可换多粒种子扩展覆盖。
  • 固定种子就一定能保证完全确定的结果。若还依赖真实时钟、网络、外部文件或哈希遍历顺序，结果依然可能抖动。

概念关联

关联概念关系说明
游戏 AI 测试固定种子让 AI 随机决策序列可复现，使对战测试成为可回归的自动化测试。
状态基线 / SHA 指纹都依赖同一条件产生同一结果，只是基线是提交指纹，种子是随机序列指纹。
测试运行器接入test_runner.gd 被修改，推测用于接入新测试，但接入方式尚无 diff 确认。

数据契约联动

完整讲解

数据契约可以理解成不同模块之间约定的通用语言。例如战斗模块知道“鱼雷伤害”写为 torpedo_damage，AI 模块也需要知道这个字段名，表现模块需要知道单位是整数还是浮点数。这些约定常被集中写在 schema 文档里。当核心数据语义改变，所有依赖字段的模块都要同步更新 schema，否则一个模块按老格式读，另一个按新格式写，两边对不上。这种多个 schema 在同一批改动里一起变化的现象就是数据契约联动。该次提交中 docs/21_combat_data_schema.md、docs/24_ai_data_schema.md、docs/25_presentation_data_schema.md、docs/26_simulation_data_schema.md 同时被修改，是数据契约联动的候选线索，而非已确认事实。

原理逻辑

  1. 共享字段语义：多个模块对同一字段名和类型有一致假设。
  2. 语义变化传播：核心概念变化会沿数据依赖链传导到所有相关 schema。
  3. 一致性保障：schema 联动避免读写双方因格式不一致而解耦失败。

具体例子

四个 schema 文档同时修改，暗示战斗、AI、表现、仿真四个层面共享的数据定义发生了联动调整；但要确认具体字段变化，仍需 diff 证据。

常见误区

  • schema 只是数据字典，改字段名全局替换即可。实际上其背后有类型、范围、必填、嵌套等约束，改动可能引发读取逻辑崩溃。
  • 看到多个 schema 同时修改就能认定存在联动。目前只有文件级证据，还需 diff 级证据确认具体变化。

概念关联

关联概念关系说明
数据构建脚本与数据资产schema 定义模式，JSON 装载数据，构建脚本维护 roster 数据，契约变化会顺着数据管道扩散。
横切变更模式多个 schema 文档同改是横切变更在数据层的具体表现。
证据粒度目前只有文件级证据，要确认契约联动需要提交或 diff 级证据。

横切变更模式

完整讲解

横切变更是一次改动跨越系统的多个不同层面。普通变更是点状的，只改一个函数；横切变更是面状的，同时改代码、配置文件、文档和测试。它影响范围广，各层之间需要保持一致。若只改运行时代码而忘记文档和数据，功能可能正常但团队认知落后；若只改数据而忘记代码，可能运行不起来。识别横切变更，就是提醒评审和测试时不只盯核心代码，还要检查所有被切到的层面。tiny-sea-war 的提交 3ec068cf 同时改了 docs、data、schema、scripts、tests 和 tools，正是横切变更模式的典型观察样本。

原理逻辑

  1. 跨层影响：一次逻辑升级需要在多个抽象层次同步落地。
  2. 一致性要求：各层之间若不同步，会产生隐藏的认知或运行错位。
  3. 影响面评估：从文件路径可预估影响范围，但具体内容需 diff 证据。

具体例子

tiny-sea-war 的提交 3ec068cf 同时修改 docs、data、schema、scripts、tests、tools，成为横切变更模式的典型观察样本。

常见误区

  • 横切变更等于改动文件数量多。实际上关键在跨层而不是量多，少量文件覆盖多个层次也是横切变更。
  • 一次提交修改几百个数据文件就是横切变更。如果只是同类型资产批量更新，不一定算，可能只是数据批量更新。
