ref 命名空间的语义分层与生命周期

完整讲解

你可以把 ref 想象成贴在提交快照上的书签。Git 每次想知道分支最新提交在哪，就去读对应书签。但书签不能全都一样对待：有些要跟着开发走，有些要钉死，有些只是镜子。Git 用 refs/ 下的路径前缀区分这些书签。refs/heads/* 是本地分支，commit、merge、rebase 会让它自动前移；refs/tags/* 是发布标签，通常创建后就不该再动；refs/remotes/* 是远端追踪引用，只记录“上次从远端看到的位置”，一般由 fetch 更新；refs/pull/* 是托管平台合成的只读引用，表示某个 PR 的最新提交。关键不是路径上多写几个字，而是命名空间决定更新语义。Git 的存储层可以一视同仁地存成一行哈希，但上层命令会根据前缀决定谁能移动、怎么移动、能不能被普通更新改写。生命周期也因此不同：分支可以频繁诞生、移动、删除；标签希望长期稳定；远端镜像只应跟随 fetch 变化；pull 引用只在 PR 生命周期内存在。

原理逻辑

  1. 命名空间是引用角色的语义标签，决定更新规则。
  2. 不同命名空间有不同生命周期：heads 活跃、tags 稳定、remotes 跟随 fetch、pull 只读且生命周期短。
  3. 存储层统一为哈希行，指令层按前缀解释。

具体例子

在本地仓库中，git commit 只会让 refs/heads/main 前进，不会移动 refs/tags/v1.0.0；git fetch origin 会更新 refs/remotes/origin/main，而不会直接改动本地 main；当你打开 GitHub 的 PR 页面时，平台会提供一个 refs/pull/123/head 的引用，它通常只读。

常见误区

  • 认为 refs/heads、refs/tags 只是文件夹，放在哪里都行。
  • 实际上 Git 的许多命令会按前缀判断语义，例如 push 默认推送 heads 而不是 tags，fetch 会把远端 heads 写到 remotes 下；把 tag 当 branch 用，或手动改写 remote ref，都会破坏“哪些引用可变、哪些引用固定”的约定。

概念关联

关联概念关系说明
packed-refs 的维护时机分支更新频繁、标签更新少，这种差异直接决定 packed-refs 的维护压力：活跃分支容易留下很多松散覆盖文件，稳定标签更适合长期躺在打包文件里。
merge-base 的计算机制merge-base 不关心输入 ref 属于哪个命名空间，只拿到提交对象，因此同一个共同祖先算法可以统一定义分支、标签、远端镜像之间的历史关系。

packed-refs 的维护时机：打包、重写与陈旧行清除

完整讲解

松散 ref 文件就是一个目录下的小文件，一个 ref 一个文件。ref 少的时候没问题，多了会让文件系统压力变大，所以 Git 会把它们合并进 packed-refs 这一个文件。合并后读取规则是松散优先，但写入规则不是这么简单。更新一个已经被打包的 ref，Git 不会去改 packed-refs 里的旧行，而是先写一个新的松散文件。因为读取时松散文件优先，新值立刻生效，packed-refs 里那行旧值还在，只是暂时被遮住，成为陈旧行。删除一个已经被打包的 ref，Git 必须重写 packed-refs，把那行真正删掉；否则只删松散文件，旧值会从打包文件里重新冒出来。陈旧行什么时候消失？等下一次 git pack-refs 或 git gc 执行时，Git 按松散优先规则收集所有当前有效 ref，重建一份 packed-refs；旧文件里的陈旧行就被物理清除了。这个设计像用便利贴更新公告栏：平时改日期不用撕掉整张海报，贴一张新便利贴就行；有人离开时必须把旧名字从名单上划掉；大扫除时再誊清一份干净名单。

原理逻辑

  1. 松散文件优先读取，保证新值立即生效。
  2. 更新已打包 ref 时写松散覆盖，避免频繁重写整个 packed-refs。
  3. 删除已打包 ref 必须重写，防止旧值从打包文件复活。
  4. 重新打包时按当前有效状态重建，消除陈旧行。

具体例子

假设 packed-refs 中有一行 111... refs/heads/main，本地没有松散文件。你提交后，Git 生成新提交 222...，并写一个松散文件 refs/heads/main 内容为 222...。此刻 git rev-parse refs/heads/main 读到 222，grep 111... .git/packed-refs 仍能看到旧行。接着再执行 git pack-refs，由于 111 被 222 覆盖，新版 packed-refs 只写 222，旧行消失。如果此时删除 main，Git 不仅删松散文件 222，还会重写 packed-refs 去掉 111，否则删除后 111 会从打包文件里重新冒出来。

常见误区

  • 以为 packed-refs 里出现的旧值就是当前值，或看到同一 ref 同时出现在两个文件里就以为仓库异常。实际上，松散优先是读取规则，重叠是更新后尚未重新打包的正常中间态。
  • 真正需要担心的是删除已打包 ref 后不重写文件，导致引用“复活”。

概念关联

关联概念关系说明
ref 命名空间的语义分层与生命周期ref 命名空间决定分支更新频繁、标签更新少，因此频繁更新的 heads 会不断制造新的松散覆盖，长期稳定的 tags 更适合久驻 packed-refs，维护压力因此不同。
merge-base 的计算机制与共同祖先选择merge-base 需要读取 ref 的当前有效 SHA；如果陈旧行没有被正确清理或覆盖关系出错，历史判定就会基于过期值。

merge-base 的计算机制与共同祖先选择

完整讲解

Git 的提交历史不是一条直线，而是一张有向无环图：每个提交都保存父提交的引用，所以从一个提交往前走，可以追溯到它的祖先。merge-base 要做的事，是给定两个提交，找出从它们都能到达的共同祖先。为什么需要共同祖先？因为三方合并使用共同祖先作为“原始版本”：左边改了什么、右边改了什么，都是相对它来计算的。如果没有共同祖先，两个提交就像来自两个完全无关的世界，Git 不知道该以谁为基准合并。判断重写和无关历史也一样：有共同祖先，说明两条线同源；没有共同祖先，说明它们根本没有共同的起点。如果共同祖先不止一个呢？Git 不会随便挑一个最老的。它要找的是不被其他共同祖先支配的最佳共同祖先。通俗地说，Git 会排除那些“太老”的候选，选择离双方更近、包含更多历史信息的共同祖先。git merge-base --all 可以把这些并列最佳的共同祖先全部列出来。这个选择为什么重要？如果选了一个太老的 base，三方合并会认为许多两边都已经做过的改动是冲突或重复；如果选了一个错误的 base，重写判定也会失真。所以 merge-base 不是简单找“某个交点”，而是在提交图上找“最近且最有代表性的共同祖先”。

原理逻辑

  1. 提交历史是有向无环图，祖先关系可沿父指针追溯。
  2. 共同祖先是三方合并的基准，用于计算双方相对原始版本的改动。
  3. 多个共同祖先时，Git 选择不被其他共同祖先支配的最佳候选，避免选择过老祖先导致合并失真。

具体例子

假设共同祖先 C 是两个分支的起点：main 之后有 F、G，feature 之后有 D、E。git merge-base main feature 输出 C。如果 feature 被 rebase 到 main 上，新 feature 基于 main 的最新提交，此时 git merge-base main feature 很可能输出 main 本身；这个变化是取证中判断 feature 是否被重写的重要信号。两个完全独立的仓库第一次尝试合并时，merge-base 找不到共同祖先，命令返回非零，提示两者历史无关。

常见误区

  • 只靠 git rev-list old..new 和 git rev-list new..old 判断。两个范围都非空，只能说明双方各有对方没有的提交；可能是从共同祖先两边分叉，也可能是两段无关历史。必须再用 merge-base 问“有没有共同祖先”，才能把“重写/分叉”和“无关历史”区分开。

概念关联

关联概念关系说明
ref 命名空间的语义分层与生命周期merge-base 不关心 ref 是 heads、tags 还是 remotes，只要传入提交对象，它就对所有命名空间给出统一的历史关系判定。
packed-refs 的维护时机merge-base 的输入 SHA 来自松散文件或 packed-refs 的当前状态；如果 packed-refs 维护产生过期值，共同祖先计算就会建立在错误证据上。

ref 命名空间决定角色，packed-refs 维护当前状态，merge-base 判定历史关系——三者构成一条理解 Git 引用的完整链路。
