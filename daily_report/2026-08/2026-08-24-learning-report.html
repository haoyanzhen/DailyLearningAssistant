无共同祖先时的合并机制：空树 base 与 --allow-unrelated-histories 的机械实现

完整讲解

要理解这个机制，我们先看普通合并是怎么回事。Git 合并两个分支时，会先找双方的共同祖先，也就是两个分支从哪个提交开始分道扬镳的那个点。三方合并就是以共同祖先做基准，比较两边各自改了什么。如果两个提交完全没有共同祖先呢？那就相当于两个人的家族史毫无交集，根本找不到共同起点。这时 merge-base 输出为空，Git 不知道拿什么当基准。--allow-unrelated-histories 的机械实现，就是人为造一个虚拟起点：空树。空树代表一个什么都没有的空白目录。把空树当作 base，左边根提交的所有文件和右边根提交的所有文件，相对于空树都等于‘新增文件’。于是三方合并有了可比较的基础：两边都新增了同一个路径且内容不同，就冲突；两边新增的路径不同，就各自保留。这样一来，原本毫无关系的两段历史也能完成合并。一个具体例子是：假设仓库里有两个根提交 A 和 B，A 分支上有 src/a.c 和 README.md，B 分支上有 src/b.c 和 README.md。执行 `git merge B --allow-unrelated-histories` 时，Git 把空树、A 的树、B 的树放进三方合并。src/a.c 只在 A 出现，src/b.c 只在 B 出现，于是都直接加入；README.md 两边都有且内容不同，所以产生冲突，需要手工解决。解决后的合并提交会带有 A 和 B 两个父提交，成为连接两段历史的新节点。

原理逻辑

  1. 普通三方合并需要共同祖先作为基准；无共同祖先时 merge-base 为空。
  2. --allow-unrelated-histories 解除默认限制，并将空树（空白目录）作为虚拟共同祖先。
  3. 两个根提交的所有文件相对空树都视为新增，于是进入标准三方合并流程：路径不同则并存，路径相同且内容不同则冲突。

具体例子

假设仓库里有两个根提交 A 和 B，A 分支上有 src/a.c 和 README.md，B 分支上有 src/b.c 和 README.md。执行 `git merge B --allow-unrelated-histories` 时，Git 把空树、A 的树、B 的树放进三方合并。src/a.c 只在 A 出现，src/b.c 只在 B 出现，于是都直接加入；README.md 两边都有且内容不同，所以产生冲突，需要手工解决。解决后的合并提交会带有 A 和 B 两个父提交，成为连接两段历史的新节点。

常见误区

  • 误以为 --allow-unrelated-histories 是“不管三七二十一硬拼历史”的开关；实际上仍走三方合计算法，只是把 base 换成空树。
  • 误以为无共同祖先合并一定冲突遍地；其实只有路径都新增且内容不同才冲突，路径不重叠时合并很顺。
  • 误以为这个开关专门用来“接盘”外部仓库；其实它只是一个解除默认限制的合并选项，底层机制始终是空树 base。

概念关联

关联概念关系说明
merge-base 的计算机制与共同祖先选择当 merge-base 为空时，这个机制用空树做虚拟 base，让无共同祖先的历史也能进入三方合并流程。
git fsck --lost-found 与悬空对象的重新锚定合并用空树 base 为两个不相交的历史建立正向连接，fsck 则负责发现对象图中已经断开的连接。
receive-pack 状态报告协议与 push 的部分成功语义两者都处在“某个提交能否进入当前历史”的判定边界，只是合并由 merge-base 决定，推送由 update 钩子决定。

git fsck --lost-found 与悬空对象的重新锚定

完整讲解

我们先建立一张图。Git 仓库里的对象像图书馆里的书，ref（分支和 tag）像目录索引。能从某个 ref 出发、顺着提交图走到的对象，叫可达对象；走不到的对象叫不可达对象，也就是悬空对象。悬空对象很常见：分支被 reset 回退、tag 被强制移动、rebase 后旧提交失去引用，都会制造出它们。它们不会立刻被删，因为 Git 的 gc 还留有保护期。git fsck 的工作，就是从当前所有 ref 出发扫一遍对象图，找出那些目录里已经查不到的书。--lost-found 则把这些书集中放到一个待认领架——.git/lost-found/ 目录。恢复动作本身很简单：确认某个悬空提交确实是你要找的旧状态，然后用 `git branch recover <SHA>` 或 `git tag old <SHA>` 新建一个引用指向它。引用一旦建立，这个对象就从不可达变回可达，重新出现在正常历史里，可以被 checkout、diff、继续开发。一个具体例子：假设你执行了 `git reset --hard HEAD~3`，原来指向的最新提交变成了悬空提交。运行 `git fsck --lost-found` 后，Git 会在 .git/lost-found/commit/ 下写入一个文件，里面就是那个提交的 SHA。你用 `git show <SHA>` 确认它确实是回退前的状态，然后执行 `git branch recover <SHA>`。新建的 recover 分支指向那个提交，该提交立即重新变成可达对象；之后你可以继续在它上面开发，或把它 merge 回主分支。

原理逻辑

  1. 对象可达性由从 ref 出发的遍历决定；失去引用的对象成为悬空对象。
  2. 悬空对象有保留窗口，在 GC 清理前仍存在于对象库。
  3. git fsck 扫描对象图并列出不可达对象，--lost-found 将它们汇总到 .git/lost-found；新建 ref 即可重新锚定。

具体例子

假设你执行了 `git reset --hard HEAD~3`，原来指向的最新提交变成了悬空提交。运行 `git fsck --lost-found` 后，Git 会在 .git/lost-found/commit/ 下写入一个文件，里面就是那个提交的 SHA。你用 `git show <SHA>` 确认它确实是回退前的状态，然后执行 `git branch recover <SHA>`。新建的 recover 分支指向那个提交，该提交立即重新变成可达对象；之后你可以继续在它上面开发，或把它 merge 回主分支。

常见误区

  • 误以为 git fsck --lost-found 会自动修复仓库；它只负责找出不可达对象并整理到 lost-found，不会自动修改任何 ref。
  • 误以为悬空对象会马上被清掉；实际上有保留窗口，这段时间正是恢复窗口。
  • 误以为只有 --lost-found 才能恢复悬空提交；其实只要拿到 SHA，手动 git branch 或 git tag 同样可以重新锚定，--lost-found 只是集中列出候选。

概念关联

关联概念关系说明
服务端审计链审计链记录 ref 曾经指向的旧 SHA，当旧值因强移或误删变成不可达对象时，fsck --lost-found 提供找回并重新锚定的操作路径。
无共同祖先时的合并机制：空树 base 与 --allow-unrelated-histories 的机械实现合并是在两个独立历史之间建立新的正向连接，fsck 则是发现历史断开后把对象重新连接回当前仓库。
receive-pack 状态报告协议与 push 的部分成功语义两者分别位于对象生命周期的入口和出口：推送的 ok/ng 决定对象能否被接纳，fsck --lost-found 决定失去引用的对象能否被重新接纳。

receive-pack 状态报告协议与 push 的部分成功语义

完整讲解

我们知道 git push 会把本地分支的更新发送到远端，远端由 receive-pack 进程负责接收。接收时有两个钩子把关：pre-receive 先整批看一遍，可以拒绝整个推送；update 对每个 ref 单独检查，可以只拒绝其中某几个。因此一次 push 可以同时包含 main 和 dev 两个分支的更新，dev 被拒了，main 却成功了。Git 如何让客户端知道这个结果？答案是 receive-pack 的状态报告。它对每个 ref 生成一行结果：ok 表示该 ref 已经更新，ng 表示被拒绝并附带原因；这些结果通过 pkt-line 协议回传给本地 git。于是客户端能逐条显示 main 已更新、dev 被拒绝。要特别记住：部分成功不是异常，而是 Git 以 ref 为更新粒度的正常现象。两个 ref 之间没有事务性捆绑，一个失败不会拖累另一个的成功。另外，post-receive 钩子在 ref 更新完成后才运行，它的退出码不会改变已经发生的更新结果；客户端看到的状态报告在 post-receive 之前就已确定。一个具体例子：执行 `git push origin main dev`，远端 update 钩子允许 main 更新、拒绝 dev 更新。receive-pack 返回的状态报告类似：`ok refs/heads/main`、`ng refs/heads/dev (update hook declined)`。本地终端会显示 main 推送成功、dev 被远端拒绝，同时 Git 命令的退出码是 1。CI 系统读取这些输出后，仍然可以针对 main 启动构建，因为状态报告已明确 main 成功了。

原理逻辑

  1. receive-pack 接收 push，pre-receive 整批把关，update 逐 ref 检查。
  2. receive-pack 对每个 ref 生成 ok/ng 状态报告，通过 pkt-line 回传客户端。
  3. 状态报告在 post-receive 之前确定，post-receive 不影响更新结果；部分成功是正常的。

具体例子

执行 `git push origin main dev`，远端 update 钩子允许 main 更新、拒绝 dev 更新。receive-pack 返回的状态报告类似：`ok refs/heads/main`、`ng refs/heads/dev (update hook declined)`。本地终端会显示 main 推送成功、dev 被远端拒绝，同时 Git 命令的退出码是 1。CI 系统读取这些输出后，仍然可以针对 main 启动构建，因为状态报告已明确 main 成功了。

常见误区

  • 误以为 git push 是全有或全无；实际多 ref 推送中部分成功是正常状态。
  • 误以为客户端进程退出码非零就推断所有 ref 都失败；必须配合状态报告才能知道具体哪个 ref 成功。
  • 误以为 post-receive 执行失败会撤销推送或让客户端显示失败；实际上 ref 更新已完成后 post-receive 只是通知器。

概念关联

关联概念关系说明
服务端 push 钩子的事件日志与外部补偿通道状态报告是当前结果，审计链是事后历史记录，两者是同一批 ref 更新事件的两个视角。
无共同祖先时的合并机制：空树 base 与 --allow-unrelated-histories 的机械实现两者共同回答某个提交能否进入当前历史：推送时由 receive-pack 和 update 钩子接受或拒绝，合并时由 merge-base 和空树 base 决定两段历史能否连接。
