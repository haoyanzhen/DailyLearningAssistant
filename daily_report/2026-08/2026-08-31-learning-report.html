gc.pruneExpire 与悬空对象保留窗口

完整讲解

很多人以为运行 `git gc` 之后，不要的分支和提交就会立刻被删掉。其实不是。`git gc` 先压缩对象，再清理不可达对象，但清理时要看这些对象已经“悬空”了多久。悬空对象就是当前没有任何分支、标签、reflog 或 HEAD 能到达的提交、树和文件。`gc.pruneExpire` 控制一个时间窗口，默认大约是两周。只要对象还没超过这个窗口，它就仍然待在对象库里，能通过 `git fsck --lost-found`、reflog 或旧引用被找回来；超过窗口后，`git prune` 才会真正把它们物理删除。这个窗口不是随便定的：太短，误删了就找不回；太长，仓库会一直膨胀。它也是并发安全的一部分——如果其他进程正想读取一个对象，过早物理删除会让读取失败，而保留窗口让这种风险变得更可控。

原理逻辑

  1. `git gc` 先压缩对象，再清理不可达对象，但清理时检查悬空时间。
  2. 悬空对象 = 当前没有任何引用能到达的提交、树和文件。
  3. `gc.pruneExpire` 控制时间窗口，默认约两周。
  4. 窗口内对象可通过 `git fsck --lost-found`、reflog 或旧引用找回；超过窗口后 `git prune` 物理删除。
  5. 窗口太短误删风险高，太长仓库膨胀；同时是并发安全的一部分，避免过早删除导致其他进程读取失败。

具体例子

想象你在团队分支上做了三天的一个重要提交，结果误操作强推覆盖了分支，提交似乎“消失”了。你立刻想到 `git fsck --lost-found`，在 `.git/lost-found/` 里找回了那个提交——因为 `gc.pruneExpire` 默认留了两周，它还没有被真正删除。如果这个仓库把保留期调成了 1 天，而你已经过了两天才发现，那这个提交就真的再也找不回来了。保留窗口就像给旧对象开了一个“失物招领处”，过了认领期才会销毁。

常见误区

  • `git gc` 后面仓库立刻变小，或者所有不可达对象都会被立即清空。实际上 `git gc` 只清理“超过保留期”的不可达对象；两周内的悬空对象依然存在，并且是 `git fsck` 可以列出来的。
  • 认为调短 `gc.pruneExpire` 只是省空间，但它同时会缩短并发进程安全读取对象的时间窗口，缩小事后审计的可用证据范围。

criss-cross 合并合并完成后，被替代的旧提交可能变成不可达对象，随后进入 gc.pruneExpire 的保留窗口，等待被清理或恢复。

packfile 临时文件命名与崩溃恢复

完整讲解

Git 在创建 packfile 时，并不会直接写一个最终文件 `pack-<hash>.pack`，而是先写一个 `tmp_pack_*` 这样的临时文件。所有写入都先落到这个临时文件里，等数据完整、校验通过之后，再用一次原子性的 rename 把它移动到正式的最终路径。对象查找的代码只认正式命名的 pack 文件，所以 `tmp_*` 文件即使存在于对象库目录中，也不会被当成有效 pack。这就产生了一个很干净的崩溃恢复性质：如果在 rename 之前进程崩溃，正式路径上什么都不存在，旧的 pack 依然完整；如果在 rename 之后崩溃，新 pack 已经正式发布，也不会有半截文件被别人读到。残留的 `tmp_*` 只是垃圾，会在后续 `git gc` 等维护操作中被清理。

原理逻辑

  1. 先写临时文件 `tmp_pack_*`，完成后再原子 rename 到 `pack-<hash>.pack`。
  2. 对象查找只认正式命名，`tmp_*` 不被识别为有效 pack。
  3. rename 前崩溃：正式路径无变化，旧 pack 完整。
  4. rename 后崩溃：新 pack 已发布，没有半截文件。
  5. 残留 `tmp_*` 是垃圾，由后续 `git gc` 清理。

具体例子

这就像你写文章时先写一个名为“草稿.tmp”的文件，一字一字敲完，确认没有错别字，再点击“另存为”变成“正式稿.md”。如果中途电脑断电，桌面上只会留下“草稿.tmp”，而“正式稿.md”要么不存在，要么是完整的旧版本，绝不会出现一个只写了一半的“正式稿.md”。别人看到“正式稿.md”时，它一定是完整内容；那个 `.tmp` 文件哪怕留着，也不会被当作正式稿来引用。

常见误区

  • 担心 `tmp_pack_*` 残留会导致 `git fsck` 报错或误当成本地对象。不会，Git 对象查找只扫描正式 pack 和松散对象，`tmp_*` 不在识别范围。
  • 认为 rename 不是原子的，可能在重命名过程中出现半个包；在同一文件系统内 rename 是原子性的，最终路径上要么是旧文件，要么是新文件，没有中间状态。

概念关联

关联概念关系说明
gc.pruneExpire`tmp_*` 在正式路径出现前不可见，悬空对象在保留窗口内同样“可见但待清理”，两者都用“最终命名达成”作为状态有效的标志。
能力协商降级临时文件在 rename 前不可假定，正如能力在协商成功前不可假定；二者都要求参与方不要把中间态当成可用的最终态。

criss-cross 合并中 best common ancestor 的支配关系

完整讲解

普通分支合并时，可以找到唯一的共同祖先，三方合并直接以它为 base。但有一种历史叫 criss-cross：两个分支反复互相合并，导致历史上同时出现多个共同祖先，而且它们之间可能互不包含。如果随便选一个共同祖先作为合并基，那么对同一对分支做两次合并，结果可能因为“碰巧选到哪个祖先”而不同，这显然不能接受。Git 解决这个问题的办法是：先算出所有共同祖先，然后剔除那些“被支配”的共同祖先——所谓被支配，就是另一个共同祖先是它的后代。被支配的那个更老、信息更少，不适合当合并基。剩下的不被任何其他共同祖先支配的候选，就是 best common ancestor。如果 best candidate 仍然不止一个，Git 的 recursive 或 ort 合并策略会先把这些候选合并成一个虚拟合并基，再用这个虚拟基去合并两个分支。这样，合并结果只由提交图结构决定，不依赖遍历路径或偶然选到的祖先。

原理逻辑

  1. 先找出所有共同祖先。
  2. 剔除“被支配”的共同祖先：即存在另一个共同祖先是它的后代，被支配者信息更少，不适合当 base。
  3. 剩下的为 best common ancestor。
  4. 若 best candidate 仍不止一个，recursive/ort 合并先合成一个虚拟合并基，再用虚拟基做三方合并。
  5. 最终合并结果只由提交图结构决定，不依赖遍历路径或偶然选到的祖先。

具体例子

想象两个程序员 A 和 B 合作写代码。A 先合入了一次 B 的代码，B 后来又合入了一次 A 的代码，结果两人的分支上都有对方的合并痕迹。到了下一次合并时，公共历史里出现了两个都可能当“基准点”的提交。如果 A 记得的是第一次合并后的样子，B 记得的是第二次合并后的样子，那结果可能完全不同。Git 的做法是：先淘汰掉那个明显更旧的基准（被另一个基准包含的），如果剩下两个都差不多新，就把它们先合成一个“折中基准”，再拿这个唯一基准去做三方合并。这样谁都不必靠“记忆里的那个偶然基准”来决定结果。

常见误区

  • 认为 Git 会比较共同祖先的提交时间，选“最近的那个”。实际上 Git 不看时间戳，只看提交图上的祖先关系。
  • 认为多个共同祖先就一定会导致合并冲突或不确定结果；只要有支配关系筛选和虚拟合并基机制，Git 仍能获得稳定合并基。
