receive-pack 状态行的顺序无关性与客户端聚合健壮性

完整讲解

当客户端推送代码到服务端时，服务端的 receive-pack 进程会逐个处理每个分支的更新请求，并且逐条返回结果：成功就返回“ok <分支名>”，失败就返回“ng <分支名> <原因>”。这些状态行是客户端判断“推送到底成没成功”的直接依据。 关键点在于：协议规范并没有保证这些状态行的返回顺序。服务端可能先返回最后一个分支的结果，也可能先返回第一个分支的结果；不同版本、不同钩子实现都可能产生不同顺序。如果客户端按“第几行对应第几个分支”来解读，就很容易出错。 所以客户端被设计为按分支名称来匹配，而不是按出现顺序。也就是说，客户端拿到一行状态，先看它说的是哪个分支，再看结果是 ok 还是 ng。这样即使状态行乱序、增删或者服务端实现有差异，客户端也能把每个分支的结果正确归位，最终给出全成功、部分成功、全失败的判定。 这背后是一个重要的工程原则：协议规范没有保证的东西，客户端就不能依赖。服务端返回顺序今天是这个顺序，明天换了实现可能就变了。面向规范而不是面向偶然实现，才能避免服务端升级导致客户端行为突变。

原理逻辑

  1. 协议规范未保证顺序，客户端不能依赖偶然实现。
  2. 按 ref 名称匹配使结果归位不依赖传输顺序。
  3. 面向规范而非面向实现，避免升级导致行为突变。

具体例子

想象一个老师给全班同学发成绩单。老师把成绩单打乱了顺序发给学生，有的学生先拿到自己的，有的同学最后才看到。但每个学生只需要看自己那一栏——“我的数学是 A，语文是 B”，而不是关心“成绩单上第几行写的是谁”。Git 客户端也是这样：它不在乎 ok/ng 行出现的顺序，只在乎每一行说的是哪个分支、结果是什么。

常见误区

  • 以为 ok/ng 状态行一定按推送顺序排列。
  • 把状态行乱序当作需要修复的 bug，其实这是协议允许的正常现象。

概念关联

关联概念关系说明
pre-receive 整体拒绝与 update 逐 ref 拒绝状态行顺序无关性保证了客户端在两种拒绝并存时也能正确识别哪些分支被拒、哪些分支成功。
side-band 通道协商side-band 通道协商决定了状态行通过什么传输通道到达客户端，而顺序无关性决定了客户端如何解读这些行。

Git protocol v2 中 side-band 通道的协商与多路复用扩展

完整讲解

想象一个工作团队要用对讲机沟通，但频道用途没有统一规定。在 Git 的早期协议（v0）里，大家事先约定了频道编号：1 号频道只传状态信息，2 号频道只传进度信息。这种固定约定简单粗暴，缺点是双方必须提前知道对方支持哪些频道，不能灵活扩展。 到了 protocol v2，Git 采用了“能力协商”机制。客户端先告诉服务端自己支持哪些能力，比如“我支持 side-band-all，也就是你可以在同一条数据流里同时打开多个通道”。服务端收到后，对比自己支持的能力，取交集，然后决定要不要使用这些额外通道。 这就像打电话：以前大家约定好“只能用 1 号线和 2 号线”，现在电话接通后先互相问一句“你支持视频吗？支持的话我们开视频，不支持就语音”。双方的能力交集决定了最终怎么通信。 v2 中未知通道编号的容错规则也更明确：客户端遇到不认识的通道编号时，不能因为一个未知通道就中断整个通信流，而是按协议定义的规则跳过或忽略。这让协议在演进过程中保持向后兼容——将来新增通道编号时，旧客户端不会被新通道卡死。

原理逻辑

  1. v0 用固定编号隐式约定，v2 用 capability 显式协商。
  2. 客户端声明能力，服务端根据交集决定最终行为，双方能力必须匹配。
  3. 未知通道的容错规则允许旧客户端不被新通道卡死，保持向后兼容。

具体例子

假设你是一个快递公司的老员工。以前快递单上有个固定的“备注栏”，所有信息都往里面写，大家都按老规矩办事。后来公司升级系统，新版快递单允许在寄件时额外勾选“需要冷链”“需要保价”这样的服务。但前提是：快递员要先确认一下送件方有没有这些新服务。如果送件方是新系统，就能用冷链；如果还是旧系统，就按最基础的配送方式来。Git protocol v2 的 side-band 协商就是这样：客户端先声明自己的能力，服务端只启用双方都支持的功能。

常见误区

  • 以为 v2 中 side-band 的通道编号语义与 v0 完全相同，实际上由能力协商决定。
  • 认为协商是双方完全对等的，实际上客户端声明，服务端根据交集决定。

概念关联

关联概念关系说明
receive-pack 状态行解析side-band 协商决定了状态行通过哪些通道传回客户端，为状态行解析提供传输层基础。
文件系统层的删除共享语义协议层的能力协商与文件系统层的删除共享语义类似，都需要参与方明确声明并处理不支持的场景。

packfile 原子重命名与“打开后删除仍可读”的跨平台语义

完整讲解

Git 在执行 gc（垃圾回收）时，会把多个小包合并成一个大包，然后替换掉旧包。这个替换过程不是“先删除旧包再写新包”，而是“先写新包，再通过原子重命名一步替换”。为什么？因为可能有其他进程（比如 fsck）正拿着旧包的文件描述符在读数据。如果先删旧包再写新包，就会有一个窗口期旧包读不到、新包还没写完。 “原子重命名”的意思是：操作系统保证 rename 这个操作要么旧名字还在，要么新名字已经就位，不会出现“名字指向一个写了一半的文件”这种中间状态。所以并发进程只要在重命名之前打开了旧包的文件描述符，就能继续读旧包；新进程打开的是新包。两边互不干扰。 但这里藏着一个依赖：进程打开旧包后，即使目录项被删除，文件内容仍然可读。这是 Unix 的语义。Windows 默认却不一样：一个文件被打开时，其他进程默认不能删除它，因为 Windows 的文件锁默认不允许删除共享。Git 在 Windows 上的解决办法是使用 FILE_SHARE_DELETE 之类的共享标志——在打开文件时就明确告诉系统“请允许其他进程在我打开期间删除这个文件”，这样 gc 的重命名在 Windows 上也能工作。 这个跨平台差异直接影响到并发安全边界：在 Unix 上，Git 只需要依赖默认的文件描述符语义；在 Windows 上，必须显式请求删除共享。如果做不到，持有旧包描述符的进程就可能在 gc 重命名时被禁止访问。

原理逻辑

  1. 重命名只是更新目录项，旧文件只要有文件描述符就仍可读。
  2. 原子性确保并发进程不会看到写了一半的文件。
  3. Windows 默认文件锁不一样，必须用 FILE_SHARE_DELETE 显式允许删除共享。

具体例子

想象一个图书馆。管理员要换新版图书，但有个读者正捧着一本旧版书在看。在 Unix 风格的管理规则下，管理员可以直接把书架上的旧书替换成新书，读者手里的旧书还能继续看，看完再还——旧书内容不会消失。但在 Windows 风格的规则下，读者只要还在看，管理员就不能动那本书，否则读者会抗议。Git 的解决办法是：在读者打开书时就签一份“允许管理员随时替换”的协议，这样管理员替换时不违反规则，读者手里的书也还能继续看。这就是 FILE_SHARE_DELETE 做的事情。

常见误区

  • 把原子重命名理解为旧文件被立即物理删除，实际上内容仍被持有描述符的进程读取。
  • 觉得跨平台差异只是性能差别，实际上 Windows 默认文件锁会让 gc 重命名失败。
