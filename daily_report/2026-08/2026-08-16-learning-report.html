内容寻址下的 blob 去重与仓库体积效应

完整讲解

Git 在保存文件内容时，会把内容放进 blob 对象，blob 的名称由内容算出，因此只要内容相同，哈希就相同。当 Git 发现某个哈希已存在时，不会重复保存，而是让所有需要该内容的地方指向同一个对象。这就是内容寻址：对象用内容给自己命名。其直接效果是仓库体积不会因相同内容被复制多次而线性膨胀，体积更接近仓库里到底有多少种不同内容。即使同一文件在一百次提交中不变，也只需共享同一个 blob；一旦内容改动一个字节，哈希变成新值，Git 为新内容生成新 blob，旧 blob 仍被历史快照引用，不会被破坏。

原理逻辑

  1. blob 的名称是内容哈希，内容相同则哈希相同。
  2. 当 Git 发现相同哈希已存在，就不再重复写入，而是复用已有对象。
  3. 对象一旦写入不可修改，因此旧内容对应的 blob 始终保留，供历史快照引用。
  4. 体积因此只与仓库中不同内容的总量有关。

具体例子

项目里有 a.txt 和 backup/a.txt 两个文件，内容都恰好是 hello。git add 之后，暂存区会记录两个路径都指向同一个 blob 哈希，比如 ce013625...，而 .git/objects 中只保存一个对象。如果只把 a.txt 改成 hello!，那么只有 a.txt 产生新 blob，backup/a.txt 依然指向原来的旧 blob。

常见误区

  • 误以为只有文件名相同的文件才共享 blob；实际上只要内容相同，无论路径、权限如何，都会共享。
  • 误以为 Git 体积小是因为保存差异；实际上保存的是完整快照，去重和压缩才是体积小的原因。

内容寻址对象库的循环依赖规避

完整讲解

一个目录在 Git 里对应一个 tree 对象，tree 的每一行记录子目录或文件及其哈希，因此 tree 可以指向另一个 tree。如果目录 A 包含 B，B 又包含 A，那么 A 的哈希依赖 B，B 的哈希又依赖 A，形成自指方程，计算无法开始。在密码学哈希函数的抗原像性假设下，构造一个内容块使自己的哈希参与构成自己，在计算上不可行，所以 Git 对象库中不存在合法成环对象图。加上对象一旦写入不能修改，循环依赖无法事后补上，因此 Git 对象图一定是有向无环图，递归遍历不会无限循环。

原理逻辑

  1. tree 对象的内容包含子项的哈希，因此父 tree 的哈希依赖于子 tree 的哈希。
  2. 若目录成环，则两个对象互为前提，形成自指方程，无法计算哈希。
  3. 密码学哈希的抗原像性使得构造满足自指的内容不可行。
  4. 对象不可写修改后，循环无法在事后弥补，因此对象图必然无环。

具体例子

假设 src 目录要包含 lib 子目录，src 的 tree 对象里有一项是 lib <哈希L>。如果 lib 也要反向包含 src，那么 lib 的 tree 对象里就应有一项是 src <哈希S>。哈希S 来自 src 的 tree 内容，而 src 的 tree 内容又包含哈希L；哈希L 来自 lib 的 tree 内容，lib 的 tree 内容又包含哈希S。两个未知数互相定义，永远无法写出一个可验证的 src 和 lib。因此 Git 仓库中不会出现这种循环目录。

常见误区

  • 误以为 Git 会主动检测循环并拒绝写入；实际上无需检测，内容寻址从数学上阻止了成环。
  • 误以为 Git 对象图是一棵严格树；实际上多个 tree 可共享子 tree，所以是有向无环图。

概念关联

关联概念关系说明
内容寻址下的 blob 去重与仓库体积效应都来自内容即地址；一个说明相同内容收敛，一个说明内容引用不能成环。
合并提交的根树生成与三方合并合并生成的新 tree 也必须遵守无环规则，只能引用已存在对象，不能原地修改旧对象。

合并提交的根树生成与三方合并

完整讲解

merge commit 是有多个父提交的 commit，其根树需要回答两个父提交快照如何变成一个新快照。Git 用三方合并：找一个共同起点 merge base，即两个分支分叉前都见过的提交。对每个文件或路径，取出 base、ours、theirs 三个版本：只有我们改则用我们，只有对方改则用对方，两边都没改保持原样，两边同样改则自动采用相同结果，两边改得不同则冲突。目录也递归执行相同规则。最终得到的完整目录树就是 merge commit 的根树，以新 tree 对象写入对象库，内容哈希由内容决定，相同内容直接复用已有对象。

原理逻辑

  1. 找到两个父提交的 merge base 作为比较基准。
  2. 对每个路径提取 base、ours、theirs 三个版本，按规则决策。
  3. 目录递归进入，逐路径生成新树。
  4. 新树以不可变对象写入，相同内容复用已有对象。

具体例子

假设共同祖先 base 中有 readme.txt 内容为 欢迎，app.js 内容为 v1。你的分支把 readme.txt 改成 欢迎来到我的分支；同事分支把 app.js 改成 v2，并把 readme.txt 改成 欢迎来到同事分支。三方合并时，app.js 只有同事改过，所以自动采用 v2；readme.txt 两边都改且内容不同，于是产生冲突。把 readme.txt 手工合并成 欢迎来到我的分支，也欢迎来到同事分支 后，这棵新的根树包含 readme.txt 的合并文本和 app.js 的 v2。这个新根树就是 merge commit 的根树。

常见误区

  • 误以为 merge commit 的根树是两个父提交树的并集或直接覆盖；真实是逐路径三方合并。
  • 误以为只有发生冲突才需要三方合并；实际上每个路径都按三方规则决策。

概念关联

关联概念关系说明
内容寻址下的 blob 去重与仓库体积效应合并结果中相同内容复用旧 blob，继承去重存储收益。
内容寻址对象库的循环依赖规避合并生成的新 tree 必须写入内容寻址对象库，遵守无环规则。
