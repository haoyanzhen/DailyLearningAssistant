GIT_QUARANTINE_PATH 环境变量与钩子进程的环境契约

完整讲解

当一次推送到达Git服务器，服务端的receive-pack进程不会马上把收到的对象存入主对象库，而是先放进一个临时隔离区（quarantine），就像“待检验区”。在钩子（比如pre-receive和update）运行期间，对象还在隔离区里，还没有成为主对象库的正式成员。钩子是独立启动的脚本进程，它怎么知道隔离区在哪？Git通过环境变量GIT_QUARANTINE_PATH来传递。receive-pack在启动钩子之前，会把隔离区的目录路径放进这个环境变量。钩子脚本读取这个变量，就能定位隔离区。这样设计有什么好处？钩子不必硬编码路径，也不会猜错位置；同时钩子可以把新对象写入隔离区，而读取时仍然能看到主对象库（通过备用对象目录机制）。换句话说，钩子看到的是一套“主对象库 + 本次推送隔离区”的组合视图。这个机制的本质是进程间契约：Git用环境变量告诉钩子“你正在隔离区工作”，钩子遵守这个约定来检查推送内容，而不会污染主对象库。如果推送被拒绝，隔离区会被整体丢弃，主对象库毫发无伤。

原理逻辑

  1. 对象先进入隔离区，钩子运行期间对象尚未成为主对象库正式成员。
  2. receive-pack通过环境变量传递隔离区路径，形成进程间的显式契约。
  3. 钩子拥有组合视图：既能读主对象库，也能写隔离区，检查失败时可以整体丢弃。

具体例子

pre-receive钩子通过GIT_QUARANTINE_PATH定位隔离区，并在其中搜索密钥文件。

常见误区

  • 误以为钩子运行时推送对象已经全部进入主对象库，实际上对象还在隔离区。
  • 误以为钩子需要自己去.git/objects下挖掘临时目录，实际上Git已通过环境变量明确告知。
  • 误以为GIT_QUARANTINE_PATH是客户端环境变量，实际上它由服务端注入钩子进程。

post-receive 带外失败与推送结果解耦

完整讲解

一次推送在服务端的处理顺序是：先运行pre-receive整批检查，然后对每个ref运行update钩子检查，接着更新ref，再运行post-receive。关键在时序：客户端通过协议收到的ref更新结果是基于“ref是否更新成功”，这个状态报告在post-receive运行之前就已经发送了。也就是说，post-receive运行时，推送结果已经“木已成舟”。post-receive的stdin会列出实际更新成功的ref的旧值、新值、ref名，但它不能改变这些ref。它的退出码如果非零，只会让receive-pack知道“事后通知失败了”，但不会让已经成功的推送变成失败，更不会让ref回滚。这就是“带外”失败：失败发生在主流程之外，主流程已经结束。那么post-receive失败之后怎么办？必须依靠外部补偿通道：比如把输出写入日志文件、发送webhook、由外部定时巡检系统比较状态，或调用审计API记录。所以设计钩子时，应该把post-receive当作不可靠的通知机制，而不是关键决策点。它的职责是“通知/记录”，职责的成败不能改变业务事实。

原理逻辑

  1. ref更新成功与否的状态报告在post-receive运行前已发给客户端。
  2. post-receive的stdin列出实际更新成功的ref，但只能读取不能修改。
  3. post-receive失败属于带外信号，需要通过外部补偿通道处理。

具体例子

post-receive调用webhook失败，客户端已显示推送成功，仓库分支已创建，但CI没收到通知。

常见误区

  • 误以为post-receive的退出码会影响客户端看到的推送结果。
  • 误以为post-receive失败后可以重跑钩子来回滚ref，实际上post-receive没有回滚能力。
  • 混淆pre-receive和post-receive的失败语义：前者失败会终止推送，后者失败只是通知失败。

概念关联

关联概念关系说明
GIT_QUARANTINE_PATH 环境变量与钩子进程的环境契约pre-receive/update在隔离区阶段可以拒绝推送，post-receive在对象入库后运行无法影响结果，两者覆盖钩子的能力边界。
missing object 的并发竞态判定与仓库损坏诊断路径post-receive失败后的补偿审计可能通过fsck检查对象，若对象已被gc清理或尚未迁移完成，会遇到对象缺失，需要区分竞态与损坏。

missing object 的并发竞态判定与仓库损坏诊断路径

完整讲解

git fsck是Git的完整性检查工具，它从refs出发遍历对象图，发现某个对象找不到时，会报告missing object。很多人一看missing object就认为仓库坏了。但实际上，对象“暂时找不到”可能来自并发操作。比如：1. git gc正在执行prune，清理不可达对象；如果某个对象被判断为不可达并删除，而另一个进程还试图读取它，就会瞬时缺失。2. push过程还在quarantine阶段，对象还没迁移到主对象库；此时如果外部检查引用指向那个对象，也会找不到。3. 对象其实在alternates（备用对象目录）引用的外部仓库中，但alternates配置暂时不可读或路径不完整。4. 甚至可能是文件系统缓存、网络文件系统延迟等。因此诊断路径应该是：第一，记录现场，包括报错的对象哈希、涉及的ref、时间点。第二，检查是否有并发的gc、prune、push进程在运行，比如查看.git/gc.pid锁文件或进程列表。第三，检查对象确实不存在：查看.git/objects/xx/xxx文件、packfile及其.idx索引。第四，检查alternates文件指向的路径。第五，重新运行git fsck多次，看是否稳定复现。如果第二次就好了，说明是瞬时竞态；如果每次都在同样位置失败，才判定为持久损坏。这个诊断路径背后的理念是：在无全局锁的分布式系统中，异常可能是并发导致的假象，区分“瞬态”和“持久态”是可靠运维的第一步。

原理逻辑

  1. Git对象库处于动态变化中：gc在删、push在加、quarantine在迁移，fsck的报错可能是瞬时状态。
  2. 诊断必须从非破坏性检查开始：记录现场、检查并发、确认对象文件是否存在。
  3. 通过多次fsck复现测试，区分瞬时竞态与持久损坏。

具体例子

管理员看到missing blob后先查看进程列表，发现git gc正在运行，等待结束后再次fsck无报错，判定为瞬时竞态。

常见误区

  • 看到missing object就认定仓库损坏，立即删除对象目录或重新clone，可能造成更大破坏。
  • 忽视并发进程的存在，在没有检查gc/push的情况下就判断为损坏。
  • 把fsck的输出当作静态事实，不理解对象库处于动态变化中。
