Git 对象库的原子写入与引用更新

完整讲解

想象你要往图书馆里放一本新书。如果先撕掉旧索引卡片，再把新书上架，中间这段时间有人来查旧书就会扑空；如果先放书再更新索引，读者又暂时找不到它。Git 不希望出现这种中间状态，所以它遵循一个原则：先放好完整对象，再改指针。 在 Git 里，对象是内容寻址的，对象名就是内容哈希。对象要进入对象库时，Git 不会直接写到最终路径，而是先写到一个临时文件，同时算好哈希、确认内容完整，再把它重命名（rename）到最终位置。这个重命名在同一个文件系统上是原子的——要么不存在，要么完整存在，不会出现半个对象。 引用（ref）是指向提交的箭头，比如 `refs/heads/main` 保存着一个 SHA。更新引用也不是直接改文件，而是先写一个 lockfile，把新值写进去，然后原子替换旧引用文件。这样外部观察者在任何时刻看到的都是“旧引用 + 旧对象”或“新引用 + 新对象”，绝不会出现引用指向不存在或半写对象的状态。 为什么这么重要？因为 Git 承诺对象一旦写入就不可变。原子写入保证了这条承诺不会被破坏。即使电脑在写入中途断电，重启后要么对象完整存在，要么临时文件被清理，对象库依然是一致的。

原理逻辑

  1. 对象写入采用“临时文件→校验→重命名”的原子顺序，避免中间状态。
  2. 引用更新采用“lockfile→原子替换”方式，保证引用要么是旧值要么是新值。
  3. 对象不可变保证了原子写入的承诺不破坏，即使崩溃也能恢复一致。

具体例子

假设你要在 Git 仓库里提交一个新版本。Git 先把新版本的全部文件内容分别写成 blob 对象，再把目录信息写成 tree 对象，最后写一个 commit 对象。每个对象都是先写临时文件、校验哈希、再放入对象库。等 commit 对象就绪后，Git 才通过 lockfile 把 `refs/heads/main` 从旧 SHA 改成新 SHA。这个过程里，如果任何一步失败，ref 依然指向旧提交，仓库不会进入“引用指向不存在对象”的状态。

常见误区

  • 常见误区是“更新引用才是关键，对象随便写写就好了”。实际上引用只负责指路，如果对象没写完整，引用指向的就是一个悬空地址。
  • 另一个误区是认为 Git 会直接原地修改对象文件——不会，对象一旦写入就不可变，新版本产生的是新的对象，旧对象仍留在仓库里。

概念关联

关联概念关系说明
Git 对象图与提交快照的递归构成原子写入保证对象先完整入库，对象图才能可靠地由 tree 和 commit 递归构成完整快照。
状态采样的时间盲区引用更新是原子的，只能从旧状态切到新状态，但采样监控不一定能观察到中间瞬态。

Git 对象图与提交快照的递归构成

完整讲解

一个 Git 提交并不是一张简单的“文件清单”，而是一个指向“目录树”的指针。这棵树把整个项目的文件结构用一种分层的方式保存下来。你平时看到的文件夹嵌套，在 Git 里就是一棵递归的树：根树下面有子树，子树下面还有子树，一直到叶子节点——叶子节点就是文件内容（blob）。 具体来说，Git 有四种对象：blob 保存文件内容，tree 保存目录条目，commit 保存一次提交的元信息并指向一棵根 tree，tag 偶尔会用到。一个 commit 对象里有一个字段叫 “tree”，它保存的是根 tree 的 SHA。根 tree 里列出的是项目顶层目录和文件，每个条目都存着对应的子 tree 或 blob 的哈希。子 tree 再递归地往下展开，就形成了整棵文件树。 因此，当任意一个文件内容改变时，对应 blob 的哈希会变，包含它的 tree 的哈希也会变，往上一直到根 tree 都会变，最终 commit 的哈希也跟着变。这让提交快照具有“整体性”：一个 SHA 就代表了整个项目在那一刻的完整状态。你不需要存储所有文件的副本，因为相同的文件内容会共享同一个 blob，这是一种天然的去重。 为什么这叫递归构成？因为你只要给出根 tree 的 SHA，就能顺着哈希一层层找到所有文件和子目录。就像根据一本书的目录，你不需要背出全部内容，目录上的每一个页码都能带你找到对应章节，而章节下面还有小节。Git 的“目录”就是 tree，“页码”就是指向子对象的 SHA。

原理逻辑

  1. Git 有 blob/tree/commit/tag 四种对象，commit 指向根 tree。
  2. tree 保存目录条目，递归指向子 tree 与 blob，构成分层文件树。
  3. 内容变化导致哈希级联，使一个 SHA 成为整个快照的指纹。

具体例子

假设项目里有个文件 `src/game.ts`。第一次提交时，Git 把文件内容存成 blob A，`src` 目录存成 tree B，根目录存成 tree C，commit 指向 C。后来你在文件末尾加了一行，文件内容变长，Git 生成 blob D，因为 `src` 目录内容变了，所以 tree E 生成，根 tree F 生成，最后 commit 指向 F。旧的 blob A、tree B、tree C 和旧 commit 仍然存在，只是 `main` 分支现在指向新 commit。两个提交共享了没变的其他文件对象，整棵树是层层叠起来的。

常见误区

  • 常见误区是认为 commit 里保存了“文件的快照副本”。实际上 commit 只保存一棵根 tree 的哈希，所有内容都存储在 tree/blob 对象里，而且相同内容只存一份。
  • 另一个误区是认为 tree 只存文件名，实际上它还存文件模式（可执行权限等）和指向子对象的哈希。

概念关联

关联概念关系说明
Git 对象库的原子写入原子写入保证对象一个个安全入库，对象图描述这些对象如何连接成完整快照。
状态采样的时间盲区对象图能解释某个 SHA 对应的完整内容，但 SHA 相同不能证明两次采样之间没有发生过瞬态变化。

状态采样的时间盲区与瞬态不可观测性

完整讲解

你有一个远程 Git 仓库，你每隔一小时用 `git ls-remote` 看一眼某个分支的 SHA。假设 10:00 看到的是 A，11:00 看到的还是 A。你能说这中间仓库完全没变吗？不能。可能有人在 10:30 把分支从 A 推到 B，又在 10:50 强制推回 A。你的两次采样之间发生了瞬态变化，但采样结果显示“没变”。这就叫时间盲区。 凡是基于采样的监控，都有这个问题。采样只在特定时刻拍一张照片，两张照片之间发生了什么，只能靠推理，不能直接看到。Git 引用（ref）的更新是原子的，不代表事件可以被采样到。SHA 相同只能证明两个采样时刻的状态相同，不能证明两个时刻之间的事件历史为空。就像你每天中午给天空拍照，如果上午多云下午转晴，你只能看到正午的样子，看不到云是怎么走的。 这种盲区不是 Git 的缺陷，而是观测方式的固有边界。要缩小盲区，就要提高采样频率，或者使用事件驱动机制（比如 hook 推送通知），但即使频率再高，也无法保证捕捉到瞬间发生又立即恢复的变化。因此，当我们需要用 Git 状态作为审计证据时，必须承认证据的粒度限制：它只能证明起点和终点的状态，不能完整叙述中间的剧情。 为什么这个概念重要？因为很多自动化系统用轮询检测“变化”，用来判断是否需要构建、部署或告警。如果两次轮询之间发生了一次“闪回”，系统可能漏报。理解了这个盲区，你就知道什么时候该信任 SHA 对比结果，什么时候需要更细的事件日志（比如 reflog）。

原理逻辑

  1. 采样只获得离散时刻的状态快照。
  2. 状态指纹相同不代表事件历史为空。
  3. 盲区是观测方式固有边界，可通过提高频率或事件流缩小但不能根除。

具体例子

想象一个保安每隔 10 分钟看一眼大门的门锁。有一次门锁被人撬开又马上锁上，保安回来时锁还是好的，于是他记录“一切正常”。但实际上刚才有人进来过。保安的记录没有错，只是采样频率太低，错过了瞬态事件。Git 的 ls-remote 监控就是这位保安，只是它检查的是分支指针有没有动。

常见误区

  • 常见误区是“SHA 没变就等于没发生过任何变化”。实际上 SHA 是状态指纹，不是事件日志。
  • 另一个误区是“提高采样频率到极致就能消灭盲区”。理论上只要不是连续实时监控，就总有盲区；即使连续监控，也可能因为传输延迟或快照瞬间而漏掉某些瞬态。真正的解决思路是同时记录事件流，而不是只依赖状态采样。

概念关联

关联概念关系说明
Git 对象库的原子写入引用更新是原子的，ref 只能从旧有效状态切换到新有效状态，但采样监控不一定能采集到中间瞬态。
Git 对象图与提交快照的递归构成对象图能解释某个 SHA 对应的完整内容，但 SHA 相同不能证明两次采样之间没有发生过瞬态变化。
