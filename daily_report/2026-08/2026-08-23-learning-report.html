reflog 生命周期时间线

完整讲解

reflog 可以理解成每个 ref 的“日记本”。每次分支或标签的指针发生变化——新建、切换、提交、重置、删除——Git 都会在对应的日记本里追加一行，记下旧指针、新指针、操作人、时间和操作原因。因为它是“追加式”的，条目按时间顺序排列，所以你可以像回放录像一样逐条查看某个 ref 的全部移动历史。想找分支的出生时间，就找“旧值是全零 SHA”的那条记录；想找删除时间，就找“新值是全零 SHA”的那条记录。需要特别注意的是，reflog 只存在于本地仓库，服务端远端 ref 没有 reflog，所以远端审计要靠钩子日志或外部系统。

原理逻辑

  1. 追加式日志：每次 ref 变化追加一行，按时间排序。
  2. 全零 SHA 作为边界符号：创建时旧值为零，删除时新值为零。
  3. 本地性：reflog 仅存在于本地，服务端没有。

具体例子

运行 git reflog show main 查看 main 分支的日志。如果找到一条记录的旧值是 0000000000000000000000000000000000000000，那么这条记录对应的就是分支创建事件，它的时间戳就是创建时间。如果某条记录的新值是全零 SHA，那么它对应的就是分支删除事件，时间戳就是删除时间。reflog 中全零 SHA 出现的含义，正是昨天强调过的“不存在”的占位符号。

常见误区

  • 常见误区是认为 reflog 是永久保存的。实际上 reflog 有保留时间，超过 core.reflogExpire 配置的旧条目会被清理，所以它是一条有寿命的审计路径，不是永久档案。
  • 另一个误区是以为远端仓库也有 reflog，其实远端 ref 没有 reflog，服务端审计只能靠钩子日志或外部观测系统。

概念关联

关联概念关系说明
对象可达性与悬空对象的清理时机reflog 是 GC 的可达根之一，未过期的 reflog 条目能让旧对象继续存活，因此与对象清理时机直接相关。
pre-receive / update / post-receive 的推送决策顺序reflog 记录的是 ref 更新成功后的结果，而 receive-pack 的隔离区是 ref 更新成功前对象的暂存状态，两者分别是事后记录与事前验证。

git fetch 对 tag 的自动跟随策略与强制同步语义

完整讲解

tag 在 Git 里通常被视为“固定发布锚点”，一旦打上标签，就代表一个不可变的版本。普通 git fetch origin 只会拉取你关心的分支对应的提交，如果这些提交恰好也有 tag 指向它们，那么这些 tag 会被“自动跟随”下载。但是，如果本地已经存在同名的 tag，Git 默认不会覆盖它，而是保留本地版本。这样设计是为了防止远端 tag 被强制移动后，下游仓库被静默篡改。要强制同步被移动的远端 tag，必须显式告诉 Git“允许覆盖”，比如使用 git fetch --tags --force，或者使用带加号的 refspec：git fetch origin "+refs/tags/*:refs/tags/*"。加号的意思是：即使这会覆盖本地已有 tag，也照做。服务端还可以设置 receive.denyTagPush 和 receive.denyDeleteTag，从源头拒绝 tag 的强制更新或删除。

原理逻辑

  1. tag 作为固定发布锚点，本地已有同名 tag 默认受保护。
  2. --tags 只改变自动跟随范围，不改变覆盖保护。
  3. 带加号 refspec 表示强制覆盖。

具体例子

假设远端有人把轻量 tag v1.0 从提交 A 强制移到提交 B。你在本地运行 git fetch origin，通常不会更新你已经存在的 v1.0 标签。如果你执行 git fetch origin --tags --force，那么本地 v1.0 会被强制指向提交 B。如果你只想覆盖这一个 tag，可以运行 git fetch origin "+refs/tags/v1.0:refs/tags/v1.0"，加号表示这次更新允许强制覆盖。

常见误区

  • 常见误区是认为 git fetch --tags 会强制覆盖本地已有 tag。实际上 --tags 只是把自动跟随的规则改成“拉取所有远端 tag”，但依然遵守“不覆盖已有本地 tag”的保护。要强制覆盖，需要加上 --force，或者使用带加号的 refspec。
  • 另一个误区是认为远端 tag 移动后，所有下游仓库会自动看到新 tag；实际上下游不会自动更新，必须显式执行强制同步。

概念关联

关联概念关系说明
reflog 生命周期时间线fetch 的 tag 跟随决定远端新 tag 是否进入本地，而本地 tag 被更新这件事本身又会在 reflog 中留下记录，因此两者共同构成 tag 更新的可见性。
对象可达性与悬空对象的清理时机tag 被强制移动后，原来指向的旧提交可能失去引用成为悬空对象，它是否会被清理取决于对象可达性与 GC 保留窗口。

对象可达性与悬空对象的清理时机

完整讲解

Git 的对象库就像一个巨大的仓库，里面保存着所有提交、目录和文件。ref（分支、标签）就像指向某个对象的名牌。当你移动或删除一个标签，原来被它指着的对象并没有立刻“死掉”，它只是暂时没人点名了，被称为“悬空对象”。Git 不会立即把它扔出去，而是定期做一次大扫除（git gc）。大扫除时会从一组“根”出发，沿着对象之间的引用关系，把所有能走到的对象都标记为“有用”，走不到的就是垃圾。但是为了安全，垃圾也不是马上烧掉，而是再放一段时间，默认两周，由 gc.pruneExpire 控制。另外，reflog 也是“根”之一，只要一个对象出现在还没过期的 reflog 条目里，它就算“可达”，不会被清理。所以一个被强移 tag 抛弃的旧提交，实际存活时间往往比想象中长得多。

原理逻辑

  1. ref 和未过期的 reflog 是可达根。
  2. gc 做可达性扫描，不可达对象进入保留期。
  3. gc.pruneExpire 控制保留窗口，默认两周。

具体例子

一个轻量 tag v1.0 原来指向提交 abc123，有人强制移动它指向 def456。运行 git fsck --lost-found 时，你可能会看到 dangling commit abc123。这说明提交 abc123 还在对象库里，只是没有 ref 指向它。如果两周内没有任何操作让它重新可达，它才会被自动 gc 或手动 git gc --prune=now 清除。在这之前，你甚至可以用 git show abc123 直接访问这个“没人要”的提交。

常见误区

  • 常见误区是认为“删除 ref 或强移 tag 后，旧提交立即从 Git 仓库中消失”。实际上它还会作为悬空对象存在，甚至可以通过 git fsck --lost-found 被找回。
  • 另一个误区是认为 git gc 会立刻删除所有不可达对象；实际上还有保留窗口和 reflog 因素，所以清理不是即时的。

概念关联

关联概念关系说明
reflog 生命周期时间线reflog 是 GC 的可达根之一，因此未过期的 reflog 条目能让旧对象继续存活，这直接延长了 tag 强移后旧提交的生命周期。
git fetch 对 tag 的自动跟随策略与强制同步语义fetch 的 tag 跟随策略决定远端的移动是否进入本地；一旦本地 tag 被强制更新，原指向的提交就可能变成悬空对象并进入 GC 的清理周期。

三个概念围绕 “ref 变化之后的完整生命周期” 展开。reflog 是本地仓库的审计日志，保证即使标签被移动也能追溯之前的状态；fetch 的 tag 跟随策略是远端变化是否进入本地的闸门，默认不覆盖以保护发布锚点；对象可达性与清理时机决定失去引用的旧对象还能存活多久。reflog 作为 GC 根之一影响清理时间，fetch 是否更新本地 tag 决定旧提交是否失去最后一个引用，GC 的可达性扫描把三者连成一个整体。
